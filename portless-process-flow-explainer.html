How a process is created, wired, and watched

Current internals
1. User creates config

The Add Process dialog builds a JSON body with name, command, cwd, env entries, auto-start, restart policy, dependencies, and optional port config.

dependsOn is a comma-separated list of process names. port.name is the symbolic name other processes can reference.

2. Server persists config

The server validates the config, creates a process ID, stores it in memory, writes .opencode/processes.jsonc, and publishes process.config.changed.

The UI then creates or reconciles idle process rows for each config.

3. Start resolves dependencies

When starting a process, the runtime first resolves explicit dependsOn names.

It also scans env values for templates like {{port:api}}. If another config owns port.name = "api", that process becomes an implicit dependency.

4. Dependency ports flow through env

Dependencies start first. Once they have assigned ports, the runtime builds a port map: { api: 4172, web: 5173 }.

Then child env values are rewritten. Example: API_URL=http://127.0.0.1:{{port:api}} becomes API_URL=http://127.0.0.1:4172.

5. Own process gets its port

If the process itself has a port config, the runtime assigns a port and injects it either as an env var or as a command flag.

If port.inject = "PORT", env gets PORT=5173. If port.inject = "--port", the command becomes vite --port 5173.

6. PTY becomes the log stream

The runtime creates a managed PTY with the config name as title, then writes the command into that shell.

The process pane renders a Terminal component for the returned ptyId. That is why users see live logs directly in the process panel and can also open the same PTY in a terminal tab.

7. Status and crash handling

The server publishes process.started, process.status, process.stopped, and process.crashed events.

The command gets an exit marker appended, so when the inner command exits inside the shell, Claxedo can mark the process crashed even if the PTY shell itself is still around.

Portless change

Portless should replace step 4 and step 5's numeric-port UX with named service URLs.

The user and agent should receive API_URL=https://api.myapp.localhost locally or a Claxedo cloud preview URL remotely, while Claxedo still owns process config, PTY logs, lifecycle, and diagnostics.

What Portless does

Route layer
  • Runs commands behind stable named URLs like https://api.myapp.localhost.
  • Starts and manages a local proxy, HTTPS certificates, trust setup, hosts sync, and route cleanup.
  • Assigns an app port, injects PORT, HOST, and PORTLESS_URL.
  • Handles framework quirks for Vite, Astro, React Router, Angular, Expo, React Native, and similar tools.
  • Supports worktree prefixes, aliases, LAN mode, route listing, and orphan pruning.
Portless is not just a free-port helper. It is a local service addressing system: names, route table, proxy, certs, and child command env.

Keep vs replace
Area Current owner Portless fit Recommendation
Process config Claxedo Portless has package config, not Claxedo pane config. Keep Claxedo as source of truth.
Process lifecycle Claxedo PTY manager CLI can spawn a child, but it is not our app supervisor API. Keep Claxedo start/stop/restart.
Port assignment Custom portpick Strong match. Replace with Portless-style allocation and route registration.
Preview URL Usually port number Strong match for local, needs adaptation for cloud. Expose URLs as first-class output.
Cloud preview Claxedo runtime proxy .localhost is wrong from the user's browser. Use Portless semantics, Claxedo cloud routing.

What gets better with Portless

DX outcome

Ports disappear from user workflow

Users click or copy a stable service URL. Ports remain internal implementation detail.

Local and cloud use one language

Local: api.myapp.localhost. Cloud: api--workspace.preview.claxedo.ai. Same name, different transport.

Worktrees stop colliding

Branch-derived names can isolate parallel checkouts without users hand-editing ports.

Agents get reliable URLs

Agents can read PORTLESS_URL and verify the app without guessing whether Vite chose 5173 or 5174.

Framework port quirks become commodity

We stop maintaining special cases for dev servers that ignore PORT.

Full replacement is too expensive

Replacing PTY supervision with portless run would blur status, tab ownership, restart policy, and diagnostics.

Cloud previews become product-grade

Cloud workspaces can expose authenticated named preview URLs through Claxedo, not random sandbox service URLs.

Current process pane remains valuable

The pane stays the cockpit: lifecycle, logs, diagnostics, and recovery. Portless becomes the address system.

Local, current

The existing process manager owns lifecycle and custom port assignment.
