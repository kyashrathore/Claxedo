# A Pi session on its Durable Object: every latency between a press and the screen

Measured on 2026-10-18 against `8b2d1e949b`, for a person in India using the signed-in web app on staging (`app.claxedo.dev`, relay room in `apac` until the ruling below moved a session host's room to `enam` on 2026-10-20, session object and control plane in `enam`/IAD). The question was the owner's: a Pi session on its Durable Object should be indistinguishable from a local one. This folder holds the rig, the runs and the answer.

**Answer.** Once the stream is going, the cloud session *is* indistinguishable from the local one: a delta reaches the person every 100-107 ms in both (pi-durable commits partial messages at most every 100 ms), with 4-7 ms of jitter on the cloud path and 10-12 ms locally. What differs is the start of a turn. From the press to the first delta the cloud path cost 1.28-1.35 s against the local path's 0.98 s with the same vendor (600 ms to first token), and the gap was made of three things: 320 ms of ocean the person cannot avoid (India to the object and back), 180 ms of three serial control-plane calls the object made before it called the vendor (420 ms per call at staging's control-plane speed, so 1.2 s), and a relay whose caches expire every 10 s and then cost one or two more control-plane round trips before the prompt is even forwarded. The vendor itself is 220 ms *closer* to the object than to the laptop. The relay cliff is halved and the three calls are one on the same day (run 5 below): a warm turn's first delta is now 1.14 s at the rig's links, 100 ms over the physical floor, and 1.49-1.52 s at staging's control-plane speed where it was 2.31 s.

## The live path, as the code runs it

A. The person presses send in the web app's composer.
- A.1 `sendPrompt` (`packages/claxedo-app/src/session/transcript/send.ts`) calls `showSent`, which upserts the optimistic user message (`promptEcho`) and marks the row as sending, synchronously, before any request leaves. **Press to optimistic echo: 0 ms** (one Solid batch).
- A.2 `server.sessions.prompt` → `deliverPrompt` (`src/server/sessions.ts`) → `transport.runtimeJson(route, "/session/<id>/prompt_async", POST promptBody)`. For a session hosted by its object the route carries `sessionHost`, so `runtimeRoutes` (`src/server/transport.ts`) calls `relay.fetch(workspaceId, path, init, sessionId)` (`src/server/relay.ts`): `POST ${relayUrl}/workspaces/<ws>/session/<id>/prompt_async` (no `?region=`: only a cloud machine's link declares one, `linkOf` in `src/server/wire/connection.ts`) with `Authorization: Bearer <Runtime Access Token>` and a JSON body. The RAT came from the control plane's connection read (lane E's path). The browser's first POST to this URL pays a CORS preflight (Authorization + content-type), answered by the relay gateway at the edge and cached 86,400 s per URL (`corsPreflight`, `packages/workspace-relay/src/cloudflare.ts`).

B. Cloudflare edge, relay gateway Worker (`packages/workspace-relay/src/worker.ts`, `createWorkspaceRelayDurableObjectGateway`): decides the room's `locationHint` (`workspaceRelayRoomPlacement`, `gateway-placement.ts` → `relayRoomPlacement`, `relay-location.ts`): it verifies the request's Runtime Access Token against the control plane's key and reads the host the token names; a `session-do:` host places the room beside the session's object, `enam` (`SESSION_HOST_LOCATION_HINT`); any other verified credential places it at the region the request declares, else the edge country, else the `apac` floor (staging's `CLAXEDO_RELAY_LOCATION_HINT = "apac"`); an unverified request gets the floor. Then `namespace.get(idFromName(room), { locationHint }).fetch(...)`. The hint only matters at the room's first creation; the object never moves ([Cloudflare: data location](https://developers.cloudflare.com/durable-objects/reference/data-location/): "Durable Objects do not currently change locations after they are created"; hints are "a best effort and not a guarantee").

C. Relay room Durable Object (`createWorkspaceRelayDurableObjectRoom`, `cloudflare.ts`), in `enam` for a session host's workspace since 2026-10-20 (`apac` when the runs below were made; a room placed before then stays where it was). `forwardCloudHttp` → `authorizeWorkspaceRelayRequest` (`server.ts`):
- C.1 `rat-verify`: the RAT's signature (cached per token).
- C.2 `rat-active`: the revocation lookup, `GET <control plane>/internal/relay/revocation`, cached 10 s per `jti` (`createCachedRevocationClient`, `resolver-clients.ts`). A room in `apac` asking a Worker pinned to IAD: ~220 ms of link plus the plane's own time.
- C.3 `target-resolve`: `GET /internal/relay/target`, cached 10 s per workspace/host/routing id (`createCachedTargetClient`). For this session the answer is `backing: "durable-object"`, `baseUrl: ""`.
- Before this branch C.2 and C.3 were awaited one after the other; now the target lookup leaves with the revocation check, and a `durable-object` target, whose host id names the object, is kept for 30 minutes (the RAT's longest life) instead of 10 s. Only the revocation check is left to expire on the 10 s cadence.
- C.4 `relayHostTokenFor` mints the 60 s Relay Host Token (cached).
- C.5 `forwardSessionHostHttp` (`session-host-forwarding.ts`): `SESSION_HOST.getByName(root, { locationHint: "enam" }).fetch(...)` with the RHT, cookies stripped, the response body passed through untouched. The room sits on the path of every byte of the stream: object (enam) → room (apac) → gateway (edge) → browser. For a person in India the room is on the way, so this adds processing, not an ocean.

D. `SessionDO.fetch` (`packages/session-host/src/session-do.ts`), in `enam`: `lifecycle.start()` (the Agents SDK `Lifecycle`, `blockConcurrencyWhile` on first use) → `serve` → `composeSessionHost(...).app.fetch` (`composition.ts`): `createRelayHostAuthMiddleware` verifies the RHT, then the shared session routes (`@claxedo/session-core`, `composeSessionRoutes`).
- D.1 `POST /session/:id/prompt_async` (`session-core/src/routes/session-core.ts`) parses the body and hands it to `createPromptAdmission` (`session-prompt-admission.ts`), whose `admitPromptTurn` is the caller's authorization and the turn's admission in one decision: `acquireSessionTurnLease` → `remoteWorkspaceSessionAccessPolicy.acquireTurn` → **the one control-plane call of the turn**, `POST /api/runtime-authority/session-authorize {action: "turn_acquire", writeClass: "agent_turn", turnId}` over the `CONTROL_PLANE` service binding (enam → IAD). The plane (`claxedo-server/src/session/runtime-turn-admission.ts`, `acquireTurn`) reads the proof's chain, the session's host placement and the workspace's owner together, takes the lease (the D1 turn authority's `acquireSessionTurn` admits only an actor who may send an agent turn on the session, in the statement that writes the lease: the one owner of that check) and, beside it, reads the turn's delivery (`session-host-delivery.ts`, `readTurnDelivery`: the creator's provider accounts as direct secrets, the workspace's plugins), and answers the lease with the delivery. `TurnLeases.observe` stores the lease in the object's SQLite and `SessionHostTurns.hold` keeps the delivery for it. Only then is the session read: the 404 for a session the object does not hold, the body transform, the permission ceiling.
- D.2 `runRuntimePromptTurn` → `runtime.turns.start` (`session-core/src/host/runtime.ts`, `startTurn`): `attachments.admit` (the attached Pi session), `transport.capabilities`, `store.startTurn` (the user message and the assistant stub, SQLite), publishes `message.updated`, launches `runTurn` detached and returns. `settleAdmission()` fires and the route answers **204**. Nothing after this is waited on by the answer.
- D.3 `runTurn` (`host/turn-runner.ts`) → `PiDurableTransport.send` (`packages/harness/src/transports/pi-durable/index.ts`): `placement.prepareTurn` → `DurablePiPlacement.prepareTurn` → `SessionHostTurns.delivery`, answered from the held delivery with no network. Then `entry.configure(credentials)`, `conversation.configure({model, thinkingLevel})` (one pi-durable commit), a `config-update` event (a local preview), and `PiHarness.submit` (`agents/harness/pi`): `_wake` (a `cf_agents_jobs` upsert + `setAlarm`), `conversation.submit` (a commit), `_wake` again. `/turn-delivery` is still asked for a lease the object took over after a restart (`SessionDO.adopt`) and for one whose accounts the vendor refused (`refresh`).
- Before 2026-10-18 this was three serial calls: a `write`/`agent_turn` authorize ahead of the route, `turn_acquire` (which named no class), and `/turn-delivery` after the 204, 22 serial D1 rounds between them (3 + 8 + 11); the one call pays 5 rounds as `countD1Rounds` counts them and 14 statements, the holder's secret read sealed beside the lease and opened only once it is written (`runtime-session-authority.turn-start.test.ts`).
- D.4 pi-durable's generation task builds the environment (`DurablePiPlacement.env` → `host.machine()`, answered from the held delivery, no network while no tool runs) and the prompt sections; `available_skills` reads nothing when the delivery carries no plugin roots. Then `models.streamSimple` → pi-ai's OpenAI/Anthropic SDK → **the vendor**, from `enam`, over the owner's direct key. No Boat, no broker.

E. Deltas. The vendor streams tokens. `streamResponse` (`@earendil-works/pi-durable/dist/harness/generation.js`) holds the partial and commits it as a trailing write at most every `PARTIAL_THROTTLE_MS = 100` ms, one commit in flight; the first token also waits the 100 ms. Each commit's publication reaches `watchEvents` (`harness/events.js`) → `PiSessionStream.batch` (`pi-durable/stream.ts`) → `piDurableEvents` translation (`translate/adapter.ts`, `messages.ts`: `message_update.text_delta` → `text-delta`) → `PiRun.queue` → `runTurn`'s `for await` → `router.project` → `deltaText` (`session-core/src/projection/client-presentation/text-parts.ts`) → one `message.part.delta` presentation event carrying only the delta → `createRuntimeEventHub` → the `/api/wr/events` SSE writer (`session-core/src/routes/events.ts`, `streamWorkspaceEventFrames` → `attachSseFanout` → `stream.writeSSE`, one HTTP chunk per frame, no coalescing, no compression) → the room's passthrough (C.5) → the gateway → the browser.
- E.1 The browser's stream: `placement-streams.ts` opens `GET /api/wr/events?sessionID=<id>` through `relay.fetch` (one stream per attached session; HTTP SSE, since the relay refuses WebSocket upgrades to a session host, `durable_object_websocket_unsupported`). `openEventStream` (`src/server/stream.ts`) parses frames per chunk inside a Solid `batch`; `event-intake.ts` → `serverEventFromFrame` → `partDelta` → `DeltaBuffer.add` (`session/transcript/deltas.ts`) concatenates deltas per part; `commitDeltasWhileShown` (`session/view/delta-frames.ts`) applies them on the next `requestAnimationFrame`. So the screen is already updated once per frame, never per token, and at most ~16 ms behind the socket.
- E.2 The object authorizes the stream once at open (`sessionEventDeliveryPolicy` → `authorizeStream`, a control-plane call) and renews every 5 s (`renewalIntervalMs ?? 5_000`, `event-delivery.ts`): one control-plane call per open stream per 5 s, off the delta path.

F. End of turn. pi-durable commits the terminal message and the submission's `done`; `PiRun.submission` settles `finish`; `runTurn` finalizes; `session.idle` goes out on the same stream 10 ms after the last delta leaves the object. Then, off the path the person sees: `turn_release`, the usage report and the session row publication (three more control-plane calls), and after the first completed turn a title request to the vendor.

Regions on the path: browser (IN) ⇄ edge (BOM/SIN) ⇄ room (apac) ⇄ object (enam) ⇄ control plane (IAD, D1 in ENAM) and object (enam) ⇄ vendor (US).

## The rig

`packages/session-host/e2e/latency/` boots one workerd (Miniflare) with the real relay Worker and room, a "pipe" Durable Object standing where the relay's `SESSION_HOST` binding points, a Node service behind it that holds every request `roomDoMs` and every response chunk `roomDoMs` on the way back (and stamps each chunk as it leaves the object), the real session-host Worker with the control plane stand-in from its tests behind `doCpMs + cpMs`, and the relay's resolver behind `2·roomDoMs + cpMs`. The client in Node sleeps `clientEdgeMs` before each request and delays every response chunk by `clientEdgeMs`. The vendor is the harness e2e scripted model server behind a proxy (`packages/harness/e2e/perf/vendor-proxy.ts`) that adds `vendorMs` each way and stamps each chunk the vendor emits. Links default to staging as seen from India: `clientEdgeMs 50, roomDoMs 110, doCpMs 5, cpMs 50, vendorMs 10, doRelayMs 10`; the vendor answers its first token after 600 ms and then 40 chunks every 25 ms. `doRelayMs` is the object's link to the relay Worker's `/.well-known/jwks.json`, which the open scenarios make the object verify relay host tokens against (`relayHostKey: "jwks"`, staging's `WORKSPACE_RUNTIME_RELAY_JWKS_URL`); the turn scenarios keep the key in the object's env. All clocks are one Node `performance.now()`.

The local comparison (`packages/harness/e2e/perf/pi-local-latency.ts`) boots the real local daemon from the harness e2e stack with the same scripted vendor behind the same proxy, at 120 ms each way (a laptop in India to a US vendor), and the same client.

```sh
bun run --cwd packages/session-host perf:latency -- --scenario relay-warm,relay-cold-cache,direct,cold-object,cp-slow,no-links --turns 6 --out docs/perf/pi-durable-latency-2026-10-18/runs
bun packages/harness/e2e/perf/pi-local-latency.ts --turns 6 --out docs/perf/pi-durable-latency-2026-10-18/runs
```

Scenarios: `relay-warm` is staging as it is, with 1 s between turns; `relay-cold-cache` sets the relay's cache TTLs to 1 ms so every request pays the resolver; `direct` sends the same requests to the object over one 160 ms link with no relay; `cold-object` restarts workerd before every turn, so the object starts from storage; `cp-slow` is the control plane at 400 ms per request, which is what staging's 0.7-2.3 s per request from India implies once the 320 ms of link is taken off; `no-links` is every link at 0, the pure compute of the path.

The open scenarios (`e2e/latency/open.ts`) press a rail row instead of sending: after one turn has put text in the transcript, `open-cold` restarts workerd before every press, so the relay room and the object both start from nothing, and `open-warm` presses again on the same topology; `open-cold-cp-slow` is `open-cold` with the control plane at 400 ms. A press is what the web app sends at once (`session-reads.ts`, `placement-streams.ts`): `GET /session/:id/outline` at the reader's viewport, `GET /session/:id/queue`, `GET /session/:id?view=open` and the `/api/wr/events` stream, and the outline's body is the first transcript text on screen. Each read is timed to its headers and its body, the object's `Server-Timing` is read off it, and the room's send and the object's answer, the control-plane calls, the resolver lookups and the object's JWKS fetches are listed per press.

```sh
bun run --cwd packages/session-host perf:latency -- --scenario open-cold,open-warm --turns 6
```

With three calls the vendor was asked 65-430 ms after the object had answered the prompt (the third call); with one it is asked as the object answers.

Streaming, every scenario: inter-delta at the vendor 25-27 ms (the scripted cadence), at the object 103-108 ms, at the client 102-107 ms; jitter (sd of the intervals within a turn) 4-6 ms at the object and 4-7 ms at the client; last delta → idle 10-12 ms. The relay and the links add a constant 160 ms to every delta and nothing to their spacing.

Cold object: the first request to a freshly started object (the event stream open here) takes 713 ms mean against 435 ms warm, of which 270 ms is the fresh relay room's own resolver lookups; the object's start from storage (constructor, Lifecycle start, `Harness.open`, `composeSessionHost`, `resumeDurableRuns`, extension install, `watchEvents`) is the remaining ~120 ms in workerd on this Mac. A turn that follows is no slower than a warm one (accepted 472, first delta 1287). An object that holds an open SSE stream never hibernates (an unfinished request blocks it, [Cloudflare: lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)), so the start is paid once per visit, not per turn.

### The floor

For a person in India and a vendor in the US, with the object in `enam`: one way to the object (160) + the vendor round trip from the object (20) + the vendor's time to first token (600, the vendor's, not ours) + pi-durable's first partial commit (100) + one way back (160) = **1,040 ms** to the first delta; local's floor at the same geometry is 240 + 600 + 100 = **940 ms**. Cloud measured 1,325 ms warm with three control-plane calls, 285 ms over the floor; with one call (run 5) a warm turn measures 1,135-1,143 ms, **~100 ms over the floor**: 60 ms the one control-plane call (`2·doCpMs + cpMs`; 410 ms at staging's 400), ~8 ms of object work, the rest the relay room's processing and link scheduling. The object's own work, timed inside it on a `no-links` run with `performance.now()` marks (1 ms resolution in workerd): acquisition answered → session read and body prepared 0 ms → turn admitted and 204 ready 1 ms; then in `PiDurableTransport.send`, the held delivery applied 0-1 ms, `conversation.configure` 1 ms, the config preview 0 ms, `PiHarness.submit` with its two `cf_agents_jobs` writes 2 ms. Inter-delta is at its floor already (pi-durable's 100 ms).

## Experiments

Kept:
- **Turn start on one control-plane call** (D.1): `turn_acquire` names `writeClass: "agent_turn"`, the plane rechecks the proof's revocation, the host placement and the owner together, takes the lease (where the turn authority decides the `agent_turn` write), reads the turn's delivery beside the lease and answers both, releasing the lease if the delivery cannot be read; `admitPromptTurn` (`session-core/src/routes/session-prompt-admission.ts`) makes the acquisition the prompt's authorization and keeps every read of the session behind it, with the policy's `prompt` answer kept for the branches that take no lease (a resend of a held message, a queued or steered delivery). Warm turns: accepted 465 → 404 ms, first delta 1,275 → 1,135 ms at `cpMs 50`; 1,177 → 755 and 2,313 → 1,485 ms at 400. D1: 22 serial rounds and statements across the three requests → 5 rounds as `countD1Rounds` counts them, 14 statements, in one. Every refusal the three requests made is still made and tested at the one request (`claxedo-server/src/routes/runtime-session-authority.turn-start.test.ts`): a forwarded token for someone outside the organization, a share narrowed to follow or withdrawn, a revoked token, a token scoped to another session, a host that does not serve the session, and an acquisition that names no class or the wrong one.
- **Relay room: revocation check and target lookup concurrently** (`authorizeWorkspaceRelayRequest`, `packages/workspace-relay/src/server.ts`). Both need only the RAT's claims. A request after both caches expired: 1,017-1,057 → 743 ms accepted (one 270 ms round trip instead of two). Test: `server.test.ts` "the revocation check and the target lookup leave together ...".
- **Relay room: a `durable-object` target is kept 30 minutes** (`createCachedTargetClient`, `resolver-clients.ts`): the host id names the object and the object never moves, so the target cannot change for a RAT; revocation keeps its 10 s cadence. On staging this turns the 10 s cliff from two round trips (apac ⇄ IAD, ~220 ms each plus the plane's time) into one. Test: "a session's own Durable Object is remembered past the cloud TTL ...". The README's claim that completed target answers were never retained was false since the 10 s cache landed; it is corrected.

Measured and not changed (owned elsewhere or by a ruling):
- **The object's work between the acquisition and the vendor** (D.2-D.3): ~8 ms in all, measured above; the two pi-durable commits and the two `cf_agents_jobs` writes are the harness's (`agents/harness/pi`, `@earendil-works/pi-durable`), and a `conversation.configure` skipped when the model is unchanged would save its 1 ms. Nothing here is worth overlapping with the network.
- **One warm connection for send and stream**: the browser already multiplexes both over one HTTP/2 or HTTP/3 connection to the edge; the room → object hop is a stub call. Sending over a WebSocket to the object would skip the relay's per-request authorization (~10 ms warm, now ≤270 ms on a cache expiry) and the first POST's preflight, at the price of authorizing a long-lived socket once (the relay refuses WebSockets to a session host by design; the control plane's revocation would no longer cut a send path within 10 s). WebSocket Hibernation would let the object sleep between turns while the browser stays attached ([Cloudflare: WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/): billable duration "do not accrue during hibernation"; "In-memory state is reset"), which is a cost, not a latency, win, and would make every turn start pay the ~120 ms start. Not taken.
- **Coalescing deltas per animation frame**: already so in the app (`DeltaBuffer` + `commitDeltasWhileShown`), and the wire is already 10 Hz because pi-durable commits partials every 100 ms. Nothing to coalesce.
- **Per-event overhead**: one SSE chunk per `message.part.delta` frame of ~300 bytes at ≤10 Hz; compression would only add buffering. Not taken.
- **Answering the turn start before persisting**: the 204 already waits on nothing after `store.startTurn`'s SQLite writes (~25 ms in `no-links`); the vendor call is not gated by the answer.
- **pi-durable's 100 ms partial throttle** (`PARTIAL_THROTTLE_MS` in `@earendil-works/pi-durable`): the first delta waits 100 ms after the first token and the stream runs at 10 Hz, locally and on the cloud alike. It is inside the harness; the ruling is to layer over harnesses, so it is not changed here. An upstream option (16-33 ms) would take 70-85 ms off every first delta and make the stream visibly smoother on both paths.
- **Object placement**: `enam` against `apac`. Moving the object next to an Indian person saves 2 × 110 ms on the two browser-facing legs of a turn and costs the vendor round trip from Asia on every model request (and Anthropic's 403 from HKG): with one model call per turn roughly a wash, with tool rounds a loss. `enam` stays.
- **The relay hop itself**: `direct` against `relay-warm` with warm caches, 471 vs 470-490 ms accepted, 1,289 vs 1,286-1,325 ms first delta: the room costs ~0-30 ms when its caches hold. The cliff was the problem, not the hop.

Losers, in the rig itself: the first version delayed response bodies but not headers, so a bodiless 204 came back with no return-link delay (312 ms "accepted" against the 470 physics allows); and a fresh control-plane stand-in per reboot made the cold-object scenario fail its second turn with `session.error`, since the plane had forgotten the session's registration and leases (the stand-in now outlives workerd across reboots, `TopologyInput.world`).

## What to measure on staging after the deploy

From India, signed in, a Pi session on a cloud workspace, DevTools network panel with `Server-Timing` visible (lane E added `timing-allow-origin` to the relay's CORS headers):
1. `POST .../prompt_async` wall time with 1 s between sends (expect ~320 ms + one control-plane request + ~30 ms), then after a 12 s pause (expect one extra apac ⇄ IAD round trip, not two; before this branch two). The relay's `server-timing` on a sampled response shows `rat-active` and `target-resolve` overlapping.
2. The `/api/wr/events` stream: time from the press to the first `message.part.delta` frame, and the frames' spacing (expect ~100 ms, sd under 10 ms). Compare with the same prompt on a local Pi session.
3. The session object's log: the one `session-authorize` (`turn_acquire`) call's timing per turn (`SLOW_REQUEST_MS` warnings at 1 s), `turn-delivery` only after an object restart or a vendor's refusal of an account, and lane E's `host-start`/`host-serve` `Server-Timing` on the object's answers; a first request on a cold object should show ~100-200 ms of `host-start`.
4. The vendor: `press → vendor request` cannot be read from the browser; the object's `console.warn` on slow control-plane calls is the proxy.

## Not verified here

Real link latencies (the rig injects the 50/110/5/10 ms one-way figures above), staging's control-plane time per request (`cpMs`; both 50 and 400 are run), the room's actual colo for an Indian opener (assumed on the browser-to-object path), the hibernation behaviour of a real object between visits (workerd neither hibernates nor evicts; the cold start is a restart from storage), and the browser's own frame timing (the rig's client is Node; the app commits deltas on `requestAnimationFrame`, so add up to 16 ms).

## Opening a session: the press to the first transcript text

Measured on staging on 2026-10-18 (signed in, from India, a rail row of a Pi session; ms after the press): the connection read answered at 982, the three runtime reads left at 983-984 and answered at 4,290 (outline, queue) and 4,489 (open view), with `host-start` and `host-serve=1117` on each; the first text was on screen at 4,492. So 3.3 s between the connection read and the text, of which the object reports 1.1 s serving.

### The live path of a press

G. The web app, on the press: `startSessionReads` (`packages/claxedo-app/src/server/session-reads.ts`) issues the outline (`GET /session/:id/outline?rows&cols&reasoning&shell&edit`), the open view (`GET /session/:id?view=open`) and, from `session-queue.ts`, the queue, through `relay.fetch`, with the Runtime Access Token the connection read answered; `placement-streams.ts` opens `/api/wr/events?sessionID=` beside them. Four requests, one RAT.

H. The relay. The gateway (edge, SIN) verifies the RAT's signature against `CLAXEDO_RUNTIME_ACCESS_TOKEN_PUBLIC_KEY_PEM` (a key import per isolate, then ~1 ms a request) to read the host it names, and calls the workspace's room: in `apac` when this was measured, in `enam` for a room created after 2026-10-20 (see "The room beside the object"). A room that is not in memory loads its isolate and imports its keys (`workspaceRelayDurableObjectOptions`, PEM: no fetch) and then, for the first request, pays `rat-verify` (local), and `rat-active` and `target-resolve` together: two `GET`s to the control plane in IAD, 220 ms of link plus the plane's time (a D1 read each: the token's revocation row and `readSessionHostPlacement`). The three reads and the stream share those lookups (`createCachedRevocationClient` and `createCachedTargetClient` share a lookup in flight), the minted Relay Host Token (`relayHostTokenFor`'s promise entry) and the RAT's claims. Then `forwardSessionHostHttp` → `SESSION_HOST.getByName(root, { locationHint: "enam" })`, 110 ms away.

I. The object, cold. workerd loads the session-host isolate (the bundle with pi-ai, pi-durable, hono and session-core) and runs the constructor, then the first request's `lifecycle.start()`: the Agents SDK's `blockConcurrencyWhile` holds the other three at the door while `PiHarness.onStart` opens pi-durable's store, `Harness.open`, `SessionDO.boot` (`composeSessionHost`: the runtime store's schema check and journal replay, `recoverBusySessions`, the stored lease if any, `resumeDurableRuns`, `harness.inspect`), `pi.root`, `pi.resume` and `recoverQueuedPrompts`. All of it is synchronous SQLite in the rig, 12 ms between the constructor and the first `serve` (probed), so `host-start` reads 0: `Date.now()` "returns the time of the last I/O" and "does not advance during code execution" ([Cloudflare: security model](https://developers.cloudflare.com/workers/reference/security-model/)), and the isolate load precedes `fetch()` altogether. On a sampled relay trace the object's cold start is `session-host-fetch` − `host-serve` − 2 × the room-object link.

J. `host-serve`. `createRelayHostAuthMiddleware` verifies the RHT. Staging's object does so against the relay's published key set (`WORKSPACE_RUNTIME_RELAY_JWKS_URL`, `sessionHostVariables` in `user-cloudflare-config.ts`), which jose fetches on the first verification, and on Workers jose shares no fetch in flight, so each of the concurrent first requests fetched it. Then `sessionOperationGuard` → `remoteWorkspaceSessionAccessPolicy.authorize` → `POST /session-authorize {action: "read"}` over the `CONTROL_PLANE` binding (enam → IAD), one per read, three identical ones at once, each on the plane: the RHT verified against `CLAXEDO_RELAY_HOST_VERIFY_PEM`, `runtimeAccessTokenActive` (D1), `readSessionHostPlacement` (D1), `authorizeRuntimeSession` (D1); the stream's is a fourth with `stream: true`. Then the read itself, from the store in memory. The reads answer together because they waited on the same things.

### Experiments

Kept:
- **One `/session-authorize` for identical calls in flight** (`remoteWorkspaceSessionAccessPolicy`, `packages/session-core/src/remote-session-authority.ts`): a call whose endpoint, credential and body equal one still unanswered awaits that answer; the entry leaves the moment the answer lands, so no decision is reused across requests, and a caller with its own abort signal keeps its own request. A press makes 2 authority calls (the three reads' one, the stream's) instead of 4. Test: "identical calls in flight share one request, and the next identical call asks the plane again". In the rig the wall time did not move (the three were concurrent already; p50 796 → 800 cold, 415 → 414 warm, within the ±5 ms between runs); on staging it is two fewer D1-backed calls per open, and a wall win only where the plane serializes them, which is for the staging trace below to say.
- **The relay's key set fetched once, from the object's start** (`SessionDO.verificationKey`, `boot`, `packages/session-host/src/session-do.ts`): the fetch leaves from inside the Lifecycle's startup callback, since `blockConcurrencyWhile` holds "all events that were not explicitly initiated as part of the callback itself" ([Cloudflare: Durable Object state](https://developers.cloudflare.com/durable-objects/api/state/)) and a fetch started before it deadlocked the start (the rig's `open-cold` answered 500 "waited for too long"); the host is composed over a resolver that awaits the key, so the start goes on while the set is on its way; every verification then finds it loaded. One fetch per cold start instead of one per concurrent first request (4 → 1 in `open-cold`). Test: "fetches the relay's published key set once per start, before its concurrent first reads are verified, never once per read" (`session-do.node-test.ts`, 4 against 2 before). Wall time unchanged in the rig: the start it overlaps is 12 ms of synchronous work.

Measured and not taken:
- **Answering reads before Pi's `Harness.open` and `boot()`**: the whole start is 12 ms of synchronous SQLite in the rig (probed from the constructor to the first `serve`), and on Cloudflare it is the same local work; the isolate load before it is not ours to reorder. Serving a read before `recoverBusySessions` and `resumeDurableRuns` would also show a status the start is about to correct. Not worth a second start path.
- **Deriving a `session-do:` host's target from the signed claims in the room**: the plane's `sandboxRelayTargetLookup` reads `readSessionHostPlacement` for it, and the lookup already leaves with the revocation check, so skipping it saves load and no wall time.
- **Prefetching the key set at the constructor or at `fetch()` before the start**: deadlocks, above.

Owned elsewhere, with the numbers this rig puts on them:
- The plane's time per `/session-authorize`, `/internal/relay/revocation` and `/internal/relay/target` (lane `perf/d1-signed-reads`): the only legs of the 3.3 s that are not links or an isolate load.
- The object's isolate load (lane `perf/worker-cold-start`): ~100 ms in workerd on this Mac, more on Cloudflare; the session-host bundle carries pi-ai's every provider.
- The three reads as one request (lane `perf/web-session-chunks` / the app): with the authority call shared they cost the object one round each way and one authorize; the queue and the open view could ride the outline.
- The room's placement for a workspace whose sessions live on their objects: ruled and done on 2026-10-20, "The room beside the object" below.
- `WORKSPACE_RUNTIME_RELAY_HOST_VERIFY_PEM` for the session host: the plane verifies the same tokens with `CLAXEDO_RELAY_HOST_VERIFY_PEM`, so a rotation already needs a plane deploy; a PEM on the session-host Worker ends the fetch (deploy config, `sessionHostVariables`).

### The room beside the object (2026-10-20)

The owner's ruling: a relay room lives next to its runtime. For a workspace whose sessions run on their own Durable Objects the runtime is the object in `enam`, so the room is created there and not near the opener; a machine's room (a cloud VM, a person's own machine) stays beside its machine, where an `enam` room would put +220 ms on every browser request from apac (files, terminals).

K. The gateway reads the decision off the one input it can verify before the room exists: the Runtime Access Token's `host_id`, signed by the control plane and verified for the room's workspace (`relayPlacementCredential`, `gateway-placement.ts`; `verifyRuntimeAccessToken` checks the signature and `workspace_id`). `session-do:<root>` is the plane's statement that the session runs on its object (`sessionHostId`, `workspace-relay-protocol`), so `relayRoomPlacement` answers `SESSION_HOST_LOCATION_HINT` for it whatever `?region=`, `x-claxedo-workspace-region` or the edge country say; a token signed by anyone else verifies for no workspace and the request is placed as an anonymous one, at the floor. The browser no longer declares a region for such a link (`linkOf`, `claxedo-app/src/server/wire/connection.ts`) and the plane's session-host connection no longer carries one. A host tunnel's credential names a machine, so nothing changes for it. The cost: the gateway now verifies the token on every request that carries one (before, only when the declared region differed from the floor), ~1 ms at the edge.

Rooms never move ([Cloudflare: data location](https://developers.cloudflare.com/durable-objects/reference/data-location/): "Durable Objects do not currently change locations after they are created"; "Only the first call to `get()` for a particular Object will respect the hint"; hints are "a best effort and not a guarantee"; by default an object "is instantiated in a data center close to where the initial `get()` request is made"), so this applies to rooms created after the deploy; a workspace whose room already sits in `apac` keeps paying the old lookups.

In the rig the room's links follow where the real gateway places it (`roomLinks`, `e2e/latency/topology.ts`, asked through `workspaceRelayRoomPlacement` with the rig's token and key): a room in `apac` is at the edge, 110 ms from the object and the control plane; a room in `enam` is 110 ms from the edge and 5 ms from both. Same build otherwise, staging links, p50 of 6 (`runs/room-run1-apac-before.log`, `runs/room-run2-enam-after.log`, with their JSON; run 1's first two cold opens are workerd's first boots at 2,237 and 1,681 ms, which the p50 excludes):

| | room in apac (run 1) | room in enam (run 2) |
|---|---:|---:|
| cold open: both lookups answered, outline leaves the room | 349 | 233 |
| cold open: outline headers at the client | 881 | 602 |
| cold open: stream open | 881 | 602 |
| warm open: outline headers | 423 | 425 |
| relay caches expired: prompt leaves the room | 326 | 225 |
| relay caches expired: accepted | 683 | 473 |
| relay caches expired: first delta at the client | 1,413 | 1,201 |
| relay caches expired: idle | 2,256 | 2,041 |

The ~210 ms is the two lookups' link (2 × 110 → 2 × 5) on a cold room and on every 10 s revocation expiry; a warm open is unchanged because the browser's path through the room is the same 115 ms of one-way link either way (50 + 0 + 110 against 50 + 110 + 5). At staging's control-plane speed the lookups cost the plane's time on top, unchanged by this.

### What to measure on staging after the deploy

A session created after the deploy (its room is new): the relay's sampled `Server-Timing` on a cold open should show `rat-active` and `target-resolve` at the plane's time plus ~10 ms, not plus 220; the response header `x-claxedo-relay-location-hint` reads `enam` on every non-stream answer for the workspace; a cloud-VM workspace's reads still answer the region its link declares, and an unauthenticated `GET .../api/wr/health?region=weur` on a fresh workspace id answers `apac`. A session whose room predates the deploy shows the old numbers: rooms never move.

Set `CLAXEDO_RELAY_TRACE_FORCE_SECRET` on the relay and send `x-claxedo-relay-trace: <secret>` on the press's reads (a DevTools header override, or `curl` with the RAT from the connection read, the three URLs at once). The sampled `Server-Timing` carries the room's `relay-auth` (`rat-verify`, `rat-active`, `target-resolve`, `rht-mint` or `rht-cache`), `session-host-fetch`, `relay-room-total`, the gateway's `relay-gateway-route` and `relay-gateway-do-fetch`, and the object's `host-start` and `host-serve`:
1. A cold open (a session untouched for 70-140 s, after which "the Durable Object will be evicted entirely from memory", [Cloudflare: lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)): `rat-active` and `target-resolve` are the plane's time plus 220; `session-host-fetch` − `host-serve` − 220 is the object's cold start; `host-serve` is one `/session-authorize` round, no longer that plus a key set fetch.
2. The plane's logs for the press: 2 `session-authorize` rows (one `read`, one `read` with `stream`), not 4; the relay's `/.well-known/jwks.json` hit once per object start.
3. A warm open 1 s later: `host-serve` ≈ one authorize round; `relay-auth` ≈ 1 ms.
4. Whether three concurrent authorizes were slower than one: compare `host-serve` before and after the deploy on cold opens of the same session.
