# One origin for the web app, 18 October 2026

The signed web app, the control plane's API and the relay were three origins (`app.claxedo.dev`, `api.claxedo.dev`, the relay's `workers.dev` name), each with its own certificate, so a cold load from India paid three TLS connections and every relay request (an `Authorization` header) and every JSON mutation paid a CORS preflight: ~205 ms per distinct URL, six at once before the first session read ([the baseline](./2026-10-18-web-baseline.md), rows 6 and 20). This change serves everything the browser needs from the app's own origin, and this is what the rig measured before and after.

## The shape

The deployment has one public origin, `CLAXEDO_APP_ORIGIN`. Its Worker (`packages/claxedo-server/scripts/deploy/app-worker.ts`, configured by `renderAppWranglerConfig` in `wrangler-config.ts`) serves the browser app's assets and runs ahead of them for the paths `public-origin.ts` names: `/api/*`, `/internal/*`, `/.well-known/*` and `/health` go to the control-plane Worker over the `CONTROL_PLANE` service binding, `/relay/*` to the relay Worker over `RELAY` with the prefix removed, each as the same request on the same origin with the edge's `cf` carried. The control-plane Worker has no custom domain of its own; `BETTER_AUTH_URL` is the public origin, so the GitHub OAuth callback is `<origin>/api/auth/callback/github` and the host-only session cookie lives on the origin the page is served from. The web build bakes no server or relay origin: the app reaches its server on `window.location.origin` and every relay room at `<origin>/relay` (`src/auth/origins.ts`, `src/server/relay.ts`), and its meta policy connects to `'self'` only.

Cloudflare's own statements the shape rests on:

- Service bindings add no network hop: "there is zero overhead or added latency", "both Workers run on the same thread of the same Cloudflare server" ([service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/)). The call still counts toward the subrequest and the 32-invocation limits.
- Placement follows the bound Worker's `fetch` handler, not the caller: "Placement only affects the execution of fetch event handlers. It does not affect RPC methods or named entrypoints", and the documented split is an edge Worker forwarding to a placed back-end Worker "which runs near your database" ([Smart Placement](https://developers.cloudflare.com/workers/configuration/smart-placement/)). The app Worker forwards with `fetch`, never RPC, so the control plane keeps running beside its D1 databases under its region pin and the relay gateway keeps running at the edge beside its rooms.
- Static assets are "always served from the location nearest to the incoming request" (same page), and `run_worker_first` takes an array of glob patterns with at most 100 entries ([Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)).
- A custom domain points "all paths of a domain or subdomain to your Worker" ([custom domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)), so the one domain carries the app, the API and the relay.
- A WebSocket passes through a Worker by returning the upstream's 101 response; the relay already answers its Durable Object's upgrades this way, and `app-worker.test.ts` proves the same through a workerd service binding, with an event stream delivered chunk by chunk and `Set-Cookie` reaching the browser.

The egress broker (`/bindings/*`, `packages/egress-broker`) is forwarded too: a sandbox's vendor calls and git clones go to base URLs under `hostedControlPlaneOrigin(env)`, which is this origin now. The broker is therefore same-origin with the app's pages, and the CORS withholding that `isBrokerPath` existed for no longer stands between a page and it. What guards it is what always authenticated it: a binding's placeholder or the signed runtime token the lease carries, never the session cookie, which the broker neither reads nor forwards (`broker.ts` strips `cookie` from what it sends on), so a page without a lease's placeholder gets a refusal, not the operator's key. `hosted-core-app.test.ts` checks every path the control plane mounts against `publicOriginRoute`, so the next mount fails a test instead of disappearing behind the single-page fallback.

What stays cross-origin, and why: the desktop app's renderer still reaches the relay at its own URL (`CLAXEDO_RELAY_ORIGINS` in its policy), so the relay's CORS allowlist (`CLAXEDO_APP_ORIGINS`, also the origin a browser's WebSocket upgrade must carry) stays; machines' host tunnels and the session host's JWKS reads use `CLAXEDO_WORKSPACE_RELAY_URL` directly. The control plane's cookie transport grants no CORS to any origin any more (`browser-auth-security.ts` keeps the CSRF checks: a cookie mutation must carry the trusted Origin, not be cross-site, and be JSON); the bearer-transport CORS of the local daemon's plane is untouched.

## Measured

`bun run --cwd packages/claxedo-app e2e:perf-web -- --reps=3 --profile=india-staging` on the shared M4 Pro (load 13–21), dev `6b380dd7ad` against this branch rebased on it, medians of three. The rig's front is the stack's one origin now, as the deployment's Worker is; before, the relay sat on a second loopback origin and the API behind the front.

| scenario (india-staging) | dev `6b380dd7ad` | one origin | requests | preflights | origins |
|---|---|---|---|---|---|
| cold boot of a session, first text | 2,416 ms | 2,228 ms | 46 → 39 | 7 → 0 | 2 → 1 |
| open the second session from the rail | 665 ms | 464 ms | 12 → 7 | 5 → 0 | 2 → 1 |
| cold boot of `/`, rail filled | 1,337 ms | 1,326 ms | 31 → 30 | 3 → 0 | 2 → 1 |
| warm reload of a session | 864 ms | 866 ms | 38 → 38 | 0 → 0 | 2 → 1 |
| return switch, typing, Settings, Marketplace, signed-out `/` | unchanged within noise | | | | |

The cold session boot loses the ~205 ms preflight that stood between the catalog and the first `outline` read (the six preflights left together, so one round trip was the cost); opening a session from the rail loses its one preflight, 203 ms of 665. The warm reload never paid one, since Chromium kept the cold boot's preflight answers, and does not change. What the rig cannot show is the handshake: its network emulation adds latency per request and never replays TCP and TLS per connection, so the second and third `connect` + TLS (about 0.3–0.6 s each from India, once per page load) that a real browser no longer opens are not in these numbers; `--target=https://app.claxedo.dev` with an exported cookie file measures them once staging serves this shape.

## What the owner has to change before staging serves it

In this order; nothing here was done by the lane.

1. GitHub OAuth app (sign-in): set the authorization callback URL to `https://app.claxedo.dev/api/auth/callback/github` (it is `https://api.claxedo.dev/api/auth/callback/github` today). The GitHub App used for repository connections signs in by device flow and needs no change.
2. `staging` environment variables: add `CLAXEDO_STAGING_RELAY_WORKER_NAME` if the relay job's variable of that name is not already set (the `app` job binds the relay by it); `CLAXEDO_STAGING_API_ORIGIN` is no longer read by any workflow (the sandbox Worker's `CONTROL_PLANE_URL` comes from `CLAXEDO_STAGING_APP_ORIGIN` now). Repository variable `CLAXEDO_CONTROL_PLANE_URL` (the desktop release's `CLAXEDO_CORE_ORIGIN`) becomes `https://app.claxedo.dev`, since the auth descriptor's issuer, resource and token endpoints move to the public origin and the desktop refuses a descriptor whose origin differs from its configured one. `CLAXEDO_APP_URL`, `CLAXEDO_PAGES_PROJECT` and `CLAXEDO_PAGES_BRANCH` served only the retired Pages workflow.
3. Merge and push to `staging`. `deploy-staging` runs `control-plane` (the Worker is deployed without `--domain`; `wrangler deploy` leaves the existing `api.claxedo.dev` custom domain attached until it is removed), then `relay` (`CLAXEDO_CENTRAL_URL` becomes the app origin), then `app` (the new Worker with both service bindings, on `app.claxedo.dev`), which waits until the origin's `/health` names this commit.
4. Detach the `api.claxedo.dev` custom domain from `claxedo-user-deployed-locked-staging`. `wrangler deploy` without `--domain` leaves an attached domain in place, and Wrangler has no detach command, so it is the [Workers Custom Domains API](https://developers.cloudflare.com/api/resources/workers/subresources/domains/): on 2026-10-20 the account's listing (`GET /accounts/683a2c01a4d43b2fa998cde8ddedaf0e/workers/domains`, read with the laptop's logged-in Wrangler OAuth token) named it `8182b9fc8fa5eedac689401c7a09f2219751cf1e`, so the detach is `curl -X DELETE -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" https://api.cloudflare.com/client/v4/accounts/683a2c01a4d43b2fa998cde8ddedaf0e/workers/domains/8182b9fc8fa5eedac689401c7a09f2219751cf1e` with a token that holds Workers Scripts write (the laptop's OAuth token reads the listing but Wrangler reports it short of scopes; `wrangler login` refreshes it), or Workers & Pages → the Worker → Settings → Domains & Routes in the dashboard. Until then the Worker still answers on that host but refuses every request with `deployment_candidate_unavailable`, since its origin check compares the URL to `BETTER_AUTH_URL`; the DNS record goes with the domain. The `hpi-20261003-0144-*` domains in the same listing belong to an older experiment's Workers, not to staging.
5. Dispatch `deploy-staging` with `components=sandbox-image` (still needed after the workflow change: the variable lives outside the digest): the sandbox Worker's `CONTROL_PLANE_URL` (its idle-stop posts) is a deploy variable outside its `DEPLOY_INPUTS` digest, so a full deploy that finds the image's inputs unchanged leaves the Worker pointed at the old host; naming the component deploys it unconditionally.
6. Everyone signed in signs in again: the session cookie moves from the `api` host to the `app` host, and the desktop's stored credential is bound to the old control-plane origin.

After the deploy: `curl -sI https://app.claxedo.dev/health` names the Worker's version tag; `curl -s -X OPTIONS https://app.claxedo.dev/api/claxedo/mode -H 'Origin: https://app.claxedo.dev' -H 'Access-Control-Request-Method: POST'` answers 404 JSON with no `access-control-*` header, as it should; a session open in the browser's network panel shows one host and no `OPTIONS` row.
