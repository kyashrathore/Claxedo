Claxedo Intended Architecture

Claxedo supports a downloaded desktop app and a hosted web app. The important idea is simple: the user can work locally, in a sandbox, or through a central Pi agent, while the system chooses the right storage and security boundary at runtime.

Desktop, skipped sign in

    Runtime Rule

    A downloaded app without sign-in is trusted only by the local machine. It stores state in SQLite and may use the local in-process runtime or a user-configured sandbox runtime.

    Plain English: users can start immediately, and nothing needs a Claxedo cloud account until they choose to sign in or use hosted web.

    The Three Decisions Claxedo Makes

    Who is the user?

    Authority is decided at request time.

    • valid Clerk token means signed account mode.
    • no token + local desktop means unsigned local mode.
    • no token + web is rejected.

    Where is the workspace?

    Workspace kind chooses the runtime environment.

    • local runs inside the local claxedo-server sidecar.
    • cloud runs in a sandbox.
    • Hosted web only allows cloud.

    Where does the runner live?

    Pi is a special central runner.

    • pi always runs in central server mode.
    • Other runners run through the workspace execution path.
    • Local execution is in-process; cloud execution uses sandbox workspace-runtime.

    Storage and Sync

    Unsigned local storage

    When the user skips sign-in in the desktop app, sessions, messages, workspaces, and credentials stay local. Cloud sandboxes can still be used if the user configures sandbox and model keys locally.

    Signed cloud storage

    When the user is signed in, sessions and messages belong to a Clerk user or organization and sync to Convex. Local desktop can still run local workspaces, but signed history becomes account-backed.

    Metadata and Message Sync Story

    The browser may talk directly to a sandbox for responsiveness, but durable history still needs a central write path. The central server is the place that knows the user, workspace lease, tenant, and storage mode.

    Session metadata

    Session lists, titles, archive state, workspace IDs, runner choice, and timestamps are lightweight metadata.

    • Local in-process sessions write metadata directly in the local sidecar.
    • Sandbox runtime reports metadata to central through typed tRPC.
    • Pi writes metadata in central because Pi already runs there.

    Message events

    Messages are the durable conversation stream, so they need idempotent append and replay.

    • Current local path persists replay from central globalBus.
    • Cloud target should use runtime-to-central typed append, not only background SSE observation.
    • Events need sequence IDs, lease/epoch checks, and retry-safe writes.

    Storage destination

    The same sync events land in different stores depending on authority.

    • Unsigned desktop writes to SQLite only.
    • Signed desktop writes locally and mirrors to Convex.
    • Hosted web writes through central to Convex.

    Why not browser-to-Convex only?

    The browser can read account-backed state, but the sandbox needs a trusted authority to validate lease, workspace, tenant, and runner identity before durable writes. That authority is central.

    Why direct browser-to-sandbox is still OK

    Direct attach improves interactivity. It does not have to be the durable sync path. The sandbox can stream UI responses to the browser while also appending authoritative events to central.

    Credential Safety

    Raw local mode

    For local desktop development, credentials can live in local encrypted storage and be used by the local sidecar and its agent adapters when needed.

    OneCLI gateway mode

    For cloud sandboxes, provider keys should stay outside the sandbox. The sandbox calls providers through a scoped OneCLI gateway, and network policy blocks direct provider egress.

    What Exists vs What Needs Work

    Already mostly present

    • Desktop local server and SQLite storage.
    • Local and cloud workspace distinction.
    • Cloud sandbox runtime provisioning.
    • Pi central runner routing.
    • Frontend Clerk login and bearer token plumbing.
    • Runtime-to-central tRPC for session metadata and heartbeat.

    Still required

    • Server-side Clerk verification and tenant scoping.
    • Convex client and signed write-through sync.
    • Per-request authority resolver: signed Convex, unsigned SQLite, web 401.
    • Durable runtime-to-central message append for cloud runtimes.
    • Hosted web enforcement: cloud workspaces only.
    • OneCLI credential injection plus sandbox egress policy.
