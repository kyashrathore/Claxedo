## Windows install time (open)

0.2.1's one install on the Windows rig took 29 min, against 2–3 min on Linux and macOS. Measured again on
2026-10-23 with `measure-install.mjs` on a fresh Windows Server 2025 (t3.large, 2 vCPU, Node 24.22, npm 11.19,
Defender real-time on):

| source | cold | warm cache | `reify:unpack` (cold) | `idealTree` (cold) | files | size |
|---|---|---|---|---|---|---|
| npm 0.2.1 | 896 s | 680 s | 671 s | 192 s | 56,130 | 846 MB |
| packed 0.2.2 | 850 s | 664 s | 662 s | 184 s | 55,327 | 593 MB |

A global `npm install -g` of the packed 0.2.2 took 1096 s. The time goes to writing files under Defender: during an
install `MsMpEng` used about 2,300 CPU seconds while node used a few hundred, npm sent ten-odd KB/s, and each
tarball's `http fetch` logged about 500 s because npm streams it into extraction (the registry itself served a
4 MB tarball to the box in 0.08 s). 0.2.2 writes 250 MB fewer bytes but only 800 fewer files and saved 5%, so the
cost is per file. The earlier "not Defender" reading timed one `npm cache add`, which unpacks nothing. Not yet run:
the same install with a Defender exclusion on the install folder, the A/B that would confirm it; the agent was
refused adding the exclusion, as a security-setting change on the box.

- What an install writes: 0.2.1 is 568 packages, 56,007 files, 824 MB. OpenCode's dependency tree is 52,419 of
  those files (94%) and 482 MB; the Claude Agent SDK's binary was 246 MB until 850a3a1d. The packed 0.2.2 is 55,204
  files, 574 MB. OpenCode, Pi, the Cursor SDK and the native packages are public npm installs the runtime declares
  (pinned exactly, their own dependencies not pinned: no lockfile ships); only Claxedo's code and the Claude SDK's
  launcher are bundled.
- On Linux (this cloud container, Node 24, npm 10.9), 0.2.1 and 0.2.2 alike: 70 s cold, 41 s of it npm resolving the
  tree (`idealTree`, about 684 manifests from the registry) and 26–28 s unpacking; 40–46 s from a warm cache; the
  OpenCode patch step 0.75 s; `claxedo --version` 1.8–1.9 s.
- An update rewrites everything: `npm install -g` of the version already installed replaced all 568 packages in
  79 s (new inodes), and `install.sh` runs it on every run without checking the installed version. A project-style
  install (a `package.json` in a private directory) reran in 6.5 s and upgraded 0.2.0 → 0.2.1 by changing 7
  packages in 15 s.
- The measurement on Windows: `packages/cli/scripts/measure-install.mjs` (`--packed <dir>` for a dry run's tarballs,
  `--npm <version>` for a published CLI) reports cold and warm install times, npm's own phases, the patch step, the
  first run, files and bytes, and Defender's real-time state. The CI job that runs it is written but not on dev:
  `claxedo-packages-release`'s dry run passes `--work-dir "$RUNNER_TEMP/packs"` and uploads `packs/*/*.tgz`, and a
  `cli-install` job (needs the dry run; windows-latest, macos-latest, ubuntu-22.04 × packed, npm; 100 min) runs the
  script. GitHub refuses workflow changes from the Claude GitHub App, so the owner pushes it (patch handed over on
  2026-10-23).
- Next: Windows shows unpacking dominant (75% of the cold install), so the lever is fewer files, which means
  OpenCode's tree (52,419 of the 55,327); resolving is 3–4 min there too, which an `npm-shrinkwrap.json` in
  `@claxedo/cli` would cut and which also pins the tree; for updates in any case, install into a private project
  directory and skip a version already installed.

## What to test, and how

Staging app: `https://app.claxedo.dev` (control plane on the same origin). Staging was wiped, so projects,
workspaces and connected machines must be created again. Never type real keys into forms; deliver a provider key
once through the app's own UI, owner-entered.

### 1. CLI install and connect from npm (Mac, Linux, Windows)

- Install: `curl -fsSL https://raw.githubusercontent.com/kyashrathore/Claxedo/dev/packages/cli/install.sh | sh`,
  pinning with `CLAXEDO_CLI_VERSION=0.2.1` (npm install scripts off, then `install-opencode-node.mjs`; knobs in
  `packages/cli/README.md`). A plain `npm i -g @claxedo/cli` needs a C++
  toolchain (tree-sitter-powershell has no prebuilt).
- Set `CLAXEDO_CONTROL_PLANE_URL` before the first `claxedo connect`; the state file freezes it (`--reset` to change).
- Create a v2 invite in Settings → Machines, then `claxedo connect <invite>`. On a Mac that also runs the desktop
  app's daemon add `--alongside-desktop`.
- Check: the machine appears, assign a folder (connectable in about 8 s), open a terminal (click → output about
  4 s), SIGTERM → it drains and exits in about 1 s, revoke → it exits 78.
- Windows rig (Windows Server 2025, EC2 ap-south-1): SSH key + Administrator password in user data (the AMI rejects
  ed25519 key pairs), AutoAdminLogon + reboot so the scheduled task can run, Git for Windows installed. The npm
  install there took 29 min once (cause not isolated, not Defender); see "Windows install time".

### 2. Agent session on a connected machine

- Pi turn with model `pi` (or `anthropic/claude-fable-5-1`) on the machine: run shell commands, scaffold and run a
  small React app, and confirm a background dev server survives the tool call and dies when the session closes.
- On Windows, Pi's bash is Git Bash; the terminal PTY is `cmd.exe`.
- Owner accounts (W4): the connector logs "provider configuration revision 1 from the owner's accounts: claude-sdk".
  A Claude Code turn on a Mac machine spent the owner's Claude plan with a scratch HOME (8.7 s); `claude` must be on
  the connector's PATH or the turn is refused "Claude Code is not installed…". Pi cannot spend a Claude plan
  (`brokered_plan_unsupported`, by design). OpenCode and Codex through the owner's accounts are not proven yet.

### 3. Direct route, pause/resume, revocation (W1, W3)

- Desktop and machine on one LAN: `claxedo connect --direct on` (on by default); connect logs
  "direct route: serving <ip>:<port>" and `GET /connection` returns `directRoutes {port, addresses, spkiSha256}`.
  Proven on this Mac by calling the listener with the pin: ws open 4–6 ms, but each HTTP call cost about 0.5 s,
  because the machine asked the control plane on every direct request. A direct request now reuses the machine's
  answers under its token, as a relayed one does (a76614db). On staging from a Linux box (dev `e36efd45`, client
  pinning the named key): six direct terminals cost one control-plane check, reads 2–4 ms, terminal create 11–20 ms,
  echo 3–6 ms (relay 83 ms p50). Not yet measured: the desktop app using the route end to end and the fallback to
  the relay when the network drops.
- Pause and resume, dev `e36efd45` on staging: the machine logs the pause 0.48 s after the request, closes its
  direct terminals, answers direct reads 503 `machine_paused` and `POST /connection` 409 by 0.86 s, and stays up;
  after a resume it serves direct reads at 0.65 s and opens a relay terminal at 1.8 s (0.2.1 took about 7 s and
  12 s). One restarted while paused waits, holding its doorbell, and serves 2.3 s after the resume. From the app,
  Settings → Machines → Details shows the pause in 0.85 s on desktop and phone (see Known open issues for resume).
- Narrow a share or remove a member while a terminal is open: refused within 2 s (60 s worst case with the push cut).

## Working rules learned this stretch

- Prove a change live first; run affected replay, e2e and the CI matrix once, at merge.
- The husky pre-push hook validates the working tree it runs in: push a lane's SHA from a worktree checked out at
  that SHA, never from the main checkout. Report "merged" only after the push prints `old..new -> dev`.
- Lanes never wait on a background notice: blocking polls with a timeout of 10 minutes or less, and the lead checks
  in on a schedule.
- Never prune shared Docker state, kill processes by PID or path (not by name), commit explicit paths only.
- In a cloud agent container, TLS goes through an intercepting proxy: a connector under `env -i` needs
  `NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt` or every request fails `SELF_SIGNED_CERT_IN_CHAIN`, and Bun's
  `fetch` ignores CIDR entries in `NO_PROXY`, so name a private direct-route address there explicitly.
- Staging D1 writes (wipe, `claim-owner`) need the owner's explicit approval each time; the claim command is in
  `docs/deploy/staging-branch.md`.
- The Claude GitHub App has no `workflows` permission: GitHub refuses any push that adds or changes a file under
  `.github/workflows/`, so hand the owner that change as a patch and push the rest.
