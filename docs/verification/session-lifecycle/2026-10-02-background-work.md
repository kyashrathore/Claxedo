# Session settings and background-work continuity

The reported session was `ses_aeda50d9-2ed8-47eb-be78-58db73786e67` in workspace `dbf01e12-98cb-425f-a8f2-4935d6670518`. The session connector denied access because this caller does not own the machine daemon route. Its stored journal was therefore not independently read in this investigation. The defects below were confirmed from the implementation and reproduced through tests, including real Claude and Codex processes against the repository's scripted model servers.

## Confirmed flow and fixes

1. **Composer → session creation.** `createComposerHarness().submission()` stripped `variant` from its returned model. `DraftSessionScreen` creates the session with that model, so only the first prompt retained the selected effort. Submission now retains the complete model, and `commitSessionSelection()` persists changed effort before an existing session sends. A persistence failure stops that submission; it does not silently send different settings.
2. **Session row → composer hydration.** `emptyOptionsPatch()` cleared catalog effort when a harness had no config-options endpoint. `scopeStamp()` also omitted provider and variant, and `harnessStatusPatch()` could not distinguish an omitted thought level from an authoritative reset. Hydration now follows the full persisted choice, including explicit default, while catalog refreshes preserve an existing session or held user selection. The OpenCode reload browser test reproduced this separate bug before the fix.
3. **Composer → durable queue → turn.** Every model-bearing submission carries its selected effort or an explicit empty default. `queuedPromptColumns()` previously dropped empty and null resets. It now encodes either explicit reset as the queue's empty-string default representation; omission still means no per-prompt override. Recovery tests close and reopen the SQLite store and verify the actual dispatched body.
4. **Claude turn → live SDK process.** `ClaudeTurns.launchFor()` previously included the whole broker config, model and effort in an immutable launch key. Mismatch called `stopBackground()`. Model, effort and permission mode now use acknowledged SDK controls on the existing process. Unchanged values send no controls. Effective launch-only changes are refused while jobs exist, with a visible configuration error. There is no implicit `stopTask` path. A task completing during a settings control cannot prematurely close the next prompt's stdin; a rejected control leaves the process and its session broker usable.
5. **Runtime configuration → transports.** `createRuntimeProjection()` holds a harness's generation stable when unrelated runtime configuration changes. `launchConfigChanged()` compares effective executable inputs structurally, excluding lease counters, expiry metadata, display labels and diagnostics. Claude, Codex, Cursor, Pi and ACP use it. Selected-provider transports ignore unrelated providers; Pi and ACP retain the full provider map. Credential bytes, account identity, endpoints, secrets and actual plugin generations still invalidate the launch. OpenCode already compares its effective provider/projection document before applying it.
6. **Codex configuration → process replacement.** Replacement checks both the native child registry and `thread/backgroundTerminals/list`. Live work or an inventory error prevents retirement. Pending configuration remains pending; a later send must apply it before starting. Real native v1 and v2 child tests and a real background-shell test prove refusal preserves work, which finishes before replacement succeeds.
7. **Subagent observation → child turn owner.** `createChildTurns()` kept the original foreground mode even after a canonical provider observation moved a child to the background. Parent completion then closed the child's route. The existing child now takes subsequent explicit mode observations. Tests verify lease retention, next-turn child text in the journal, absence of dropped-route diagnostics and eventual terminal settlement.

Explicit task stop, cancellation, session close, process failure and actual security/configuration changes retain their own lifecycle paths. This change does not promise process survival after a crash or explicit close, or provider-side cache hits.
