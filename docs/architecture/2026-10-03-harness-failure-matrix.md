# Harness failure triggers, errors, and ownership boundaries

Several unsafe sharing changes would corrupt routing or configuration **without producing a dedicated error**. Existing guards instead refuse some combinations, and some already-shared resources have a wider failure scope. These are different findings.

This matrix covers the configuration, account, MCP/plugin, concurrency, cancellation, process-loss, and recovery boundaries relevant to the [architecture assessment](2026-10-03-claxedo-session-execution.md) and [implementation plan](../plans/2026-10-03-harness-lifecycle-and-memory-plan.md). It is based on source and existing test inspection, not a claim that every row was reproduced in the running app. It does not enumerate unrelated provider billing errors or every possible third-party error string.

## How to read the errors

- **Current guard:** implemented refusal or recovery behavior. It is not automatically a defect to fix.
- **Current shared scope:** current code intentionally shares this state or failure domain. Whether that violates a product requirement needs a concrete conflicting use case.
- **Proposed-sharing risk:** would follow from the specified ownership change; the change has not been made or reproduced in production.
- **Unverified outcome:** the mutation is identifiable, but its observed effect depends on upstream caching/reload behavior and still needs the named experiment.

`TransportError` has separate `transport`, `code`, `message`, and optional `detail` fields. For example, “codex / configuration” below describes those fields, not a claimed HTTP error code. [runTurn()](../../packages/session-core/src/host/turn-runner.ts) normally persists the exception's message and optional detail into the failed turn. It does not promise every transport code reaches the UI unchanged.

For runtime snapshot application, [createSessionConfiguration()](../../packages/workspace-runtime/src/workspace/configure.ts) converts a returned `{ state: "refused", reason }` into **HTTP 409**, code **`runtime_config_refused`**, message **`The harness refused the configuration for <sessionId> (<reason>)`**. [The config route](../../packages/workspace-runtime/src/routes/config.ts) returns **HTTP 500**, code **`runtime_snapshot_apply_failed`**, message **`Runtime config apply failed`** for an ordinary thrown error that is not a `RuntimeConfigApplyError`. The precise transport exception is logged. Deferred post-turn failures go through `onHeldFailure`; they are not retroactive HTTP responses.

## Codex app-server

Current owner: one root entry owns one RPC/process, with root, native-child, and title-thread state underneath it. [Sources: session binding](../../packages/harness/src/transports/codex-app-server/session.ts), [sessions lifecycle](../../packages/harness/src/transports/codex-app-server/sessions.ts), [RPC](../../packages/harness/src/transports/codex-app-server/rpc.ts), [request routing](../../packages/harness/src/transports/codex-app-server/index.ts).

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| CX1 — current guard | Credentials/projection change arrives while `entry.state === "busy"` or `providerTurn` exists. | `{ state: "deferred", until: "after-active-turns" }`; no immediate error. | The entry holds the update. A later eligible application can reopen/resume the root. |
| CX2 — current guard | A changed launch profile requires `replace()` while native children or background terminals remain. | codex / configuration: `Claxedo cannot replace the Codex process while background tasks are running. Wait for them to finish or explicitly stop them before changing launch settings.` | Replacement is refused for that entry. Finish or explicitly stop its background work before retrying. |
| CX3 — current recovery | `turn/start` does not answer within its 60,000 ms request deadline. | codex / process: `Codex turn/start did not answer within 60000ms`. `rpc.abandon()` retires the process. | Today's root entry loses its process; its next attachment can resume the saved upstream thread. A naive pool would retire all siblings too. |
| CX4 — current stop uncertainty | Stop waits for unresolved startup beyond its deadline, or interrupt succeeds but completion is not observed. | Startup: `Codex turn startup exceeded the stop deadline`. Missing completion returns `execution: "unknown"`; it does not necessarily throw a visible error. Background cleanup can return `deadline_exceeded`, `cancellation_unsupported`, or `provider_unreachable`. | Recovery must retain uncertainty. An interrupt acknowledgement, including an upstream empty-turn-ID interrupt, is not proof that all work ended. |
| CX5 — proposed-sharing risk | Two entries share the same `CodexRpc`, but both call the current `bindEntry()` and replace its single `onRequest` handler. | If the last-bound entry has no active turn, JSON-RPC **-32000**, `Codex request has no active turn`. If it has an active turn, **no guaranteed error**: an earlier root's request can be answered through the later root's broker, directory, and permission mode. | Approval isolation breaks before the UI can repair it. Install one process router using authoritative thread ownership. |
| CX6 — proposed-sharing risk | A shared process broadcasts sibling root frames through every entry's current outside-turn notification handler. | Possible wrong child buffering and `codex.usage_unbilled`, message `Codex reported usage for thread <id>, which no turn of this session can be billed for`. Incorrect attribution need not produce this warning in every ordering. | Route root/child/side frames once to their actual owner; do not classify a sibling as a prospective child. |
| CX7 — proposed-sharing risk | `close()`, launch replacement, or timeout keeps calling `entry.rpc.retire()` after that RPC is shared. | Retirement fails pending RPC calls with `Codex process retired`; process exit can surface `Codex app-server exited with code <code>` or `signal <signal>`, optionally followed by stderr. | All occupants lose execution. A shared implementation needs coordinated process loss plus separate thread release. |
| CX8 — current mutable scope; interference unverified | Two consumers resolve the same `codexHomeKey()` and prepare different process-level profiles. The key includes owner, broker URL/auth mode or own-login, and plugin-selection mode; it does not identify every selected plugin/version/config value. | `prepareCodexProfile()` writes `config.toml` and marketplace/cache content in that home. **No profile-conflict error exists.** Whether an already-running process picks up a particular write depends on upstream reads/cache. | This does not require process pooling to be a file-sharing concern, but no conflicting public flow was reproduced here. Pooling by this home path alone would be unsafe; isolate immutable profile generations and test active/idle readers. |
| CX9 — current guards | Selected account unavailable, own login disallowed without a selection, or unsupported SSE MCP reaches the transport directly. | `CredentialSelectionError` / `account_unavailable`: `Codex account unavailable: <reason>` or `Codex requires a selected account for this session owner`. Direct MCP guard: codex / configuration, `Codex cannot load SSE MCP server <name>`. | Choose valid owner credentials. The ordinary MCP projection filters SSE as `unsupported-by-harness` before this direct guard; see shared cases. |

Additional exact guards: `Codex returned a different or missing thread` prevents rebinding a requested resume to another thread; `Codex turn already active` rejects a second transport turn on one entry. [Turn source](../../packages/harness/src/transports/codex-app-server/turn.ts), [terminal stop source](../../packages/harness/src/transports/codex-app-server/terminals.ts), [notification source](../../packages/harness/src/transports/codex-app-server/notifications.ts), [profile key](../../packages/harness/src/profiles/codex/home.ts), [profile writer](../../packages/harness/src/profiles/codex/index.ts).

## Claude Agent SDK

Current owner: one independent Query/CLI per active conversation. Normal results with no background tasks close input; an idle retained Query is not the default lifetime. [Sources: index/configure](../../packages/harness/src/transports/claude-sdk/index.ts), [turns](../../packages/harness/src/transports/claude-sdk/turns.ts), [live query](../../packages/harness/src/transports/claude-sdk/live-query.ts), [query callbacks](../../packages/harness/src/transports/claude-sdk/query-options.ts).

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| CL1 — current guard | A changed launch revision requires draining/replacing a still-live Query with background tasks. | claude / configuration: `Claxedo cannot replace the Claude process while background tasks are running. Wait for them to finish or explicitly stop them before changing launch settings.` | `configure()` can already have returned `applied` after updating the entry; this refusal occurs later when the next launch needs replacement. It is not the same contract as Codex's deferred response. |
| CL2 — current guard | A live SDK permission or model/effort update rejects. | `Claude refused the permission mode change`, or `Claude refused the model or effort change: <cause>`, code `configuration`. | The affected Query reports failure. A caller must not manufacture a successful mode/model change. |
| CL3 — current stop uncertainty | Interrupt rejects, or the run has not settled by the stop deadline. | Rejected interrupt logs `Claude refused the interrupt; ending its process` and terminates the Query. Deadline path terminates and returns `{ execution: "unknown", cleanup: "unknown" }`. | A termination attempt is not verified cleanup. Only this dedicated session process is targeted today. |
| CL4 — current protocol failure | SDK stream ends without a result. | claude / protocol: `Claude SDK stream ended without a result`. Other process failures preserve the cause message and optional stderr detail. | Fail the affected turn; preserve the upstream session binding for supported resume. |
| CL5 — proposed-sharing risk | Reuse one Query as if it were two independent conversations, or share its bound tool/elicitation callbacks. | Existing same-entry overlap gives `Claude turn already active`. Bypassing that guard has **no dedicated cross-session error**: input, transcript ownership, and callbacks still belong to one Query/session. | A long-lived multi-turn Query cannot implement independent concurrent chats. Keep separate CLI executions unless upstream supplies a different supported API. |
| CL6 — current credential guard | Machine login is forbidden and no selected credential exists, or its placeholder expired. | claude / configuration: `This person's Claude session has no selected credentials` or `Claude credential placeholder expired`. An unavailable selection uses its supplied reason. | Fail that owner's launch; do not borrow another person's login to make it work. |

The MCP merge rejects a duplicate name with `Duplicate Claude MCP server <name>`. A stdio server with an explicit `cwd` is filtered as unsupported by the shared projection, rather than silently dropping `cwd`. Query MCP, plugins, and permission callbacks belong to the Query launch; ordinary home/project settings may still be shared external files. This audit did not reproduce one Query changing another's in-memory config. [Credentials](../../packages/harness/src/transports/claude-sdk/credentials.ts), [error translation](../../packages/harness/src/transports/claude-sdk/errors.ts).

## Cursor SDK

Current owner: a workspace-local `CursorHostRegistry` shares workers by binding/home; each worker stores Agents and runs by session ID. [Registry](../../packages/harness/src/transports/cursor-sdk/host-registry.ts), [worker](../../packages/harness/src/transports/cursor-sdk/host.ts), [configure](../../packages/harness/src/transports/cursor-sdk/index.ts), [cancel](../../packages/harness/src/transports/cursor-sdk/cancel.ts).

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| CU1 — current guard | A launch-affecting config change reaches a busy entry. | `{ state: "refused", reason: "Cursor turn active" }`. Runtime snapshot application returns `runtime_config_refused` / 409. | Current turn remains on the old launch. Retry the configuration after it ends; do not report that it already applied. |
| CU2 — current shared failure | Worker does not answer a `cancel` or `close` command before its deadline. | Originating command: `Cursor cancel exceeded its deadline` or `Cursor close exceeded its deadline`. Retirement rejects sibling pending calls with cursor / worker: `Cursor SDK host retired`. | The entire compatible worker is retired, not only the requested Agent. Later acquisition replaces the failed worker; sessions resume their Agent IDs through the lifecycle path. |
| CU3 — current stop uncertainty | Worker acknowledges cancel but the tracked run does not end by the deadline. | Recovery code `cancellation_timeout`; message `Cursor stop: Cursor cancelled the run, and it had not ended by the stop's deadline`. | This branch does **not** itself invoke the no-reply worker retirement in CU2. Execution and cleanup remain unknown. |
| CU4 — current timeout/crash | A streamed run has no activity for its countdown, or worker transport exits/fails. | `Cursor run exceeded its inactivity deadline` (default countdown 600,000 ms) triggers a cancel attempt. Worker channel failure gives `Cursor SDK host exit failed`, `... stdout failed`, or the corresponding channel reason. | An inactivity timeout first targets the run; an unresponsive cancellation can escalate to CU2. A worker failure affects its pending sessions. |
| CU5 — current mutable scope; interference unverified | Idle entry changes plugins/config while a sibling uses the same home. `configureEntry()` recomposes using `path.basename(entry.host.home)` and only acquires a different worker when `host.binding` changes. | **No home-generation conflict error exists.** Files in the shared `.cursor` home can change. Whether an existing Agent reloads a specific plugin/settings file is not established here. | Initial home keys include plugin instance IDs, but that does not prove immutable live generations. Characterize two-Agent active/idle updates before widening sharing. |
| CU6 — current credential/concurrency guards | No selected or permitted owner API key, unavailable selection, or overlapping same-session run. | cursor / configuration: `Cursor SDK requires an API key` or `Cursor account unavailable: <reason>`. Adapter overlap: `Cursor turn already active`; worker overlap: `Cursor run already active`. | Credentials and run state are per owner/session even though the worker is shared. Loosening those identities would have no guaranteed cross-owner error. |

Per-Agent MCP is supplied at Agent creation and nonempty run updates. Native plugin discovery is mediated by home/settings sources. There is no established arbitrary per-Agent native plugin-root isolation API in this audit. [Profile key/composition](../../packages/harness/src/profiles/cursor/index.ts), [credentials](../../packages/harness/src/transports/cursor-sdk/credentials.ts), [error translation](../../packages/harness/src/transports/cursor-sdk/errors.ts).

## OpenCode2 embedded V2 SDK

These cases concern the current beta-19271 embedded V2 integration, verified through the harness import and commit history linked in the [architecture assessment](2026-10-03-claxedo-session-execution.md). The transport ID and exact errors retain `opencode`/`OpenCode`; they are not evidence of an old V1 integration.

Current owner: one engine per workspace transport; account state is engine-wide, MCP/skill launch documents and tool reloads are directory-scoped, and sessions remain individually addressed. [Transport](../../packages/harness/src/transports/opencode-sdk/transport.ts), [launch policy](../../packages/harness/src/transports/opencode-sdk/launch-policy.ts), [tool port](../../packages/harness/src/transports/opencode-sdk/tool-port.ts).

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| OC1 — current guard | Opening/probing another selected-account configuration while incompatible entries already exist. | opencode / configuration: `OpenCode sessions require one selected account; different selected accounts need separate engines`. | It refuses the incompatible operation instead of creating a private account context in the same engine. |
| OC2 — current guard | A different `accountOwner` tries to use an engine already bound to an owner. | `OpenCodeOwnerMismatchError`, code `owner`: `OpenCode engine credentials belong to another session owner`. | Refuses the other owner. This is a real current limit on sharing, not evidence that instances would provide authorization isolation. |
| OC3 — current shared scope | `configureBound()` changes credentials/provider definitions or a projection. | **No isolation error:** credentials/provider definitions update all entries in the engine; projection updates every entry in the same directory. `applyProjection()` writes the directory document and reloads MCP/skills. | This matches the current broad configuration owner. A proposed independent per-session config feature would break its intended isolation unless these maps, writes, and rollbacks change together. |
| OC4 — current tool guard | Two session tool registrations in the same directory use the same name but different description/input/output schemas. | Plain `Error`: `Conflicting OpenCode Session tool definition for <name>`. Calling an unregistered tool gives `Tool <name> is not registered for Session <id>`. | Directory tool aggregation blocks conflicting definitions. Existing context filtering/execution checks still limit who can call registered tools; a unified schema cache is not itself proof of cross-session execution. |
| OC5 — current stop uncertainty | Interrupt exceeds the deadline, has an uncorrelated terminal event, or rejects. | Deadline returns `{ execution: "running", cleanup: "unknown" }`; uncorrelated terminal returns `unknown`. Rejection returns recovery code `provider_unreachable`, `OpenCode refused the interrupt: <cause>`. Internal `OpenCode interrupt deadline expired` is caught, not emitted as the deadline result's message. | The shared engine is not killed to make one stop appear successful. Runtime recovery owns the unresolved state. |
| OC6 — current guards | Close an active entry, request a session permission mode, or use machine-environment provider credentials for a non-owner. | `OpenCode session has an active turn`; `OpenCode does not expose a session permission mode`; code `credential_unavailable`: `OpenCode provider <id> reads its key from the machine environment, which only the machine owner's sessions may use`. | Preserve the active session or refuse the unsupported operation. These are intentional constraints. |
| OC7 — proposed-instance risk | Add an SDK instance selector but leave config documents, tool definition maps, reload callbacks, creation metadata, and recovery initialization at current scope. | Potential last-writer configuration or wrong reload owner has **no dedicated instance-mismatch error**. OC4 may catch a schema conflict, but does not make the other maps instance-scoped. | Full instance-aware configuration migration is required if that feature is chosen. More retained instances are not demonstrated memory savings. |
| OC8 — current rollback failure | Opening a session fails and restoring providers/config/tools/session state also fails. | opencode / session: `OpenCode open failed and rollback failed: <failure list>`. | Report the combined failure, rather than pretending only the new session was touched. Engine-wide state restoration affects the shared owner. |

An in-process engine exception and a fatal daemon-process failure are distinct: there is no portable fixed error for the latter, and all local runtimes in that daemon lose their host if it crashes. [Cancel](../../packages/harness/src/transports/opencode-sdk/cancel.ts), [errors](../../packages/harness/src/transports/opencode-sdk/errors.ts), [credentials](../../packages/harness/src/transports/opencode-sdk/credentials.ts), [config](../../packages/harness/src/transports/opencode-sdk/session-config.ts).

## Pi RPC

Current owner: one Pi RPC process, session stream translator, and active session per Claxedo entry. “Remote client viewing a cloud runtime” is **not** the same as `StartInput.locality === "remote"`; locality concerns where the harness executes relative to its runtime. `Index`, `stream`, `launch/resume`.

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| PI1 — current guard | A changed launch projection/credential reaches a busy stream. | `{ state: "refused", reason: "Cannot reconfigure Pi during an active turn" }`; runtime snapshot 409 `runtime_config_refused`. | After eligibility, the transport retires and resumes the same upstream session with the new profile. |
| PI2 — current MCP guards | Duplicate MCP names; SSE reaches direct mapper; stdio requested for a remote-locality harness. | pi / configuration: `Duplicate Pi MCP server <name>`; `Pi cannot load SSE MCP server <name>`; `Pi cannot run stdio MCP server <name> for a remote session`. | Correct the declared server/scope. Common projection can filter unsupported SSE/name forms earlier. Cloud placement by itself is not this remote-locality rejection. |
| PI3 — current MCP startup/registration failures | Injected extension never consumes the handoff, or an individual `registerMcpServer()` call throws. | Unconsumed handoff: pi / protocol, `Pi did not load Claxedo's MCP extension, so the session's MCP servers were not handed over`; launch is retired. Per-server registration exception: UI error notice starts `Claxedo could not add these MCP servers to Pi:` followed by names/causes. | Handoff consumption and successful registration are different checks. The per-server extension notice does not itself abort the whole launch. |
| PI4 — current stop uncertainty | `clear_queue` or `abort` RPC misses deadline, or process becomes unreachable. | `Pi clear_queue timed out` / `Pi abort timed out`, transport code `timeout`; cancel result code `cancellation_timeout`. Other failures map to `provider_unreachable`. | Returns execution unknown and cleanup owned on stop failure. Successful RPCs still return unknown until `agent_settled` was observed. |
| PI5 — current resume guard | A session with previous turns has no matching saved JSONL, or resume returns a different ID. | pi / session: `Pi session <id> has had turns, but its session file is gone from <directory>`; or `Pi resumed a different session`. | Fail without replacing a worked conversation. An empty session with no turns has a separate supported ID-resume path. |
| PI6 — proposed-sharing risk | Point two current `PiSessionStream`s at one RPC process and treat it as concurrent conversations. | Same stream overlap gives `Pi turn already active`. Two independent translators on one event feed have **no guaranteed cross-session error**: each translator was constructed with its own Claxedo session ID, while the peer holds one active session. | Frames/dialogs could be stamped into the wrong conversation. RPC switching is sequential reuse, not multiplexing. |
| PI7 — current process/config guards | Process exits; unsupported permission mode is requested; invalid model key is supplied. | `Pi process exited (<signal-or-code>): <optional stderr>`; `Pi has no permission modes`; `Pi requires a provider/model key`. | Process loss is entry-scoped today. Embedded SDK sharing would make extension crashes/event-loop stalls a new worker-level risk, with no guaranteed universal error string. |

`BUILT_IN_MCP.pi = false` is a current declaration defect, but no runtime failure message follows from the flag alone in the inspected consumers. Actual MCP works through the injected extension. `MCP handoff`, `RPC`, `stop result`, `config`, [registry](../../packages/harness/src/registry/table.ts).

## Custom ACP

Current owner: one peer/connection per Claxedo session. Protocol session IDs permit addressing; actual multiplexing and independent execution depend on the peer. [Startup/resume](../../packages/harness/src/transports/acp/startup.ts), [lifecycle](../../packages/harness/src/transports/acp/lifecycle.ts), [configure](../../packages/harness/src/transports/acp/index.ts), [cancellation](../../packages/harness/src/transports/acp/cancellation.ts).

| ID and classification | Exact trigger | Error or observable result | Scope and recovery |
| --- | --- | --- | --- |
| AC1 — current config branches | Launch change while busy; configuration during an uncertain outcome; restart while native subagents remain live. | Busy: `deferred / after-active-turns`. Uncertain: `refused`, `ACP session outcome is uncertain`. Live children: acp / configuration, `Claxedo cannot replace the ACP process while subagents are running. Wait for them to finish or explicitly stop the session before changing launch settings.` | Preserve the current execution/peer until its state permits restart; runtime refusal mapping differs from thrown failure as explained above. |
| AC2 — current cancel branches | Peer acknowledges cancellation but its prompt remains pending through deadline; or cancellation itself fails. | `ACP session/cancel timed out` (or `was abandoned`). Acknowledged-but-running returns `cancellation_timeout` and execution running. Other cancel failure marks uncertain and fails queues with `ACP cancel failed; prompt outcome is uncertain`, while cancellation result reports `provider_unreachable`. | Closing a remote connection does not establish that remote execution stopped. |
| AC3 — current uncertainty guard | Peer prompt becomes inactive beyond the configured countdown, then another prompt is attempted. | Initial acp / timeout: `ACP prompt outcome is uncertain`; subsequent transport send: `ACP session outcome is uncertain`. | Reconcile rather than silently launching replacement work. |
| AC4 — current resume guards | Peer declares neither resume nor load; or requested prior conversation is no longer available. | `ACP agent declares neither load nor resume`; `ACP agent no longer has session <id>; it is not replaced`. | Refuse unsupported or missing-session recovery. Do not downgrade to new-session creation. |
| AC5 — current capability reporting | MCP transport/cwd/locality unsupported by peer projection, or portable plugin roots sent to a peer without the supported extension. | MCP warning `acp.mcp.not-applied`: `MCP servers not applied: <name> (<reason>)`. Plugin roots have `unsupported-by-harness`; `ACP_PLUGINS_NOT_APPLIED` is `this ACP agent accepts MCP servers only`. | These are capability/not-applied results, not universal hard launch errors. Local `@agentclientprotocol/claude-agent-acp` >= 0.10.9 has the inspected plugin-options extension. |
| AC6 — current connection/ownership guards | Process transport and locality disagree, or owned process retirement cannot be verified. | `ACP connection kind does not match locality`; retirement uses acp / `ownership` with the underlying retirement message. | Unverified retirement blocks lifecycle progress; retrying must not create competing owned execution. |
| AC7 — proposed-sharing risk | Reuse current entry-bound peer callbacks/close lifecycle for multiple independent sessions, or pool a peer that serializes internally. | **No guaranteed standard error.** Callback misrouting can corrupt session ownership; close can disconnect all occupants. A peer may serialize, reject, or start one heavy child per session. | Require peer/version-specific concurrent flows, callback routing, release semantics, and child-tree measurement before pooling. |

ACP configuration readback can also throw `ACP agent kept <kind> <kept> instead of <requested>` rather than claiming a setting took effect. [Sync](../../packages/harness/src/transports/acp/sync.ts), [MCP projection](../../packages/harness/src/transports/acp/projection.ts), [plugin extension](../../packages/harness/src/transports/acp/extensions/claude-options.ts), [connection](../../packages/harness/src/transports/acp/connection.ts).

## Shared runtime and deployment boundaries

| ID | Trigger | Exact contract or result | Consequence |
| --- | --- | --- | --- |
| SH1 | Harness stream ends with no canonical terminal event, outside the cancellation-special case. | provider / `missing_terminal_event`: `Harness stream ended without a terminal event`. | Runtime must not synthesize success. [Turn runner](../../packages/session-core/src/host/turn-runner.ts) |
| SH2 | Previous-generation launch cannot be reconciled before a mutation. | HTTP 503, `workspace_launch_unreconciled`: `Launches a previous owner of this workspace left are unresolved`. | Reads and mutation admission have different behavior; cleanup certainty gates new execution. [Durable state](../../packages/workspace-runtime/src/workspace/durable-state.ts) |
| SH3 | Remote session authority is unavailable, has no endpoint, or yields unreadable/failed transport. | HTTP-oriented denial 503, `session_authority_unavailable`. | No guessed permission or owner login. Local owner access has its separately admitted path. `Remote policy` |
| SH4 | Harness projection does not support a requested MCP form. | `notApplied` item with `reason: "unsupported-by-harness"`; filter removes it from the applied set. | Codex/Pi SSE, Pi invalid server-name form, and Claude/ACP stdio `cwd` have explicit filters. Do not report the direct transport guard as the only user path. [MCP support](../../packages/harness/src/contract/mcp-support.ts) |
| SH5 | A workspace is disposed while a hypothetical process is shared across independent workspace owners. | No cross-workspace pool contract exists today. Current disposal reaches transport/process retirement. | Reusing that process without a new lifetime owner could stop another workspace with ordinary process-loss errors or a disconnect. This is a proposal constraint, not a demonstrated current cross-workspace bug. |
| SH6 | Account, RAT, HTT, RHT, or session/turn lease is revoked or expires. | The relevant boundary refuses/closes/declines renewal; no universal harness error applies. | Relay delivery, host serving, and turn authority must remain separate from worker compatibility. Reconnect is not permission to bypass the revoked boundary. |

## Required experiments before turning risks into bug claims

1. **Codex profile collision (CX8):** use two real harness sessions with distinct requested launch projections that resolve to the same current home; record the exact files read/written and effective MCP/plugin/provider state before and after changing one session. Hold the sibling active, then repeat idle. If the supported public configuration flow always changes both intentionally, record that result instead of inventing an independent-session defect.
2. **Cursor live home update (CU5):** run two Agents in one worker, change one entry's projection through the owning config flow, and observe each Agent's effective tools/settings during and after the update. Test both plugin addition and removal. Establish intended workspace-wide versus session-specific behavior first.
3. **OpenCode2 scope (OC3/OC7):** create two sessions in one directory; verify the current engine-account refusal and shared projection behavior. An instance prototype must prove separate schemas/config, deterministic recovery initialization, rollback, and teardown before replacing that owner.
4. **Correlated process loss (CX7/CU2/AC7):** with two active sessions, force a fixture peer's stop timeout or owned worker exit. Verify every affected session's failure/recovery state, transcript, usage, and pending requests, plus an unaffected session in another worker/workspace.
5. **Resume and cancellation (all):** use the real supported harness versions and fake only external model/peer boundaries. Test absent saved sessions, withheld startup replies, acknowledged-but-running cancel, background work, and stale completion after replacement. Record actual messages and state transitions, including branches where the correct result is uncertainty rather than an exception.

Until those experiments run, the source-backed error branches above are known; the proposed-sharing and file-interference rows remain explicitly qualified. The plan preserves current guards and makes these experiments prerequisites for expanding sharing.
