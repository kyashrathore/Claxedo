# ACP support review — 2026-09-20

This review compares Claxedo's current adapter with the current ACP v1 documentation and updates. ACP v2 is still a draft. The implementation changes below are local and uncommitted.

## Changes implemented

1. **Concurrent sessions:** removed the process-wide prompt queue. Each ACP session admits one active prompt, while different sessions can run concurrently. Permission callbacks, progress listeners, and quiet countdowns remain keyed by agent session ID. A shared process failure still affects its sessions.
2. **Model changes:** session configuration uses `session/set_config_option`; it no longer changes a connection-wide model and restarts processes. Unsupported model changes fail instead of pretending to succeed. OpenClaw controls its model because its ACP bridge exposes no model selector.
3. **Slash commands:** agent `available_commands_update` notifications now become canonical session metadata. Both stores preserve the list, including an empty replacement list. The composer shows the current session's commands and argument hints. Invocation uses the existing `/command arguments` prompt path. Early notifications during `session/new` are retained until the local binding exists. Commands are session metadata, not assistant messages. The older `commands` capability also gates native summarize operations, so it remains false for ACP; it does not gate this negotiated command list.
4. **Fork discovery:** negotiated support survives idle disposal. A cold capability read probes the agent without consuming the source session's restoration. Fork restores its source session when necessary; unsupported agents still fail.
5. **Restoration ownership:** each process tracks which agent sessions it has actually created, resumed, loaded, or forked. Restoring one session no longer causes its sibling to skip resume on the same process.
6. **Missing agent history:** unsupported resume/load still fails. Only a structured `-32002` error identifying the exact upstream session, received from resume/load, triggers a fresh session. Claxedo seeds bounded saved conversation context and persists a visible “Cache busted — agent context rebuilt from saved conversation” marker. The pending context survives failed delivery. Authentication, connection, configuration, and prompt errors do not trigger replacement or prompt retries.

## Explanations and remaining limitations

### Recovery

A browser disconnection, an ACP socket disconnection, and an agent process crash are different events. A surviving remote agent may still be running; a dead stdio process is not. Reconnecting a transport does not tell us whether a prompt whose response was lost already performed work. Even the v2 draft describes uncertain submission outcomes and possible duplicate submissions on retry. Automatic prompt resending is therefore not a general recovery mechanism.

Session rejections and cancellation no longer dispose a shared process. Unacknowledged cancellation preserves the original turn, event writer, and process lease; the UI shows `uncertain_execution`, and late output continues into the saved transcript. Lost transports still need explicit remote reconnection and agent-state reconciliation; no prompt is automatically resubmitted.

### Resume support and missing storage

V1 agents may omit both resume and load capabilities. Older/minimal/stateless implementations are possible. Claxedo fails when neither is advertised. The v2 draft's stronger requirements do not retroactively apply to a v1 connection.

A missing backing session can follow storage deletion, expiration, a changed profile/store, or loss of an in-memory session. Those are possible causes, not diagnoses of this machine. Rebuilt transcript context restores conversation knowledge, not hidden provider state or pending tool execution. The shared renderer bounds restored text to 60,000 characters.

### Questions, permissions, and subagents

ACP permissions use the existing permission owner and dock. ACP form and URL requests are normalized inside the SDK into ordinary `AgentQuestion` rows using the same shared MCP-question projection as Codex. Forms use a custom JSON answer; the adapter retains the schema and validates before settlement. The client has no ACP form renderer, browser regex worker, special answer cache, or connection-operation API. Invalid answers retain the ordinary question and draft. Dismiss maps to decline, while interruption/cancellation remains adapter-owned.

Question history survives reload, but a live JSON-RPC resolver does not survive process loss. Disconnected questions are cancelled; saved rows never manufacture a resolver. Request-scoped questions must correlate with an actual outstanding session-owned RPC. Initialization and session creation share the reserved `AgentSessionStartBinding`. Unowned capability probes cannot present questions. Pattern validation runs only in the bounded SDK worker.

Negotiated native subagent lifecycle notifications now enter canonical child admission and separate transcript stores. Nested children, output after parent completion, replay deduplication, and disconnected children have focused wire coverage. Capability reads report negotiated child visibility, while unsupported targeted child controls remain disabled. Tool names never infer lineage.

### Startup questions before a session is bound

The creation route now persists an `AgentSessionStartBinding` with local session ID, workspace, directory, connection, and registration operation before invoking the adapter. This record contains no upstream session ID and does not create an executable or visible session. `process.ts` correlates the exact outgoing `initialize` or `session/new` JSON-RPC request with that owner. A human question suspends the request inactivity countdown; cancellation, rejection, and process loss retire its resolver without disposing sibling sessions.

The public question routes authorize the verified creation reservation and call dedicated startup answer methods. Ordinary answer methods still require complete execution bindings. Managed event delivery checks the same reservation per startup interaction, without populating the normal session-grant cache. Read-only start-status authorization also admits the exact creator after reservation failure/compensation; it never authorizes stale answers. Duplicate creation while the first operation is active is refused, including the interval after provider binding but before configuration/registration finishes.

The draft UI persists the owner reference, reads `/session-start/:id`, and uses the existing question dock/cache. Reload holds the canonical workspace event scope. A recovered successful creation navigates to the created session without replaying the original prompt. A dead creation with no persisted session becomes an explicit interrupted failure; an existing session whose registration outcome is unresolved is reported separately and requires exact registration reconciliation.

Verification includes the real ACP JSON-RPC implementation behind public workspace create/question/status routes, concurrent startup isolation, unauthorized/mismatched answers, durable failure, post-bind duplicate creation, SQLite reopen before provider binding, managed SSE creator isolation/revocation, and mounted draft reload tests. These deterministic integrations are supplemented by the final packaged-desktop native-dock flow below. External-provider startup elicitation remains unverified; the desktop test uses a real stdio fixture.

Standalone connection authentication/logout is not exposed in the application. Credentials come from trusted configuration or the agent's own setup flow. Authentication-required is reported as a failure. The separate workspace connection lifecycle, database tables, routes, events and settings controls were removed; generic SDK connection-operation contracts would be required before adding standalone interactive authentication correctly.

### Instructions

Claxedo currently sends workspace/session instructions as text before the user's prompt. An `audience: assistant` annotation does not give that text system/developer priority. The external agent owns its own system prompt. A stronger instruction API needs explicit agent support.

### Remote transport and attachments

"Remote connection" means an HTTP/WebSocket ACP endpoint instead of a subprocess stdio connection. It does not mean a remote Claxedo workspace, and an endpoint may be on localhost. Filesystem reachability is now explicit through `connection.sharedFilesystem`, defaulting to false for every transport. Otherwise the adapter sends negotiated inline content or rejects an unsupported attachment before submission.

### Permission durability

There is no timeout while awaiting the user's permission answer. The request holds a lease on the prompt inactivity countdown. Once answered, the countdown resumes if the agent goes silent.

Remembered grants and pending UI state can be durable, but a dead process's JSON-RPC resolver is not. The agent must reissue or restore an interrupted operation. The new optional ACP tool `name` field is informational and does not authorize broader remembered permissions.

### Goals, readiness, setup

Goal support is the negotiated `_meta.goal` extension used by this adapter, not a universally supported ACP core control. Readiness is Claxedo's status; an enabled descriptor is not proof of a successful handshake. ACP provides a standardized agent registry, while Claxedo's descriptor CRUD and secret boundary are its own operator configuration API.

## Current acceptance and support boundaries

The required implementation work is bounded by the twelve reviewed concerns. Supporting ACP does not require claiming every optional capability or adopting the draft v2 lifecycle.

| Requirement | Current evidence | Remaining work |
| --- | --- | --- |
| Independent sessions, nondisruptive model changes, slash commands, negotiated fork | Runtime/wire regressions; real Codex session and command UI acceptance | Keep provider capability gates; no global prompt queue or process restart for a model change |
| Durable transcripts and explicit recovery | Exact SQLite reopen with real Codex/Claude; public subprocess tests cover resume, missing history, auth failure, unsupported resume, pending approval and late cancellation output | No promise of recovering output an agent never delivered; no automatic replay after an uncertain turn |
| Questions during initialization and creation | Real stdio public `/question` tests cover creator ownership, typed validation, rejection, late answers and successful creation | Final packaged native-dock flow passes; standalone in-app authentication is not exposed |
| Human approval and bounded form validation | Existing permission path and SDK worker tests; ordinary question draft and error behavior | Final packaged malformed/schema rejection and corrected-answer flow passes |
| Truthful readiness and controls | Configured/ready/failure generation observations and focused UI checks; no separate Connect operation panel | Cold draft, successful empty options, and existing-session omission pass in the final package |
| Remote content and loss | Actual loopback WebSocket public routes prove inline image delivery/refusal, received output persistence, explicit resume without prompt replay | Internet/TLS/proxy deployment testing is deployment-specific; ACP does not establish exactly-once remote tool execution |
| Provider interoperability | Real subscription-backed Codex Luna/low and Claude Sonnet/low pass; OpenClaw bridge initializes with model selection unsupported | OpenClaw inference remains unverified because its existing gateway advertises no available model; this optional provider does not block Codex/Claude acceptance |
| Repeatability | Repository regression files and opt-in real-provider runners; full product closure checks and architecture ratchets | SDK/contract/WR/client regressions and final native-dock package pass; aggregate app architecture debt and publish-doc mismatch remain separately documented |

Future support work should be driven by a concrete provider or user flow: registry installation UX, additional configuration controls, and optional lifecycle methods can be added when negotiated. Universal revert, privileged system-instruction injection, remote exactly-once execution, and unadvertised child controls are not guarantees supplied by ACP.

## Current ACP documentation

The [updates page](https://agentclientprotocol.com/updates) and linked protocol documentation distinguish these features:

| Surface | Current standard status | Claxedo implication |
| --- | --- | --- |
| Tool names | Stable optional field | Informational identity; not permission scope |
| Elicitation | Stable v1 | Session and reserved-start form/URL requests use ordinary questions; schemas remain in the adapter. Standalone connection operations are not exposed. |
| Session config and model config category | Stable | Use agent-advertised controls; no invented selector |
| Boolean config options | Stable, client opt-in | Requires explicit negotiated support |
| Request cancellation | Stable | Different from whole-session cancellation |
| Message IDs | Stable optional field | Agent IDs can identify message boundaries |
| Usage updates | Stable | Context/cost updates differ from billed turn token usage |
| Resume, close, delete, list, session info | Stable, with v1 capability rules | Do not assume an arbitrary agent implements every optional surface |
| Additional workspace roots | Stable | Separate from primary `cwd` |
| Logout | Stable | Authentication lifecycle separate from process restart |
| Registry | Standardized | Can support discovery and installation UX |
| Fork | RFD/negotiated agent capability | Invoke only when advertised |
| HTTP/WebSocket transport | Proposal remains draft | Existing transports do not imply standardized replay/reconnect |
| ACP v2 | Draft | Breaking lifecycle changes; not silently applicable to v1 |
| Goal | Extension in this implementation | Requires explicit negotiation |
