## 1. Baseline violation → fix map

For each of the 20 rule entries in `a11y-baseline.json`, grouped by surface. "Prunable" = will fixing
this let the rule id be removed from that surface's baseline array (per `a11y-sweep.spec.ts`'s
shrink-only contract).

### 1.1 `home` — `color-contrast`, `landmark-one-main`, `page-has-heading-one`, `region`

The `home` surface is `RailWorkbenchCanvas`'s zero-project empty state
(`src/claxedo-ui/rail/rail-workbench-canvas.tsx:41-53`) rendered inside
`AppShellLayout`'s root (`src/shell/app-shell-layout.tsx:272-273`, `data-claxedo`).

- **`landmark-one-main` + `region`** — root cause is structural, not a widget: nothing in the app
  shell declares `role="main"`/`<main>` anywhere. Grepped every `<main`/`role="main"` in
  `src/**` — the only hits are inside dialog-matrix test harness pages and the marketplace/error
  pages, none of which wrap the live app shell. `app-shell-layout.tsx:272-322` renders
  `RailSidebarShell` (the sidebar/rail — candidate for `<nav>` or `role="navigation"`) and
  `RailWorkbenchShell` (`src/claxedo-ui/rail/rail-workbench-shell.tsx:58-118`, the pane column —
  candidate for `<main>`) as sibling `<div>`s with no landmark roles at all. **Fix**: wrap
  `RailWorkbenchShell`'s outer `<div>` (`rail-workbench-shell.tsx:59`) in `role="main"` (or promote
  the element itself to `<main>`) with an `aria-label` (e.g. "Workbench"), and give
  `RailSidebarShell`'s root a `role="navigation"`/`<nav>` + `aria-label` ("Sidebar" or similar). This
  single structural change is the root cause for `landmark-one-main`/`region` on **all three**
  surfaces that list them (`home`, `session-page`, `prompt-input-focused`) — fix once, prune three
  baseline entries. Lands in `src/shell/app-shell-layout.tsx` + `src/claxedo-ui/rail/rail-workbench-shell.tsx`
  + `src/claxedo-ui/rail/rail-sidebar.tsx` (root element).
  **Prunable**: yes, for `home`/`session-page`/`prompt-input-focused` `landmark-one-main` and `region`
  together (6 of the 20 baseline entries collapse to one fix).

- **`page-has-heading-one`** — confirmed by contrast: this rule is **absent** from `session-page`'s
  and `prompt-input-focused`'s baseline entries even though they share the same shell as `home`. The
  reason: `message-timeline.tsx:1488-1495` renders the active session's title as `<h1 data-slot=
  "session-title-child">` once a session with a title exists — so once a turn has settled, an `<h1>`
  exists and the rule stops firing. `home`'s empty state (`rail-workbench-canvas.tsx:44-53`) has no
  session and thus no `<h1>` anywhere. **Fix**: add a visually-present-or-`sr-only` `<h1>` to the
  empty-state fallback (e.g. wrap "No projects yet. Create one to get started." in an `<h1>` styled
  identically to the existing `<span>`, or add a `sr-only` `<h1>` reading "Claxedo" /
  "No projects yet" immediately above it). Lands in `rail-workbench-canvas.tsx:44-53`.
  **Prunable**: yes, for `home` only (the only surface that lists it).

- **`color-contrast`** — computed against the live theme tokens (WCAG relative-luminance formula,
  not measured in-browser — flag for live verification but the math is exact for the token pair):
  `rail-workbench-canvas.tsx:47` renders "No projects yet. Create one to get started." with
  `text-text-weak` on the ambient `bg-background-base`. `packages/ui/src/styles/theme.css:94,165`:
  light mode `--text-weak: #8f8f8f` on `--background-base: #f8f8f8` → **3.04:1**; dark mode
  `theme.css:363,434`: `--text-weak: rgba(255,255,255,0.422)` blended onto `--background-base:
  #101010` → **4.13:1**. WCAG AA requires 4.5:1 for this text size (14px/`text-14-regular`, below the
  18pt/14pt-bold "large text" threshold that would drop the bar to 3:1) — **fails in both themes**.
  **Fix**: bump the empty-state message to `text-text-base` or a token ≥4.5:1, or bump text size to
  qualify for the "large text" 3:1 threshold (unlikely to be the intended fix — the token is wrong,
  not the size). Lands in `rail-workbench-canvas.tsx:47`.
  **Prunable**: only for `home`'s `color-contrast` entry specifically — see §1.2 for why
  `session-page`/`prompt-input-focused`'s `color-contrast` is almost certainly a *different*,
  higher-impact token and needs its own fix before those entries can be pruned.

### 1.2 `session-page` + `prompt-input-focused` — `aria-allowed-attr`, `button-name`, `color-contrast`
    (`landmark-one-main`/`region` covered by §1.1)

These two surfaces share a baseline (same rule ids minus `page-has-heading-one`, per §1.1) because
`prompt-input-focused` is `session-page` plus the composer focused — the message timeline and shell
are still in the DOM either way.

- **`color-contrast`** (session-page + prompt-input-focused) — same luminance-math approach as §1.1,
  and a much higher-traffic hit: `src/components/prompt-input/frame.tsx:212` and `:220` both apply
  `text-v2-text-text-faint` to, respectively, the **actual typed message text** in the contenteditable
  composer and its placeholder. `packages/ui/src/v2/styles/theme.css:32` maps
  `--v2-text-text-faint: var(--v2-grey-600)`; `packages/ui/src/v2/styles/colors.css:10`:
  `--v2-grey-600: #808080`. Backgrounds: `--v2-background-bg-base` = `--v2-grey-50` (`#ffffff`,
  light) or `--v2-grey-1000` (`#242424`, dark) (`v2/styles/theme.css:18,150`; `colors.css:4,14`).
  Computed: light **3.95:1**, dark **3.93:1** — both fail AA's 4.5:1 for the composer's 13px
  (`text-[13px]`) body text. This token (`--v2-text-text-faint`) is also used by
  `radio-v2.css`, `keybind-v2.css`, `inline-input-v2.css`, `file-tree-v2.css` and more, so this is a
  systemic under-contrast token, not a one-off — worth flagging to whoever owns the v2 token set even
  though only the composer instance is in scope for this baseline entry. **Fix**: darken
  `--v2-text-text-faint` (or introduce a separate, higher-contrast token for composer *input* text —
  placeholder text is conventionally allowed lower contrast than typed content, so these two uses at
  `frame.tsx:212` vs `:220` may deserve different tokens). Lands in `packages/ui/src/v2/styles/colors.css`
  (token value) — **outside WP-C1's `src/components/prompt-input/{frame,slash-popover}.tsx` (ARIA
  only) ownership grant**; flag as a cross-package dependency, same shape as §1.4's Dialog fix.
  **Prunable**: yes for both surfaces, once the token (or the two call sites) are fixed — this needs
  live contrast verification of the fixed value before pruning, not just a "looks darker" check.

- **`button-name`** (session-page + prompt-input-focused) — traced by grepping every `<button`/
  `IconButton` in the render tree reachable from a settled session (composer chrome, toolbar,
  message timeline) for a missing accessible name. Confirmed clean: `submit-control.tsx`,
  `toolbar-controls.tsx`, `context-items.tsx`, `image-attachments.tsx`, `agent-harness-selector.tsx`
  (all icon-only controls there carry `aria-label` or have visible text content). **Found**:
  `src/pages/session/message-timeline.tsx:1391-1404` — the "jump to bottom" / resume-scroll button:
  ```tsx
  <button class="pointer-events-auto flex items-center justify-center w-10 h-8 bg-transparent
    border-none cursor-pointer p-0 group" onClick={props.onResumeScroll}>
    <div class="..."><Icon name="arrow-down-to-line" size="small" /></div>
  </button>
  ```
  No `aria-label`, no text content — the only content is a decorative `<Icon>` (which itself sets
  `aria-hidden="true"`, `packages/ui/src/components/icon.tsx:162`). Its visibility is controlled by
  `opacity`/`pointer-events` classes (`message-timeline.tsx:1386-1389`, driven by
  `props.scroll.overflow && props.scroll.jump`), **not** `display:none`/`aria-hidden` — the node stays
  in the DOM and in the accessibility tree at all times, so axe flags it regardless of whether it's
  visually shown. This is the only unlabeled interactive control found in `message-timeline.tsx`
  (the file's other bare `<button>` at line 1451, the parent-session breadcrumb, has visible text
  content `{parentTitle()}` and is fine). **Fix**: add `aria-label={language.t("session.scroll.
  resumeToBottom")}` (or similar new i18n key) to the button at `message-timeline.tsx:1391`. Lands
  in `src/pages/session/message-timeline.tsx` — **not in WP-C1's explicit "Owns" list** (owned by
  WP-B8 per the LLD's `src/pages/**` grant), so this is a genuine cross-WP coordination point, not
  a WP-C1-internal fix; flag to the leader rather than editing silently.
  **Prunable**: yes for both surfaces, pending the live axe re-run confirming no second unlabeled
  button exists elsewhere in the tree (this was a targeted grep of the most-traffic files, not an
  exhaustive one — see §5 for the honest caveat).

- **`aria-allowed-attr`** (session-page + prompt-input-focused) — **not conclusively pinned by static
  analysis**; this needs a live axe run to get the violating node's exact selector. What was
  ruled out, with evidence (checked every explicit `role="..."` in the reachable render tree against
  axe-core 4.12.1's own `axe.js` role table, dumped via `python3` against the bundled
  `node_modules/.bun/axe-core@4.12.1/.../axe-core/axe.js`):
  - `role="textbox"` (`frame.tsx:193-196`, `aria-multiline`/`aria-label`/`aria-disabled`) — all three
    are in `textbox`'s `allowedAttrs` (`aria-multiline`) or globally allowed (`aria-label`,
    `aria-disabled` — both have `global: true` in axe's `ariaAttrs` table). Clean.
  - `role="separator"` (both resize handles, §"Already landed" note above) — `aria-orientation`/
    `aria-valuemin/max/now` are all in `separator`'s `allowedAttrs`; `aria-valuenow` is even
    `requiredAttrs`. Clean.
  - `role="button"` (`navigation-row.tsx:48`, `terminal-surface-navigation.tsx:103`,
    `rail-sidebar.tsx:2017,2275,2402` — `aria-expanded`/`aria-current`/`aria-label`) — all in
    `button`'s `allowedAttrs` (`aria-expanded`, `aria-pressed`) or global (`aria-label`,
    `aria-current` — both `global: true`). Clean.
  - `role="status"`/`role="alert"` (`session-status-stage.tsx:70,82,106`) — only rendered at the
    `pending`/`long`/`failed` timeout stages, which the mock-runtime single-turn scenario doesn't
    reach. Not in the DOM for this baseline's scenario.
  - `role="img"` (`agent-harness-selector.tsx:317-329`, `session-navigation-list.tsx:91`) — the
    former is gated behind `selection().isHarnessMode`, false for the default `opencode` harness the
    sweep uses (per `a11y-sweep.spec.ts`'s HARNESS NOTES); the latter has only `aria-label`/`title`
    (global), clean either way.
  What's genuinely unchecked: every `<button>`/other-role element's aria-* was checked by name against
  axe's role tables, but this was not an exhaustive DOM walk (no live render). **Recommended next
  step for whoever picks this up**: run `bunx playwright test a11y-sweep -g "session page"` once and
  read `results.violations.find(v => v.id === 'aria-allowed-attr').nodes[].target` — the spec already
  computes this (`a11y-sweep.spec.ts:195-201`'s `describeNew` helper prints it on failure; temporarily
  add an unrelated new rule id to `a11y-baseline.json["session-page"]` to force the assertion to
  print the *existing* violations' node targets, then revert). This doc did not run that command
  (read-only scope) but the two most likely candidates (both resize separators) are ruled out with
  concrete evidence above, saving that time.
  **Prunable**: unknown until the live node is found and fixed.

### 1.3 `settings-dialog` — `aria-dialog-name`, `button-name`, `color-contrast`, `label`

`settings-dialog` = `DialogSettings` (`src/components/dialogs/settings.tsx`) opened over a settled
session. Kobalte's `Dialog.Content` calls `createHideOutside` on the background while modal
(`node_modules/.../@kobalte/core/dist/chunk/KRZCLZJ6.js:109-112`), which is why `landmark-one-main`/
`region`/`aria-allowed-attr` from `session-page` do **not** carry over into this surface's baseline —
the background is hidden from the accessibility tree while the dialog is open. `button-name` and
`color-contrast` *do* still appear, meaning they originate from inside the dialog itself, not from
the (now-hidden) background.

- **`aria-dialog-name`** — root cause found and verified against Kobalte's actual source, not
  guessed: `packages/ui/src/components/dialog.tsx`'s `Dialog` component (used by every dialog in the
  app) does **not** declare an `aria-label` prop on `DialogProps` (`dialog.tsx:6-15`) and, more
  importantly, its render function does not spread arbitrary rest props onto `<Kobalte.Content>` —
  it only ever passes `data-slot`, `data-no-header`, `classList`, `onOpenAutoFocus` explicitly
  (`dialog.tsx:27-41`). Kobalte's `DialogContent` sets `role: "dialog"` and
  `aria-labelledby: context.titleId()` where `titleId` is only populated when a `<Kobalte.Title>`
  mounts (`KRZCLZJ6.js:136-165`, `243-244`) — there is no fallback to a directly-supplied
  `aria-label`. Two call sites are affected:
  - `src/components/dialogs/settings.tsx:68` — `<Dialog size="x-large" transition class="flex-1">`
    passes neither `title` nor `aria-label`; the desktop layout never renders a header block at all
    (`<Show when={props.title || props.action}>`, `dialog.tsx:43`), so there is no `Kobalte.Title` and
    no name. The only visible "Settings" text is inside `<div class="hidden ... max-sm:flex">`
    (`settings.tsx:80-90`), `display:none` at desktop viewport widths, so it doesn't rescue the name
    even if it were programmatically associated (it isn't).
  - `src/components/dialogs/select-file.tsx:428-431` (this **is** the `command-palette` surface, see
    §1.4) — passes `aria-label={...}` straight to `<Dialog>`, which the wrapper silently drops per
    the above. The caller already did the right thing; the primitive is the bug.
  **Fix**: give `Dialog` (`packages/ui/src/components/dialog.tsx`) an `aria-label?: string` prop and
  forward it onto `<Kobalte.Content aria-label={local.ariaLabel}>` (only when `title` isn't already
  supplying a name, to avoid two competing name sources). Then: `settings.tsx:68` needs either a
  `title="Settings"` (adds a visible header — larger UI change) or `aria-label="Settings"` (minimal,
  matches the existing mobile-only visible text). This is the highest-leverage single fix in this
  document: one primitive change plus one one-line caller fix resolves `aria-dialog-name` on **both**
  `settings-dialog` and `command-palette` (§1.4). Lands in `packages/ui/src/components/dialog.tsx` —
  **outside WP-C1's LLD "Owns" list** (packages/ui is the shared design-system layer, not named as
  WP-C1 scope) — flag as a cross-package dependency to coordinate before landing, same as §1.2's
  color token.
  **Prunable**: yes for both `settings-dialog` and `command-palette`.

- **`label`** — root cause found and verified against the `Switch` primitive's actual render output:
  `packages/ui/src/components/switch.tsx:10-28` renders `<Kobalte.Input data-slot="switch-input" />`
  (a native `<input type="checkbox">` under Kobalte's Switch) and only renders `<Kobalte.Label>`
  `when={local.children}` (`switch.tsx:15-19`) — i.e. only when the caller passes visible label text
  as children. Every `<Switch>` usage in the default-open "General" settings tab
  (`src/components/settings/general.tsx:205,220,235,407,427,442,551,564` — 8 instances) passes
  `checked`/`onChange` only, **no children**. Each one's row title/description
  (`SettingsRow`, `general.tsx:603-623`) is applied as `aria-labelledby`/`aria-describedby` on a
  wrapping `role="group"` div (`general.tsx:621`) — but ARIA name computation does not propagate an
  ancestor group's `aria-labelledby` down onto a descendant native `<input>`; each switch's own
  accessible name is empty. Confirmed the fix pattern already exists and is unused: `Switch` accepts
  a `hideLabel` prop (`switch.tsx:6,16`) that renders `<Kobalte.Label class="sr-only">` — exactly the
  visually-hidden-label pattern already used correctly by the three `<TextField>` instances lower in
  the same file (`general.tsx:331-345,354-369,377-392`, each with `label={...} hideLabel`). **Fix**:
  add `hideLabel` and thread the row's own title text as children to each of the 8 `<Switch>` calls
  in `general.tsx` (e.g. `<Switch hideLabel checked={...} onChange={...}>{language.t("settings.
  general.row.reasoningSummaries.title")}</Switch>`) — the title strings are already computed as
  `SettingsRow`'s `title` prop one line above each call site, so this is a small, mechanical,
  low-risk fix. A 9th instance exists at `src/components/settings/models.tsx:114` (not on the default
  tab, so not in this baseline entry, but the same bug — worth fixing in the same pass for
  consistency, per AGENTS.md "sweep the pattern" convention). Lands in
  `src/components/settings/general.tsx` (+ optionally `models.tsx`).
  **Prunable**: yes.

- **`button-name`** — not pinned to a specific node by static search of the default "General" tab
  (grepped `general.tsx` for `<button`/`IconButton`: zero hits — the tab uses only `<Select>`,
  `<Switch>`, `<TextField>`, and one text-labeled `<Button>` at `general.tsx:575-584`, all of which
  have accessible names via visible text or the `Kobalte.Value` trigger text). One **plausible,
  timing-dependent** candidate found: the Theme `<Select>` at `general.tsx:305-323` passes no
  `placeholder` prop. `packages/ui/src/components/select.tsx:148-155`'s `Kobalte.Value` render
  function falls back to `local.placeholder || ""` when nothing is selected — an **empty string**,
  not `undefined`. `theme.ids()` (`general.tsx:150`) is populated asynchronously by
  `theme.loadThemes()` in `onMount` (`general.tsx:77-79`); if axe scans before that promise resolves
  and before `theme.themeId()` matches an option, the Select trigger `<button>` (via
  `Kobalte.Trigger as={Button}`, ultimately a native `<button>` per `packages/ui/src/components/
  button.tsx`) would have no icon (chevron is conditional), no placeholder text, and no `aria-label` —
  a genuinely empty accessible name. The Language `<Select>` directly above it
  (`general.tsx:179-193`) is not at similar risk since `language.locales` (`general.tsx:139-144`)
  looks synchronously available. **Fix, low-risk regardless of whether this is the exact node**: add
  an explicit `placeholder` (e.g. `language.t("settings.general.row.theme.title")` or "Loading
  theme…") to the Theme `<Select>` at `general.tsx:305-323`, matching the defensive pattern that
  should probably apply to every `<Select>` that can render before its `options()`/`current` resolve.
  Lands in `src/components/settings/general.tsx:305-323`.
  **Prunable**: only after live confirmation this is the actual node — flag as unverified.

- **`color-contrast`** — no in-dialog candidate found via source reading beyond the same `text-weak`/
  `text-weaker` family already implicated in §1.1/§1.2 (used throughout `general.tsx` for row
  descriptions, e.g. `text-12-regular text-text-weak` at `general.tsx:36x` region). Given `--text-
  weak` was independently computed to fail AA in §1.1 (3.04:1 light / 4.13:1 dark) and is used
  pervasively for description/secondary text across the whole settings surface, the most likely
  candidate is the same token family rather than a dialog-specific color. Treat as covered by the
  same `--text-weak`/`--v2-text-text-faint` remediation in §1.1/§1.2, not a separate fix, but **do
  not prune this baseline entry until a live scan confirms** which of the two tokens (or a third,
  unfound one) is actually flagged inside the dialog specifically.

- **`color-contrast`** — `select-file.tsx:458` renders file/directory paths with `text-text-weak`

  `--text-weak` is fixed (§1.1), re-run the sweep before assuming this entry is clear — the palette
  might have a second, still-unfound violation independent of the token.
  **Prunable**: likely, pending live re-verification.

## 2. Combobox/listbox ARIA plan — @-mention and slash-command popovers

Traces `src/components/prompt-input/frame.tsx` (the contenteditable "textbox"),
`src/components/prompt-input/slash-popover.tsx` (the popup), and
`src/components/prompt-input/popover-controller.ts` (the active-item/keyboard-nav state that already
exists) against the WAI-ARIA 1.2 "Combobox with List Autocomplete" pattern, attribute by attribute,
cross-checked against axe-core 4.12.1's own role tables (not just the ARIA spec prose) since the LLD's
literal instructions would otherwise introduce a new violation — see the flagged correction below.

**Current state** (verified, zero `aria-expanded`/`aria-controls`/`aria-autocomplete`/
`aria-activedescendant` anywhere in `src/components/prompt-input/*.tsx` via grep):

**⚠ Correction to the LLD's literal wording (LLD lines 448-449).** The LLD says to add
`aria-expanded`/`aria-controls`/`aria-autocomplete`/`aria-activedescendant` onto the *existing*
`role="textbox"` element. Checked against axe-core's own `ariaRoles.textbox.allowedAttrs`
(`['aria-activedescendant', 'aria-autocomplete', 'aria-multiline', 'aria-placeholder', 'aria-
readonly', 'aria-required']`) — **`aria-expanded` and `aria-controls` are not in that list**, and
`role="textbox"` doesn't declare them as allowed anywhere in the ARIA 1.2 spec either. Adding them as
literally instructed would introduce a **new** `aria-allowed-attr` violation while fixing the
`a11y-combobox` finding — a regression trade, not a fix. The correct target role, confirmed against
axe's `combobox` role table (`requiredAttrs: ['aria-expanded', 'aria-controls']`, `allowedAttrs:
['aria-owns', 'aria-autocomplete', 'aria-readonly', 'aria-required', 'aria-activedescendant',
'aria-orientation']`), is **`role="combobox"`**, not `role="textbox"`. This is also the semantically
correct WAI-ARIA APG pattern for this exact widget (an editable text field that controls a popup
listbox). Trade-off to record in the WP-C1 report: `role="combobox"` does **not** list
`aria-multiline` as an allowed attribute (the ARIA "editable combobox" pattern assumes a single-line
input; there's no first-class multi-line-textarea-that's-also-a-combobox role in ARIA 1.2). Since the
composer is genuinely multi-line, the practical options are (a) drop `aria-multiline` when switching
to `combobox` and accept the minor semantic loss, or (b) toggle the role dynamically (`"combobox"`
only while a popover is open, `"textbox"` otherwise) to keep `aria-multiline` most of the time at the
cost of the role changing under the user. Recommend (a): keep `role="combobox"` permanently (the field
can always trigger a popup by typing `@`/`/`), toggle only `aria-expanded`/`aria-controls`/
`aria-activedescendant` presence with popover state. Simpler, no role churn, and `aria-multiline` was
only ever informative for AT, not required for the field to function.

## 3. NavigationRow native-`<button>` migration risk list

Traces `src/claxedo-ui/navigation-islands/navigation-row.tsx` (WP-B3's shared row primitive,
deliberately left as `role="button"` div — see its own doc comment at `navigation-row.tsx:11-19`
"ARIA semantics polish ... is deferred to WP-C1") and the two consumers
(`session-navigation-list.tsx`, `terminal-surface-navigation.tsx`), plus the three structurally
identical `role="button"` disclosure spans in `rail-sidebar.tsx` (not built on `NavigationRow`, but
the same pattern, same appendix finding category — "should be swept").

**Current shape**: `navigation-row.tsx:47-49` — `<div role="button" tabIndex={0} onClick={activate}
onKeyDown={/* Enter/Space */} ref={(el) => el.setAttribute("draggable", "true")}>`. Consumers add
`data-active`/`classList` for the active-row highlight but **no `aria-current`/`aria-selected`** —
confirmed via grep of both `session-navigation-list.tsx` and `terminal-surface-navigation.tsx`, only
`data-active` (a CSS hook) marks the active row today, exactly the appendix's finding.

**What breaks if `role="button"` div → native `<button>` is done naively:**

1. **`navigation-row.vitest.tsx:61`** — `expect(row.getAttribute("role")).toBe("button")`. A native
   `<button>` has an *implicit* role, not an explicit `role` DOM attribute — `getAttribute("role")`
   returns `null` on a real `<button>`. This assertion must change to either drop the check (implicit
   role is sufficient and is what axe/AT actually read) or switch to an accessibility-tree-aware
   query (`@testing-library`'s `getByRole("button")` rather than `getAttribute`). **Must be updated in
   the same change**, not after — it will fail immediately post-migration otherwise.
2. **`e2e/playwright/core-sidebar-tree.spec.ts:481`** — `header.locator('[role="button"]
   [aria-label*="project"]')` and **`core-sidebar-tree.spec.ts:531`** —
   `header.locator('[role="button"][aria-label*="workspace"]')`. Both are raw CSS attribute selectors
   against the **`rail-sidebar.tsx`** disclosure-caret spans (`rail-sidebar.tsx:2402` and `:2275`
   respectively — not `NavigationRow`, but the same migration category and worth doing in the same
   sweep per the appendix's explicit "this same div-role=button pattern likely recurs ... and should
   be swept" note). `[role="button"]` will **not** match a native `<button>` (no explicit attribute to
   select on). These two locators must change to `header.getByRole("button", { name: /project/ })` /
   `{ name: /workspace/ }` (Playwright's `getByRole` resolves implicit roles correctly, so this is a
   safe, mechanical rewrite) **before or in the same commit as** migrating those three spans.
3. **`nested-interactive` check, not a test but a correctness constraint**: `rail-sidebar.tsx:2006-
   2030` nests the disclosure span inside a `<div data-testid="workspace-header" onClick={...}>`
   (not itself a button/interactive role) — migrating the inner span to a real `<button>` is valid
   HTML nesting (div > button), no double-button-nesting risk there. Verified for all three
   `rail-sidebar.tsx` instances (`:2006-2030`, `:2264-2288` region, `:2390-2409`) — none nest inside
   another `<button>`.
4. **`terminal-surface-navigation.tsx:98-115`** — the "Close terminal" affordance is a `<span
   role="button" tabIndex={0} onClick onKeyDown>` **nested inside** `NavigationRow`'s own
   `role="button"` div (the row itself). If `NavigationRow`'s outer shell becomes a real `<button>`,
   nesting a second interactive `<button>` inside it is **invalid HTML** (buttons cannot contain
   interactive descendants) and most browsers/AT collapse or mis-expose the inner control. This is
   the one location that **cannot** be a simple "div → button" swap on the outer shell without also
   restructuring: either (a) keep the outer row as a non-interactive container with a single
   click/keydown-delegating wrapper and make *both* the row-activate target and the close button real
   `<button>`s as *siblings* rather than parent/child (bigger structural change to `NavigationRow`'s
   API — it currently takes a single `onActivate` + arbitrary `children`, so the row's "clickable
   surface" and its children are structurally nested by design), or (b) leave the close control as a
   `role="button"` span (accepting the semantic-html finding stays open for that one control) while
   fixing the outer shell. Flag this as the one sub-case in this sweep that needs a design decision,
   not a mechanical rename — the appendix's proposed fix ("native `<button>` ... dropping the manual
   Enter/Space handling") doesn't account for this nesting constraint.
5. **`session-navigation-list.tsx`'s archive control is unaffected** — it's already a real `<button>`
   as a sibling inside `NavigationRow`'s children (`session-navigation-list.tsx:105-113`), not nested
   inside another interactive role beyond the (currently div, soon-button) row shell — same nesting
   concern as #4 applies here too once the row shell becomes a button, just not yet flagged by the
   appendix since it wasn't named. Same resolution options as #4.
6. **`aria-current` addition** is additive/safe — no test currently asserts its *absence*, only
   `data-active` presence, so adding `aria-current={props.row.active ? "true" : undefined}` (or
   `aria-selected`, per the WAI-ARIA APG "list of tabs" vs "listbox" distinction — the appendix
   suggests `aria-current`, matching `CompactSwitcher.tsx:270`'s existing `aria-current={item.active ?
   "page" : undefined}` pattern for consistency across the two "current item in a strip" widgets in
   the app) alongside `data-active` is a pure addition with no known test breakage.

**Net recommendation**: migrate `NavigationRow`'s outer shell (`navigation-row.tsx:47-49`) to a real
`<button type="button">` plus add `aria-current`, fix the one vitest assertion (#1), and fix the two
e2e locators (#2) in the same change. Treat the nested-close-button case (#4, and by extension #5) as
a separate follow-up requiring a small structural decision, not blocking the outer-shell fix — the
outer-shell fix alone already resolves the "hand-rolled Enter/Space" and missing-`aria-current` parts
of the appendix finding for the row itself.

   a11y` as a dependency; lazy-load and `term.loadAddon(new AccessibilityAddon())` conditionally on

3. **Verification**: per the appendix's own refactor step, this needs a real screen-reader pass
