# ui-components (health 6/10, test spec-grade 5/10)

**Verdict:** The directory is bimodal. One lineage — tab-page-utils.ts, page-editor-model.ts, page-editor-ai.ts/geometry/dock, review-vcs-cache.ts, review-workspace-tabs.ts, review-open-diffs.ts, page-index.tsx's grouping helpers, status-editor-dialog.tsx's array helpers — is genuinely well-factored: pure functions taking explicit deps, extracted from god components with matching *.test.ts files that read as real behavior specs. The other lineage is classic hard-fork debt: a 1050-line untested process-diagnostics dialog that mixes data grouping, kill/terminate business logic and five render subcomponents; a 489-line SSE-driven multi-agent 'Arena' feature with zero tests; three copy-pasted global-singleton portal-slot modules; and a naming split where the Notion editor's own logic/test/style files still carry the pre-rename 'tab-page' prefix while the component itself is 'page-editor'. Test coverage is real where the code was deliberately decomposed into pure modules, and absent everywhere the code stayed imperative/effectful — and at least one existing suite (page-index.test.ts's 'optimistic mutations' block) never actually calls the functions it claims to test. None of this is unfixable; the codebase already demonstrates the target pattern in review-* and page-editor-* pure modules, it just needs to be applied to the remaining god files.

## Findings
- **[high] dialog-process-diagnostics.tsx: 1050-line god file with destructive process-kill actions and zero tests** (test-coverage)
  The file combines OS-row-to-group aggregation (buildExternal, groupStatus, scoring), formatting helpers (formatAge, formatUptimeSeconds), business actions that terminate/kill real OS processes (terminate(), the 'kill-leaks'/'kill-stale' bulk actions), and five inline subcomponents (ProcessCard, MetricCell, ProcessSection, GroupRow, ChildRow) in one file — with no accompanying test file anywhere in the directory. Given this dialog can SIGKILL processes and 'clean up' groups in bulk, the aggregation/scoring logic (which drives which rows get killed) should be pulled into pure, tested modules the way review-vcs-cache.ts / review-workspace-tabs.ts already are.
  Files: packages/claxedo-app/src/claxedo-ui/components/dialog-process-diagnostics.tsx
- **[high] Three copy-pasted global-singleton 'portal slot' modules instead of one factory** (duplication)

## Tests: Bimodal. Where the codebase deliberately extracted pure logic (tab-page-utils.ts, page-editor-model.ts, review-vcs-cache.ts, review-workspace-tabs.ts, review-open-diffs.ts, page-index.tsx's groupPagesByStatus/allowedPageStatusTransitions, status-editor-dialog.tsx's array helpers), the matching test files are genuinely spec-quality: named by behavior, exhaustive over edge cases (empty lists, unknown status, boundary indices), no mocking, and would let an agent reconstruct the logic from the tests alone. Where the code stayed imperative/effectful (process diagnostics, AI request orchestration, the Arena SSE feature, the mermaid pan/zoom NodeView, add-process-dialog's form), there is no test file at all. Worse, at least one existing suite (page-index.test.ts's 'optimistic mutations' block) creates the appearance of coverage over code paths (rollback-on-API-error) it never actually invokes, which is more misleading than having no test at all.
Gaps:
- dialog-process-diagnostics.tsx: no tests for buildExternal/groupStatus grouping, terminate/kill action wiring, or filter counts — the riskiest (destructive) logic in the directory
- page-editor-ai.ts: no tests for executeAiRequest's session-creation fallback, run-invalidation on rapid re-trigger, or the streamed diff-typing loop's abort path
- page-arena-dock.tsx: no tests for the hand-rolled SSE line/event parser or the start/stop/pause/retry state machine
- claxedo-session-review.tsx: no coverage of line-comment add/update/delete, focus-scroll-to-comment, expand/collapse-all, or the large-diff 'render anyway' override
- page-index.test.ts / page-index.vitest.tsx: movePage/dropPage rollback-on-error is asserted nowhere despite mocks being wired for it
- slash-commands.test.ts: the shipped filter predicate is never actually invoked — the test defines its own copy
- retain-mounted-tabs-policy.ts and add-process-dialog.tsx: no test file at all, inconsistent with sibling modules that follow the same pattern

# ui-layout (health 5/10, test spec-grade 5/10)

**Verdict:** The layout engine (layout/) is genuinely well-built: pure, typed reducers, an alphabetically-ordered A-N spec test suite that reads as an executable behavior contract, and load-bearing comments explaining non-obvious invariants (scratch-cache for same-tick mutations, identity-equality short-circuiting to avoid a Solid reactive-loop stack overflow). The problems concentrate in the layouts/ UI layer and the seam to layout/ and claxedo-layout-actions/: a 2684-line god component (rail-sidebar.tsx) that also serves as the sole source of core domain types (ProjectItem/SessionItem/WorkspaceItem) for the entire actions layer, a 1186-line test file that tests a hand-copied shadow reimplementation of production logic rather than the real functions (citing a source file, rail-layout.tsx, that no longer exists), a duplicated/inconsistent terminal-fit event dispatch, and two independent, semantically-diverging keyboard-shortcut systems both bound to mod+w and mod+alt+Arrow keys. The 'layout' vs 'layouts' split is directionally defensible (engine vs UI) but the near-identical names and the type-ownership inversion make it confusing for a new contributor to find the truth.

**Verdict:** The state/context layer is architecturally disciplined at the module level: each slice (metadata, terminal, workspace, rail, workspace-panel, process-pane) has one clear owner and the harness-config subsystem is decomposed into ~11 single-responsibility files composed by harness-config-store.ts. # tests-as-specs (health 7/10, test spec-grade 7/10)

**Verdict:** The suite (289 `*.test.ts` bun:test files, 43 `*.vitest.tsx/ts` vitest+jsdom+@solidjs/testing-library files, ~31 large Playwright specs) is above-average for a hard-fork headed toward heavy external contribution. The best files genuinely meet the tests-as-specs bar: src/shell/identity/session-ref.test.ts, src/session/submit/dispatch.test.ts, src/terminal/terminal-focus-switch.test.ts, and the lettered src/claxedo-ui/layout/tests/A-hydration.test.ts..N-reactivity.vitest.tsx suite read as an executable spec of the pane/session/harness domain models, with real dependency injection (fake fetch, fake requestFrame/write, in-memory storage) and concrete input/output assertions. The suite is undercut by a recurring anti-pattern: ~49 files (e.g. src/components/dialog-create-cloud-project.test.ts, src/components/dialog-select-mcp.test.tsx, src/claxedo-ui/context/harness-store.test.ts) read the SOURCE FILE'S RAW TEXT via `Bun.file(new URL(...)).text()` and assert `.toContain`/`.not.toContain` against import strings -- architecture-boundary enforcement leaking into feature test files instead of staying in the already-excellent src/architecture/scanners.ts guard layer. In the worst case (dialog-create-cloud-project.test.ts) this IS the entire file: zero behavior is exercised. Accessibility and Electron-bridge behavior are essentially untested (a11y assertions in ~9/336 files, no axe-core anywhere; main.tsx/browser-pane.tsx/titlebar.tsx electron glue has 0 direct tests), which matters because both are stated goals of the coming refactor.

THE STANDARD FOR THIS REPO:
Naming: `<subject>.test.ts` (bun:test) is the default for pure-logic specs with no real DOM. `<subject>.vitest.tsx` (vitest + @solidjs/testing-library) is used ONLY when the assertion needs a real Solid mount/reactive timing/keyboard/aria behavior that Solid's SSR stub fakes (createEffect no-ops, createMemo runs once under plain bun:test+happydom). Never mix `bun:test` and `vitest` imports in one file. One `describe` per exported function or named behavioral seam, not per file.
Test names are full contract sentences: `<input/state> -> <output/effect> when <condition>`. Bad: "works", "handles edge case". Good (from src/components/prompt-input/submit.test.ts style): "demo path returns the reply via onDemoReply and never calls promptAsync".
Structure: no mandated given/when/then labels, but each test should read as: construct concrete input -> invoke the exported function/mounted component -> assert concrete end-state. Prefer one clear assertion cluster per test over sprawling multi-phase tests (K-journeys.test.ts is the sanctioned exception: numbered journey steps J1-J16 documenting a user flow, itself labelled as such).
What must be asserted: real return values via `toEqual`/`toMatchObject` against literal expected objects, or observable end-state (DOM attribute via `getAttribute`, ordered array of side-effect calls with their payloads, store snapshot) -- never "was called N times" without also checking payload/ordering.
What must never be mocked: the unit under test, and any pure in-repo collaborator it composes with. Only mock true I/O boundaries -- fetch, SDK client, timers/rAF, storage -- and inject them as parameters (terminal-focus-switch.test.ts's `requestFrame`/`write`/`onOverload`; dialog-select-mcp.test.tsx's `fakeFetch`). Never substitute a real behavioral assertion with a check that a file's raw text does/doesn't contain a string (`Bun.file(...).text()` + `.toContain`) -- that belongs as a named rule in src/architecture/scanners.ts + a *.guard.test.ts, where it is centrally tracked with an allowlist/baseline, not scattered ad hoc per feature file.

# naming-vocab (health 5/10, test spec-grade 5/10)

**Verdict:** There is a real, disciplined canonical layer (src/shell/identity/session-ref.ts with host/toolSandbox/sessionId, and the harness rename with an explicit LEGACY_RUNNER_KEY compat shim) that matches the stated target vocabulary well. But that discipline has not propagated: "workspace" carries at least five unrelated meanings across the tree (directory path, opaque control-plane id, toolSandbox.kind enum value, a project's sub-worktree map, and the plan's own aspirational "workspace = server" sense that context/server.tsx still calls "server"). Two LocalProject types with different shapes silently coexist, two near-identical cloud-workspace-creation dialogs serve two parallel app shells, and the product's own package.json names (claxedo-app, claxedo-server, claxedo-desktop, claxedo-web) are still scoped @opencode-ai while sibling internal packages use @claxedo. Test names in submit.test.ts still say "runner" pervasively even though the source completed the harness rename, which fails the tests-as-specs bar for that vocabulary. None of this is exotic to fix, but it is exactly the surface area that will confuse first-time OSS contributors.

## Findings
- **[critical] "workspace" means at least five different things** (naming)
  (1) src/claxedo-ui/utils/active-workspace.ts `resolveActiveWorkspaceId` = a literal directory path string, no separate identity. (2) src/shared/query/runtime.ts `WorkspaceRuntimeSnapshot` has BOTH a `workspaceId` and a separate `directory` field — an opaque control-plane id distinct from the path. (3) src/shell/identity/session-ref.ts `toolSandbox.kind === "workspace"` is an enum value distinguishing it from `"local"`/`"virtual"` sandbox kinds. (4) src/context/layout.tsx `LocalProject.workspaces`/`sandboxes` = a map of sub-worktrees inside one registered project. (5) The rewrite plan's own target vocabulary states "workspaces = servers the app connects to", a sense realized nowhere in code — src/context/server.tsx still calls that concept "server"/`ServerConnection`. A new contributor cannot infer which of these five a given `workspaceId` prop means without tracing call sites.
  Files: src/claxedo-ui/utils/active-workspace.ts, src/shared/query/runtime.ts, src/shell/identity/session-ref.ts, src/context/layout.tsx, src/context/server.tsx
- **[high] Product-facing packages still scoped @opencode-ai while sibling packages moved to @claxedo** (naming)
  packages/claxedo-app, packages/claxedo-server, packages/claxedo-desktop, packages/claxedo-web all keep `"name": "@opencode-ai/..."` in package.json, importing each other and being imported as e.g. `@opencode-ai/claxedo-app` (see src/main.tsx, src/shell/app-shell-state.ts, src/shell/app-shell-layout.tsx). Meanwhile agent-sdk-runtime, agent-event-runtime, sandbox-manager, workspace-runtime, wakes, workgraph, channels, connections, mcp all use `@claxedo/*`. The four packages that ARE the open-sourced product still read as OpenCode-owned in every import and on npm.
  Files: packages/claxedo-app/package.json, packages/claxedo-server/package.json, packages/claxedo-desktop/package.json, packages/claxedo-web/package.json, src/main.tsx, src/shell/app-shell-state.ts
- **[high] LocalProject defined twice with two different shapes** (duplication)
  src/context/layout.tsx:61 defines `export type LocalProject = Partial<Project> & { worktree: string; expanded: boolean }` (SDK-derived). src/claxedo-ui/components/dialog-edit-project.tsx:17 independently defines its own `export type LocalProject = { id, worktree, name?, icon?, expanded, sandboxes?, commands? }` — a hand-rolled shape with no relation asserted to the first. Both are exported and both are imported elsewhere by name (e.g. src/components/titlebar.tsx imports the layout.tsx one). Same identifier, two sources of truth, direct violation of AGENTS.md's "do not introduce a second source of truth".
  Files: src/context/layout.tsx, src/claxedo-ui/components/dialog-edit-project.tsx, src/components/titlebar.tsx
- **[medium] Two near-identical "create cloud workspace" dialogs for two parallel app shells** (duplication)

  Files: src/components/dialog-create-cloud-project.tsx, src/components/dialog-create-cloud-workspace.tsx, src/pages/home.tsx, src/claxedo-ui/claxedo-layout-actions/project-actions.tsx

  src/components/prompt-input/submit.test.ts has ~15 test names using "runner" ("runner draft submit reuses the prewarmed session", "runner submit uses the harness-selected model", "signed runner submit ignores stale shell mode", etc.) even though the same file's production counterpart and src/claxedo-ui/context/harness-*.ts completed a rename to "harness" with an explicit LEGACY_RUNNER_KEY compat path. Under the tests-as-specs bar, an agent handed only these test names would reconstruct the wrong canonical term ("runner") for the concept the app now calls "harness".
  Files: src/components/prompt-input/submit.test.ts, src/claxedo-ui/context/harness-preferences.ts, src/session-client/harness/profile.test.ts
- **[medium] claxedo- prefix stutters when nested, and adds no disambiguation inside its own repo** (naming)
  src/claxedo-ui/claxedo-layout-actions/ is a directory nested inside claxedo-ui and prefixed with "claxedo-" again (reads "claxedo-ui / claxedo-layout-actions"), and it sits alongside a sibling file of almost the same name, src/claxedo-ui/claxedo-layout-actions.tsx (the barrel that imports from the folder).   (a) the retired upstream product this app forked from; (b) one of four supported harness/transport values — `TransportCapabilities.transport` union includes `"opencode"` alongside `claude-acp`/`codex-acp`/`cursor-acp` (src/shared/data/types.ts); (c) the wire-schema namespace from @opencode-ai/sdk (Message/Part/Event) used as the lingua-franca shape every harness gets normalized into, e.g. `applyOpencodeConversationEvent`/`opencodeConversationSnapshot` in src/shell/chat/opencode-conversation.ts apply even to non-opencode-harness sessions. ## Naming
- `workspaceId (used identically for a directory path in UI/layout code AND for an opaque control-plane id in WorkspaceRuntimeSnapshot)` → `activeDirectory (layout/UI sense) vs workspaceId reserved exclusively for the WorkspaceRuntimeSnapshot control-plane identifier`: the same field name currently means two unrelated things depending on layer; splitting the names lets a reader trust the type without tracing call sites
- `@opencode-ai/claxedo-app, @opencode-ai/claxedo-server, @opencode-ai/claxedo-desktop, @opencode-ai/claxedo-web` → `@claxedo/app, @claxedo/server, @claxedo/desktop, @claxedo/web`: matches the scope already used by every other Claxedo-owned package (agent-sdk-runtime, workspace-runtime, wakes, channels, connections, mcp, ...); the product's own top packages should not read as OpenCode-owned on npm/imports
- `src/claxedo-ui/claxedo-layout-actions/ (+ sibling file claxedo-layout-actions.tsx)` → `src/claxedo-ui/layout-actions/ (drop the repeated product prefix; parent dir already establishes it)`: eliminates the "claxedo-ui/claxedo-..." stutter and the folder/file name collision
- `context/server.tsx ServerConnection / "server"` → `keep as-is only if the rewrite plan's stated target ("workspaces = servers the app connects to") is abandoned; otherwise this is the one identifier that should become "workspace" once the other four senses of that word are resolved`: the plan's own glossary calls this concept "workspace", but the code calls it "server" — the two need to be reconciled explicitly, not left to drift
- `ProcessPanePanel.tsx` → `ProcessPanel.tsx (or ProcessPanelRow.tsx if it renders one row in a list)`: its own doc comment calls it "an individual process panel", not a pane; the current name fuses two of the four view-surface words used elsewhere in the tree
- `LocalProject defined in src/claxedo-ui/components/dialog-edit-project.tsx` → `import LocalProject from @/context/layout.tsx and extend it (or rename the local shape to ProjectEditDraft) instead of redeclaring the same exported name`: two same-named, differently-shaped exported types is a landmine for anyone who imports the wrong one by accident
- `dialog-create-cloud-project.tsx vs dialog-create-cloud-workspace.tsx` → `consolidate to one dialog component (parametrized by shell if pages/home.tsx is still reachable) or delete pages/home.tsx's copy if that shell is dead`: near-duplicate implementation of the same create-workspace flow for two parallel app shells
- `test names using "runner" in src/components/prompt-input/submit.test.ts` → `rename to "harness" throughout (e.g. "harness draft submit reuses the prewarmed session") to match the renamed production concept`: tests are meant to double as the executable spec; they currently teach the retired vocabulary

## Tests: Where the naming discipline is strongest (src/shell/identity/session-ref.test.ts), the tests read as a genuine behavior spec: they use the canonical host/toolSandbox/sessionId vocabulary consistently and each test name states an input scenario and an expected derived value. That quality does not hold across the codebase's vocabulary, though: submit.test.ts names dozens of cases with the retired term "runner" even though the source finished renaming to "harness", so a reader of test names alone would misreconstruct the current concept name. Several other suites (harness/profile.test.ts, harness/store-state.test.ts) mix "runner" and "harness" in the same file for what is explicitly a migration/back-compat path, which is fine when clearly labeled legacy, but submit.test.ts does not label its "runner" tests as legacy — they read as the live spec.
Gaps:
- No test file anywhere in src/ asserts that the two LocalProject type definitions must stay structurally compatible (or must not both exist) — nothing would fail if they drift further apart
- No test enforces or documents which of the five "workspace" senses a given call site's workspaceId argument refers to (e.g. a type-level or runtime assertion that WorkspaceRuntimeSnapshot.workspaceId is never equal to directory, or vice versa)
- No test exercises dialog-create-cloud-project.tsx and dialog-create-cloud-workspace.tsx side-by-side to show whether they are expected to diverge in behavior or are pure duplicates
- No repo-level guard test (in the vein of src/architecture/scanners.ts) flags reintroduction of "runner"/"runnerHost" outside the one documented legacy-compat site, so the retired term could silently creep back in as new code is added
