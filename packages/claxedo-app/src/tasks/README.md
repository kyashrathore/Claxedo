# Tasks

Owns: the Tasks page (`TasksPage` at `TASKS_PAGE_PATH`, `/tasks/:taskId?`, which the rail registers as `tasksPage` in the shared page tab): a project's tasks as a list or a board, the create dialog, a task's detail with its subtasks, images and linked sessions, and starting a task's session from a preset; and Settings → Presets (`presetsSettingsSection`, `/settings/tasks-presets`). Tasks, presets, session links, validation and start admission belong to the server (`@claxedo/tasks`, served at `/api/claxedo/tasks`); this domain reaches them only through `useServer().tasks` (`createTasksApi` in `src/server/tasks.ts`: the typed `TasksClient` and the query keys under `queryKeys.tasksAll`).

## Concepts

- **Task reads** (`data/queries.ts`): the task list (`useTaskList`, keyed by `TaskListFilter`: project, status, `parent` any or root, `includeArchived`), a task's detail (`useTaskDetail`: the task, its links and its attachments), its children (`useTaskChildren`), the presets (`usePresetList`) and the server's tasks capabilities (`useTasksCapabilities`) live in the TanStack Query cache under `keys.scope`. Lists page by cursor: the task list on "Load more", while the children and the presets follow every page until one fails. No server event refreshes them (`tasksAll` is `once` in `src/server/freshness.ts`): every command this domain sends invalidates the whole scope (`useTasksInvalidation`), so a change made by an agent's task tools or another browser shows after this app's next task command, or when the page opens again after its reads have left the cache. Nothing reads them before the page opens, so a boot sends nothing under `/api/claxedo/tasks/`.
- **Page state** (`TasksStore`, `store.ts`): the collection, list or board, status filter, show subtasks, group by status, date field (updated or created), the detail rail's collapse, the chosen project, per-task edit drafts, conflicts and errors, the last preset started with, and per-task start refusals. `TasksPage` creates it, so it lives while the page is mounted, across `/tasks` and `/tasks/:taskId`, and goes with the page when the tab shows other content. Nothing in it is persisted.
- **Project**: the toolbar's pick, else the project of the placement the route names (`useActiveProjectId`), else the first of `queries.projects.list()`; no list is read until one is known. A task's key is the project's letters (`projectKey`: the first three letters of a one-word name, else up to four initials) and `taskNumber` (`20`, or `20.1` for a subtask).
- **Collections** (`TASK_COLLECTION_STATUSES`): Active (To do, In progress, Needs you), Backlog, and All tasks, the only one that asks the server for archived tasks; `visibleTasks` drops what the collection excludes. The board draws one column per status of the collection. Dropping a card on another column sends `task.set_status` with the card's revision, and an archived card does not drag. A task is created only as Backlog or To do (`TASK_CREATE_STATUSES`), so only those columns offer "+".
- **Commands** (`view/task-commands.ts`): status, edit, archive, restore and add subtask go through `client.command` with a fresh `clientRequestId` and the revision the page last read. `busyWhile` marks one task busy at a time and disables its controls. A `stale_revision` refusal (`refusalOf`) keeps the typed title and description, adopts the current revision and shows the task's current title as a conflict, so the next Save applies the edits on top; any other refusal shows its message, and field reasons map to `tasks.field.*`.
- **Edit draft**: a task's title and description in `taskEdits` until saved or discarded. Save and Discard show only while the draft differs from the task, and ⌘S/Ctrl+S saves. The title is one line (a newline becomes a space); the description is Markdown source in a plain textarea.
- **Subtasks**: one level. Only a root task's detail has Subtasks, with done/total and an add field that is closed while the task is done or archived. A row's progress is the server's `children` count, in which archived children count as neither.
- **Create** (`DialogCreateTask`, `TaskCreateForm`): title, description, status, project and images, sent as one `task.create`. Images are read one batch at a time (`createImageQueue`): only PNG, JPEG, GIF and WebP, at most `TASKS_BOUNDS.taskAttachmentsMax` (6), each at most `taskAttachmentMaxBytes` (1.5 MiB). A larger image is redrawn on a canvas as WebP, else JPEG, at 0.85 quality and 0.7× smaller each round for up to six rounds before it is refused (`image-drafts.ts`). Submit waits for reads in flight. Images are added only at create; the detail reads each one's bytes through `client.readAttachment` into an object URL that it revokes on cleanup.
- **Slots and attempts** (`model.ts`): a task's session links grouped by configuration slot (`primary`, `planning`, `implementation`, `review`), newest attempt first; the slot's current link is its highest attempt. Liveness (`live`, `archived`, `deleted`, `unavailable`) and handoff (`sent`, `pending`, `unknown`) come only with a detail read. A list row carries the link count alone, so its main button is Open whenever the task has a link, and Open reads the detail and opens the primary slot's current session, else the first live one, else refuses with that slot's liveness. In the detail rail a live slot offers Open session; any other slot starts `admissibleAttempt` (the same attempt while live, the next otherwise), as "Start again" once a link exists, with Continue from previous session when the current link is not deleted and its preset still configures the slot. A live link whose handoff is `pending` offers Send task, which reruns the start with that link's preset, slot and attempt; `unknown` shows "Delivery unknown" and offers nothing, because nobody can tell whether the first message arrived.
- **Start** (`data/start.ts`): `useTaskStartOffers` builds each control's `TaskStartOffer` from the unarchived presets (in the detail, only those configuring the slot). Starting re-reads the task for its revision and attempt, asks `client.startPreview`, refuses with the first blocker or when continuing from an unreadable transcript, then calls `client.start` with the preview's `digest`, invalidates, and opens the session: `/w/<placement>/session/<id>` when the reference names a workspace, `/s/<id>` otherwise. A success makes that preset the next default; a refusal stays in `startRefusals` and shows on that task's control.
- **Preset** (`presets/`): the user's reusable how and where for an agent: name, Local or Cloud execution, a required primary configuration and optional planning, implementation and review ones (harness, model and effort each), instructions, whether agents may start it (`agentStartable`), and for Cloud the plugins and skills to install. The editor holds a `PresetEditorDraft` in `PresetsStore` and validates it with `parsePresetEditorDraft` before `preset.create` or `preset.edit`; archive and restore are commands too. A placement the server does not offer (`useTasksCapabilities().placements`) is disabled, but a saved one is kept and starting it is refused rather than moved elsewhere. Harness and model come from the composer's `DraftHarnessPicker` over the first placement in `queries.placements.list()`, so the editor needs a project; switching harness clears the model and effort the picker carried over (`rebaseConfiguration`). The capability picker lists the Marketplace catalog's plugins and skills (`useCapabilityCatalog` over `queries.marketplace.catalog()`); a Local preset uses the machine's own skills and plugins and ignores the selection.
