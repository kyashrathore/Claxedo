# auth

Owns: the account, as one port with two bindings: the browser's own sign-in session with the identity provider (Better Auth), and on the desktop Electron main's account, reached over the preload's `api.account` bridge. Also the full-screen auth routes and the origins they talk to. It does not own who may do what; that is `src/access/`.

## Concepts

- `AccountBinding` (`binding.ts`): what `createAuth` is built over. `open()` returns an `AccountSession`: the user, whether sign-in is in flight, why it is unavailable, whether a signed identity is still being looked up, whether sign-in is offered, sign-in, sign-up, sign-out, refresh, and `controlPlane`, how the app reaches the account's control plane. The build picks one binding (`vite.account-binding.ts`, `VITE_CLAXEDO_AUTH_ADAPTER`), imported as `#account-binding`:
  - `better-auth` (`better-auth-binding.ts` over `browser-binding.ts`): the web. `controlPlane` is `cookie`: the server the app talks to is the control plane, and its Better Auth session cookie authenticates requests. `serverAccess` (`app.tsx`) turns it into cookie requests and the browser account while signed in, and into no account access signed out. Sign-in is offered when the server issues sessions and the adapter is available.
  - `desktop` (`electron-binding.ts` over `desktop-binding.ts` and `desktop-bridge.ts`): the Electron renderer. Main owns the credential and the OAuth flow in the system browser; the renderer holds no token, URL or method. `controlPlane` is `port`: `run(operation, input)` names one operation of `@claxedo/account-contract`'s closed set and main decides the request. Sign-in is offered when the build is signed-capable (`VITE_CLAXEDO_HOSTED_ACTIVATION=true`, v1's hosted activation flag). The renderer starts `pending` until main answers, adopts every state main pushes (`claxedo.account.stateChanged`), and drops an invoke answer that a push overtook. A rejected operation re-reads main's state before the caller sees the failure. The module throws at load when the preload exposes no complete bridge.

- `BrowserAuthAdapter` (`browser-auth.ts`): the provider-neutral contract. `better-auth-adapter.ts` is the one implementation: it composes `better-auth-client.ts` (the library's client, its results and the callback URL), `better-auth-session.ts` (the signals, the live descriptor, the session and `initialize`) and `better-auth-actions.ts` (sign-in, sign-up and sign-out). The web's binding (`better-auth-binding.ts`) builds it.
- `BrowserAuthDescriptor`: the deployment's declaration, read from `GET /api/claxedo/auth/descriptor` and validated against the canonical `account-contract/auth` types by the guards in `browser-auth-descriptor.ts`, whose test checks every verdict against the zod schema they replaced; a mismatch leaves the app signed out with the reason, never a startup failure.
  - At start, `initialize` takes the descriptor the deployment published into the shell (`publishedDeployment`, `src/server/README.md`) instead of reading it, while that copy's `expiresAt` is ahead; an expired copy is never used, and the descriptor is read as before. Sign-in, sign-up and a session refresh always read the live descriptor and refuse one whose deployment or configuration version differs from the one the page started with, so the published copy only decides which sign-in methods the page offers before anyone acts. A social sign-in the page's descriptor offers asks the server for the provider's address while that read is in flight (`disableRedirect`) and leaves for it (`window.location.assign`) only once the live descriptor agrees, so the click costs one round trip before the provider instead of two.
- `AuthUser`: the sanitized identity (id, name, email, image). The browser binding exposes no token; the HTTP-only Better Auth cookie stays with the browser. Desktop main owns its credential.
- The auth routes answer JSON, and a proxy's HTML error page has no fields to read, so `authResponseBody` reads a body only when the response says it is JSON (`better-auth-error.ts`).
- Origins (`origins.ts`): `appOrigin()` is the page origin, which on the hosted deployment also serves the auth and API routes under `/api` and the relay under `/relay` (`relayUrl()`), so the browser opens one connection and no request is cross-origin; `serverIssuesSessions()` is `VITE_CLAXEDO_ISSUES_SESSIONS !== "0"`.

- Invitation continuation (`login-continuation.ts`): sign-in or sign-up retains `/invitations#<token>`, then calls the server's typed `acceptOrgInvitation` action. The server owns email matching, expiry, revocation, single use and membership; the app owns only the authentication and acceptance screen. Authenticating records the token in this tab's `sessionStorage` (`claxedo:invitation:started`), and a signed-in page joins on its own only when it takes that record for its own token (`resume()`); a link opened while already signed in, in another tab, or after a different user signed in waits for Accept invitation, so a link alone never adds someone to an organization.
- Consent requester (`oauth-consent.ts`): a client this deployment registered (`claxedo-cli`, `claxedo-desktop`) is named by the deployment, never by its own `client_name`. Any other client registered itself without authentication, so the page calls it unverified, quotes the name it chose, shows the host its signed `redirect_uri` sends access to, and pre-checks no scope.
- Re-authentication continuation (`requiresFreshSignIn`, `view/login-redirect.ts`): the Worker's authorize route sends a signed-in reader back to `/login` when the request carries `prompt=login`, `prompt=create` or a `max_age` their session is older than, and Better Auth 1.7.1's authorize route re-prompts on `prompt=login` however fresh the session is. So `/login` never forwards an existing session on such a request: it asks the reader to sign in again, records in this tab's `sessionStorage` (`claxedo:authorization:signInStarted`) that it started that sign-in, and forwards only when it takes that record for the same request, with `login`, `create` and `max_age` removed and every other prompt kept. A failed email sign-in drops the record. `prompt=select_account` never reaches `/login`: the deployment configures no account-selection page, so the authorize route refuses it back to the client.
- Native client continuation (`loginDestination`): a sign-in that continues a native client's authorization request loads the Worker's authorize URL as a full navigation, never through the client router, because on a deployment whose API and app share an origin the router would render the app shell at that path and the consent page would never appear.

## Machine

`AuthState`: `signedOut(reason?)` → `signingIn` → `signedIn(user)`; `signedIn` → `expired` when a refresh finds no session or is refused, and `signingIn` → `expired` when the stored credential a launch restores is one the server has rejected. On the desktop an interactive sign-in instead goes `signedOut` → `awaitingBrowser` → `signedIn(user)` or `signInUnfinished`. `refresh()` re-reads the session only while signed in, one read however many callers ask during it, and never throws: a refusal is logged and becomes `expired`. On the web the server scope calls it on every 401 the control plane answers (`onSignInRefused`), so a cookie the server stopped accepting signs the reader out once, wherever it was refused; a 401 about something else (the session read still names the user) leaves them signed in. The control plane admits a session revoked elsewhere for up to 60 s after its last live check of that cookie ([request authentication](../../../claxedo-server/src/platform/auth/README.md#worst-case-lag)), so that 401 can arrive up to a minute after the revocation. `expired` builds no account access, like `signedOut`, so the shell sends the reader to `/login`, which says the sign-in expired. Events: `started`, `browserSignInStarted`, `browserSignInUnfinished`, `settled(user, reason?)`, `signedOut`, `expired`. The session's `loading`, `user` and `unavailable` signals feed `settled`, its `ended` signal (the server stopped accepting the credential it held) feeds `expired`, and while `loading` holds the state stays `signingIn`, even after a sign-in call returns; nothing else decides the state. A binding whose sign-in happens in the system browser (the desktop's) also has `browserSignIn`: its `state` (`idle`, `waiting`, `unfinished`) feeds the two browser events, and `cancel` is `useAuth().cancelSignIn()`. Its sign-in sends no `started`: `awaitingBrowser` and `signInUnfinished` are signed out, so the reader keeps the machine's scope and the local app stays rendered while the browser step runs, instead of the startup placeholder `signingIn` shows. Main's desktop states map onto it: `pending` (main waits for the browser's callback, as long as the authorization request stays valid, until Cancel or a newer Sign in replaces it) → `awaitingBrowser`; `unsigned` marked `signInUnfinished` (that wait timed out, was cancelled or failed) → `signInUnfinished`, until the next sign-in starts; main publishes `signed` as soon as the credential is adopted, with the subject its JWT bearer names, so launch never waits on userinfo; `signed` with no user id (an opaque bearer, until userinfo names the account) → `signingIn`, so no signed-out scope opens between two accounts; `signed` with a user id → `signedIn` (with `identityResolving` while its name is still being looked up); `signed` whose lookup failed before naming any user → `signedOut` with the reason; `unsigned` → `signedOut`; `unavailable` with the reason `revoked` (the server rejected the session main held, because the person logged out in the browser or an administrator revoked it) → `expired`, which the rail says in one line, "You were signed out. Sign in again.", until the next sign-in starts; any other `unavailable` → `signedOut` with main's detail as the reason. A state main never sends decodes as unavailable, never as signed.

`restoringUserId()`: the last user id this browser recorded (`persistence.ts`), only from creation until the first `settled`, which ends it in the same update as the state; an interactive sign-in never sets it. The app builds the server scope for it so startup reads run beside the session read (`src/shell/README.md`).

`InvitationState` (`model.ts`): `idle` → `authenticating` → `accepting` → `joined(result)` or `failed(failure)`. Pending email verification returns to `idle`. A refused acceptance can be retried explicitly; a successful acceptance is retained so the screen sends no second consume request.

## Routes

`authRoutes` (`routes.ts`): `/login` and `/invitations` draw `AuthSplit` (`view/auth-split.tsx`): the kit's `ArtworkPlate` in the left column from 768 px, and one column with the title, one line and the sign-in methods (the provider's mark on its button, then email) on a phone. Routes: `/login`, `/device` (device grant approval, where the person types the code their terminal shows and approves the CLI's sign-in; a `user_code` in the link is never read, so a link someone else sends cannot pick the request), `/oauth/consent` (MCP scope consent), `/invitations#<token>` (sign-up/sign-in and invitation acceptance). The shell registers them outside the app shell.

The sign-in form (`view/login.tsx`, `LoginForm`) renders in two documents and takes from each a `LoginHost` (`view/login-redirect.ts`): where it is (`location`) and how it leaves for a path once signed in (`replaceWith`). In the app the host is the client router (`view/login-page.tsx`, `LoginPage` and `OrgInvitationPage`, registered in `authRoutes`), and signing in with email navigates to `/` in place. In the signed-out document (`src/login-document.tsx`, the entry `src/login.tsx` and `login.html`) the host is the window: the document is what the edge serves to a browser without the session cookie at `/` and `/login` (`packages/claxedo-server/scripts/deploy/shell-document.ts`), it replaces the URL with `/login` as the shell's gate does, and signing in with email loads `/` as a full navigation, since the app is not in this document; a social sign-in leaves for the provider either way. The document composes the auth binding, the theme and the preferences the form draws under, and nothing else of the app (`vite.login-entry.test.ts` holds its chunk graph); the invitation flow needs the server's `acceptOrgInvitation`, so `/invitations`, like `/device` and `/oauth/consent`, is served the app.

## Invariants

- The consent page only narrows scopes: Allow always submits the scopes left checked, so a scope the page did not offer (`claxedo:admin` to a client this deployment did not register) is never granted by omission.
- The device page names the requesting client the same way and says that approving grants the device full account access; the server issues user codes only to `claxedo-cli`.
- Signing out clears every `claxedo:` preference and the last user id; a different user signing in clears them too.
- On the web, `claxedo:auth:lastUserId` names the account this browser is signed in as, and every tab shares the one session cookie. `browserAccountBinding` listens for another tab changing it (`watchOtherTabIdentity`, `persistence.ts`, disposed with the auth owner): a signed-in tab reloads when another tab signs in as someone else or signs out, so it never keeps showing the first account or writes that account's preferences back after the switch cleared them. A signed-out tab stays on its page. A storage event never reaches the tab that wrote it.
- No test bypass exists in this domain; flows sign in against the real Worker with the scripted OAuth provider.

- The desktop renderer never holds the account's credential: its binding has no token, and every control-plane call crosses main by operation name.
