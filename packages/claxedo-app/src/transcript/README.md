# Transcript

The renderers of one session's parts: user and assistant messages, tool rows, work groups and the turn fold, markdown with code, math and Mermaid, file and diff viewers, the Review code view, subagent chips, the message-navigation rail, and the retry card. The timeline (`src/session/view/timeline`) lays the rows out; this domain draws each one.

It is the old app's session renderers, **moved, not rebuilt**: only import paths, Claxedo names, and kit twins where the corpus (flow 30, `e2e/corpus/`) shows no visible difference. A logic change is its own slice, proven by the corpus.

## Owned concepts

- The data context (`data.tsx`): `DataProvider` and `useData()` carry the store the renderers read, the placement folder, and the host's callbacks (session and task hrefs, subagent resolution, file URLs, tool images, and `loadToolBody` for a tool part a page sent as its header). A header-only tool row (`part.headerOnly`) draws its collapsed header from the input and metadata the header reads, can open although it holds no body (`bodyPending` on `BasicTool`), and asks for its whole part when it opens; a patch's header keeps each file's path and counts (`patchFiles(files, headerOnly)`). `useOptionalData()` is for renderers that also mount outside a session.
- Parts (`message-part.tsx`): the registry from `part.type` and tool name to a renderer, the harness tool-name aliases, and the user-message, text, reasoning, tool, image and file renderers.
- Tool rows (`basic-tool.tsx`, `activity-row.tsx`, `claxedo-tool*.ts(x)`, `plan-tool.ts`, `question-*.ts(x)`, `tool-error-card.tsx`, `scrollable-output.tsx`, `shell-wrapper.ts`, `local-preview.ts`).
- Grouping and the fold: the rule is `@claxedo/agent-runtime-contract/turn-fold`, shared with the runtime's turn record; this folder draws it (`same-groups.ts`, `work-group-summary.ts`, `turn-fold-row.tsx`).
- Markdown (`markdown*.ts(x)`, `mermaid.ts`, `transcript-link.ts`, `safe-link.ts`), and image availability per URL (`image-availability.ts`).
- File and diff viewing (`file.tsx`, `file-media.tsx`, `diff/`, `session-diff.ts`, `review-code-view*.ts(x)`, `line-comment*.tsx`).
- Subagents (`subagent-chip.tsx`, `agent-glyph.tsx`), the rail (`message-nav.tsx`), the retry card (`session-retry.tsx`), and `formatDuration`.
- Strings: `transcriptDictionary` (`i18n.ts`, `locales/`).

## Why tool rows read this way

- Every tool row, group header, file row and fold row has one anatomy (`ActivityRow`): a muted icon, a verb and a truncated tail, a hover brighten, and a chevron that fades in at the pointer. The row sets one dim tone and the 14 px icon inherits it; a per-element ladder (icon, base, weak, weaker) made a row read as three mismatched shades. Hover lifts the text only, since the icon carries category, not attention. Chevron and brighten are gated on `@media (hover: hover)` so touch never reveals chrome, keyboard focus mirrors hover, and nested rows inside a work group are dimmer and icon-less (depth by dimming). Content sits above the overlay hit target but is click-through except for real links and buttons. Colors resolve through the legacy tokens so the light theme stays correct.
- A row has a chevron only when its body shows something: a renderer that gates its body on output it never got still passes a child (the `<Show>` itself), which used to put a chevron on a row that opens nothing. The resolved children are computed once and reused by the body; a deferred row is not built until opened, so until then only the presence of a child counts. A generic tool passes children only when it has output.
- A running tool can open: streaming output is the only sign of how far along a long call is.
- The subtitle and args show as soon as the input names them (the file being read, the pattern searched), not when the call finishes; the shell row keeps its command in the header while running and while expanded, since "Running" alone says nothing. The command's input carries `command` as soon as its partial JSON parses.
- A shell row reads "Ran <command>" with the inner script: harnesses wrap shell tools in a login shell (Codex sends `/bin/zsh -lc '<script>'`), identical on every call. A non-zero exit shows beside the command, so "Ran" never reads as success.
- A subtitle cannot ellipsize an atomic inline, so a subtitle inside an inline-block wrapper (the shell row's animated command span) clips mid-word; the wrapper's display comes from a sheet imported later, so the attribute selector wins the cascade, not source order.
- A JSON payload embedded in a subtitle collapses to `{…}`: the one clipped line shreds it mid-token, and the body shows it in full. Only balanced runs collapse, so a lone brace in prose survives.
- Arg chips for tools with no renderer are short scalars only; a long string is already the subtitle.
- Icons key on the canonical tool intent, the only classification every harness shares: a file edit is `edit`/`write`/`apply_patch` on opencode, `Edit`/`Write`/`MultiEdit` on Claude, `write`/`edit` on Cursor, `file-change` on Codex, anything on ACP, and all land on `intent: "edit"` (`canonicalToolIntent`, ACP's own `kind === "edit"` rule). Intents with no settled mark fall through to the wrench, not a borrowed wrong mark. Name fallbacks cover the opencode native engine's tools without a display; `web_fetch` has no alias because no harness sends both spellings. The fallback is a wrench, not `mcp`: most unrecognized tools are not MCP.
- MCP detection uses `intent` and `kind` first (Codex `item/mcpToolCall/*`, Cursor `mcp*`, Claude `mcp__server__tool` all arrive classified); the name check is a substring, not the `mcp__` prefix, because MCP resource tools carry no prefix and differ per harness (`ListMcpResourcesTool`, `list_mcp_resources`).
- A tool with no renderer reads as a sentence: the action from its name, the object from its input. Some names arrive as one lowercased token (`SendMessage` as `sendmessage`) and need a table; every other name is split mechanically. A single word becomes a title only for an MCP name, whose server carries the missing context; a plugin name repeated by its server (`plugin_posthog_posthog`) collapses to one word. A marker, not the title text, tells a generic row from a registered renderer's, since a locale can spell the title any way.
- Harness aliases map other harnesses' tool names onto the registry's OpenCode vocabulary (Codex's shell tool is `command`, input `{command, kind}`); unaliased, they fall to the generic row, with a raw arg dump, an MCP icon and nothing to expand, and they miss work-group folding, which keys off these names.
- A skill's id is `input.skill` on Claude's dynamic-tool lane and `input.name` on OpenCode's. A completed skill with no output still opens to its call.
- Claude's `ExitPlanMode` sends `{plan, planFilePath}`; the file lives in the harness's config folder outside every workspace, so the call's markdown is the only copy. A plan event no host takes leaves the row to expand inline.
- A question's decline is read from the part's metadata, which the harness sets; the error text is free prose the CLI may reword. A settled question holds the answer the reader typed, so it never folds into machinery. An unanswered question renders nothing and neither breaks nor joins a run.
- An error card's text before the first ": " becomes its subtitle only when the caller gave none; a caller-named subtitle takes nothing from the text. The card's accent is the dim end of the critical ramp; `--card-accent` is too loud in a hairline transcript. Severity is carried by a 16 px glyph, not colored text.
- An open error card pads its text for the copy button by the button's presence (`:has(> .ui-tool-error-card-copy)`), not by an ancestor's `[data-open]`. Blink keys descendant invalidation by attribute name, not value, so under `[data-open="true"] [data-slot=…]` a `data-open` change on any element fully restyled every element carrying `data-slot` below it, including below the workspace panel's own shell. Closing the panel recalculated 987 elements for 13.8–15.7 ms in its click task; now its 890 descendants only inherit the shell's new `pointer-events`, for 3.3–4.0 ms.
- A capped output box (240 px, a dozen lines, shared with bash output) shows its scroll range without hover. Its reveal control is measured from the content, not the box. Lifting the cap deletes the box's own scroll range, so the line under the reader moves by exactly that range; inside the virtualized list the spacer grows only on the next measure pass, a frame later, so the spacer (the `data-index` row's parent) grows first and the list rewrites it on measure. The position is re-asserted for a few frames while the list's resize passes settle; the reader's wheel or drag wins, and a pointerdown beyond the content box is the scrollbar. Expansion is controlled by the caller so it outlives a virtualized unmount.
- Running tools start their bodies from the end: the viewport opens on the latest turn, so heavy default-open bodies near the bottom become interactive first.
- A tool's live elapsed time is tabular, so ticks do not shift layout. `formatDuration` is the one duration voice (`5s`, `2m 14s`, `1h 22m 5s`) for the fold row, running rows and tickers.
- The "Local preview · 127.0.0.1:port" chip reads bare output text only: a URL inside a quoted string is serialized configuration, and a control-plane path is an endpoint, not an app; process listings leak both.
- Images a tool produced hang off the tool row itself: every adapter harvests an image block from any tool result (an MCP screenshot as readily as a `read` of a png). A header-only row carries no attachments, so its images appear with its body when the row opens. The strip is its own component, so a row with no images asks for neither the dialog nor the data context (`useDialog` throws with no provider). Tool attachments that stayed on disk carry only a path, turned into a fetchable URL by the data context. An image thumbnail is 320 × 240 px; inset box-shadows do not paint over `<img>`, so the hairline is an overlay.
- A pending tool call carries no metadata, output or attachments; only a completed call has output and attachments.
- A `url` from tool or agent output with a rejected scheme renders as an inert label rather than a target the click handler would refuse.
- The subagent child registry owns whether delegation happened: a wrapper can fail or be interrupted after admitting a child, and the child's chip stays. SDK-runtime harnesses (Codex, Claude, Cursor, ACP) never stamp `MessageAbortedError`, so the timeline passes the turn-level interruption in.

## Why first-party tool rows read this way

- `claxedo-tool-view.ts` lists every tool the first-party MCP registers with its row title; the key set is the roster, and an engine-prefixed `claxedo_<name>` is claimed only when `<name>` is listed, since that spelling carries no server to prove it addressed this one. Both server names are used by registrations and persisted calls. An explicit first-party server identity beats a bare native tool name.
- Codex reports an MCP call as `{server, tool, arguments}`, so the arguments sit one level down there.
- The output reaches the card only as a string, so its JSON is recovered from it; a tool that writes prose above its payload marks the payload's line, and the card decodes what the producer named rather than guessing where prose ends.
- A Stop row reads the contract's own test (`turnStopped`), not the operation state: `cancel_turn` reaches `succeeded` only under a cleanup no adapter can prove, so a state read labels every healthy Stop as failed. An answer the contract cannot parse says nothing about the turn.
- A task or session link is a plain anchor to the surface's route, so the router takes the click and cmd- or middle-click open a tab; the click is stopped so the row does not toggle. The data context's `navigateToSession` is not used: a pane that never wired it still defines it, and the click went nowhere.
- The row's one accent is the task or session it was about; a state pill's 16 px mark is its only sign at rest, at the row's dim tone so it never reads as a button. The body indents 22 px (the 14 px icon plus its 8 px gap) so it sits under the verb.
- A Claxedo MCP call keeps its own row: the task or session it made is the record the reader came for.

## Why grouping and the fold work this way

- The rule is `@claxedo/agent-runtime-contract/turn-fold`; the contract's README says why it groups and folds as it does.
- A work group is collapsed by default; its body scrolls at 224 px with edge fades only when it overflows, and dims its members. An open member (a diff, a file, an output) grows the list to fit rather than scrolling through 224 px. Its header matches the tool rows' tone and 14 px icon.
- The group summary is present-continuous while running and past tense when settled, the first segment sentence-case and the rest lowercase, joined with " · ". While a member runs, the header shows that member's live summary, so a long run stays one updating row. A group stays active between members until execution moves past it: `busy` belongs to the active turn's trailing group, and a completed member does not close it. Members no bucket claims are still named: a single call as its own row names it, a run of one tool counted by that tool ("ran 2 skills", or its opaque label verbatim), a mixed run by its count.
- The collapsed "Thought for Ns" body is muted 13 px with no large top margin.

## Why markdown renders this way

- Blocks are parsed independently, so a `[docs][1]` in one block cannot see a `[1]: url` defined in another or later in the stream. The lexer's definitions are appended to every prose block's parse source and render as nothing, so a long document keeps its frozen prefix when a definition appears; collapsing the text into one live blob re-rendered the whole transcript as raw healed text on every delta and reflowed it at completion.
- A streaming list or table renders its available rows now; waiting for another token inserts the whole block above content already visible.
- A streaming reply re-lexes only from its open block. Every block before it was closed by the block after it, and block structure is decided line by line, so later text cannot reshape a closed block. The exception is a reference definition, which resolves a link in an earlier block, so text that carries one is lexed whole. Lexing the whole message on every delta cost 32.5 ms per delta at 37k characters.
- While a reply streams, its open block is parsed and sanitized once for each state it reaches. The render effect paints the open block with the sync parser, and the resource reuses that same block instead of parsing it again. The first paint and the resource build each block in `markdown-blocks.ts`, and a block's hash is the checksum of its raw source, marked as a first paint when the kit's `markdownEnhances` says the async pass would still change its markup (math). The async result replaces exactly those paints; a first paint the pass would leave unchanged is final, and the resource returns it and fills the block cache instead of parsing it again. With one hash for both, a closed formula would stay unrendered; with two, every block was parsed twice and morphed onto identical markup.
- Copy and full-screen controls are Solid roots, so they are created on the committed DOM only and kept across morphs: morphdom never discards a control node. When they were built on the freshly parsed copy of a block, a streaming table rebuilt them on every delta, and morphdom dropped that copy without disposing its roots (about 16 MiB and 45k detached nodes per streamed reply). The full-screen button reads the table when it is clicked, so a growing table keeps one button.
- Known issue: a streaming `` Run the `config` `` followed by a `# User Guide` heading still wraps the heading in healed inline code. Reusing the frozen prefix and closing the unclosed tick before `# ` was tried and reverted: it duplicated a prose line until completion.
- The projection (`markdown-stream.ts`) lexes a body once with the transcript's own marked instance (`transcriptMarked`, the kit's transcript extensions), and a completed block's synchronous first paint parses that block's tokens rather than lexing its source again; the open block of a stream is parsed from its healed source.
- First paint is real markdown for completed and streaming bodies alike (the block cache or a synchronous parse); escaped source is never committed for a completed body, which was the plain-to-markdown flash. The async parser renders math afterwards, in the blocks that have it. At the end of a stream, and on a cold completed wait, the last streamed DOM stays until the matching rich result arrives. The markdown DOM's initial commit belongs to Solid's render phase: a deferred effect left a mounted text row empty for a frame, and the timeline could not expose first-fold text until the next one. `html()` suspends while the parser is pending, and suspending here would reach the pane boundary and disconnect the session surface, so the component reads `latest`. A partial block-cache hit counts as a miss, and the whole text renders synchronously.
- `marked`'s `Token` union ends in `Tokens.Generic`, so the fence variant cannot be narrowed to; one checked accessor reads its two fields.
- Code fences name shiki grammars; anything shiki does not bundle falls back to plain `text`, which has no grammar to load (`bundledLanguages` has no `text`, and asking shiki to load nothing throws in the worker). Attachment language labels come from the file extension (attachments carry `text/plain` for all text files; a leading-dot name like `.gitignore` has none), and only language metadata loads eagerly.
- A code block inside prose (a fence in a list or a quote, an indented block) is highlighted like a top-level fence (`markdown-code-tokens.ts`): its `<pre>` gets the code frame when the block is decorated, and the worker's tokens become the same token spans, painted from the highlight cache before the block commits or once the worker answers. When the kit's async parse highlighted it with its own shiki, the frame arrived with the colors: each such block grew 24 px after the first paint, and a finished reply's markup changed twice.
- Completed code-block highlights live in a module-scope cache keyed by theme, language, source length and a 32-bit FNV-1a checksum, verified against the stored source so a collision is a miss. The worker round trip costs about 50 ms per session switch, and a per-component map re-paid it on every remount. Today's only theme tokenizes into CSS variables, so light and dark restyle cached tokens. Only completed blocks are cached and only on success (fallback tokens for a failed worker are never pinned). `codeHighlightCacheLimits` caps it at about 8 MB of UTF-16 text (source, tokens and styles; roughly twice that resident) with 4096 entries as a backstop. 256 entries / 2 MB thrashed on a sweep across the open sessions (`OPEN_SESSION_LIMIT`, 8, in `src/session/store/open-sessions.ts`). An entry larger than the whole budget is skipped.
- Parsed markdown blocks are cached the same way: about 8 MB (typical blocks run 1–3 KB, so ~4096 entries); ~200 entries thrashed on every multi-session sweep, and a tighter entry cap reintroduced thrash at about 25 blocks per session visit. A remount that misses repaints the raw-text fallback and swaps to parsed HTML a frame later.
- Markdown has its own DOMPurify instance, with its config set once through `setConfig`. A config passed on each call is re-parsed into fresh allow-lists every time, which took about a quarter of the sanitize time for a streaming reply's open block.
- Sanitized markdown keeps the same link schemes the transcript's linkifier recognizes, so a target the app can route survives instead of reaching the page with no href; `data:` images are checked by DOMPurify's `DATA_URI_TAGS` first.
- Images render as fixed compact tiles: loading, loaded and failed occupy the same box, so a late decode or a stream re-render cannot shift the transcript; a loaded tile opens the full image, including inside a link. A bare `<img>` re-fetches on every block replacement and flickers alt text and the broken glyph, so an image's availability has one owner, `imageAvailability(src)` (`image-availability.ts`): one probe per URL for the page's life, its outcome a signal. A markdown body reads that signal from its own render scope (`createImageWaits` in `markdown-images.ts`): the tiles still waiting are the ones in its committed DOM, and they settle when the signal does and are released with the body. A probe that never answers holds only its `Image`; when waiters were callbacks over tiles in a module-level list, every re-opened transcript stayed alive while an image hung (+12,240 nodes and +9.9 MB over 80 session switches). A `file://`, absolute or relative source resolves through the workspace's raw-file route before probing; outside the workspace, or on a host with no file route or no data provider, it stays a chip. The `<img>` stays in place until the tile replaces it (appending it to the detached tile first makes `replaceWith` a no-op). The click handler reads the live DOM: morphdom preserves nodes but not their listeners when a streaming block changes its image.
- Links are offered to the host in the capture phase, so no descendant can stop the click first; a host that claims links further up still wins. A host claims a link by cancelling the event; an uncancelled event keeps the anchor's own `target="_blank"`, which a plain web build relies on. A target the sanitizer would refuse never reaches default navigation, whatever button or modifiers carried the click.
- A code span is a link only when its whole value is one (`curl https://example.com` stays a command); an exact match ends at a paren where a run inside prose may open one.
- Inline code reads as an object, not syntax: a neutral pill with prose-colored text and a hairline inset ring on a legacy token, so it reads in both themes. Painting every span with `--syntax-string` turned prose into a wall of teal, and tinting detected paths made a wall of green; the path affordance is the pointer and a dotted underline. `~/…` is not a path chip (the file panel cannot expand it), `:line[:col]` is not part of the filename, and extensions come from GitHub Linguist's `languages.yml` (commit `e9fe3c9f23`) plus lockfile suffixes, excluding numeric manpage extensions so `1.2` stays plain code. A slash-shaped value without a known filename is a `path-candidate`, visually inert until a workspace-aware host confirms an exact file match: extensionless files, folders, event names, routes, MIME types and package specifiers look identical.
- The reply's first element sits flush at the top and its last at the bottom. The renderer marks them after each commit (`data-markdown-edge="first"`, `"last"`, or both; `markdown-edges.ts`), morphdom carries the mark across a block update, and the CSS keys on the attribute. Blocks are `display: contents`, so the margins belong to their children; structural rules (`[data-markdown-block]:last-child > *:last-child`) made Blink track last-child state under every markdown block and restyle a block's subtree whenever an element in it gained or lost a last child. With the marks, a 3,000 px transcript scroll restyles 4,462-4,888 elements instead of 5,001-5,085.
- A table copies as tab- and newline-separated text, which keeps its shape in a spreadsheet and stays readable in an editor.
- `schedule` in the worker queue can start a run from the previous run's `finally`, so the in-flight promise is re-read after every await.
- A newly mounted completed body delays its rich work; a non-interactive surface sets the delay to 0.

## Why Mermaid is rendered and sanitized this way

- One shared loader (`mermaid.ts`) for every surface with assistant diagrams: one lazy import, one `initialize`, one id counter, so no second configuration drifts from the strict-mode, HTML-labels-off policy the sanitizer is tuned for. HTML labels are off because they wrap every label in a `<foreignObject>`, the classic sanitizer bypass; native `<text>` output was verified identical across flowchart, sequence, class, state, er, gantt, pie, git and mindmap.
- The diagram source is assistant output, so its SVG is untrusted whatever the renderer does: `securityLevel: "strict"` is exactly what the advisories against mermaid `>=11.1.0 <11.10.0` bypass. Every SVG goes through `sanitizeSvg` before `innerHTML`, with its own DOMPurify instance and profile: the markdown profile allows only `svg` and `path`, which strips every `<g>`, `<text>`, `<rect>` and `<marker>`, and the markdown `rel=noopener` hook must not run on SVG nor the SVG `<style>` hook on markdown.
- `sanitizeSvg` returns "" when it cannot vouch for the markup, and the caller renders nothing (the plain code block stays, and the marker clears so a later retry can run). The raw SVG never reaches the DOM as a fallback.
- Mermaid ships the diagram's whole theme in one `<style>`, so the element stays and its contents are hardened: no `@import`, no resource URLs; `url(#…)` stays, since markers and gradients use it. `foreignObject` (and its subtree, so its markup cannot spill back as text), `use`, `animate` and `set` are forbidden; `image` and `feImage` too, since `image` is in DOMPurify's default data-URI tags and passes ahead of any URI policy (verified against DOMPurify 3.3.1) and mermaid never emits either. Event-handler attributes are pinned forbidden, including SMIL-only ones. URIs allow same-document fragments, relative paths, http(s) and mailto; whitespace a browser discards is stripped first (DOMPurify's `ATTR_WHITESPACE`), or `java\tscript:` slips past. `SANITIZE_NAMED_PROPS` stays off: it rewrites ids to `user-content-*` and breaks mermaid's `#id`-scoped styles and arrowheads. SVG elements report a lowercase `nodeName`.
- Sanitized SVG is cached by source, so a remounted row does not pop its diagram in after first paint; renders in flight are shared by source, so a wrapper replaced mid-render joins the pending render.
- A top-level ```` ```mermaid ```` fence is always a code block and never reaches `decorate()`, so it is driven from the code path, only once the fence is complete (each failed attempt clears the marker, so an ungated call re-renders on every token). Nested and top-level fences end differently (Marked and Shiki keep the closing line break), so both are normalized to one canonical body. A render whose source changed meanwhile is dropped.
- Once rendered, the source `<pre>` hides and the themed diagram shows; errors fall back to the code block, never mermaid's error graphics.
- A diagram is drawn in idle slices (`nextIdleSlice`, `src/lib/idle.ts`): loading and initializing mermaid, parsing the source, rendering, and sanitizing and committing the SVG each wait for the next idle period, so none of them lands in the task that applies a streamed delta. Mermaid measures text in the DOM, so it cannot move to the markdown worker, and its public API renders layout and drawing in one call: that call stays one task (about 21 ms at 1x and 95 ms at 4x CPU for a five-node flowchart), the rest are short. On desktop the timeline sets the native helper as the renderer, so the page keeps only sanitizing and committing the SVG: 1.6-4.9 ms per diagram against 9-43 ms mermaid.js tasks on the web for the same seven diagrams. When the whole pipeline ran in the task that showed the diagram, that task took 123-162 ms at 4x.

## Why links carry a scheme policy

- `SafeLink` (`safe-link.ts`): `internal` is a root-relative route, fragment, query or dot-relative path; `external` is an absolute URL on a scheme a host can open, the same set the transcript autolinks, duplicated so card primitives do not import the markdown pipeline. `javascript:`, `data:`, `vbscript:`, protocol-relative `//host` and unparseable strings never become links. A second separator (`//host`, `/\host`) rebases the URL onto that host under WHATWG parsing, so only a lone leading `/` is a root path.
- A caller-supplied row or card link is dropped unless it passes this policy.

## Why the file and diff viewers work this way

- A text view windows its rows like the diff viewer: a workspace file tab mounts and disposes its viewer on every activation, so a mount must scale with the viewport, not the file (a 3200-line file must not build 3200 rows). Without a document (SSR) the strategy yields no virtualizer, and the plain fallback needs the whole-file readiness and selection checks. A view rooted in an element sits in a panel scroller and gets a panel-sized window; Pierre's 1000 px buffer is sized for a page (`viewportHeight + 2 × overscrollSize`), so an ~860 px panel built about three times the visible rows. A panel-hosted view keeps ten lines around the visible range.
- Scrolling to a line belongs to the viewer: a line outside the window has no element, so the viewer moves its own scroller to where the line sits (`codeMetrics.lineHeight` per row), the virtualizer draws that window, and the caller re-reveals from `onRendered`. A line number the file does not have is refused.
- Find reads the file's own text when the viewer windows it: the rendered rows can only report on-screen matches, so the count was wrong and matches below the fold were unreachable. Matches are per line, case-insensitive and non-overlapping, as the rendered-row scan was; a trailing newline ends the last line rather than starting another. Rendered rows supply only the ranges to paint, paired positionally so a row whose highlighting splits its text differently still paints at its own offsets; unrendered lines stay countable and navigable. A diff has no single line list and keeps the rendered-row scan. A reveal re-applies on the next frames until the match has a range, at most 10 frames (a virtualizer draws within a frame or two; ten ends within a sixth of a second); a find nobody revealed from starts no loop. Scroll re-applies once per frame, and only for a windowed viewer. CSS Custom Highlights (`CSS.highlights`, `Highlight`) are probed at runtime, once.
- `FileContents.contents` is typed `string` but comes from a tool payload that can carry anything, so it is serialized readably rather than showing an empty pane or `[object Object]`.
- Media stays visible while the same file is re-read (a VCS diff refresh); only a new key resets to the placeholder.
- Worker pools: the two pools differ only in `lineDiffType`, which `@pierre/diffs` reads only in `computeLineDiffDecorations` on a diff's line pair, so a whole-file highlight takes whichever pool is already warm. A cold pool draws nothing until shiki initializes and re-renders a few hundred ms later, off the interaction; Review warms its own style's pool (`split` above `md`), and a file tab insisting on `unified` paid a second worker boot and wasm load. Each pool has 2 workers, not Pierre's default of 8: more workers cost memory and can slow things down, and Safari boots workers noticeably slower.
- The pool's main-thread highlighter is `@pierre/diffs`'s one shared instance (`dist/highlighter/shared_highlighter.js:14-19`): the first caller fixes its engine, and shiki has no engine-less highlighter (`@shikijs/primitive` only warns when the engine is missing) although plain text never runs one (`isPlainLang`). The patch gives that instance the JavaScript regex engine; the workers keep Oniguruma. While the workers work, only `getPlainFileAST` and `getPlainDiffAST` (`WorkerPoolManager.js:415-425`, `:459-467`) render with it, both `forcePlainText`, so the pre-render is identical either way; before the patch it decoded the inlined oniguruma WASM on the main thread about 100 ms after the first panel open, an 11.9 ms task. Each task also attaches its grammar to that instance (`WorkerPoolManager.js:617-624`) so a pool whose workers failed renders on the main thread (`FileRenderer.js:54`, `:410`), and there the engines differ: over 462 files (the bench and large workspaces' diffs, 264 TypeScript files and 108,546 lines, identical; the corpus, 147 TS/TSX files, 5 files and 8 lines differ, plus 9 lines of one markdown `ts` fence; css, json, diff, log, zsh and text identical), the JavaScript engine splits a trailing `// comment` after code on the same line into an operator and words where Oniguruma yields one comment token.
- Pierre's beta virtualized instances keep their first diff target and resolve separator metrics at construction, so a virtualized viewer resets when that is unsafe while plain timeline diffs keep the instance as content streams. The viewer skips the extra rerender when an instance has no annotations applied and none to apply.
- `resolveFileDiff` caches by exact content (the name plus the patch, or the name plus both sides, length-prefixed because contents can hold NUL) and stamps each entry with a serial `cacheKey`. Pierre keys its highlight LRU on it (without one, an expanded row ran the plain AST on the main thread and re-rendered the shadow tree when the worker answered) and treats equal keys as the same target. A serial per distinct content means a changed diff can never inherit a stale highlight, the risk a hashed key would carry; eviction only costs a re-highlight. Snapshot and VCS producers request full context; tool patches use jsdiff's shorter default. A full patch collapses into one leading hunk; separated hunks omit ranges and stay partial.
- The scroll-parent walk differs from `pierre/virtualizer.ts` on purpose: that one also treats the deprecated `overflow: overlay` as scrollable.
- `LruMap` exposes the `lru_map` package's surface (the Vite configs alias `lru_map` here) and boxes values, so a present `undefined` is distinguishable without re-checking `has`.
- `ShadowRoot.getSelection()` is a Chromium extension lib.dom does not declare; the selection falls back to the document's.
- Comment hover follows the pointer and content scrolling under a still pointer with passive listeners, not a per-frame poll; they detach on the first event after the button leaves the DOM, since the utility has no teardown hook.
- Line-comment annotations each get a detached host with its own Solid root, updated through a signal, so Pierre can reparent the host without re-rendering; unchanged annotations keep their identity to avoid no-op rerenders, and a virtualized row keeps its draft text and edit identity when it releases its UI. The anchor's click and hover handlers attach through `on:` (a direct listener) on its button, or on the popover div when `inline` hides the button.
- Attachment cards share one 160 px, two-line shape in the composer and the timeline.

## Why the Review code view works this way

- One Pierre `CodeView` owns the whole changed-file document (layout, virtualization, scrolling, worker highlighting); `ReviewCodeView` maps the review model onto controlled items and exposes the scroll element and a file-position reader, so a restoration can target a file it cannot see instead of replaying a pixel offset.
- File headers use Pierre's custom-header mode: the engine leaves a light-DOM slot per file and the component portals the accordion header into it, so app CSS and context providers apply. A collapsed file's height is `diffHeaderHeight` (44); the rendered header must match exactly, or every collapsed row reserves the difference and the sticky header stack floats down. The file header option is on here (the inline viewers turn it off, and CodeView drops the slot and sticky region without it). Not container-managed: that mode is the React wrapper's portal path and disables header-slot rendering. Hosts are retained only while Pierre renders the item, and the slot snapshot releases the portal synchronously when it leaves. Rendered items carry `data-review-file` in light DOM, and the custom element gets a block box (an inline one measures zero around shadow content). Those stamps are written in the same render that mounts the row, from Pierre's post-render and slot-snapshot callbacks, so the row's first style pass already sees `session-review-diff-wrapper`; stamped a frame later, they invalidated the rendered rows again and the next frame recalculated 456 elements when the panel opened. The content request for rows in and near view stays in the next frame: made synchronously inside Pierre's render, it left Review at the top when it came back from a file tab, in 3 of 3 runs of flow 14.
- A file whose patch has not loaded is a custom item with its own header. When the patch lands the item becomes a diff, so Pierre removes the custom element, focus falls to the page, and Pierre's next render focuses the scroll container. If that custom header's toggle had focus, the first frame after the swap focuses the same file's new toggle, unless focus has moved elsewhere in the meantime; a click or Enter that opens a file for the first time keeps focus on its toggle. The handoff is tried in that one frame only: in flow 14 the new toggle was connected by then in 12 of 12 swaps, though at Pierre's first post-render it was not yet in 6 of them, and a header that is not there by then never takes focus later.
- Items are keyed by the review file id, never `fileDiff.name`: Pierre names a parsed patch from its `+++` header, so `--- a/x` / `+++ b/x` is named `b/x`.
- Comment UI is built on first use and released when the file leaves the rendered range; a collapsed row owns no annotations, gutter or selection. Annotations are read for every file, because an annotation takes document height wherever it sits, so that read builds no controller or DOM and returns the same array while comments and draft are unchanged (a new array tells CodeView to re-measure). Parsed content is retained for the document independently of the DOM, copied field by field because callers may pass store proxies whose values change in place. Comment wiring is fixed per mount: it decides which slot renderers the engine allocates. Only a surface with comment wiring owns a selection, in controlled mode, because the app's store is the one selection anyone reads.
- A reveal target is held until the engine can resolve it: CodeView resolves through committed items, and a line needs an expanded diff with computed layout, so a target published earlier would be dropped. It is retried at each commit and reported through `onRevealed` only once applied. Targets compare by reference: a published target is not re-applied against a reader who scrolled away, while a new request for the same file is a new object. `setItems` queues its own pass, which suffices for content arrivals; a held reveal forces that commit synchronous, because `tryReveal` needs its layout.
- Hover-only header controls arm on pointer movement, not `pointerover`: rows move under a still pointer as the document scrolls. Scrolling and leaving clear them; focus keeps them for the keyboard. A mount animation would override `opacity: 0` and flash controls on rows virtualization materializes, so they stay out of flow.
- Options: the app's one Pierre style owner (the OpenCode theme, the shared `unsafeCSS` mapping Pierre variables to app tokens, the file viewers' reading defaults); long lines scroll inside their row; a hunk break carries only its line info; `lineDiffType: "none"` in both styles to agree with the worker pool, which bakes it into every highlighted render (disagreement flashes word highlights that vanish when the worker lands), and that pool survives a style toggle. The engine's 8 px gap and padding read loose next to the 2 px list it replaced. `setOptions` replaces the whole object, callbacks included, so header and post-render owners are carried across. `CodeView.setup` owns scrolling, the ResizeObserver and readiness re-renders, so no retry timer is needed.
- The scroll handler is typed as Solid's, and narrowed once at runtime by checking the event's fields, because consumers read `currentTarget` to restore scroll.
- A file row is one flex line of icon, folder, filename and actions; folder and name are two spans of one path with no gap. Both truncate from the start (an RTL box, with the text kept in reading order), and the folder shrinks a hundred times faster so a row eats folders before the name. The hover cluster sits in a positioning parent wide enough to cover the change counts it replaces. Change counts are muted and tabular at rest and colored on row hover, scoped to review rows.

## Why subagent chips work this way

- Each subagent gets a deterministic two-tone glyph seeded by its child session id (FNV-1a picks one of ten shapes; the caller supplies the accent), with a slow scan while the child runs, gated on reduced motion.
- A chip's line under the name is flattened and clamped: a finished subagent writes its own summary (headings and all) to the row, which otherwise runs out of the transcript column. The configuration and model sit beside the name one step dimmer; shrink weights scale by slot width, so summary and detail empty out before the name shrinks. What the child runs comes from the spawn call's input (`create_subagent` names a slot or a harness and model; Claude's Agent tool a model), the only place it survives; effort is left out.
- The first 3 chips show, the rest sit behind a toggle. One chip per subagent: a parallel batch answers in one message, and an interaction row points back at its spawn, so the spawn wins the row. An interaction row reports a message to an earlier spawn and scrolls to it, never an anchor to the child.
- A chip with a session href is an anchor, so cmd- and middle-click reach the browser's new tab; a chip without one is a button. With no surface claiming the open, a standalone reader follows the session's route; a transcript that is not `openable` goes nowhere.

## Why the rail works this way

- The rail reads only a user message's id and summary, structurally, so an optimistic turn can be passed; its callbacks are generic over the caller's row type.
- Preview text joins every part of a turn, so it is computed only for the one open card.
- Kobalte compares `relatedTarget` against its content node, so a non-Node target is never inside it.
- The overlay edge is one border clipped to the padding box with `--shadow-md`, like hover cards and popovers; the extra ring shadow read as a doubled outline on dark surfaces.

## Why turn-body loading looks this way

- A held turn body shows nothing for its first 100 ms: a full read landing inside that window paints as if it had never been held, and only a longer wait earns a loader (`session-turn.css`).

## Other shapes

- `DataProvider`'s session row demands no `slug` or `version`: they are read nowhere here, and inventory-sourced rows carry neither.
- Each renderer is registered under one `part.type` and re-checks the discriminant, which lets TypeScript narrow; reaching the throw means the registry was wired wrong.
