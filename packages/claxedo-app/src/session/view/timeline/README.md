# Message timeline

Owns: the session transcript's list. That is the rows built from one session's messages and parts, their virtualization, the anchor that keeps older turns from shifting the reader, the scroll memory and mount cache that make a return land where the reader left it, the turn fold, the message-navigation rail, the queued-prompt bubbles, the error and recovery rows, and opening files, links, plans and subagents from the transcript.

Sent annotation chips are drawn by `message-comment-chip.tsx`: file line comments, image marks and quoted text share their frame, with each kind owning its content. `MessageComment.fromPart` reads the attachment text; the timeline owns its comment rows and passes each parsed comment to the chip.

This is a protected area (`AGENTS.md`): a logic change is its own slice, proven by the corpus (flow 30) and signed off by the owner.

## Host (`TimelineHost`, `model.ts`)

The timeline reaches the app through one prop, `host`, which `createTimelineHost` (`src/session/view/timeline-host.ts`) builds for the session screen. From context it reads only `useData()` (`@/transcript`, for `resolveSubagents`) and `showToast` from `@/ui`.

- `sessionKey`, `sessionId`; `placementPath`: the placement's folder, used only to relativize file paths and to build the absolute path for Copy path.
- `conversation`, `parentConversation`: `TranscriptConversation` from `@/transcript`.
- `sessions`: the session list's rows as `TimelineSessionRow` (`id`, `title`, `parentId`, `archived`, `lastTurn`).
- `status`: `SessionStatus` from `@/server`; the host shows an `unknown` status as `idle`.
- `turnSettlePending(userMessageId)`: true while the transcript read for that turn is in flight.
- `recordViewport(size)`: the scroller's measured size, which the session stores use to size the next transcript page read.
- `syncSession?`: reads a session's conversation; used for a subagent's parent when the child has no task description and the parent's transcript is not loaded.
- `settings`: four accessors (reasoning summaries, shell and edit tool rows expanded, turn tokens).
- `transcriptTypography`; `t: TimelineTranslate`, typed on the 63 keys the timeline uses (`TimelineTextKey`).
- `platform`: `openLink`, and `renderMermaid` from `desktopBridge()` (`@/lib/desktop-bridge`), present only on desktop.
- `openFocus(focus)`: opens a `TimelineFocus` (file, browser, plan or subagent) as a workspace-panel tab; a subagent tab records the panel's session as its parent.
- `openSessionInPane(sessionId, label?)`: opens a subagent in the pane at phone width.
- `findFiles(query, signal)`: file-search candidates; resolves to `[]` on a failed lookup, never rejects.
- `navigation.toSession(id)`.

## Props (`message-timeline-props.ts`)

`userMessages` are `TranscriptUserMessage`s: a runtime user message, or an `OptimisticUserMessage` (`origin: "optimistic"`, carrying the prompt's own `parts`) that the store keeps for a prompt the runtime has not echoed yet; the user row draws it until the echo replaces it. `queued` is the session's held prompts (`QueuedMessages`, owned by `src/session/transcript/queue.ts`), drawn after the last row until the admitted message appears in the conversation. `onScreen` is false while the floating composer's transcript is collapsed.

## Data

`TranscriptConversation`: `messages` sorted by id (the session store inserts by `searchById`), so `Binary.search` works; `parts` keyed by message id; `partsWithText`, the ids of parts whose text has had a non-blank character. The timeline never mutates these. Unchanged messages and part arrays must keep their identity across updates, because the per-turn memos are gated on identity (`timeline-row-equality.ts`).

## Status

| `SessionStatus.kind` | Timeline meaning |
| --- | --- |
| `idle` | turn over; the turn's diff summary shows |
| `working` | active turn: Thinking row, jump-button dot wave |
| `retrying` | active turn with a Retry row: the harness's `message`, a countdown to `nextAt` and the `attempt` when the harness reports them (Codex reports neither), optional `action` |
| `interrupted` | No active turn, Thinking or Retry row; the session dock offers Resume and the composer accepts a new message |
| `failed` | the newest turn stays the active turn but is not working: no Thinking row, no diff summary; its error row comes from the assistant message's `error` |

## Invariants

- The idle status can land before the turn's final transcript read. While `turnSettlePending(userMessageId)` is true the turn is still working: its Thinking row stays and it does not fold.
- A reader's toggle of a fold, a group or a tool row calls `onReaderToggle`, which stops following the end, so what opens grows downward and no row above it moves.
- The host's docks may cover the bottom of the timeline. `--timeline-dock-inset` (set by the session screen) pads the end of the scroll content by that band and lifts the jump button above it (`timeline-viewport.css`, `timeline-jump-button.tsx`).
- The jump button cancels its fade transition when it unmounts. A timeline leaves while that transition is still running, and Chromium can keep a removed element's running CSS transition on the document timeline, which held the whole detached timeline (431 nodes) alive after a session switch; flow 30's `image-never-loads` case measures it.
- The Thinking row stays painted for 80 ms (`THINKING_HIDE_HOLD_MS`, `thinking-visibility-hold.ts`) after whatever cleared it; dropping it at once collapses the virtualizer and jumps the composer.
- A row's key is stable across rebuilds and `TimelineRow.reuse` keeps an equal row's identity; a tag-narrowed row accessor (`rowOfTag`) latches the last matching row for the tick before Solid disposes the branch.
- Mount snapshots (scroll, measurements, open groups, open and revealed tools; `timeline-mount-cache.ts`) are kept for 64 sessions, fold choices (`turn-fold-store.ts`) for 16. Both are module-level caches, listed as named exceptions in `scripts/checks/data/module-state-exceptions.ts`.
- A transcript shorter than the viewport sits at its bottom (`data-timeline-bottom-anchor`, a flex spacer above the rows), so the latest turn first paints where it stays when older rows arrive above it.
- The column is 768 px wide, 880 px from a 1536 px window (`message-nav-layout.ts`, and the `md:` and `2xl:` max-width classes on each row).
- File paths in the transcript and terminal links resolve through `@/lib/workspace-file-focus`: `~`, `..` segments, paths outside the placement and the placement folder itself never open; a `:line[:col]` suffix is parsed off, so `src/foo.ts:42` opens `src/foo.ts` at line 42. The app cannot expand `~`.

## Why the rows are built this way

The row builder is `Timeline.constructMessageRows` (`message-timeline.data.ts`); the row union, keys, equality and reuse are `timeline-row-model.ts`.

- A turn's rows depend on whether each text part has text, not on the text itself. That fact is the store's `partsWithText`, recorded when the part's first non-blank text lands, so the row memo reads one key per part and the deltas after it wake nothing; the fold count reads a part's type untracked. Reading the text would rebuild every row of the turn on every delta of a streaming reply.
- The row memo hands the builder each message's part array unwrapped from the store, so building rows reads plain objects. A part array changes only by being replaced, which the memo tracks by key; the one in-place change is a streamed delta, and rows never read streamed text except the Thinking row's heading, which is its own memo while the turn works.
- The builder reads only a user message's `id`, `time.created` and optional `summary`, all of which the optimistic stub carries, so a just-typed turn renders before the runtime echoes it, and a turn whose prompt never reached the runtime still has a duration.
- Turn semantics (error, interruption, settlement, fold, tokens, cost) always come from every assistant message of the turn. The visibility set only bounds the part rows of the last turn on a cold idle open (the final assistant message and those holding subagent calls) until the reader's first interaction.
- A thought belongs to the tool it comes before: `groupParts` puts it in that tool's context or work group, so commands with thoughts between them fold into one group whose title counts only the tools. A thought before text, a lone work tool, a subagent spawn or nothing yet stays its own row. The last thought above a reply explains the reply; a streaming thought has no next part yet, so it draws open on its own and joins the group when the next tool lands.
- A run of tools cannot span the interruption row: grouping the refs whole would merge the runs either side into one group, which the fold would count as one where the turn draws two.
- A turn has a fold row only when it is settled, not working, and has `FOLD_MINIMUM` (2) foldable groups (`turnFoldDecision`, `@claxedo/agent-runtime-contract/turn-fold`), counted over the parts the turn holds. The server's page estimate (`packages/agent-runtime-contract/src/turn-page.ts`) counts with the same contract functions.
- The fold row is the turn's header: it sits above the turn's content, not wherever the first tool landed. An undefined fold choice leaves the turn on auto; an explicit choice always wins.
- The gap row before a turn is built once per turn outside its row memo and placed when the turns' rows are joined, before every turn but the first. A turn's rows never depend on its position, so a page landing above does not rebuild the turn that was first: with the gap inside the memo, a 9 KiB turn landing above a 5 MB one cost 91 ms at 4x CPU, most of it the 5 MB turn's rebuild.
- The live row: while a tool runs or a thought streams, the turn's trailing group is live (the work group reads "Running <command>", the reasoning row shimmers). The Thinking row fills every other stretch of a working turn, before the first part and between groups, so the live row flips between the two rather than stacking both. Only the newest assistant message says whether the turn is open and only its groups can be live: a step-per-message harness completes each earlier step while the next streams, and a stale busy status must not hang the row under a completed answer.
- Aborts: native aborts are recorded on the message itself; runtime aborts on the session's turn outcome, which must name the exact assistant message. Missing completion metadata is not an abort: a normal turn can be observed between its idle event and its completion checkpoint. The interrupted divider's duration ends at the turn outcome's `completedAt`, or for a native abort at the latest activity on the interrupted message's parts.
- An interrupted turn is a centred divider (`MessageDivider`) worded with the same `formatDuration` as "Worked for {duration}". A failed turn is an inline status line with its recovery action, not a card.
- A failed turn keeps its assistant message, not only the error: that message's `providerID` and `modelID` are what the turn dispatched with, and the error row names that provider.
- Part rows exist only for the contract's `GROUPABLE_PART_TYPES`, which must stay in step with the renderer's `PART_MAPPING` (`src/transcript/message-part.tsx`): a row for a part type with no component renders empty.
- The turn's summary diffs keep the last diff per file in display order, with a Set so a large summary stays linear.
- The indexes of assistant messages by parent and by pending completion exclude optimistic messages, which have no parent id and no completion time. A stub's parts are its own (`OptimisticUserMessage.parts`), not the conversation's, so the echo replaces message and parts in one step.
- A stale uncompleted assistant message makes its parent the active turn only while that parent is the newest prompt; once a follow-up lands, the new user message owns the turn even if the old completion frame is still in flight.
- An admitted prompt reaches the transcript over events before the next queue read drops its record. The record carries the id the turn's user message gets, so the queued bubble yields to the row as soon as the row exists.
- Per-turn row inputs are equality-gated (`timeline-row-equality.ts`): a streaming part event produces a new conversation snapshot and a new by-parent map every tick, and item comparisons turn that into work proportional to the changed turn. A session row's `lastTurn` is compared by `status`, `completedAt` and `assistantMessageId`, because the host maps fresh session rows on every list change.
- Rows are plain records built by a factory, not class instances: nothing asks `instanceof`, and a class could only be typed by asserting through `unknown`.
- A row element carries the turn key (`data-message-id`) and its own content (`data-content-message-id`, `data-content-part-id`): a user-message row is its user message, an assistant-part row the assistant message and first part of its group. The agent-app-benchmark driver reads them to verify that an exact message painted.
- The previous-messages row is not a restore anchor (`data-timeline-anchor="none"`): it is keyed by the first rendered turn, so the reveal it anchors re-keys or removes it.
- The virtualizer can publish an item list that briefly omits a key while its row is still mounted (`<For>` disposes it a tick later). A non-keyed `<Show>` accessor read in that window throws Solid's stale-value error and takes down the pane boundary, so the row entry is latched and renders its closing frame.
- `data-index` is stamped on a row element before `measureElement`, because JSX applies it after refs and `measureElement` drops unindexed elements; that call is also the mount measurement.
- The content element (`data-timeline-content`) wraps the queued bubbles too: the auto-scroll and scroll-state observers watch it, and a bubble mounting below the virtual rows counts as content growth.

## Why scrolling works this way

- Overscan is 1 row until the reader's first wheel, touch or pointer press, then 6: 6 rows leave no blank band on a 1,400 px/frame flick, and 12 rows still left 443 px blank at 5,600 px/frame while doubling the worst renderer task (16 to 31 ms).
- Opening at the end and staying at the end are different promises. `shouldAnchorBottom` opens a session on its latest turn; `followsEnd` holds while a turn is active (`turnActive`), and on a settled transcript only until the reader's first scroll gesture (the first view), because after that a size change is the reader opening a fold or tool row, and re-pinning to the new end takes them away from what they clicked. During the first view the virtualizer keeps the end and rows are measured before paint (`measureUnmeasuredRows`), so the first page, the latest turn's full read and late measurements land without moving the latest turn and a row never paints at its estimate and then shifts.
- The virtualizer's `rangeExtractor` is a getter, not a stable closure. virtual-core memoizes `getVirtualIndexes` on the extractor's identity plus overscan, count and range; Solid signals read while the extractor runs are invisible to that memo, so a stable closure serves stale indexes. Reading the signals in the getter, inside the adapter's tracked options read, subscribes the virtualizer and mints a new identity.
- The item-key function is a memo of the row keys, so its identity changes only when the rows do; a fresh closure on every options read would make virtual-core recompute every row's measurement on every adapter run. Size estimates read part text untracked: an estimate is a guess until the row is measured, and a tracked read would re-run the adapter on every delta of an unmeasured streaming row.
- Size estimates (`timeline-virtualization.ts`): turn gaps and fold rows use their typography heights; a text part of 20 or more lines among the last 50 rows is estimated at 26 px per line, capped at 60,000 px; every other row at 180 px. A 1,849-line part renders at about 53,000 px, and a low cap makes the anchored viewport chase a large correction, showing a blank viewport after a session switch. Overestimating is the cheaper error, so the cap only bounds adversarial payloads.
- A capped first fold forces its virtual measurements while the surface is still hidden and makes the bottom-anchor write before paint. `timeline-first-fold-reveal.ts` finishes that mount in a microtask after Solid commits the rows, rather than hiding a ready surface for another frame; its activation key and cancel flag stop a retained surface's queued task from revealing or scrolling a different session. The timeline holds its pane's reveal (`holdPaneReveal`) until then.
- Insert holds mean the reader owns the viewport. A row inserted inside the viewport near the tail (a reply's first part landing above the Thinking row, or an append) is already in view: pinning the bottom would shift every visible row by its height. The hold lasts 250 ms, covering the insert's own measure pass and the deferred bottom-anchor microtask. The displaced row is found by key, because index-keyed measurements are mid-flush. A history prepend changes the first key and is never an in-view insert. When the hold lifts, the timeline follows once if the insert pushed the tail below the fold; that decision is made at insert time, because a reply landing in the same batch as the idle does not read as working (`followsInsertBeside`, true when the displaced row is the Thinking row).
- `getTotalSize()` is read before `getOffsetForIndex` in scroll-to-message and before the tail check after an insert hold, because both read a lazily refreshed measurement cache and stale positions make the check miss.
- Resize compensation (`shouldAdjustScrollPositionOnItemSizeChange`) applies only to rows above the rendered range and stands down while bottom-anchored: anchoring already moves the viewport by the total-size delta, and a second compensation doubles it.
- A zero-height measurement is dropped: a rendered row is never 0 px, so zero means it was measured hidden or detached, and caching it collapses the total size to `paddingEnd`, painting the last turn at the top with a gap above the composer.
- The pin scan keeps a mid-history reader's visible rows rendered for two frames through a resize larger than the viewport. It is skipped while bottom-anchored: the anchor re-scroll wins anyway, and the scan forces a layout per rendered row inside the resize flush.
- Rows enter and leave the virtual list as the reader scrolls, so the list must not be a parent that sibling selectors track. It sits under `[data-component]` and `[data-slot]` ancestors, which Blink's ancestor filter cannot tell apart by value: a sibling rule whose ancestor compounds are attribute-only is matched against every row, flags the list, and each row added or removed then restyles the whole list. `30-unseen-transcript-work.spec.ts` asserts that a scroll causes no whole-list restyle. A reply's first and last elements are marked by its renderer (`data-markdown-edge`), not found by positional selectors (see the transcript README).
- Row frames carry no `content-visibility: auto`, and `file.css` forces file views inside a row `visible`: a row in skip state measures at its placeholder size, so an overscan row would be measured and painted at the wrong height and a fast flick would show blank boxes. The overscan band is at most 6 rows, so eager rendering is cheap.
- History prepend (`timeline-prepend-anchor.ts`) restores the captured row's offset each frame until it holds for 30 frames or 180 have run. When the anchored row is virtualized out (a reveal that prepends more than a viewport while the scroller is at the top), there is no element to measure, so the loop falls back to the virtualizer's own offset for the row; once that write brings the row into range, the DOM path takes over. A reader's gesture settles the loop: it applies the anchor once more and stops, rather than dropping the restore it owes, because the gesture often arrives before the loop's first frame and the virtualizer anchors a settled transcript to its start.
- Scroll memory (`timeline-scroll-memory.ts`) captures only from an active surface with a nonzero height, and not while the prepend loop is restoring: none of those is a new reading position.
- `message-timeline-observe-offset.ts` wraps the virtualizer's offset observer with restore-first reconnect. When the scroll element is detached and re-inserted under a persistent host (a workbench slot move, a suspense re-attach), the browser resets its scroll position while the virtualizer's `scrollOffset` still holds the place, and the stock observer never re-fires. The wrapper writes the stored offset back to the element; delivering the reset offset instead would render the range at the top and then re-anchor at the bottom, two row-set rebuilds in one long task. Only when the write does not stick is the native offset delivered. Its mutation observer sits at the persistent route root (`main`, or `body` outside it) to see a slot move, and reacts only to a removal, from one of the viewport's ancestors, that removes the viewport; additions matter only after such a removal.
- `timeline-displayed-frames.ts`: session surfaces stay mounted after the workbench stashes them, hidden with `content-visibility: hidden`. That stops style, layout and paint, not JavaScript: a stashed timeline's `requestAnimationFrame` loop would keep running against an element with no layout, never reach the settled measurement that ends it, and burn its whole frame budget once per retained session. The loop reads the displayed state on every arm and every frame (a surface can be stashed after a frame was scheduled), parks a stashed step rather than dropping it (restoring the reader's row is what a return needs), and `resume()`, called when the timeline becomes active, restarts a parked step. Bottom-anchoring likewise waits for `displayed()`, since `scrollToEnd` cannot land on a stashed surface.
- `active-pane-projection.ts`: retained panes stay mounted while hidden, and reading a query or store from them keeps the whole projection graph subscribed to background updates. The projection keeps its last value while inactive and stops reading the source; the active edge reads it once. The status, session rows and ambient subagents are projected while the pane is active and on screen, the title while it is active.
- Whether the timeline is on screen is an input the layout owns (`onScreen`). Off screen, the transcript's messages, each turn's parts and rows, and the timeline's row list keep their last value without reading the store (`whileOnScreen`), and the virtual list renders no rows. The store keeps accumulating, and the first frame back rebuilds the rows in one pass. Without it a collapsed transcript runs the virtualizer on every delta: 1,833 timeline computations and 178 geometry writes per streamed turn, for rows nobody can see.

## Why gestures work this way

- A wheel, touch or drag inside a nested `[data-scrollable]` box (a capped tool output) belongs to that box, not the transcript, until it reaches the box's edge; counting it would leave follow-bottom mode on every output scroll.
- The list's handlers (`message-timeline-list-gestures.ts`) receive `props` rather than a spread of it, so every read is a reactive prop access at dispatch time.
- A pointer press on a control (button, link, input, `role="button"` or `role="menuitem"`) is an action, not a scroll gesture: expanding the cold virtual range on pointerdown replaces the pressed row before click, so WorkGroup and recovery buttons would never receive the click.
- A drag-to-select starts on a child node, so a pointer move with the button held marks a gesture and autoscroll yields. Bottom-following itself belongs to the virtualizer (`followOnAppend`) and the resize anchor's re-anchor.
- The previous-messages row keeps focus off itself on mousedown: in the floating card a focused button blurs the composer, the composer folds, and the bottom-anchored row moves under the pointer before mouseup, so the click lands behind the card.

## Why the rail and gutter work this way

- The rail shows once the transcript has more than ten turns (`messageNavVisible`) and the pane fits the column plus a 60 px gutter on each side (`messageNavFits`). It mounts after the first reveal, in the frame its gutter first shows, so it appears with the rows that brought it.
- The compact rail reaches 48 px into the pane (`left-3` plus its 36 px width); the gutter reserves 60 px so every row, including a wide table or diagram, has 12 px after it. The gutter pads both sides, so the column keeps its width and centre and the transcript does not shift.
- The gutter is keyed off `data-session-timeline-nav-gutter` on the timeline root (`timeline-viewport.css`), set from the same memo that mounts the rail, never a `:has()` on the rail's own element. A `:has()` makes its subject a Blink invalidation anchor, and the timeline is the most mutated subtree in the app; no `:has()` may have an ancestor of the timeline as its subject.
- The gutter is decided before first paint by the ResizeObserver alone (`createMessageNavRoom`): its first callback runs after the frame's layout and before that frame paints, and a flip after paint would shift the whole column and restart every pending paint-stability wait. A width read when the timeline mounts would force the new pane's whole layout inside the switch task.

## Why links and files open this way

- A file, a plan and a subagent's transcript open as workspace-panel tabs, not a second pane: splitting takes the reader's turn down to half width. At phone width (`isPhoneWidth`, up to 767 px) the panel would cover that turn, so there the child takes the pane.
- File-path anchors and image links are handled in the capture phase, so `preventDefault` beats the markdown's `target="_blank"`; a bubble-phase handler lets Electron open the link in both a browser and the panel. The renderer marks every link `_blank`, including scheme-less local paths like `[README.md](/Users/…/README.md)`, which the browser would open as a dead tab on the app origin. Local `file:` URLs are also file paths; other schemes, protocol-relative hrefs and in-page anchors are not file paths, modifier and middle clicks are left alone, and a click that ends a text selection is not a navigation. Markdown image tiles own the full-image preview, even inside a link; an http(s) link on an image, a file-part link or an image URL opens as a browser tab.
- Other links reach the timeline as a `claxedo:open-link` event from the renderer (`timeline-link-open.ts`). An http(s) URL on `localhost`, `127.0.0.1`, `0.0.0.0` or `[::1]` is a dev server of this workspace and opens as a browser tab; any other http(s), `mailto:`, `vscode:` or `claxedo:` URL goes to `platform.openLink`. Any other scheme is left uncancelled and falls back to the anchor's own `_blank`.
- Path chips render mentions as `@path`, and the sigil is stripped before resolving; a path that really starts with `@` (an npm scope folder) is indistinguishable, and the mention reading wins. A `path-candidate` chip opens only after `findFiles` returns that exact path, because a wrong path would open a blank tab.
- File links inside the workspace open in the file panel. Absolute paths outside it open in the same file panel on desktop for placements on this computer; `useFilesApi` reads their contents through the guarded desktop IPC. Only the context menu's Open externally action uses `platform.openPath`. Unavailable or rejected opening reports an error.
- The context menu takes its path from a Markdown anchor's href, the chip's text or, for filename slots that render only the basename, from `data-path`. It offers Open and Copy path, plus Open externally when the desktop opener is available. Copy path resolves the absolute file path and strips line/column suffixes; slot text must not fabricate `<placement>/<basename>`.
- The `claxedo:open-link`, `claxedo:open-plan` and `claxedo:open-subagent` details ride on DOM `CustomEvent`s, so they are read structurally.
- Mermaid rendering is registered once (`installTimelineMermaid`). On desktop the renderer is the preload's `renderMermaid`: the main process runs the native helper (`claxedo-desktop/native/mermaid-renderer`) with the colors from `mermaidThemeVariables`, and mermaid.js is never loaded. A native failure leaves the code block; there is no fallback to mermaid.js. The web build draws with mermaid.js. Either way the transcript re-sanitizes the SVG through `sanitizeSvg` before it reaches the DOM.
- A wide table or diagram borrows the pane gutters only when its content is wider than the column, at most 20% of the column on either side, and never beyond the scroll viewport's content box after the rail gutters, so shrinking the pane removes bleed first (`markdown-surfaces.css`).

## Why failed turns read this way

- A failed turn's wire error carries more than `data.message`: the engine's `APIError` also has `statusCode`, `responseBody` and `responseHeaders`. The row's text is the message, with the relay prefix stripped and a JSON error body unwrapped to its type and message, followed by the response body when it differs; it sits in a disclosure, collapsed by default, with a copy button once open. `responseBody` exists on only some members of the wire error union, so it is read structurally.
- The row's summary is composed when the row is built, not at mount, so the primary line never paints raw provider bytes first; the card derives it only when a caller has none. The class copy (`turnRecovery.<class>.title`, `.description`, `.action` in the timeline's text keys) is translated at mount and is used only when the error gave nothing more specific.
- With an HTTP status, the summary is a status sentence naming the dispatched provider ("Anthropic rejected the credential (401). Check your API key in Settings, then try again.") for every class: a real status says something more specific than the class copy. Without one, the class keeps its repair sentence, a usage limit reads the provider's limit and reset time (`providerUsageLimitDetail`), and `unknown` ends at a sentence that still says what is known. A status-less error does not prove the provider was unreachable.
- Relays (the opencode gateway among them) prefix the provider's message with `Error from provider (<label>): `, where the label is the relay's upstream account, not a provider. The prefix is stripped, and the summary names the provider the turn was dispatched to, falling back to the relay label only when the turn has no provider id.
- An operator ACP connection dispatches with `acp:<slug>` as its provider id; its label comes from `harnessDisplayLabel` (`@/lib/harness-catalog`).
- The recovery class is attached to every failed turn, not only the first: it is position-independent, and the recovery line mounts on its presence. A turn-admission conflict reads "Message wasn't sent" instead.
- `turn-recovery.ts` reads the class the server stamps on `error.data.firstTurnErrorClass`, and classifies a class-less error with the server's own classifier, `classifyFirstTurnError` in `@claxedo/agent-runtime-contract`. It reads the credential broker's codes before the prose rules: without them a 403 naming a route the binding does not allow reads as `credential` and asks the user to reconnect a working account.
- `rate_limit` is a temporary refusal (a 429, "try again later") that the same account clears by waiting, so its line offers Resend. `usage_limit` is an exhausted plan or quota window, which a resend on the same account hits again until it resets, so it asks for another model or account, with no button. Harness adapters name either from the harness's own structured error where it has one; the message is read only without it.
- A failed turn names the account it ran on (`error.data.account`, which the runtime reads off the binding the turn launched on): a stored credential by its label, or this computer's login when none was bound. The runtime records it only for the native harnesses; a failure without one shows no account line.
- Recovery copy is position-independent (never "first turn") and says "agent", never "harness", "ACP" or "adapter".

## Why the smaller pieces work this way

- Queued prompts are drawn after the last row in the user-message bubble with the transcript's own `ui-user-message` classes, dimmed until admitted, so the hover action row behaves like a sent message's. The list is indexed, not keyed: every queue read returns fresh records, and a keyed list would rebuild each bubble on every read under the pointer. A prompt held by another client's edit shows as editing, releasable but not editable here. Its action buttons opt out of the 44 px touch floor (`data-claxedo-compact-touch`), since three floored buttons read as a toolbar.
- A subagent with a tool-call edge draws as a chip on that call's part, and only once the turn holding the part is loaded; a subagent with no edge (`ambient`) draws under Background subagents from the first paint.

## Flows

Flow 30 covers the timeline. `30-transcript-corpus.spec.ts` replays every case in `e2e/corpus/cases/` through the scripted agent and compares each stage (open, then after each scroll, fold toggle, reload or session switch) against recorded baselines: a screenshot, the turn rows' accessibility tree, the scroll position and the background subagents. `30-unseen-transcript-work.spec.ts` covers streaming off screen, the whole-list restyle and the jump button's dots; `30-transcript-markup.spec.ts` and `30-transcript-main-thread.spec.ts` cover markdown markup, copy and Mermaid.

## Diagram colors

Mermaid takes its theme colors from the app's CSS variables. The contrast theme's surface tokens are `color-mix(...)` expressions, which mermaid's color parser rejects, and an element's computed color serializes a mixed color as `color(srgb …)`, which it rejects too. `mermaidThemeVariables` resolves each token through an element's computed color and rewrites that form as `rgba(…)`; without it every diagram falls back to its code block.
