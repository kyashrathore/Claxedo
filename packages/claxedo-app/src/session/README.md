# Session data

## Reconcile rules of the session list

`src/session/list/transition.ts` is the one owner of rows, order and status in the rail. Nothing else fetches, caches or patches rows. These rules are the contract; a change here changes the transition and flow 31 in the same change.

1. **Subscribe, then fetch, holding events.** The stores subscribe to the server stream before the first list read. The list reads one page per project, 5 rows at a time, from the one server that lists that connection's sessions (`sessions.list`): the first read and every re-read fetch the first page of every project the catalog places, and `loadMore(projectId)` fetches that project's next page. A project whose page could not be read keeps no rows from that read and names its failure (`pageFailure`); the other projects' pages land. A page that lost one of its sources (a signed desktop's account page) lands the rows it has and marks its project `pageDegraded`, which the rail shows with a retry. A `sessionUpserted`, `sessionRemoved` or `statusChanged` that arrives while the first read or a re-read is in flight is held and replayed on top of the response; one that arrives while its own project's `loadMore` page is in flight is held for that page.
2. **The newer `updatedAt` wins.** A row is replaced only by a version whose `updatedAt` is not older; an older one is dropped whole. `lastHumanTurnAt` never moves backwards, because the server row can be written by a title change after the turn that ordered it. `createdAt` keeps the first value seen, so a list store and the runtime that each stamp creation never reorder sessions created close together. `lastTurn`, the outcome of the session's last turn, and the selections (`harness`, `model` and `permissionMode`) come only from the session's own read and its events, because a list item never carries them: a newer row without them keeps the ones held. The local list records a session at the runtime's own `updatedAt`, so a session's first read is never older than its listed row, and a selection write moves `updatedAt` when a value changes, so an older row never rolls a selection back.
3. **Tombstones.** A `sessionRemoved` leaves a tombstone keyed by the session id, timestamped at receipt. A list response or event that carries the row again is ignored while the tombstone stands. A response sent after the tombstone prunes it.
4. **A replay gap re-reads.** A `streamGap` re-reads every project's first page, replacing those windows; rows outside the first page are dropped, except open sessions, and `loadMore` pages them back. A gap during a read is remembered and the re-read follows the read. `sessionsChanged`, the server's doorbell for an inventory that gained or lost a row without naming it, re-reads every project's first page and merges it, so the pages `loadMore` fetched stay; a doorbell during a read waits the same way, and a waiting gap outranks it.
5. **Own create and send are pending entries keyed by `clientRequestId`.** A create shows a pending row (`pending: true`, a `pending:` session id) until the server's row confirms it or the request fails; like the server's row, it has no human turn, so it sorts where the server will put it. A send stamps the row with the send time so it moves to the top now. The first server version of the row newer than the one the send started from ends the stamp, unless all it changes is the session's selections (the send's own harness, model or permission mode write, which publishes the row before the turn starts): the same `lastHumanTurnAt` and last turn with a different selection keeps the stamp. When the stamp ends, if the server counted the turn as a human turn, that version's `lastHumanTurnAt` keeps the row on top; if it did not (the runtime stamps human turns only from signed actor claims, so an unsigned local app gets none), the row returns to the server's place. Only server timestamps are compared, so the browser's clock can't hold a stamp. A failed send removes it. Only the reader's own send moves a row before the server says so.
6. **No guessed status.** Status comes from `statusChanged` events, from the status each listed row carries (the list's server attaches the last status it knows, and whether an open permission or question waits on the user), and from an opened session's own read. A listed status is a read at its page's send time; an event at or after that time beats it, and an event also ends the listed wait, since a reply moves the session on. A session with no status fact is `{ kind: "unknown" }`; nothing derives status from timing or message contents. Background work is a second fact beside the status, kept apart because a turn's events never re-state it: `backgroundWorkChanged` events, the listed row's `backgroundWork` and the opened session's read feed it under the same rule (a read loses to an event at or after its send time), a status event never touches it, and it is held and replayed with the other events during a read. The row view carries both; `sessionActivity` (`list/activity.ts`) is the one reading of them for the rail, the workbench tabs and plugins: a wait on the reader, then a running turn, then a failed turn, then background work, which shows as working while the turn's status reads idle.

Order is flat and is the server's `human_turn_desc`: `lastHumanTurnAt` descending, where a session without a human turn counts as 0 and sorts below every session with one; then `createdAt` descending; then the session id descending. Each project's fetched window ends at the order key of its last row, so a project's rows are a prefix of that project's order across all its placements. A confirmed row after its project's key stays hidden until `loadMore` reaches it, even while it is open; a row of a project that has no window yet stays hidden until a read gives it one. Archived rows and subagents (`parentSessionId`) are not shown.

## Owned concepts

| Concept | Home |
| --- | --- |
| Session rows, tombstones, pending entries, the fetch window and page failure per project, and status per session | `list/` (`model.ts`, `rows.ts`, `statuses.ts`, `transition.ts`, `visible-rows.ts`, `reads.ts` for the first read, `loadMore` and re-reads, `store.ts`) |
| Per-row reads: `order()` is the visible rows' refs in order, derived from the entries and fetch windows alone, so a status never re-orders anything; `view(id)`, `rowOf(id)` and `statusOf(id)` re-run a reader only when that session's row view, row or status changes. Each keeps one signal per key being read, fed by one computation over the list's state (`list/keyed-reads.ts`); a status event re-runs a constant number of store computations and then only that session's readers. There is no whole-list accessor: a consumer that needs every row walks `order()` and reads `view(id)` | `list/store.ts`, `list/visible-rows.ts`, `list/keyed-reads.ts` |
| Agent requests (permissions and questions), their reply machine, and each session's last requests read: the session's own read and the list's bulk read both answer it, and the one sent last wins, so a failure shows until a read sent after it succeeds | `requests/` |
| One session's transcript, todos, diff, goal, older pages, the optimistic user message and the queue | `transcript/` (`context.ts` holds one session's state; `events.ts`, `snapshot.ts`, `older.ts`, `send.ts`, `queue.ts` and `goal.ts` change it; `store.ts` composes the view) |
| The subagents a session delegated to: from the session read on open and on a stream gap, then `subagentUpdated` events, merged by `subagentKey` with a revision per field (a terminal status never reverts; the child session and provider are set once; tool-call edges are only added) | `transcript/subagents.ts`, `transcript/subagent-merge.ts` |
| The LRU of open sessions, the one stream dispatch and the provider | `store/` |

Fetched data never enters these stores and pushed data never enters the query cache. A session's deltas are held by its transcript store (`transcript/deltas.ts`), merged per part field, and appended in place on the part's field when the session's view commits them (`view/delta-frames.ts`): once when the view mounts, before it renders, and then once per animation frame. A session with no view on screen schedules no frame, and its deltas wait, so a return renders the text that streamed while it was hidden in its first frame instead of revealing it at the streaming pace. Every other write to the transcript commits the held deltas first, so they keep their place in the order: a part upsert that carries text replaces what they added, and a snapshot overwrites text it already includes. A message or part upsert replaces only that message's parts array or the messages array, so unchanged messages and part arrays keep their identity for the timeline's row memos.

`partsWithText` records, per part id, that a part's text has had a non-blank character (`partHasText` and `textIsPresent` in `@claxedo/agent-runtime-contract/turn-fold`, the same test the fold groups by). The store sets it where parts land: an upsert, a page read, and a delta, which checks only its own characters, so a streaming reply is never scanned whole. It is set once and never cleared, because text only grows; a row that asks whether its part has text reads that one key and is not woken by the deltas after it.

## State machines

| Machine | States | Where |
| --- | --- | --- |
| Session list | `subscribing`, `fetching(held)`, `live(more per project: idle / loading(held) / failed)`, `rereading(held)`, `failed(error)`; each entry `confirmed`, `pending` or `tombstone` | `list/model.ts`, `list/transition.ts` |
| Session read | `loading(held)`, `ready`, `rereading(held)`, `missing`, `failed(error)`; shown as `SessionLoadState` (`rereading` shows as `ready`) | `transcript/model.ts` |
| Follow-up read | `none`, `waiting(replace / refresh)`; a waiting `replace` is not downgraded | `list/model.ts`, `list/reads.ts` |
| Older page | `idle`, `loading`, `failed(error)` | `transcript/model.ts` |
| Request | `open`, `answering`, `answered`, `expired`, `failed(error)` | `requests/model.ts` |

## The per-session store

- `open(ref)` returns the session's view and keeps the 8 most recently opened sessions; the ninth evicts the least recent, disposing its root and telling the list it closed.
- An evicted session keeps its latest turn (`retained`: the turn as the view holds it, with the older cursor of the latest-turn read) when it is idle, whole and has no pending prompt, in the same cache. A return to it while its list row's `updatedAt` is unchanged opens a view whose first read takes it as its transcript, so it asks for the row and outline without a page, and shows what a first visit shows: the latest turn, the nav rail and the subagents placed. A changed row, any event for the session or a stream gap drops the kept entry.
- A page lands in the conversation as one reactive update: `prependPage` and `replaceLatest` (`transcript/conversation.ts`) batch their writes to messages, parts and text presence, since each write otherwise re-ran the timeline's virtualizer effects and forced a layout (an older page's landing task went from 20-26 ms to 11-14 ms). Each read also lands whole: an older page with its cursor and phase (`older.ts`), the first read's row, page, outline, held events and phase (`snapshot.ts`), a tool part read whole (`part.ts`), a settled turn's messages and parts (`settle.ts`).
- Every page, the first read's and each older one (`SessionView.loadOlder`, the turns before the older cursor, as tall as the first page), sends every part of its turns, each tool part as its row header (`headerOnly`) unless the reader's shell or edit setting opens its row. Nothing is read after a page lands until the reader acts: opening a fold reads nothing, and opening a header row reads its whole part once (`SessionView.loadPart`). A whole part a later read or reread sends as its header keeps its body, and a newer whole part replaces it (`mergedPart`).
- The cache of kept sessions is bounded by count only: 32 entries, the least recently cached going first. A kept turn is never dropped, trimmed or refused for its size, because it is content the reader already loaded or watched generate (DECISIONS 2026-09-27 owner); byte budgets belong to what a first view reads.
- `outline` is the session's turn outline, read from its user messages alone: per turn the user message id, its created time and title, and a 120-character snippet of the prompt; the newest 500 turns, `complete` when no older turn exists. It arrives with the first read, from the control plane for a cloud session and from the runtime for any other, so a stream gap re-reads it with the snapshot. It moves `loading → ready(outline) | unavailable`; `unavailable` is a machine session whose machine is offline or whose runtime answers it has stopped. It feeds the nav rail's turns that are not loaded (`view/nav-turns.ts`). A turn that loads replaces its outline entry, a new turn arrives as a loaded message, and a turn removed from history stays listed until the next read.
- The snapshot read lands the row and status into the list, the requests into the requests store, and replaces the newest page of the transcript. Messages older than that page (loaded with `loadOlder`) stay. One read runs at a time; asking again joins it, and `loadOlder` joins an older-page read in flight the same way. The phase starts in `loading`, so events are held from mount, and the read in flight is tracked apart from the phase. Transcript events that arrive during a read are held and replayed after it; a held upsert never un-settles a completed assistant message or a finished part. Deltas are never held: a delta that lands before the snapshot is overwritten by it, because the snapshot already carries its text.
- `send` mints the user message id from the adapter, inserts the optimistic stub under that id (sorted last), stamps the list, and sends the prompt with `messageId`; the runtime echoes the user message under the same id, which replaces the stub. The stub is the echo the adapter predicts for the prompt (`promptEcho`: agent, model and the prompt's own parts), so the timeline draws the user's text before the runtime answers. A failed send removes the stub and the stamp and rejects with the `AppError`. `showSent` inserts the stub and stamps the list for a prompt that was sent another way: a draft's first prompt, which rides on the session's create.
- `turnSettlePending(userMessageId)` is true while a snapshot read is in flight and that id is the last user message.
- When the session's status turns idle, the last turn is read once by its user message id (`?turn=<id>&coverage=1`) and merged as updates, since a harness may end a turn without re-sending the assistant message with its completion time; without it the turn never folds.
- `queue` reads the runtime's held prompts through the adapter, re-read on: own send accepted, `statusChanged`, a user `messageUpserted`, and a stream gap. No timer. A queued record whose `messageId` matches an optimistic stub replaces the stub, so the prompt shows as queued and editable. `beginEdit` holds the record and sets `editing`; the composer owner loads its text (`queuedMessageText`) into the composer and calls `cancelEdit` to release it.
- `goal` comes from the snapshot's goal read and `goalChanged` events, which are held during a read like the transcript's. A goal fact older than the one held is dropped: a different goal is ordered by `createdAt`, the same goal by `updatedAt`. A removal records the removed goal's `createdAt`, so a late update of that goal can't bring it back. `goalActions` are the actions the session's harness supports; `controlGoal` applies the server's answer.
- `status` and `row` are read from the list store, `requests` from the requests store: one home per fact.

## Flows

Flow 38 (`e2e/flows/38-session-sources.spec.ts`): a project's rows are a true prefix of its order across its folder and its worktree at every Show more; a boot reads one page per project and no status, permission, question or wake; a project whose page fails leaves the others' rows and its retry loads it.

Flow 31 (`e2e/flows/31-session-list-races.spec.ts`): the race cases from the plan; at the end of each case the visible rail rows equal the server's list and statuses. The cases share one daemon per worker and each works in its own workspaces and project (`31-session-list-races.controls.ts`); the comparison covers the case's own sessions, including the ones it deleted (`31-session-list-races.oracle.ts`). The reconnect case restarts that daemon, because only a restart drops the server's event log and so forces the replay gap of rule 4; it runs last.
