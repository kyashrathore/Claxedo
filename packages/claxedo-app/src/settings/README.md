# settings

Owns: the settings sections the shell's settings page shows. The shell owns the page itself (`/settings/:section`), its sidebar mode and each section's `h1`; this domain exports `settingsSections` and draws what goes under the heading.

A connect that needs the provider's approval waits on `server.integrations.awaitGrant`, which reads the attempt again at the grant's interval (5 s unless the provider names one). A redirect grant (an MCP server's sign-in) settles on the deployment's callback page in the tab the sign-in opened, so the read also goes out the moment the person comes back to the app (the page turning visible or the window taking focus) instead of up to an interval later; a device grant (GitHub) waits out the provider's interval whatever happens, since polling sooner earns a `slow_down` that lengthens it.

`settingsSections` includes the Usage and Organization sections from their own domains. Settings → Models comes from `@/accounts` and is registered by the shell next to this array.

## Connecting a machine

The drawer mints a pairing code when it opens (`createConnectCode`, `pairing.ts`: `minting` → `minted` or `failed`, every event carrying its attempt so a late answer changes nothing) and shows the command the control plane answered for it, under a tab for macOS / Linux and one for Windows, the platform the browser reports chosen first. With no signed-in account it mints nothing and says to sign in. While no machine has redeemed the code, the line under the command counts down its 15 minutes on the shared second clock; when the code runs out unredeemed, or its pairing reads `expired`, the drawer mints another.

The drawer follows the pairing through `server.queries.machines.pairing(id)`, which the `machinesChanged` event refreshes with the machines list it sits under: the control plane's `machine.changed` notice, sent to the owner's organization rooms when a code is redeemed or its install reports, when it is answered, when a machine comes online or changes what it serves, and when its owner changes it. Each stage is one line: waiting for the command, installing on the named machine, then the approval card, then approved, connected and "<folder> on <machine> is ready"; or denied. The card (`PairingRequestCard`, `view/pairing-request.tsx`) names the machine with its system, architecture, country and when it asked, offers its name to change, shows the folder the command ran in, says so in one line when that folder is the home folder or the whole disk, and has Deny and Approve. A folder request from a machine already connected asks to share that folder on it and has no name. Its buttons run on the same `ActionState` machine as Details' actions, over `PairingAnswer`.

Signing out first cancels the person's unused codes (`machines.cancelPairings`), so a command pasted afterwards says its person signed out.

Under the pairing command, "For a server without a browser" (`ServerConnect`, `view/server-connect.tsx`) serves a machine nobody approves from a browser, such as a cloud VM on its first boot. It takes a name and the folder to share, typed in full as the server writes it, since a cloud-init run has no meaningful working folder; Make the command is enabled once the folder is an absolute POSIX or Windows path. It mints a pre-approved invitation (`server.machines.invite`, the hosted `machines.invite`): single use, for an hour, with that folder as the machine's one root, which the control plane assigns as its first workspace, as the person who minted it, when the machine redeems it, so nothing waits for an approval. The answer carries the commands with the control plane's own origin, shown under tabs with copy: a cloud-init snippet (the default), macOS / Linux and Windows. `createServerCommand` (`server-invitation.ts`: `editing` → `minting` → `minted` or `failed`) owns it; editing either field returns to `editing`, so no command shows for a form that has since changed, and an answer for an earlier attempt changes nothing. `CommandLine` (`view/command-line.tsx`) is the copyable command both sections show; a snippet keeps its lines.

## Connecting a machine over SSH

On the desktop, where the preload offers `window.api.sshConnect` (`ssh-bridge.ts` reads it and turns each answer into a typed value; anything else is the `unavailable` failure), the drawer also has Connect over SSH… (`SshMachineConnect`, `view/machine-ssh.tsx`). The person gives `[user@]host`, and optionally a port, a key file and the folder on the machine to share (the home folder when empty); their own ssh config and agent do the rest, and nothing is stored. The flow is the `SshConnect` machine (`ssh-connect.ts`): `editing` → `checking` (Electron main runs the system `ssh` non-interactively and asks the machine for its system) → `confirmingHost` when the host is unknown, showing each key's fingerprint until the person trusts it (`trusting`, which records the key in their own known_hosts and checks again) or cancels → `minting` (`server.machines.pair()`, the drawer's own code path) → `installing` (main fetches the connect script from the account's control plane, runs it only when it hashes to the sha256 the plane states beside it, and streams exactly those bytes to `sh -s -- <code>` in the chosen folder; the script's numbered steps arrive as they print) → `installed`; any step can end in `failed`, which keeps the form for another try. Every answer carries its attempt, and a step carries its run id, so a late answer changes nothing. While it installs, the pairing is followed through `server.queries.machines.pairing(id)` as the pasted command's is: the same `PairingRequestCard` once the machine asks, then the stage line up to "<folder> on <machine> is ready". Closing the drawer cancels a running install. Each failure is one line: no ssh on this computer, no such key file, unreachable host, refused sign-in, a changed host key, known hosts the ssh config does not keep, a system other than Linux or macOS, no such folder, a script that could not be downloaded or failed its checksum, a dropped connection, or the machine's own line (an expired or used code, a denial).

## Machine details

`createMachineCheck` (`machines.ts`) runs when the drawer opens and on Check again, never on a timer. It walks three hops in order and stops at the first that fails, so every hop after it reads "Not checked":

1. This device to Claxedo: `server.machines.recheck()` reads the devices list past the cache with no retry. A refusal is the hop's failure, shown by its error class's title.
2. Claxedo to the machine: the machine on that fresh list, found by its host id. Absent (removed elsewhere), Paused or Offline is the hop's failure; otherwise its last check-in is the detail.
3. The machine answering through the relay: `server.machines.probe()` reads `/global/health` of the first folder the devices list says the machine serves (`serving_workspace_ids`: assigned and acknowledged on its latest beat) through the transport, which mints the folder's connection and goes through the relay. A machine that serves no folder leaves this hop unchecked.

The `MachineCheck` machine is `reachingClaxedo` → `reachingRuntime` → `finished` with a `CheckVerdict` naming the failing hop; every event carries its attempt, so an answer from before a Check again changes nothing. The headline names the first failing hop, one line says what to try (`claxedo doctor` on the machine for an offline one), and Copy diagnostics copies the hops, the facts (state, last check-in, folders served, error class and code, when and which attempt) as text.

Pause and Resume are one button that flips with the machine's state (`machines.pause` / `machines.resume`, the owner's `POST /api/claxedo/host/enrollments/pause` for that host id only); the line under it says what happened ("Paused: nothing reaches <name> until you resume it"), and the check runs again. Remove asks through `requestConfirm` (its sessions stay in history; new ones cannot start there until it is added again), then `machines.remove` revokes it, the drawer closes and a toast says it was removed. `ActionState` (`idle`, `working`, `done`, `failed`) owns the buttons' busy state and the line; a failure names the action and its error class's title.

What the machine reports about itself comes from the devices list as the control plane answers it; the app compares nothing. When the machine said why it cannot serve (`MachineBlock`: its Linux service cannot start while lingering is off or without its user's systemd, its Windows task waits for its user's logon, the desktop app's daemon runs beside it, or it was stopped), `BlockedNotice` (`view/machine-report.tsx`) heads the drawer with that one line and the command the machine named to fix it, with a copy button; the control plane clears it when the machine next starts serving. `MachineFacts` shows its CLI version and system and, while the control plane says the CLI is below the version it accepts, "Update available" with the command that updates it.

Rename (`view/machine-rename.tsx`) changes the machine's name through `machines.rename`, the remote-access devices route's `PATCH` for that host id. Shared folders (`view/machine-roots.tsx`) lists the owner's roots for a machine that has them, each with Stop sharing: `requestConfirm` names the projects the devices list says removing that root alone retires, or says nothing runs from it, then `machines.setRoots` sends the other roots to the owner's scope route, which retires those assignments in the same write. Both re-read the machines list and the placements around it, and run on `ActionState`, the folder being removed as the action.

## Keyboard shortcuts

Rows are the palette's registered commands (`commands.options()` filtered by `commands.has`, which drops the palette's "suggested" copies) plus the palette itself (`command.palette`, as today), grouped by each command's category. Recording suspends the palette's own keybindings (`commands.keybinds(false)`) until a key is pressed or Escape cancels; the recorded binding is stored with `commands.setKeybind`, so the shell stays the one home of overrides. The section draws its first 40 rows at once and 60 more each animation frame (`view/reveal.ts`) until every row is drawn, so opening it with hundreds of commands stays under one frame; rows are keyed by command id, so a rebound shortcut updates its own row's text and nothing else is rebuilt.

## Strings

`i18n.ts` imports one dictionary per language from `locales/`; English is complete and the other sixteen fall back to it.
