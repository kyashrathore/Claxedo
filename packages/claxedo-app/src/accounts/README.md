# Accounts

Owns: the logins each agent harness runs on, and today's app's surfaces for them: Settings → Models (`modelsSettingsSection`, registered in the shell's settings sections) and the first run's AI step. Both render the same `AgentHarnessAccounts` for the CLI harnesses (Claude Code, Codex, Cursor) and the same `HarnessProvidersSection` for the catalog harnesses (Pi, OpenCode).

## Data

- `useAccounts()` (`store.ts`) reads stored accounts (`server.queries.accounts.list`), the ones in use (`effective`) and whose account the person spends per provider with the organization's own rows (`sources`, `/api/claxedo/credentials/account-sources`), all from the connected server: on a desktop that is the daemon, whose selection decides what a local turn spends, so the Organization-account row and the choice shown are the ones local turns honour even while signed in (`src/server/README.md`, sandbox keys). `onMachine()` says whether this server is the machine the harnesses run on: the bootstrap names a serving machine (`server.capabilities().servingMachine`), whose name is `machineName()`. Only then does it read this machine's CLI logins (`machineLogins`), and on the web the snapshot holds none. Nothing reads them at app start: the machine-login read starts the harness CLIs, so it runs only when Settings → Models or the AI step mounts.
- Rescan asks every CLI again (`server.accounts.rescan`, `fresh=1`) and rereads the stored rows; on the web it only rereads them (`server.accounts.refresh`). Select, remove and check go through `server.accounts`; a failed write is a "Request failed" toast.
- Selecting, removing and changing cloud consent are one exclusive `activity` (kind and key). Checks are not: the store keeps the set of accounts whose check is in flight, keyed by the credential id (a machine login by `machineCheckKey`, one per harness), so a check on one account never disables another account's Check, and `checking(key)` answers for one account alone.
- A live check of a stored account is kept on the page (`liveChecks`) and outranks the verdict the server stored; a check that never reached the provider is kept as `unknown` with its reason, so the row says "Couldn't check · {reason}".
- Each row's Check (`AccountCheckButton`) is disabled while its own check runs and marks itself `aria-busy`, which turns its icon for at most 34 turns of 0.9 s (about 30 s, the server's provider requests time out at 10 s each); under reduced motion the shared `reduced-motion.css` stops the turn and only the disabled state shows. Its tooltip says "Check now · last checked {ago}", or "Check now" before any check, and the compact age stays beside it.
- `model.ts` holds the harness list (Claude Code, Codex, Cursor) and the rules: which row is selected (the org account when the person chose it for every provider of the harness; otherwise, among their own, the server's effective read when it names one of their rows, then the stored mark, then this computer's login), whether a login is refused or unavailable, whether this computer's login would strand a binding, and whether a harness can run a turn (`harnessRunnable`). Off a machine (`cloudOnly`) every session runs in a cloud sandbox, and a harness runs only on an account the server says reaches the cloud (`delivery.cloud`, the server's `credentialReach`). A sandbox is delivered one account per person per vendor host, the most recently chosen; today the accounts of one harness that reach the cloud all answer on its vendor's one host, except a ChatGPT plan, which answers on its own host and reaches a sandbox as its access token. So the account in use is the most recently chosen of those (`accountInUse`), and the choice applies to every harness that uses that vendor, Pi included, which the harness's account list says on the web. Saving another account never switches the host; only choosing one does. On a machine a harness binds through the first of its providers holding an account.
- `account-words.ts` turns a row into what the row says: label, second line (verdict, plan windows), hint, alert, reach and cloud consent. Only a refused health (`isRefusal` in `@/lib/account-health`: the provider turned the login away, its billing is gone or it expired) offers Reconnect and stops the harness running; a rate-capped account is marked with when its soonest window resets, keeps its radio and runs, since the cap lifts on its own.
- On a machine each row says in words where its login comes from and where it works: "Stored in Claxedo" (stored keys belong to the account) or, for a CLI login that names its email, "Signed in on {machine}", then "Local and cloud" or "Local only", with the longer explanation as its tooltip. A CLI login without an email is labelled "Login on {machine}". The machine's name is the machine list's row for this machine (`queries.machines.list()`, named by Electron main on the desktop). The web shows neither: every account there is stored and every session runs in the cloud.
- A harness with no account says "No {harness} account yet" with Add an account. While the reads load, the section says "Reading sign-ins on {machine}…" on a machine and "Loading accounts…" on the web, after the placeholder delay.

## Organization account and cloud consent

- A CLI harness lists an "Organization account" entry after the person's own accounts and this computer's login only when the organization has an account for that harness, or the person has already selected the org source. An absent unselected org account renders no row; a selected org source with no account stays visible with its unavailable explanation until the person chooses their own account or machine login. Choosing it writes `org` for all of the harness's providers (`server.accounts.setSource`); choosing any own entry writes `own` first and then marks the chosen account (`server.accounts.select`), on the web as on a machine; this computer's login is chosen by clearing the marks, which only a machine offers. Only the chosen side is ever spent, so an org choice where the organization holds no row of its own is shown as unable to run, never as a fallback to the person's own key, and says the organization has no {vendor} API key and to ask an admin to add an organization account.
- The server's `can_manage_org_accounts` fact says who adds, checks and removes the organization's rows: its owners and admins on a hosted plane, the unsigned local operator on the single-user installation; everyone else only chooses them. `useAccess().can("accounts.manageOrg", sources)` reads it in three places: the org row carries its credential ids, and so Check and Remove, only for a manager (`orgAccountWords`); Add an account offers the organization only to a manager (`organizationTarget`); and the removal deletes every stored binding in the account and refreshes the listings. The CLI's machine login never carries removable credential ids.
- An organization account is one API key per vendor, saved under the harness's vendor provider (`vendorProvider` in the runtime contract's `HARNESS_TABLE`: `anthropic` under Claude Code, not `claude-sdk`), so every harness that runs that vendor can choose it: the CLI harnesses whose providers include it and Pi when a Pi provider spends it (`harnessesServedBy`, `model.ts`). Removing a row asks first through `requestConfirm` with the destructive button ("Remove {label}?"); for the org row the dialog lists those harnesses in the app's locale ("Used by Claude Code and Pi", `useServedBy`, `Intl.ListFormat`).
- Off a machine (`cloudOnly`) with two or more rows to choose from, a help icon beside the harness's Accounts tab (beside its name on the AI step) carries the sentence that cloud workspaces use one {vendor} account for the person and that the choice applies to every harness running that vendor (`CloudChoiceHint`, `offersCloudChoice`); with one row, or on a machine, there is no choice to explain and no icon.
- On the web and the desktop alike, each Pi provider row offers the same own/org choice where the organization holds an account or the person chose one (`CatalogAccountSourceChoice`), read from and written to the shared `/api/claxedo/credentials/account-sources` for the stored providers the Pi provider runs on (`piProviderAccountIds`).
- On a machine (`onMachine()`), a stored account that its provider can deliver to a cloud sandbox carries an "Allow in cloud sandboxes" switch, which writes `local` or `shared` to every row of the account (`server.accounts.setScope`); an account whose rows disagree says cloud use is allowed for some bindings, and a failed write stays on the row.

## Catalog harnesses

`createHarnessProviders(harness, placementId?)` wraps the composer's `createProviderCatalog` over `server.harnessConfig.providers`, without a workspace for account settings: the providers the harness offers, the connected ones first, and each connected provider's detail loaded once so its source tag (Config, Environment, API key, Custom) can show. A catalog of more than 24 providers lists the connected and the popular ones until a search names others. Connect opens the same drawer in the engine's words ("Connect {vendor} for {engine}"); Disconnect, offered for API-key and custom providers, deletes the person's stored rows of that provider id alone (`server.providerConnect.disconnect`), so another harness's account for the same vendor stays; a disconnect that removed nothing fails rather than reporting success. Each stored key of yours under such a provider (`providerOwnKeys`, `model.ts`) is a `KeyRow` with Check alone, the same check and words as a sandbox key (a provider Claxedo cannot check says so), since Disconnect is that row's remove; Disconnect asks first through `requestConfirm` with the destructive button, naming the provider and the harness whose saved keys it deletes. A Pi provider connected by another harness's login (Anthropic by a Claude Code token) is tagged "Via {harness}" (`source: "harness"`) and offers no Disconnect. OpenCode also takes a custom OpenAI-compatible provider (`DialogCustomProvider`, a `FormDrawer` whose description links OpenCode's provider docs, saved through `server.providerConnect.saveCustomProvider`): its key rides in the header the form names (Authorization sends it as a Bearer token), its other headers are only the contract's metadata allow-list (`isCustomProviderMetadataHeader`), and disconnecting it also drops its declaration. The server offers a key for each provider the organization declared.

## Models tab

Each harness section on Settings → Models has an Accounts and a Models tab, except a harness with no account to run on: a Claude Code, Codex or Cursor with none stored or logged in, and a Pi or OpenCode with no connected provider, show only their title and the rows that connect one (the Pi and OpenCode list keeps its search only while the catalog is large enough to list just the popular providers), the open one remembered per harness while the page is open, and a "{count} models" figure on the Models tab for the models switched on once they are listed. Accounts always render, including before any project or workspace exists. Switches and Enable all / Disable all write the composer's model visibility (`useModelVisibility` from `@/composer`), which the composer's picker reads. Enabled ACP connections get a section whose Accounts tab says they run on the connection they were set up with.

Claude Code, Codex and Cursor list their models without a project (`useAccountModelSource`, `model-sources.ts`): `server.queries.harnesses.catalogOptions(harness)` reads the connected server's `/api/claxedo/credentials/harness-models`, the list for the account the person runs that harness on (the daemon on a desktop, whose selection decides what a local turn spends; the hosted plane on the web). Claude Code's and Codex's come from the lists the server ships for its Claude Code and Codex versions, Claude Code's in the form of that account (a plan's or an API key's; this computer's login lists the plan's, since asking it which would start the CLI), and Cursor's from Cursor's API with the person's stored Cursor key. So a desktop whose installed CLI is newer or older than those versions may offer a model in the composer that Settings does not list. The read sits under the accounts query prefix, so choosing, adding or removing an account reads it again. A refusal names the harness and the server's reason ("Couldn't list {harness}'s models: {reason}"): no account chosen, an organization account the organization does not hold, no stored Cursor key, or Cursor unreachable.

Pi, OpenCode and the ACP connections list a workspace's models, read for the settings placement, a pure derivation (`settingsPlacement`, `settings-placement.ts`) of the projects list (`useProjects`, in catalog order) and the placements, with five states, each drawn by `PlacementNote` (`models-tab.tsx`):

- `loading` while the projects list loads;
- `failed` when it cannot be read, with its error's message;
- `noProject`: models appear here once there is a project, and the accounts are in the Accounts tab;
- `unavailable`: there are projects, but none is available with a primary placement, so the first one is named with why it cannot answer: its folder is missing (the project's `missingCheckout`, with the folder) or its workspace is not available;
- `ready`: the first available project's primary placement, named by its project.

Only opening such a Models tab in the `ready` state reads that harness's models (`usePlacementModelSource`): OpenCode from its provider catalog (every provider's detail loaded once), Pi and a connection from `server.queries.harnesses.options`. Both sources are a `ModelSource` of `loading`, `failed` (with the reason the read's `AppError` gives) or `ready` with its groups. A failed placement read says that the project could not list the harness's models and why ("{workspace} couldn't list {harness}'s models: {reason}"); a read that lists none says the harness reports no models. Models are grouped by provider (Pi by vendor); a harness that is its own only provider lists its models without a group row.

No read the Models tab makes starts a workspace or a harness CLI. The account read never names a workspace; `queries.harnesses.options` goes through `readHarnessOptions`, the read the composer's draft uses, which refuses an asleep workspace rather than waking it (`src/server/README.md`, Waking and Harness options). Provider catalogs are the server's, and OpenCode's per-workspace catalog is answered without the runtime while it is down. Account catalogs are unscoped and never wake compute.

Provider model groups render one `SettingsList` card: the header owns provider identity, enabled count, disclosure and bulk action; the body owns search and shared `SettingsRow` model switches; the footer owns the shown/matching count and loading ten more. Expansion is local UI state initialized from enablement once; changing individual or bulk visibility never changes it. A search change resets its ten-row preview. `model-rows.tsx` virtualizes more than 100 loaded rows. Visibility keys and group context are owned by `model-sources.ts`, shared by the rows and harness counts.

## Harness catalog (`@/lib/harness-catalog`)

- The ids, names and provider ids of Claude Code, Codex and Cursor are the runtime contract's `HARNESS_TABLE`: the server stores a login against those ids and the machine scan reports them, so a second list here would lose an account the moment the two disagreed. Pi and OpenCode are engines a reader picks, not logins anything is stored against, so they carry only a name and a brand mark.
- A key no catalog entry answers to (a historical session's harness, an operator's ACP connection id) is named by `harnessDisplayLabel`, the label of last resort; a server-supplied label wins wherever discovery data is at hand.
- A registry key (`claude-sdk`, `codex-app-server`) names the binding a login is stored against and nothing a reader would recognise, so it is shown as its harness's name (`harnessLabelForProviderId`).
- A harness's vendor id (`anthropic` under Claude Code) is that vendor's models routed through the harness, never something signing its CLI in answers for. A login's reach is compared against the harness's bindings only (`partialMachineLogin` in `model.ts`); against the full list every complete login would read as partial. A key the table has never heard of has no vendor row to subtract, so its whole list is its bindings.
- The connect card says one of two sentences (`ConnectContext`): `harness` is a login the harness itself runs on (one account, one harness); `engine` is a vendor's models made available inside an engine that runs several vendors, where the account is not the thing being run. Only the provider id a harness's own sign-in is stored against (`harnessForConnectProvider`) takes the harness sentence; every other provider id (`openai` under Codex) takes the engine one. Both halves of each sentence are read through `connectContextKey`, so a locale that carries one and not the other shows a missing string rather than quietly falling back to the other sentence.

## Connect

"Add an account", "Reconnect" and a catalog provider's Connect open `DrawerProviderConnect`, a `FormDrawer` whose description says the account is saved to Claxedo. `createProviderConnect` (`connect-form.ts`) lists only the methods the server returns for the provider (`server.queries.providerConnect.authMethods(harness)`; a hosted server returns only those whose account a cloud sandbox can be delivered, which includes Codex's ChatGPT plan sign-in), joined by type to the vendor copy in `connect-methods.ts`; while they load, when the read fails, and when the server offers none, the drawer says so and its submit stays disabled. A provider with several methods offers them as a radio group, and the chosen method's fields follow below it. The drawer's one submit does the chosen step (`connectSubmit`, `connect-submit.ts`): Continue (or Replace account) saves a pasted key or token, Sign in starts a sign-in, Continue sends its pasted code, and while a sign-in is pending or waiting for the browser the submit says so and stays disabled.

- On a harness's Add an account a manager first chooses For me or For the organization (`ConnectAudience` in `connect-state.ts`; a member never sees the choice, and Reconnect never offers it). The organization's side lists only the API-key method and saves with `server.accounts.saveOrgAccount(vendorProvider, secret, label)`; the server refuses a Claude or ChatGPT plan pasted there, since a plan belongs to one person, and the refusal stays under the key field. A vendor already holding an organization account says "This replaces {label}". Its toast says the organization account was added and which harnesses can now choose it; adding it changes no one's choice.
- A key or subscription token for the person is saved as a managed credential with the user's label (`saveKey`, the same route on the desktop and the web) under its method's kind, `api_key` or `oauth_token`, so the server can refuse a subscription token that is not the access token `claude setup-token` prints and say what it is instead; or it replaces the token of the account being reconnected (`reconnect`). A refusal stays under the field only until the value is edited (`setValue`, `setCode`). The server keeps one row per upsert key, so a save can replace a stored account rather than add one: the hosted store keeps one row per person and provider whatever its kind, and the registry on a machine keeps one pasted subscription token per provider because a token names no account (an API key is fingerprinted, so a second key is a second row). `replacedAccountLabel` (`model.ts`) mirrors that rule from the stored snapshot; when it names an account, the form says "This replaces {label}" above a Replace account button and starts the label field on that account's label, so the replacement and its label are the person's choice, never silent;
- a sign-in runs `authorize`, then `callback` (at once for an `auto` grant, after the pasted code for a `code` grant), handing back the `attempt` the authorize answered: the server keeps no state between the two, so the callback can land on another instance. A failed sign-in shows its error under the fields, and the submit starts it again.

Success shows "{vendor} connected" (or the organization toast), rescans (on the web, rereads the accounts) and closes the drawer.

## Sandbox keys

Settings → Sandbox providers (`sandboxSettingsSection`, `SandboxSection`) holds the keys for the services that run cloud workspaces, which only the sandbox manager spends and no harness or workspace receives. Signed out it shows only the sign-in notice, since a signed-out desktop provisions no cloud workspace. `useSandboxKeys()` (`sandbox-store.ts`) reads `server.queries.accounts.sandbox()` (`/api/claxedo/credentials/sandbox-drivers`, the hosted account's answer wherever one exists, so a signed desktop lists the organization's keys its cloud workspaces start on, and its Check and Remove are `server.accounts.checkSandboxKey` and `removeSandboxKey`): the drivers this host can start a cloud workspace on (every catalog driver that runs in a Worker on a hosted plane) with their fields, the stored keys and the driver new workspaces use. Cloud workspaces start only on one of these keys; a deployment has no provider account of its own. A server that keeps no sandbox keys answers 501 and the page shows only its error; the keys are drawn only when `useAccess().can("sandbox.manage", …)` passes on the listing's `can_manage` fact (an organization owner or admin on a hosted plane, the operator at the machine locally), and anyone else reads that the organization's owners and admins manage them. The key form is one implementation (`view/sandbox-key-form.tsx`): `createSandboxKeyDraft` holds the chosen provider, its field values, the missing-field check and the save (`server.accounts.saveSandboxKey`, checked at once), and `SandboxKeyFields` draws the provider select and its fields. Add a key… wraps it in a `FormDrawer` (`DrawerSandboxKey`); the first run's Where step renders it inline in its card (`InlineSandboxKeyForm`). Check and Remove are the accounts' own `check` and `remove` (`KeyRow`), and Remove runs only once `requestConfirm` returns yes from its destructive Remove key; the default picker lists the drivers that hold a key and writes `server.accounts.chooseSandboxDriver`, and with no key reads "None yet". A check that never reached the provider stays on the row as "Couldn't check" with its reason.

## Flows

- Flow 15, "accounts can be connected before any workspace exists": with no project, disconnect Pi's providers through the confirmation (cancelling once keeps them), add a Cursor key, see it in Accounts, and see a connection's Models tab say models appear once there is a project.
- Flow 15, "with no project, Claude Code and Codex list the server's models": Claude Code lists Opus, Sonnet and Haiku and Codex its models, Cursor with only this computer's login says it needs a stored key, the only model reads are the three account reads, and no workspace connection is asked for.
- Flow 15, "a project whose folder is gone": with the only project's folder deleted, the Scripted ACP connection's Models tab names the project and its missing folder, and Claude Code's still lists its models.
- Flow 15, "a workspace that cannot list a connection's models": with the folder deleted after the projects were read, the Scripted ACP connection's Models tab names the project and the read's failure.
- Flow 15, "Models lists each agent's accounts": add two Cursor keys through the drawer, switch between them, remove both through the confirmation (both apps).
- Flow 15, "Check runs for its own account alone": with two Cursor keys, a held check spins and disables only its own Check, the other stays available, both settle to "Couldn't check", and the tooltip says when it last ran.
- Flow 15, "the operator adds an organization account": as the local operator add a Cursor organization account from Add an account (For the organization), choose it, see its Check, remove it through the confirmation that says it is used by Cursor, and see the chosen organization side left unavailable.
- Flow 15, "the local operator removes a saved organization account": select the machine login, see the org row's Check, cancel removal in the dialog that lists Claude Code and Pi, remove the saved organization credential, and verify deletion and machine selection persist after reload (desktop and phone).
- Flow 15, "a chosen organization account that was removed": the org choice is refused while the organization holds no Cursor account, an organization Cursor key is added, chosen and removed, and the selected source says the organization has no Cursor API key and to ask an admin to add an organization account, choose the machine login, and verify the empty org row disappears and the own-source selection persists after reload (desktop and phone).
- Flow 15, "the machine's operator adds a sandbox provider key": add a Modal key through the Sandbox group, see it checked and chosen as the default provider, remove it (web and phone).
- Flow 53, "a member chooses the organization account": a signed member sees and chooses the organization's Cursor account without Check or Remove, gets no For the organization choice in Add an account, and with two rows reads the cloud choice in the help icon beside Accounts.
- Flow 59, Settings → Models beside an asleep cloud workspace: Claude Code's Models tab lists Opus, Sonnet and Haiku from the hosted plane's account read, which names no workspace, and nothing asks to start the workspace and the server starts none.
- Flow 1 checks the AI step lists the Claude Code card.
