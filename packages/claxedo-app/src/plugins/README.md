# App plugins

An **app plugin** changes this app: it adds sidebar items, pages, panes, settings sections, overlays, commands, `@` mentions, themes and icon skins, and calls the app's own server as the user. It runs in the app, never on the server or in an agent. An **agent plugin** (the Marketplace, `src/marketplace/`) changes what an agent can do: it installs skills and MCP tools into agent sessions and runs where the agent runs. The two share nothing but the word; every user-visible string here says "App plugins".

The plugin host. It runs the app's built-in first-party plugins, which the host ships as bundles, and the machine's live plugins from the daemon, and it is the only code that knows a plugin exists. Both kinds get the same `PluginApi` and the same loaders. The contract is `@claxedo/plugin-api` (`packages/claxedo-plugin-api`); this folder implements it over the shell's registries.

## Owned concepts

- **Plugin build** (`model.ts`): a manifest, its origin, the `definePlugin` definition and an optional dictionary. The origin is `live` (the plugin's folder, the daemon's bundle hash, when it was built and its last build error) or `bundled` (the hash of the bundle the host shipped). A build's identity is its hash, so every save of a live plugin is a new build.
- **Activation** (`activation.ts`): `activate(api)` runs inside a plugin-owned Solid root under `catchError`, with context from `HostServices.owner` even after asynchronous loading or when another owner is active. Every registration goes through the plugin's `RegistrationSink` (`registrations.ts`). Activation disposal aborts `api.context.signal`, disposes every entry, runs the cleanup `activate` returned and disposes the root. Solid roots do not dispose automatically with their parent; the provider disposes its host, which disposes each lifecycle's activation. A sink refuses registrations after its plugin is disposed.
- **Bindings** (`bindings/`): the `PluginApi` for one build. `transcript.toolCards` (`bindings/transcript.ts`) registers tool card templates into the shell's `toolCards` registry through the build's intake (`bindings/tool-card-intake.ts`), refusing a tool that already has a card. A live build's templates are checked with `readToolCardTemplates` (`bindings/tool-card-check.ts`, a chunk of its own with the plugin API's zod schemas, fetched before a live build activates); a bundled build's are the host's own code, registered as given and checked by its package's tests (`tool-cards.test.ts` in Tasks and Documents), as a bundled plugin is approved because the host ships it. A template's page link resolves to the plugin's own page first, then to an app page of that id, as `pages.open` does. The transcript draws them (`src/transcript/tool-card-template.ts`). `sessions.open` resolves the session's workspace through `placements.locateSession` (one catalog reread when the catalog does not hold that workspace yet, as after a cloud start creates it) and then navigates, so a plugin can open a session the list has not shown yet. `workspaces.followStart` (`bindings/workspaces.ts`) follows a cloud workspace's start through `cloud.followStart` and reports each step in the session screen's words (`useWakeProgress`) until it runs or fails; the failure is the server's reason. Entry ids are `<pluginId>/<id>`; theme and icon skin ids stay as given because the theme id is what `data-theme` names, and a taken id is refused. Every page, pane, settings section and overlay view renders inside the plugin's error boundary (`boundary.tsx`). `server.fetch` accepts only same-server paths under a route the manifest names, and `server.operation` only operations it names; both are mistake catchers, not a sandbox. Plugin-facing reads that reach app hooks (a workbench tab's title) run under the plugin host's owner (`HostServices.owner`), because activations, the frame's boot and its mirror run outside the component tree. A theme's tokens are CSS custom properties without the leading `--`; the shell registers the theme with the kit (`shell/view/registered-appearance.tsx`) and a skin draws its icons while the theme of the same id is selected.
- **Choices** (`preferences.ts`): per principal scope, through `persistedSignal`: which plugins are switched off (on by default), and each live plugin's approval. Safe mode (`?safe-mode` on the app URL) keeps every live plugin off for that load; a bundled plugin keeps running, since it is the app's own code.
- **Approval** (`approval.ts`): a bundled plugin is approved because the host ships it, and no approval record is written for it. The user approves a live plugin's manifest, not its id. An approval records the access the manifest declared (server routes, operations, `requires`), the build hash and when. `approvalCheck` compares it with the running build: `unapproved`, `accessChanged` (the declared access differs, with what was added and removed), `codeChanged` (same access, new build, with its build time) or `approved`. Only `approved` runs. Every other check stops the plugin until the user approves the running build, because a plugin's folder is in the workspace, where an agent's edit or a pulled commit changes its code without the user, and on the desktop that code runs in the app's own realm. An approval names the build the user was shown, so a build that changed while the dialog was open is not approved by it.
- **Requirements**: `requires` names server capabilities as open ids (`tasks`, `documents`). A capability is offered when the bootstrap declaration's `deployment.capabilities` lists it (`capabilities.plugins`), which the server reports for each first-party server plugin it mounted. The host re-checks them whenever the declaration changes and activates or disposes to match.
- **Host** (`host.ts`, `lifecycle.ts`): one lifecycle per plugin, wanted when switched on, its requirements are met, it is approved and, for a live plugin, safe mode is off. A new build activates beside the running one and replaces it only once it activated. A build that is still starting is not started again when a preference or capability signal changes (two activations of one build shared one dictionary, and the first one's disposal removed it).
- **Settings → App plugins** (`view/`, section `app-plugins`): under the shell's one heading, what app plugins are and the same warning the approval dialog shows (`PluginWarning`, one copy per platform), as a quiet line, then every plugin with its version, state and why it is not running, or "No app plugins yet." when there is none; on and off; its manifest in readable form (name, id, version, folder with a copy action, routes, operations, requires, build hash, last build); and remove, after `requestConfirm` with the destructive Remove. A bundled plugin says "Built in" and has no folder, no build time and no remove. The approval dialog shows the same warning and manifest, and what changed when the access did.

## Surface pages (`surface-page/`)

A page is either rendered (the plugin's `render` returns JSX) or a **surface page** (`surface(channel, props)`): the plugin sends A2UI v0.9 messages (`@claxedo/plugin-api/surface`) and the app draws them with its native renderer (`@/surface`), inside a container that names the plugin. The messages of one `send` land as one Solid update, so a component they add mounts already reading the data that came with it (the composer's agent picker seeds itself once, on mount). The person's actions go back to the plugin's program. Only data crosses; no plugin component renders. A settings section can be a surface too (`surface(channel)`, with a `group`, `workspace` or `app`), drawn by the same host component (`PluginSurfaceSettings`), and `settings.open` navigates to one of the plugin's own sections. Around every plugin surface the host provides the renderer's reference components (`SurfaceReferencesProvider`, `surface-page/drawn-surface.tsx`): the catalog's `AgentConfigurationPicker` is drawn with the composer's `AgentConfigurationPicker`, over the viewer's own catalogs; an agent reply gets none, so there it draws only a note.

- **Opening** (`bindings/regions.ts` → `surface-page/view-lazy.ts` → `surface-page/view.tsx`): the surface page views, with the renderer and the plugin API's message schemas, are a lazy chunk the provider fetches once the first screen has settled (`prefetchWhenSettled`), so they are not in the boot. Each mount of a surface page creates a `Surface` with a fresh `surfaceId` and calls `openPluginSurface` (`surface-page/controller.ts`), which calls `definition.surface(channel, props)` under `catchError` in the page's owner, so the plugin's own Solid code is owned by the page. A surface page with `tab: true` is a tab page (`PageEntry.tab`) and shares the page tab with the app's own tab pages, under its `icon`.
- **Navigation**: the shell keeps a page mounted while only its route params change (`/tasks` → `/tasks/tsk_1`), so the page compares the params by value (`surface-page/page-params.ts`, a reparse with the same values is no change) and hands each change to `program.navigated(props)` instead of opening a new program; the program keeps its state. A throw from `navigated` fails the page like an action's.
- **Messages**: every message `channel.send` receives is untrusted and is applied in send order through `Surface.apply`, which parses it with `surfaceMessageSchema` before it changes anything (the renderer is the one owner of that check). A message outside the protocol, or one the renderer refuses (another surface, not yet created), throws `SurfaceMessageError` and fails the page; that message and every later one is dropped.
- **Actions**: `SurfaceView`'s `onAction` goes to `program.action`; a throw or a rejection fails the page.
- **Failure**: the page's failure is a state of `SurfacePageState` (`surface-page/model.ts`); the view throws it into the page's `PluginBoundary`, which shows the reason and a retry. Retry mounts the page again: a new surface, a new `surfaceId`, a new program. A failure that arrives asynchronously from the plugin's code (or the web frame's `surface.open`) reaches the page by throwing under the owner the program was opened in (`runWithOwner`).
- **Closing**: unmounting the page closes it: `program.dispose` runs once, and anything the program sends afterwards is ignored.

| From | Event | To |
| --- | --- | --- |
| open | failed(error) | failed(error) |
| open, failed | closed | closed |
| failed, closed | failed | unchanged |

## State machine

`PluginState` and `pluginTransition` in `model.ts`:

| From | Event | To |
| --- | --- | --- |
| off, loading, failed | switchedOn(build) | loading(build) |
| loading | activated | on(build) |
| loading | activationFailed(reason) | failed(build, reason) |
| on, swapping | swapStarted(to) | swapping(build, to) |
| swapping | activated | on(to) |
| swapping | activationFailed(reason) | on(build, lastFailure) |
| on, swapping | crashed(reason) | failed(build, reason) |
| any | switchedOff | off |

A failed build is not retried until a new build arrives or the plugin is switched off and on. Effects (roots, imports) run in `lifecycle.ts`, outside the transition.

## First-party plugins (`first-party/`)

- A first-party plugin is a workspace package with a `claxedo` manifest block and an app entry, whose id is in `FIRST_PARTY_PLUGIN_IDS` (`@claxedo/plugin-api`). The daemon refuses a live plugin that takes one of those ids, and does not load one already registered.
- **Bundling.** `FIRST_PARTY_BUNDLES` (`first-party/bundles.ts`) imports `@claxedo/tasks/app?claxedo-plugin-bundle` and `@claxedo/documents/app?claxedo-plugin-bundle` lazily. It and the adapter's operation table (`src/server/operations.ts`, which composes `DOCUMENTS_OPERATIONS`) are the only app modules that import a plugin (`script/first-party-plugins.test.ts`). `vite.plugin-bundles.ts` resolves that specifier to the package and builds its app entry with `@claxedo/plugin-build` (run under Bun, which reads the workspace packages' source), so the build emits `{ manifest, hash, code }` as its own chunk; no plugin code is in the app's closure and nothing is fetched at runtime, which matters on the desktop's `file:` renderer. The web build and the desktop renderer (which extends the web config) both carry the plugin.
- **Loading** (`first-party/load.ts`): at the host's start each bundle's chunk loads and becomes a `bundled` build through the same loaders as a live one: on the desktop the code runs in the app's realm (`in-app.ts`, shared with live plugins), on the web in its own sandboxed frame (`frame/`). A chunk that fails to load, or a bundle naming another id, is logged with the plugin's id; a bundle whose code throws becomes a build whose activation fails, shown in Settings.
- **The two plugins.** Tasks (`packages/claxedo-tasks`, its app entry described in `src/app/README.md` there) registers the Tasks page, Settings → Presets and the `task_*` transcript cards. Documents (`packages/claxedo-documents`) registers only the `documents_list` and `documents_open` cards; Documents has no page.
- **Requirements** are those of any plugin: Tasks requires `tasks` and Documents `documents`, so each activates only where the server mounted it, independent of `features.livePlugins`.
- The live reconcile drops only live plugins, so a daemon list never removes a bundled one.

## Live plugins (`live/`)

- **Only the machine's owner.** The daemon answers the list, the bundles, add and remove only to the machine's owner (unsigned, the loopback gate; signed, `authorizeMachineOwner`), and `plugins.changed` reaches no signed subscriber. Every request carries the viewer's own credentials through the adapter. A refused list (`auth` class) is `notOwner` (`live/list-state.ts`): nothing is listed, activated or asked, and Settings says the machine's app plugins belong to its owner. Approvals and switches are kept per principal scope.
- The daemon's list (`server.queries.livePlugins.list()`, read only when the server reports `features.livePlugins`, re-read on `pluginsChanged`) is reconciled with the host: a new hash loads a new build, a removed row drops the plugin, and a failed daemon build keeps the served hash and shows `lastError`. A load in flight is keyed by its hash and the row's `lastError`, so an error the daemon reports while that hash's bundle is still loading starts a load that carries it, and the earlier load's result is dropped.
- A live bundle may export `dictionary` (`{ en: { key: text }, …locales }`, `dictionary.ts`): on the desktop it joins the app's dictionaries while the plugin is on; in the web frame `i18n.t` looks it up by the mirrored locale. A malformed one fails the load. Keys should carry the plugin's id: the app's own keys win a collision.
- A live build's manifest is the one the daemon built it from (the row's `manifest`); a `manifest` the bundle declares in code is not consulted beyond its id. The hash covers the manifest, so a manifest change alone is a new build.
- A load that fails becomes a build whose `activate` throws, so the machine keeps the running build and shows why. A plugin whose first build failed shows the daemon's error.
- When a live build needs approval, the host asks once per build; the answer is kept per principal. Settings asks again when the switch is turned on.
- **Desktop:** the bundle text is fetched through the adapter (the bundle route needs auth), imported from a Blob URL, and runs in the app's realm against `globalThis.__claxedoPluginRuntime` (`live/runtime.ts`, installed by `in-app.ts`).
- **Web:** the bundle never runs in the app's realm. `frame/` runs it in a sandboxed iframe (`sandbox="allow-scripts"`, never same-origin), so it has an opaque origin and cannot read the app's storage or DOM.

## The web frame (`frame/`)

- One hidden control frame per live plugin runs `activate` and forwards its registrations as plain descriptors over a `MessagePort` (`protocol.ts`). The host registers them through the same `PluginApi` a desktop plugin gets, so manifest limits and error boundaries apply unchanged.
- A rendered page, settings section or overlay renders in its own slot frame, which activates the plugin again and renders only that target.
- A surface page has no slot frame. The control frame registers it with `surface: true`, and the host registers it as a surface page (`frameSurfacePage`, `host-surfaces.ts`) drawn by the same `surface-page/` host component. Opening it invokes `surface.open {pageId, surfaceId, path, params}` over the port; the control frame (`runtime/surfaces.ts`) calls the plugin's `surface(channel, props)` in a Solid root of its own, and `channel.send` posts `{type: "surface", surfaceId, messages}`. The host routes them by `surfaceId` (`createSurfaceRoutes`) into the page's channel, where they are validated like any plugin's; a delivery for no open surface, or without a message list, is a `FrameProtocolError` reported through the frame's failure path. Opening a surface settings section registers it with `surface: true` too (`frameSurfaceSettings`), and `surface.open` names its target, `{kind: "page", pageId, path, params}` or `{kind: "settings", sectionId}`. A param change invokes `surface.navigated {surfaceId, path, params}`, after a fresh mirror. Actions invoke `surface.action {surfaceId, action}`; closing the page invokes `surface.close {surfaceId}`, which disposes the program and its root, and the frame stops forwarding that surface's messages.
- A frame's `transcript.toolCards` registers `{kind: "toolCards", templates}`; templates are data, so the host draws the cards and checks them as it checks a desktop plugin's.
- Plugin functions stay in the frame: commands and mention searches are invoked over the port. Host calls (`server.fetch`, `sessions.create`, `ui.confirm`, …) are answered by the host. `ui.confirm` is `requestConfirm` (`bindings/ui.tsx`) with the plugin's title, description and labels, Confirm and Cancel from this domain's copy where it names none, and never the destructive button, since the API cannot say a confirmation destroys anything. A `server.fetch` answer carries its body as text only for a JSON, XML, JavaScript or `text/*` type in UTF-8 (whose text is what `response.text()` reads anyway), and as base64 otherwise (`frame/response-body.ts`), so an image reaches the frame byte for byte. `workspaces.followStart` streams `{type: "progress", id, text}` messages for its call id before the call's result. Synchronous accessors (projects, tabs, statuses, locale, current session) read a mirror the host pushes on change. The push is an effect, which runs after the page that a route change mounts, so `frameSurfacePage` posts the current mirror (`refreshMirror`, read untracked) immediately before `surface.open`; the port delivers in order, so the frame's `surface()` reads the project and session the page opened under.
- The frame runtime is `frame/runtime/index.ts`, bundled on its own through Vite's worker build so it has no imports, and never validates surface messages itself (the host does), fetched same-origin by the host, and imported from a Blob URL by the frame's bootstrap. The frame gets the app's stylesheets and theme attributes, so the kit looks native. Panes and icon skins are not available in the frame; the kit's sprite icons cannot load there.
- The Vite dev server serves the frame runtime unbundled, so web live plugins need a built app.

## Trust and warnings

- **Desktop:** an app plugin runs in the app's realm, unsandboxed, with the app's full access on this computer: what the user sees, the user's server, every desktop bridge, and links out through the user's browser or the Browser tab. The owner accepted that residual (DECISIONS, "desktop app plugins run in-app"). The warning (`plugins.warning.desktop`) says so and asks the user to turn on only app plugins they trust.
- **Web:** an app plugin runs in a sandboxed frame and reaches the server only through the host's manifest-checked calls; the warning (`plugins.warning.web`) says so.
- The approval dialog shows the full warning for `PluginsContext.platform`, where the person decides; Settings says it in one quiet line, since it is routine there.
- **Network lock.** The app's Content-Security-Policy names its own server's exact origin (and, hosted, the relay origins given at build), never a wildcard host or port, and allows no other connection, frame or form target, and no other image but an `https:` one, which the transcript shows as v1 does (DECISIONS, Owner 2026-09-25 22:40): the build's `<meta>` on the web (`vite.web-document.ts`), a header main stamps on the desktop renderer's documents (`claxedo-desktop/src/main/renderer-content-security.ts`); both come from `content-security-policy.ts`. The web frame's own policy (`src/plugins/frame/document.ts`) can only tighten what it inherits: `connect-src 'none'`, `media-src 'none'` and `img-src data: blob:`, so a web plugin loads no outside image, `https:` included, and because a frame's own navigation is checked against its parent's policy, the app frames only its own origin. On the desktop, `will-navigate` and `window.open` refuse every URL that is not the app document; a link the user clicks to another origin leaves through the preload's `openLink`, and one to the app's own origin stays with the router. Flow 37 proves it on both. What the policy cannot stop: WebRTC (Chromium enforces no CSP directive for it), so a plugin can reach a STUN or TURN server of its choosing, and on the desktop the unsandboxed residual in the DECISIONS entry.

## Server access

`api.ts` is the host's only way to the server: `server.request` for a plugin's `server.fetch` (after the manifest check), the adapter's live plugin list, bundle and removal. `server.operation` goes to the adapter's `operation`, the one routing owner for the `documents.*` operations: on the web and the unsigned desktop they go to the connected server's `/documents` routes (the daemon's unsigned, the control plane's when signed on the web); on a signed desktop they cross Electron main by name, as today's app runs them through its account bridge. A plugin's requests carry the viewing user's credentials and nothing else, and the server applies that user's access.
