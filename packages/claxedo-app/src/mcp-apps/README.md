# mcp-apps

Owns: the host side of MCP Apps (SEP-1865, protocol `2026-01-26`) in the transcript. A completed MCP tool part whose `metadata.mcp.app` names a `ui://` resource draws that app in a sandboxed frame in place of its tool row. Plan: `docs/plans/2026-10-18-feat-mcp-apps-host-plan.md` (§5–§7).

## Owned concepts

- **App part** (`part.ts`): `isMcpAppPart` is true for a completed tool part with `toolMcpFacts(state.metadata).app`. The app document is the part's one attachment with mime `text/html;profile=mcp-app`, a base64 `data:` URL of at most 2 MiB (`MCP_APP_MAX_BYTES`). `toolReplay` builds the `tool-input` and `tool-result` (or `tool-cancelled`) notifications from the stored part: `{ content: [{ type: "text", text: output }], structuredContent, _meta: resultMeta }`.
- **App document** (`AppDocument` in `model.ts`): `pending` while the transcript holds only the part's header (`headerOnly`), `ready { html }` once the body is read, `invalid` when the attachment is missing, of another mime, not base64 UTF-8 or over the cap. A header-only part has no attachments, so the row asks the transcript's `loadToolBody` for the body when it mounts; that read is the lazy fetch of the document, so a session's first page paints its text before any app document loads.
- **Frame document** (`csp.ts`, `document.ts`, `bootstrap.ts`): the frame is one `<iframe sandbox="allow-scripts allow-forms">` (never `allow-same-origin`, so its origin is opaque). Its `srcdoc` holds only our `<meta http-equiv="Content-Security-Policy">` and `MCP_APP_BOOTSTRAP`, never app markup. A srcdoc frame inherits the app's own policy (measured below), whose `script-src` has no `'unsafe-inline'`, so the app's inline scripts cannot run as written. Instead:
  - `MCP_APP_BOOTSTRAP` is a fixed inline script. Its hash, `MCP_APP_BOOTSTRAP_HASH`, is in our frame policy and, through `MCP_APP_BOOTSTRAP_SOURCE` in `content-security-policy.ts`, in the shared app policy that both the web build and the desktop renderer use. A test recomputes the hash from the text.
  - On the iframe's first `load`, the row posts `{ type: "claxedo:mcp-app-document", html }` once. The bootstrap accepts exactly one such message, only from `parent`, parses it with `DOMParser`, copies the `<html>` and `<body>` attributes, and adopts the parsed head and body children into the live document.
  - Every `<script>` is recreated: inline text becomes a `blob:` URL, an external `src` is kept (the policy decides), and other attributes are copied. Classic scripts run first in document order, then deferred and module scripts in order, with async ones started at once. Then the bootstrap dispatches `DOMContentLoaded` on `document` and `load` on `window`, once. `nomodule` and non-JavaScript types are inserted unchanged and not run.
  - Nothing calls `document.open` or `write`, so the start produces exactly one iframe `load`, and a real navigation still produces a second.
  - Still blocked: inline event-handler attributes (`onclick=`), inline import maps, `eval`, and `javascript:` URLs, because neither policy allows inline script.
  - The frame policy is the spec default with the bootstrap hash and `blob:` in place of inline scripts: `default-src 'none'`, `script-src 'sha256-…' blob:`, inline styles, `data:` images, media and fonts, `connect-src 'none'`, `frame-src`, `object-src`, `form-action` and `base-uri 'none'`. The resource's declared `connectDomains` (connect-src), `resourceDomains` (script, style, img, font, media), `frameDomains` (frame-src) and `baseUriDomains` (base-uri) are added after filtering through the contract's `mcpAppCsp`. Because the inherited app policy also applies, a declared origin works only where the app's policy allows it too.
- **Bridge** (`bridge.ts`, `jsonrpc.ts`): JSON-RPC 2.0 over `postMessage`. It accepts only messages whose `event.source` is the frame's `contentWindow`, each at most 256 KiB as serialized JSON, with at most 16 app requests in flight; it posts to `"*"` because the frame's origin is opaque. Method table: `ui/initialize` (answers `protocolVersion`, `hostInfo`, `hostCapabilities` naming only what the reader can use, `hostContext`), `ping`, `ui/open-link` (http and https only), `ui/message`, `tools/call`, `resources/read`, `ui/request-display-mode`; notifications `ui/notifications/initialized`, `size-changed` (height clamped to 80–2000 px) and `notifications/message` (logged). Everything else, including `ui/update-model-context`, `sampling/*`, `ui/download-file` and partial input, answers method-not-found.
- **Host context** (`host-context.ts`): theme (light or dark from `data-color-scheme`), the spec's style variables mapped from the app's tokens (`STYLE_VARIABLE_SOURCES`; keys are the spec's `McpUiStyleVariableKey` names that have a counterpart), display mode, available modes, container size, locale and platform. Tokens are read and watched through `src/ui/theme-tokens.ts`, the one reader the browser pane's guest theme also uses. A change sends `host-context-changed` with only the keys whose value changed.
- **Consent** (`consent.ts`, `requests.ts`): who may drive an app (Decision 3). `tools/call` is owner-only (`useAccess().session(ref).owner`), lists the server's tools, refuses a tool that is missing or whose `_meta.ui.visibility` lacks `"app"`, and asks through `requestConfirm`, naming the server, the tool and the arguments, unless the tool is `readOnlyHint`. `resources/read` is owner-only and always on the app's own server. `ui/message` takes text content only, needs the transcript's `sendPrompt` (present only for a reader who can send) and always asks. A follow reader is refused with no prompt; a declined prompt never reaches the server. Any prompt first returns a fullscreen app inline, so the dialog is never under the top layer.
- **Server calls** (`api.ts` over `server.mcpApps` in `src/server/mcp-apps.ts`): `GET /session/:id/mcp/:server/tools`, `POST …/tool-call` `{ tool, arguments }` and `POST …/resource-read` `{ uri }`. A 409 `unsupported_operation`, or a runtime that is not running (the call never wakes it), is `isOperationUnavailable`; a 404 is `not_found`.
- **Session** (`store.ts`): `McpAppSessionProvider` gives rows the session's `SessionLocation` and remembers the last reported height of up to 64 apps, so a remounted row (the timeline virtualizes rows) is sized before its app reports. A row without the provider still draws its app, and every server request answers unavailable.

## Machines

- `AppFrameState` (`appFrameTransition`): `loading` → `ready` on `initialized`; `ready` → `unavailable` on an unsupported operation or a sleeping runtime; `unavailable` → `ready` on the next answered server request; any state → `stopped` on `navigated`. `stopped` is final: the frame is removed and the row says the app was stopped.
- `BridgePhase` (`bridgeTransition`): `waiting` → `initializing` when `ui/initialize` is answered → `open` on `ui/notifications/initialized` → `closed`. Before `open` the host sends nothing but answers; on `open` it replays the tool call once and sends any context change made since the initialize answer. Requests other than `ui/initialize` and `ping` are refused while `waiting`.
- The view's states: loading (the placeholder sized from the remembered height or 320 px, and the frame until `initialized`), ready, stopped, unavailable, and failed, which is an `invalid` document: the row draws the caller's `fallback`, the ordinary tool row.

## Flows

- **Mount:** `McpAppToolRow` reads the facts and document from the part. Pending → placeholder and `loadToolBody`; ready → `McpAppFrame`; invalid → fallback. `McpAppFrame` loads the bootstrap srcdoc and, on its first `load`, posts the document.
- **Initialize:** the app sends `ui/initialize`, the bridge answers with the current host context, the app sends `initialized`, the bridge replays input and result.
- **Size:** `size-changed` sets the inline height (clamped), remembered per part.
- **Display mode:** fullscreen shows the same container in the top layer (`popover="manual"`, `showPopover`), so the frame never reloads; Escape while the host has focus, the exit control, a navigation or a consent prompt returns it inline.
- **Links:** `ui/open-link` opens only with the frame focused and the host holding transient user activation (a click inside a child frame activates its ancestors), then dispatches the transcript's `claxedo:open-link` from the frame element through `openLink`, so loopback links open in the browser pane as transcript links do.
- **Navigation:** a second `load` of the iframe means the app navigated: the bridge is torn down and the row shows `stopped`.
- **Teardown:** the row sends `ui/resource-teardown` when it unmounts. The bridge waits up to 2 s for the answer before closing, but Solid removes the iframe in the same task, so an app gets the request and cannot rely on the wait.

## Constraints measured

Measured in Chromium 141 (`/opt/pw-browsers/chromium_headless_shell-1194`). The parent page was served with the real production policies as a header: `webContentSecurityPolicy(origin)` and `rendererContentSecurityPolicy(origin, [])` (no dev additions). The frame was `appFrameDocument(mcpAppPolicy({ connectDomains: [another origin] }))`, and the test app was posted on the first `load`. Both policies gave the same results:

- **Load count:** the iframe fired `load` exactly once. An app that set `location.href` produced a second `load`, which is still treated as a navigation; on desktop the navigation itself is refused by `frame-src 'none'`.
- **Script order:** two inline classic scripts and two inline module scripts ran as `classic-1,classic-2,module-1,module-2,DOMContentLoaded,load`. The `ui/initialize` the module posted reached the parent.
- **Adopted markup:** `<html lang>`, the `data-*` attributes, the body class, the `<title>` and an inline `<style>` all applied.
- **Blocked:**
  - `eval` threw `EvalError`;
  - a `fetch` to an undeclared origin was refused by the frame's `connect-src`;
  - a `fetch` to a declared outside origin was refused by the inherited app `connect-src`;
  - an inline `onclick` was refused by both policies.
- **Nested app policy:** an app's own `<meta http-equiv=CSP content="img-src 'none'">` blocked a `data:` image our policy allows, so it can only tighten.
- **Desktop frames:** `frame-src 'none'` (the desktop renderer) does not block a srcdoc frame; it does block `data:` frames and network navigations.
