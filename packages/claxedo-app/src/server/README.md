# server

The only module that knows today's server: its routes, its OpenCode-shaped payloads and event names, and how to reach the daemon, the control plane and the relay. Everything else in the app imports `src/server/index.ts` and speaks Claxedo types.

## Owned concepts

- Session surface reads (`session-reads.ts`): history starts as soon as the placement is known, concurrently with session metadata. The surface resolves only when both canonical results are available. Both promise branches are observed immediately, including when placement lookup fails. Status and other runtime facts keep their separate promises; history routing and stopped-workspace recovery do not depend on metadata completing first.

- The contract: `index.ts` (the public surface), `api.ts` (the APIs and `Server`), `types.ts` (sessions, projects, placements, status, capabilities), `harness-types.ts` (harness options, status and session config), `terminal-types.ts`, `git-types.ts`, `cloud-types.ts`, `account-types.ts`, `usage-types.ts`, `marketplace-types.ts`, `events.ts` and `ids.ts`. `api.ts` holds the contract rather than `index.ts` so the e2e program can typecheck the adapter without the provider's JSX.
- `ServerConfig` (`config.ts`): the server URL (explicit, else `VITE_CLAXEDO_SERVER_URL`, else the page's own origin when the daemon serves the app), the auth source (`none`, `basic`, `bearer`), and on a signed desktop `account`, the account's `run` over Electron main (the daemon gets no user bearer, so its auth source stays `none`).
- `HostedAccount` (`account.ts`): the signed desktop's control-plane calls. `run(operation, input)` names one operation of `@claxedo/account-contract`'s closed set, crosses main, and decodes the answer with that operation's own decoder; a changed shape is an `internal` failure naming the operation. `hostedOperationError` (`errors.ts`) reads main's failure: `HOSTED_HTTP <status> {detail, body}` keeps the status's class and the body's code and message (else main's detail), "not signed in" is `auth`, and anything else is `network` (main could not reach the control plane).
- `Transport` (`transport.ts`): authenticated requests to the server, and to the runtime serving a placement. A local placement is reached on the same origin with `?directory=`; a remote one through the daemon's `/workspaces/<id>` proxy on loopback, else through the relay (`relay.ts`) with a Runtime Access Token from the read-only `GET /api/workspace/:id/connection`, read again a minute before expiry. That read never starts compute: it mints only off a running sandbox, and a stopped or provisioning answer is `workspace_stopped` (`wire/connection.ts`). The only request that starts one is the explicit start, `startRuntime` (`workspace-start.ts`): `POST /api/workspace/:id/connection` until the server answers ready, waiting each time for the server's `retryAfterMs` (clamped to 0.5 to 30 s) on a `provisioning` answer or a 409 `cloud_runtime_unavailable` that carries one, at most 30 attempts, as today's app; the relay then keeps the ready link.
- Stopped cloud placements (`placement-runtime.ts`): `isStoppedCloud` is a cloud placement the catalog reports not `reachable` (its sandbox lease is not ready). `workspaces.route` refuses such a placement with `workspace_stopped` before any request leaves, so no read, stream or status sweep can wake a sandbox; `workspaces.locate` is the unguarded address the session list uses.
- `ServerError` (`errors.ts`): the one table from responses and turn failures to `AppError` classes. A turn failure takes the runtime's own `firstTurnErrorClass` (`credential` → `auth`, `usage_limit` → `rate_limit`, `session` → `not_found`), else its HTTP status, else `internal`. `network` and `rate_limit` are retryable; nothing else is. A reply whose code names a settled state is not retryable whatever its status: `harness_config_options_unavailable` (a 502 saying the harness cannot list its options, such as Cursor without a key) is the answer, and asking again gets it again. TanStack Query's default error type is registered here.
- The event stream (`stream.ts`, `streams.ts`): `cp/events` and, when the server declares `events.hostAggregate`, the host aggregate `wr/events`. Parsed by `eventsource-parser`; resumed by `Last-Event-ID`; a `stream.replay-gap` frame becomes `streamGap`. On the desktop `cp/events` can ride a WebSocket so it holds no HTTP/1.1 slot.
- The event intake (`event-intake.ts`): maps frames to `ServerEvent`s in arrival order, lets the status owner admit them, invalidates queries through the event table and hands each event to the subscribers.
- Placements (`workspaces.ts`, `wire/placements.ts`): the bootstrap catalog, held in the query cache and read reactively. A placement id is the workspace store id. A placement's `gitRemote` is the workspace row's `repo_url`, else its `git_remote`, else the project's `git.remote`, the order today's app reads them in. A `SessionRef` becomes a runtime route only here. Worktrees are created through the local server (`worktrees.ts`).
- The signed desktop's catalog (`account-placements.ts`, `account-link.ts`, `wire/account-catalog.ts`): with an account, the placement owner also reads the account's workspaces (`workspace.list.provisioner` and `workspace.list.machine`, the authority rows v1's signed catalog reads, served alike by the hosted Worker and a self-hosted node) into its own query (`accountCatalog`), grouped into projects by `project_id` and named as the hosted shell names them (project name, repository name, owner/repo of the remote, workspace name), and `catalog()` is the daemon's placements followed by the linked account placements. Every account placement is a remote `workspace:<id>`; its kind is `cloud` unless its backing is a machine's worktree, which keeps its host and remote directory. Local and control-plane project ids differ for the same repository (a desktop share names no project, so the control plane mints `prj_*`); the link is the shared workspace id:
  - a control-plane project with a workspace whose id is a local workspace id, or whose own id is a local project id, is that local project: its other workspaces (a cloud workspace, another machine's) become placements of the local project, and the local placement wins for the shared workspace;
  - a control-plane project with no such workspace is its own project, listed after the local ones (`projects.list`, `projects.byId`), with its own placements;
  - `accountProjectIds(projectId)` names the control-plane projects whose sessions belong to a project: the paired ones for a local project, itself for a control-plane-only one, none otherwise. The session list's two-source merge reads it.
  - An account catalog that cannot be read is logged, and the desktop lists its own placements; `placementsChanged`, `cloudWorkspaceChanged` and a replay gap invalidate it with the bootstrap, and `refresh` re-reads both. A control-plane placement's route is its `workspace:<id>`; reaching its runtime from the desktop is the session sources plan's S5, not this catalog.
- Projects (`projects.ts`, `wire/projects.ts`): records by id from `/api/claxedo/projects`, plus on a signed desktop the account's control-plane-only projects.
- Session homes (`session-reads.ts`, `workspaces.home`): a cloud placement's session history always comes from the control plane, which stores cloud sessions (`central-session.ts`: `/api/control/sessions/:id/messages`, the first page as its `latest-surface` view and older pages of 50 `before` the `X-Next-Cursor`; a latest-turn read takes its `latest-turn` view); every other placement's comes from its runtime (`view: latest-surface`, older pages by `{before,limit}`). What only a sandbox holds (the session's own row, status, requests, todos, goal, queued prompts, subagents, the latest turn) is read from the runtime while the placement is live (`onRuntime`); for a stopped cloud placement it answers what a stopped sandbox holds (idle, nothing pending, no goal) and the row comes from the workspace's `/api/control/sessions` inventory. A runtime read that answers `workspace_stopped` (the catalog was older than the stop) re-reads the catalog once and answers the stopped facts. A machine-placed session whose machine is offline (a remote placement the catalog says is unreachable) is not live either: its row comes from the same inventory, its transcript is empty until the machine is back (the control plane stores none for it), and nothing is read from the machine (`isOfflineMachine` tells the screen).
- Control-plane sync of cloud sessions (`session-projection.ts`), ported from today's app: the control plane stores a cloud session's transcript only when a client asks it to pull from the runtime, so on a server that issues sessions a created cloud session is registered (`POST /api/control/workspaces/:id/sessions/:sid/register`) and every turn end (`statusChanged` to idle or failed) asks for a checkpoint. One attempt each; a failure is logged and the next turn end pulls the whole history again. Without it a stopped sandbox's session would have no history to show.
- Managed session creation (`session-reservation.ts`): a server that issues sessions requires every session to be reserved before the runtime creates it, so `sessions.create` reserves an id through `/api/control/session-registrations/reserve` and creates the session under it with the reservation header.
- Remote placement streams (`placement-streams.ts`): a live remote placement's runtime frames (`/api/wr/events` through the relay or the daemon's proxy) are streamed while one of its sessions is open (`attachPlacement`, taken by the session store per open session), and the stream opens or closes as the catalog says the sandbox runs; the frames go through the same intake as the server's streams.
- Waking (`workspace-wakes.ts`): only a send wakes a stopped cloud workspace. `sessions.prompt` and `sessions.create` call `wakeIfStopped` first, which runs one explicit start per workspace however many sends wait on it, and re-reads the catalog when it is up; `cloud.start` (Settings → Projects) is the same start. `cloud.runtime(placementId)` is one machine per placement (`wake-machine.ts`): `live` or `asleep` from the catalog, `waking(bootMode?)` while a start runs, and `wakeFailed(error)` after a refused start (a 409 without a retry hint, or 30 provisioning answers) until the next start or the sandbox runs.
- Sessions (`sessions.ts` composes the calls over one `SessionContext` from `session-context.ts`): the list (`session-list.ts`), one page per project from the connection's list owner, `/api/claxedo/session-list` on loopback (the daemon, or a self-hosted node) and `/api/control/session-list` otherwise, with `scope=project` and the project id. On a signed desktop the page also takes the account's page for each control-plane project the project pairs with (`workspaces.accountProjectIds`, read through AccountPort's `session.page`), and an account-only project reads the account alone. `session-sources.ts` merges the pages as one keyset walk: each source reads after the same order key, the first `limit` rows of their union in the list's order are the page, a session two sources answer keeps the daemon's copy, and the next `after` is the last row shown (`wire/list-order.ts`). A failed account page leaves the daemon's rows and marks the page `degraded`; a failed required page fails it. each row carries the status its server last knew and whether it waits on the user, and a session whose last turn failed here since lists as failed (`status.listed`); a session read that answers the surface (messages `{view:"latest-surface"}`, the row and its diff summary) and the status, requests, todos and goal as separate promises, so a caller can paint the surface without waiting on the rest, and older pages through `{before,limit}` (`session-reads.ts`; a page is a JSON list with the older cursor in `X-Next-Cursor`); create with the harness in the query and the body; prompt through `prompt_async` with a client-minted ascending message id, where `delivery` (`queue` or `steer`) hands a prompt sent during a running turn to the runtime's queue and the answer says how it was admitted (`start`, `queue` or `steer`); a prompt with a `goal` starts the goal (`POST /session/:id/goal`) instead; stop through a `cancel_turn` recovery request (`session-stop.ts`); the held and queued prompts (`session-queue.ts`); the goal (`session-goal.ts`); the subagents a session delegated to (`GET /session/:id/subagents`, and `subagent.updated` frames as `subagentUpdated`; rows are the runtime contract's `AgentSubagentUpdate`, passed through).
- Harness options (`harness-options.ts`, `wire/harness-options.ts`): one read of `/api/claxedo/agent-config/harness/options` for a placement's harness, optionally for a session or a model, decoded once into the model, effort (`thought_level`) and fast-tier (`service_tier`) choices with their current values, the model the harness resolved, and whether the answer is live (`harness`), `catalog` or `empty`, and stale. The workspace runtime answers live options, and no route today declares an answer stale; one that does, or one that cannot be read, settles as "Model options unavailable" and is read again only when the harness or the scope changes, never on a timer. A `model` in the request asks for that model's effort levels, and a `sessionId` for the harness the session runs. ACP sends a select's choices as `options` (`value`/`name`) and the native SDK path as `selectOptions` (`id`/`name`); both decode into one `HarnessOptionSelect`. The workspace runtime answers `{options, resolvedModel?}` straight from the harness and only the daemon route adds `source` and `stale`, so an answer declaring neither is live. `models` is absent when the harness lists none, and `thoughtLevels` when it offers fewer than two; `resolvedModel` is the model the harness names as current for its next turn, never a catalog default. A choice's `description` carries what its `name` omits, the version and context window ("Opus 4.8 with 1M context"). The composer loads it per scope through `harnessConfig.options`; Settings caches it through `queries.harnesses.options`. `wire/harness-selection.ts` is the one place that turns a harness id into `nativeHarness` or `connectionId`.
- Harness config (`harness-config.ts`, `session-config.ts`, `wire/harness-state.ts`): a folder's harness status (`/api/claxedo/agent-config/harness`) and a session's harness config (`/session/:id/config`), decoded into `HarnessState` and `SessionConfig`; and the session config patch. `HarnessState.thoughtLevel` is the effort a bound session saved, so only a session's config carries one. `workspaceKey` keys a workspace as today's app does: by its folder when this machine serves it, by its workspace id otherwise. Permission modes (`permission-modes.ts`) are one query per session, and per placement and harness for a draft: read once, replaced by a mode change's own answer, and invalidated when the session's harness changes. The agent connections catalog is one query, `queries.agentConnections.list()` (`agent-connections.ts`): read once, invalidated by a connection's removal, and read again when the harness picker opens. A failed read or write throws a `ServerError`.
- Provider catalogs (`provider-catalogs.ts`, `wire/provider-catalog.ts`): a harness's providers from `/api/claxedo/agent-config/providers` in its summary form (`view=summary`: connected providers with their models, the rest named with none; opencode's is 47 KB against the full 2.3 MB). `loadDetail` reads one provider (`provider=<id>`) when a picker needs a provider the summary left empty, and merges it with the `connected` and `default` that read answers.
- Status (`status.ts`): the one owner of session status. A listed row's status is the list's; an opened session's is one `GET /session/status` on its runtime, with its `lastTurn`. Its requests are read with it (`session-requests.ts`, `/permission` and `/question?sessionId=`). No read spans placements. A failed turn is learned from `session.error` frames, per placement, and stays failed across reads until the session runs again, as in today's app; it does not survive a reload. A session read also takes `lastTurn` from its row, so an opened session whose last turn failed reads failed. Fed by `session.status`, `session.idle` and `session.error` frames; a turn error named `MessageAbortedError` is a cancelled turn, not a failure. An idle that follows a failure is held and settled from the session's `lastTurn` (a refused delete aborts the turn with an error, but the turn is recorded as completed). No timer invents a status.
- Capabilities (`capabilities.ts`): one value from the bootstrap declaration alone, so a boot reads nothing for it. Every harness is available on a loopback daemon and runs on a machine otherwise; whether pi has a connected provider is the provider catalog's answer (`queries.providerCatalogs`), read when the picker opens. Whether this server serves Tasks is `queries.tasks.availability()`, read only when a plugin requires `tasks`; the Tasks page reads its own capabilities. Capabilities never read machine logins: that read starts each CLI (0.9 s cold) and Cursor's calls its vendor, so it is the explicit `queries.accounts.machineLogins()`, for the screens that detect agents. Capabilities carry no model lists: models come from harness options per placement, and opencode's provider catalog alone is 2.3 MB. A loopback daemon is this machine even before enrollment, and its placements carry this machine's id.
- Queries (`queries.ts` and one file per area): TanStack Query options for fetched data. Keys come only from `query-keys.ts`. Events invalidate through `invalidationKeys`. `setQueryData` is used only for a mutation's own result.
- Turn writes (`turn-writes.ts`): whether a turn could have changed its placement's files, from the intent the runtime puts on each tool part (`state.input.intent`). It remembers each tool part of a session's turn by its latest update. A turn that ends (idle or failed) after a tool whose intent writes, or that carries no intent, invalidates the placement's files and git state once. The reading intents (`read`, `search`, `list`, `fetch`, `lint`, `reasoning`, `todos`, `question`, `image`, `switch_mode`) write nothing, so a turn that only read invalidates nothing, and neither does the turn's second idle frame. A replay gap invalidates every placement's files and git state. The runtime pushes no file-change event today (`file.watcher.updated` and `vcs.branch.updated` never arrive), so the turn is the only signal.
- Plugin host calls: `request` is an authenticated request to the server for the routes a plugin's manifest names (the plugin host checks the manifest first); live plugins (`live-plugins.ts`, `wire/live-plugins.ts`): `queries.livePlugins.list()` reads `/api/claxedo/live-plugins` (each row with the manifest its served bundle was built from and the build time), `livePlugins.bundle` fetches a bundle's text with the viewer's credentials, and `livePlugins.remove` unregisters one. `plugins.changed` becomes `pluginsChanged`, which invalidates every live plugin query. `operation(name, input)` (`operations.ts`) is the one routing owner for the hosted operations the app offers plugins: the `documents.*` operations (list, statuses, get, create, fromRepo, update, content get and put with `If-Match`, snapshots and restore, agentOpen, runtimeConflictResolve, moveToRepository). Any other name, or an input missing what the operation needs, is refused as `invalid` on either path. On the web and the unsigned desktop an operation is the connected server's `/documents` route; on a signed desktop (`config.account`) the same name and input go through `HostedAccount`, and main sends them to the account's control plane. Hosted operations the signed desktop sends to its account's control plane go through `HostedAccount`, never through `request`.
- Terminals (`terminals.ts`, `wire/terminals.ts`): the runtime's pty routes and socket. Text frames are output; a binary frame whose first byte is 0 carries `{cursor, checkpoint?}`; other binary frames are output decoded as one UTF-8 stream. A malformed meta frame closes the socket with 1002.

## State machines

- Connection (`stream.ts`): `connecting → connected`, and `connected → reconnecting(attempt)` on a drop. A stream never gives up while the app is open: a daemon restarted for an update or a laptop that slept keeps reconnecting, as today's app does. Backoff doubles from 250 ms to a 15 s ceiling (today's cap) with jitter in the top half. `retry` reconnects at once; the provider calls it on `online`, on window focus and when the page becomes visible. A stream with no frame for 30 s (three heartbeats) is dropped and reopened. A reconnect after the server lost the cursor gets `stream.replay-gap`, and every store re-reads on `streamGap`. `stream.test.ts` checks that attempts past any count still reconnect.
- `server.connection` aggregates the open streams: reconnecting if any is reconnecting, else connecting, else connected. A bootstrap read that fails before any stream opens is offline with its reason; `retryConnection` reads it again.

## Invariants

- A frame that is not JSON, or has no type, is logged and dropped; the stream stays open.
- Frames are mapped in arrival order: at once while every frame's directory is placed, and behind the catalog re-read once one is not. The frames of one network chunk publish in one reactive batch. A frame naming a directory the catalog does not place re-reads the catalog once per directory until the next refresh; a failed re-read becomes a `streamGap`.
- The intake publishes each event as soon as it is mapped, in arrival order, and schedules no animation frames: rendering belongs to the views. A session's streamed deltas are held by that session's transcript store until its view commits them in a frame (`src/session/README.md`).
- Nothing outside `src/server/` imports `src/server/wire/`.
- `ServerProvider` owns the handle it is given: it provides the query client, retries the connection when the browser comes online or the page becomes visible, and disposes the handle on cleanup.

## Additive contract changes

- `ServerEvent` gained `sessionsChanged`, `placementsChanged`, `documentsChanged`, `usageChanged`, `cloudWorkspaceChanged`, the terminal events and `harnessHealthChanged` (the runtime's `harness.health` frame: a session's harness health and connection state).
- `AgentRequestReply`'s `dismiss` arm gained an optional `request` kind.
- `Server` gained `queries` and `cloud`; `PlacementsApi` gained `list`; `ServerQueries` gained `harnesses.options`; `HarnessInfo` gained `unavailableReason`; `PromptInput` gained `delivery`, and `prompt` answers the `PromptDelivery`; `Server` gained `request` and `livePlugins` (`bundle`, `remove`) and `ServerQueries` gained `livePlugins`; `SessionsApi` gained `subagents` and `ServerEvent` gained `subagentUpdated`; `Placement` gained `gitRemote`.

## Known limits

- The list costs one read per project at boot and none per placement; statuses ride on its rows.
- The relay path (remote placements off loopback) and the hosted control plane are not exercised by the probe.
- On loopback a remote cloud placement is reached through the daemon's `/workspaces/<id>` proxy, which ensures the sandbox; only the catalog's `reachable` keeps a read from waking a workspace that stopped after the catalog was read.
- The control plane stores no diff summary, todo, goal or `lastTurn` for a session, so a stopped workspace's session shows none of them.

## Proof

`CLAXEDO_E2E_PORT_RANGE=46800-46899 bun e2e/probes/adapter-smoke.ts` runs the adapter against a real daemon started by the e2e harness, through a TCP proxy it can cut: projects, placements, files, git, terminals, harness options, create, session reads, a streamed turn, the project list and its row statuses, queue, stop, resume by `Last-Event-ID` and a forced replay gap.
