# server

The only module that knows today's server: its routes, its OpenCode-shaped payloads and event names, and how to reach the daemon, the control plane and the relay. Everything else in the app imports `src/server/index.ts` and speaks Claxedo types.

## Owned concepts

- Startup (`startup.ts`): the server owns `loading`, `ready`, and `failed { failure }`. Catalog and capability failures retain the typed error. Concurrent retries share the pending startup; failed startup retries reload capabilities even if its stream already opened, without opening a duplicate stream. Once ready, retry reconnects the existing stream. HTTP error envelopes preserve the server's explicit retry decision. Browser-account tests and flow 48 cover identity failure, canonical invitation admission, explicit retry, and reload recovery.

- `SessionRef` belongs to `@claxedo/agent-runtime-contract` and identifies a session by `{ sessionId, workspaceId }`. `SessionLocation` is the app's navigation context: its placement id is the workspace id, with branded ids and separate project metadata. Plugins and Tasks exchange the canonical reference.

- Session first reads (`session-reads.ts`): a session opens from one first read that answers its row, its turn outline and the page its transcript draws first (`wire/first-read.ts`), asked for with the reader's viewport (`rows`, `cols`, `reasoning`). The open view's facts are a second read the first never waits for, and the status settles once both have landed, because a failed last turn on the row decides it. Both promise branches are observed immediately, including when placement lookup fails.

- The contract: `index.ts` (the public surface), `api.ts` (the APIs and `Server`), `types.ts` (sessions, projects, placements, status, capabilities), `harness-types.ts` (harness options, status and session config), `terminal-types.ts`, `git-types.ts`, `cloud-types.ts`, `account-types.ts`, `usage-types.ts`, `marketplace-types.ts`, `events.ts` and `ids.ts`. `api.ts` holds the contract rather than `index.ts` so the e2e program can typecheck the adapter without the provider's JSX.
- `ServerConfig` (`config.ts`): the server URL (explicit, else `VITE_CLAXEDO_SERVER_URL`, else the page's own origin when the daemon serves the app), the auth source (`none`, `basic`, `bearer`), on a signed desktop `account`, the account's `run` over Electron main (the daemon gets no user bearer, so its auth source stays `none`), and in a browser signed in with Better Auth `cookies: true`: requests carry the session cookie (`credentials: include`) and the account is the connected server.
- `HostedAccount` (`account.ts`): the signed account's control-plane calls. `run(operation, input)` names one operation of `@claxedo/account-contract`'s closed set, crosses main on desktop (`createHostedAccount`), or in a signed browser (`createBrowserHostedAccount`) goes to the connected server with the cookie, admitting only the operations the registry exposes to the renderer, as main does; either way it decodes the answer with that operation's own decoder; a changed shape is an `internal` failure naming the operation. `hostedOperationError` (`errors.ts`) reads main's failure: `HOSTED_HTTP <status> {detail, body}` keeps the status's class and the body's code and message (else main's detail), "not signed in" is `auth`, and anything else is `network` (main could not reach the control plane).
- `Transport` (`transport.ts`): authenticated requests to the server, and one placement router for desktop and web. A local placement is reached on the same origin with `?directory=`. A remote one (a cloud sandbox or another machine) goes through the daemon's `/workspaces/<id>` proxy only on an unsigned loopback connection; a signed desktop and the web reach it through the relay (`relay.ts`) with a Runtime Access Token from the connection read, `workspace.connection.read` through `HostedAccount` on the desktop and `GET /api/workspace/:id/connection` otherwise, read again a minute before expiry or once after a 401. The relay sends only that token, with cookies omitted. That read never starts compute: a stopped or provisioning answer is `workspace_stopped` (`wire/connection.ts`). The catalog lists only workspaces the account may open, so every runtime read spends the workspace's connection. The only request that starts one is the explicit start, `startRuntime` (`workspace-start.ts`): `workspace.connection.mint` on the desktop and `POST /api/workspace/:id/connection` otherwise, until the server answers ready, waiting each time for the server's `retryAfterMs` (clamped to 0.5 to 30 s) on a `provisioning` answer or a 409 `cloud_runtime_unavailable` that carries one, at most 30 attempts; the relay then keeps the ready link.
- Shared placements (`shared-sessions.ts`, `workspaces.ts`): `session.shared.list` is the signed account's list of sessions other people shared with it, each with its workspace, project, title, owner name and `follow` or `send` level. The rows stay out of the owned catalog, so a shared workspace never becomes a placement. The router resolves a session's owned placement first; a session that has none loads the list and routes through its row, and nothing else does: a placement id alone or a sibling session in the same workspace is `not_found`. A shared route carries `sharedSession`, so the relay asks for `session.connection.read` (`GET /api/workspace/:id/connection?sessionId=…`; on the desktop through `HostedAccount`), whose token reaches that one session, and caches the link per workspace and session. `placement-streams.ts` streams a shared session through the same route, and frames resolve by workspace and session id. The list is re-read on focus, on the rail's refresh, on `sessionsChanged` and replay gaps, and when a shared stream is refused; a row that is gone closes its stream. The Worker decides every connection, and a revoked share's old token lives at most its 30-minute TTL (15 to 60 minutes when configured).

- Stopped cloud placements (`placement-runtime.ts`): `isStoppedCloud` is a cloud placement the catalog reports not `reachable` (its sandbox lease is not ready). `workspaces.route` refuses such a placement with `workspace_stopped` before any request leaves, so no read, stream or status sweep can wake a sandbox; `workspaces.locate` is the unguarded address the session list uses.
- `ServerError` (`errors.ts`): the one table from responses and turn failures to `AppError` classes. A turn failure takes the runtime's own `firstTurnErrorClass` (`credential` → `auth`, `rate_limit` and `usage_limit` → `rate_limit`, `session` → `not_found`), else its HTTP status, else `internal`. `network` and `rate_limit` are retryable; nothing else is. A reply whose code names a settled state is not retryable whatever its status: `harness_config_options_unavailable` (a 502 saying the harness cannot list its options, such as Cursor without a key) is the answer, and asking again gets it again. TanStack Query's default error type is registered here.
- The event stream (`stream.ts`, `streams.ts`): `cp/events` and, when the server declares `events.hostAggregate`, the host aggregate `wr/events`; a signed desktop also reads its account's hosted `cp/events` through the `controlPlane.events` operation (`account-events.ts` over the desktop account bridge), outside the connection state, so a hosted outage never marks the local server offline. Parsed by `eventsource-parser`; resumed by `Last-Event-ID`; a `stream.replay-gap` frame becomes `streamGap`. On the desktop `cp/events` can ride a WebSocket so it holds no HTTP/1.1 slot. A hosted `session.status.changed` notice for a session whose own stream is open (an open remote session's `wr/events`, or any session of a placement this server serves) is dropped (`event-intake.ts`): that stream said it sooner.
- The event intake (`event-intake.ts`): maps frames to `ServerEvent`s in arrival order, lets the status owner admit them, invalidates queries through the event table and hands each event to the subscribers.
- Placements (`workspaces.ts`, `wire/placements.ts`): the bootstrap catalog, held in the query cache and read reactively. The placement owner observes its query for as long as it lives (a disabled `QueryObserver`, which also drives that reactivity), so the cache never collects it: routing, the rail and every session read look placements up synchronously, and the cache drops an unobserved query 10 minutes after its last read from the server, which would leave a switch no placement to open. A placement id is the workspace store id. A placement's `gitRemote` is the workspace row's `repo_url`, else its `git_remote`, else the project's `git.remote`, the order today's app reads them in. A `SessionLocation` becomes a runtime route only here. Worktrees are created through the local server (`worktrees.ts`), forwarding the optional name and base reference without substituting another reference if creation fails.
- The account catalog (`account-placements.ts`, `account-link.ts`, `wire/account-catalog.ts`): with an account, the placement owner also reads the account's workspaces (`workspace.list.provisioner` and `workspace.list.machine`, the authority rows the hosted Worker serves) into its own query (`accountCatalog`), observed the same way, grouped into projects by `project_id` and named as the hosted shell names them (project name, repository name, owner/repo of the remote, workspace name), and `catalog()` is the daemon's placements followed by the linked account placements. The bootstrap declares `deployment.serverKind`: on `hosted` (the Worker serves no daemon routes) the bootstrap lists no projects, so the account placements are the whole catalog, `projects.list` and `projects.byId` read the account's projects alone (an unknown id is `not_found`), `/api/claxedo/projects` is never requested, project create, update, remove and reclone are refused before any request (`project_configuration_unavailable`, `projects.configurationAvailable()`), and the rail keeps an assigned color locally. Every account placement is a remote `workspace:<id>`; its kind is `cloud` unless its backing is a machine's worktree, which keeps its host and remote directory. Local and control-plane project ids differ for the same repository (a desktop share names no project, so the control plane mints `prj_*`); the link is the shared workspace id:
  - a control-plane project with a workspace whose id is a local workspace id, or whose own id is a local project id, is that local project: its other workspaces (a cloud workspace, another machine's) become placements of the local project, and the local placement wins for the shared workspace;
  - a control-plane project with no such workspace is its own project, listed after the local ones (`projects.list`, `projects.byId`), with its own placements;
  - `accountProjectIds(projectId)` names the control-plane projects whose sessions belong to a project: the paired ones for a local project, itself for a control-plane-only one, none otherwise. The session list's two-source merge reads it.
  - `accountKnows(workspaceId)` says whether the account's catalog places that workspace: a machine workspace this machine published, or any account placement. It decides where a signed desktop's reader marks live (below).
  - The bootstrap and the account catalog are read together. An account catalog that cannot be read is logged on a daemon, which lists its own placements, and fails the read on hosted; `placementsChanged`, `cloudWorkspaceChanged` and a replay gap invalidate it with the bootstrap, and `refresh` re-reads both. A control-plane placement's route is its `workspace:<id>`; reaching its runtime from the desktop is the session sources plan's S5, not this catalog.
- Cloud create (`cloud.ts`): `cloud.create({ projectId })` creates a cloud workspace of a project this server holds, on this server. `cloud.create({ source })` creates a repository's cloud workspace on a signed desktop's control plane, which derives its project, through `HostedAccount` (`workspace.create`, with a connected repository's `repoFullName` flat, as Electron main declares the operation); without an account it is refused. Both re-read the catalog before answering, so the new placement is routable.
- Projects (`projects.ts`, `wire/projects.ts`): records by id from `/api/claxedo/projects`, plus on a signed desktop the account's control-plane-only projects.
- Session homes (`session-reads.ts`, `workspaces.home`): a cloud placement's session history always comes from the control plane, which stores cloud sessions (`central-session.ts`: the first read is `/api/control/sessions/:id/outline` with the viewport, whose row is the one the inventory lists; an older page is `/api/control/sessions/:id/page` with the viewport `before` a turn's cursor, and a tool row's whole part `/part`; `transcript-reads.ts`). With an account these reads and the inventory below go through `HostedAccount` (`session.outline`, `session.turnPage`, `session.part`, `session.list`), because the local daemon serves no `/api/control/sessions` (a signed browser's account reaches the same routes on the connected server); every other placement's comes from its runtime (`GET /session/:id/outline` with the viewport, `/page` and `/message/:messageId/part/:partId`). What only a sandbox holds (the session's row with its selections and last turn, status, requests, todos, goal, queued prompts, subagents) is read from the runtime while the placement is live (`onRuntime`), so a live cloud session's first read also reads its row from the sandbox; for a stopped cloud placement it answers what a stopped sandbox holds (idle, nothing pending, no goal; the queued prompts as unknown, `undefined`, since the sandbox keeps them) and the row comes from the workspace's `/api/control/sessions` inventory. A runtime read that answers `workspace_stopped` (the catalog was older than the stop) re-reads the catalog once and answers the stopped facts. A machine-placed session whose machine is offline (a remote placement the catalog says is unreachable) is not live either: its row comes from the same inventory, its transcript is empty until the machine is back (the control plane stores none for it), and nothing is read from the machine (`isOfflineMachine` tells the screen): an older page or a tool's part read is refused as a network error, so the transcript keeps its older cursor and pages again once the machine is back.
- Control-plane sync of cloud sessions (`session-projection.ts`): the control plane stores a cloud session's transcript only when a client asks it to pull from the runtime, so with an account a created cloud session is registered (`session.projection.register`) and every turn end (`statusChanged` to idle or failed) asks for a checkpoint (`session.projection.checkpoint`), on a desktop whose daemon issues no sessions too. One attempt each; a failure is logged and the next turn end pulls the whole history again. Without it a stopped sandbox's session would have no history to show.
- Managed session creation (`session-reservation.ts`): a runtime reached through the relay requires every session to be reserved before it creates it, so with an account `sessions.create` on a remote placement reserves an id through `HostedAccount` (`session.reserve`, whose registry fixes the kind to `create`), checks the answer echoes that session, operation and `reserved`, and creates the session under it with the reservation header.
- Remote placement streams (`placement-streams.ts`): while a session of a live remote placement is open (`attachPlacement`, taken by the session store per open session), its runtime frames stream from `/api/wr/events?sessionID=<id>` through the placement router, one stream per session however many attach, into the same intake as the server's streams. The runtime also serves an unscoped `wr/events` to a principal its workspace authority admits, which the app does not open, so a remote session that is not open changes only on a list re-read. The frames carry the placement's workspace id, since the runtime names its own directory. A stream opens or closes as either catalog (the daemon's or the account's) says the placement runs, and a refused stream stays closed.
- Waking (`workspace-wakes.ts`): only a send wakes a stopped cloud workspace. `sessions.prompt` and `sessions.create` call `wakeIfStopped` first, which runs one explicit start per workspace however many sends wait on it, and re-reads the catalog when it is up; `cloud.start` (Settings → Projects) is the same start. `cloud.runtime(placementId)` is one machine per placement (`wake-machine.ts`): `live` or `asleep` from the catalog, `waking(bootMode?)` while a start runs, and `wakeFailed(error)` after a refused start (a 409 without a retry hint, or 30 provisioning answers) until the next start or the sandbox runs.
- Sessions (`sessions.ts` composes the calls over one `SessionContext` from `session-context.ts`): the list (`session-list.ts`), one page per project from the connection's list owner, `/api/claxedo/session-list` on loopback (the daemon) and `/api/control/session-list` otherwise, with `scope=project` and the project id. With an account the page also takes the account's page for each control-plane project the project pairs with (`workspaces.accountProjectIds`, read through AccountPort's `session.page`), and an account-only project reads the account alone. `session-sources.ts` merges the pages as one keyset walk: each source reads after the same order key, the first `limit` rows of their union in the list's order are the page, a session two sources answer keeps the daemon's copy, and the next `after` is the last row shown (`wire/list-order.ts`). A failed account page leaves the daemon's rows and marks the page `degraded`; a failed required page fails it. The page takes `settled` (`active` or `all`), which each list owner applies before it pages; each row carries the reader's marks, `seenAt` and `settledAt` (`page.readers`). A signed desktop's marks for a session the account knows (its workspace is `accountKnows`, or it is shared with the reader) live on the account, so the merge takes that session's marks from the account's copy, never the daemon's; a paired project's two pages are therefore read with `settled=all`, and the merge drops the rows `sessionSettled` says the reader settled. The marks are written by `sessions.markSeen` and `sessions.settle` (`session-reader.ts`), which answer the reader's marks after the write: to the account (`session.seen`, `session.settle`) for a session the account knows on a signed desktop, else `/api/claxedo/session/:id/{seen,settle}` on loopback and `/api/control/sessions/:id/{seen,settle}` otherwise. The `session.reader.changed` notice on `cp/events` becomes `readerChanged`. Each row carries the status its server last knew and whether it waits on the user, and a session whose last turn failed here since lists as failed (`status.listed`); a session read that answers the first read (the row, its diff summary, the outline and the first page) and the status, requests, todos, goal and subagents as separate promises, so a caller paints the first page without waiting on the rest; those five facts are one runtime read, `GET /session/:id?view=open` (`wire/session-open.ts`), where a fact the runtime could not read comes back as that fact's error and fails only its own promise, and older pages through `{before,limit}` (`session-reads.ts`; a page is a JSON list with the older cursor in `X-Next-Cursor`); create with the harness in the query and the body; prompt through `prompt_async` with a client-minted ascending message id, where `delivery` (`queue` or `steer`) hands a prompt sent during a running turn to the runtime's queue and the answer says how it was admitted (`start`, `queue` or `steer`); a prompt with a `goal` starts the goal (`POST /session/:id/goal`) instead; stop through a `cancel_turn` recovery request (`session-stop.ts`); one background task stopped by the call that started it (`stopBackgroundTask`, `POST /session/:id/background-task/stop`), answered `{ ok: true }` once the harness accepted or `not_found`, any other refusal thrown, and whether the session's harness can do that at all as `queries.harnesses.stopsBackgroundTasks`, its `/capabilities` `backgroundTasks`; the held and queued prompts (`session-queue.ts`); the goal (`session-goal.ts`); the subagents a session delegated to (`GET /session/:id/subagents`, and `subagent.updated` frames as `subagentUpdated`; rows are the runtime contract's `AgentSubagentUpdate`, passed through).
- Harness options (`harness-options.ts`, `wire/harness-options.ts`): one read for a placement's harness, optionally for a session or a model: a remote placement asks its runtime (`/session/:id/config-options` or `/api/wr/harness-config-options`) through the placement router, and a local one asks the daemon's `/api/claxedo/agent-config/harness/options`, which falls back to its catalog; decoded once into the model, effort (`thought_level`) and fast-tier (`service_tier`) choices with their current values, the model the harness resolved, and whether the answer is live (`harness`), `catalog` or `empty`, and stale. The workspace runtime answers live options, and no route today declares an answer stale; one that does, or one that cannot be read, settles as "Model options unavailable" and is read again only when the harness or the scope changes, never on a timer. A `model` in the request asks for that model's effort levels, and a `sessionId` for the harness the session runs. ACP sends a select's choices as `options` (`value`/`name`) and the native SDK path as `selectOptions` (`id`/`name`); both decode into one `HarnessOptionSelect`. The workspace runtime answers `{options, resolvedModel?}` straight from the harness and only the daemon route adds `source` and `stale`, so an answer declaring neither is live. `models` is absent when the harness lists none, and `thoughtLevels` when it offers fewer than two; `resolvedModel` is the model the harness names as current for its next turn, never a catalog default. A choice's `description` carries what its `name` omits, the version and context window ("Opus 4.8 with 1M context"), and an alias choice's `resolvedModel` names the full model id it runs. The composer loads it per scope through `harnessConfig.options`; Settings caches it through `queries.harnesses.options`. `wire/harness-selection.ts` is the one place that turns a harness id into `nativeHarness` or `connectionId`.
- Harness commands (`harness-commands.ts`, `wire/harness-commands.ts`): `queries.harnesses.commands` reads the runtime's `/command` for a placement's harness, answered as the runtime contract's `RuntimeCommand` list: the user's saved commands (`origin: "saved"`, with the `content` they expand to) followed by the harness's own (`origin: "transport"`, with an optional `source` and argument `input.hint`). A row without a name, an origin, or a saved command without its content fails the read as a contract mismatch.
- Harness config (`harness-config.ts`, `session-config.ts`, `wire/harness-state.ts`): a folder's harness status (`/api/claxedo/agent-config/harness`), decoded into `HarnessState`, and the session config patch. A session's harness, model, effort and permission mode are its row's `config` (`wire/session-row.ts`), which the runtime fills with effective values and republishes as `session.updated` after every selection write, so no route reads them separately. `workspaceKey` keys a workspace as today's app does: by its folder when this machine serves it, by its workspace id otherwise. Permission modes (`permission-modes.ts`) are a plain read for an ACP agent's list, made when its chip opens, and the mode write, whose answer is the session row. The agent connections catalog is one query, `queries.agentConnections.list()` (`agent-connections.ts`): read once, invalidated by a connection's removal, and read again when the harness picker opens. A failed read or write throws a `ServerError`.
- Provider catalogs (`provider-catalogs.ts`, `wire/provider-catalog.ts`): a harness's providers from `/api/claxedo/agent-config/providers` in its summary form (`view=summary`: connected providers with their models, the rest named with none; opencode's is 47 KB against the full 2.3 MB). `loadDetail` reads one provider (`provider=<id>`) when a picker needs a provider the summary left empty, and merges it with the `connected` and `default` that read answers. OpenCode's catalog is per workspace: the server asks the named workspace's own engine, so config and custom providers appear only with a `workspaceId`. Both reads take an optional placement, send its `workspaceId` for opencode alone and key the cache by it; pi's catalog is the same everywhere and ignores the placement.
- Status (`status.ts`): the one owner of session status. A listed row's status is the list's; an opened session's is the status its open view carries, with its `lastTurn`. No read spans placements. A failed turn is learned from `session.error` frames, per placement, and stays failed across reads until the session runs again, as in today's app; it does not survive a reload. A session read also takes `lastTurn` from its row, so an opened session whose last turn failed reads failed. Fed by `session.status`, `session.idle` and `session.error` frames; a turn error named `MessageAbortedError` is a cancelled turn, not a failure. An idle that follows a failure is held and settled from the session's `lastTurn`, read again through its open view (a refused delete aborts the turn with an error, but the turn is recorded as completed). No timer invents a status. A session whose turn is not running while its harness runs work outside any turn (a Claude background agent or shell in a process that outlives the turn) is `runningInBackground`, its own status: `sessionStatusWithBackgroundWork` is the one rule, turning an `idle` or unknown turn status with active background work into the shared `RUNNING_IN_BACKGROUND` and leaving a running or failed turn's status as it is. The runtime reports the two facts apart and the app keeps them apart, because a turn's events never restate background work: the turn's status as above, and the work as `backgroundWork: { agents, shells, other }` on a listed row's status and on the open view's `status` fact (read as the `backgroundWork` fact, all zero when absent) and `session.background-work` frames with the same counts (`backgroundWorkChanged`). The work is active while any count is above zero. A turn that ends while work runs is therefore `runningInBackground`; the next turn, whether the person's prompt or the one Claude runs to report the work, is `working`; work that settles with no turn after it leaves the session `idle`. Claude's harness reports the work settled before it admits that report turn.
- Capabilities (`capabilities.ts`): one value from the bootstrap declaration alone, so a boot reads nothing for it. `features.connections` is the declaration's `deployment.connections`: the desktop's local server mounts no Connections family and says so, so the integrations catalog is never asked of it. Every harness is available on a loopback daemon and runs on a machine otherwise; whether pi has a connected provider is the provider catalog's answer (`queries.providerCatalogs`), read when the picker opens. Whether this server serves Tasks is `queries.tasks.availability()`, read only when a plugin requires `tasks`; the Tasks page reads its own capabilities. Capabilities never read machine logins: that read starts each CLI (0.9 s cold) and Cursor's calls its vendor, so it is the explicit `queries.accounts.machineLogins()`, for the screens that detect agents. Capabilities carry no model lists: models come from harness options per placement, and opencode's provider catalog alone is 2.3 MB. A loopback daemon is this machine even before enrollment, and its placements carry this machine's id.
- Machines (`machines.ts`): `queries.machines.list()`. A server that issues sessions answers the account's enrolled machines (`/api/claxedo/remote-access/devices`), and the one whose host id is the declaration's `enrollmentId` is this machine. A loopback server that issues none is this machine alone, enrolled or not, and its id is the capabilities' `thisMachine`. On the desktop it is named as Electron main names it: `ServerConfig.thisMachineReport` is main's `hostConnector.status()`, whose `displayName` is the name the machine derives for itself (`@claxedo/helpers/machine-name`) or its owner's rename. Without a report, as on the web, it is "This machine".
- Queries (`queries.ts` and one file per area): TanStack Query options for fetched data. Keys come only from `query-keys.ts`. Events invalidate through `invalidationKeys`. `setQueryData` is used only for a mutation's own result.
- Turn writes (`turn-writes.ts`): whether a turn could have changed its placement's files, from the intent the runtime puts on each tool part (`state.input.intent`). It remembers each tool part of a session's turn by its latest update. A turn that ends (idle or failed) after a tool whose intent writes, or that carries no intent, invalidates the placement's files and git state once. The reading intents (`read`, `search`, `list`, `fetch`, `lint`, `reasoning`, `todos`, `question`, `image`, `switch_mode`) write nothing, so a turn that only read invalidates nothing, and neither does the turn's second idle frame. A replay gap invalidates every placement's files and git state. The runtime pushes no file-change event today (`file.watcher.updated` and `vcs.branch.updated` never arrive), so the turn is the only signal.
- Plugin host calls: `request` is an authenticated request to the server for the routes a plugin's manifest names (the plugin host checks the manifest first); live plugins (`live-plugins.ts`, `wire/live-plugins.ts`): `queries.livePlugins.list()` reads `/api/claxedo/live-plugins` (each row with the manifest its served bundle was built from and the build time), `livePlugins.bundle` fetches a bundle's text with the viewer's credentials, and `livePlugins.remove` unregisters one. `plugins.changed` becomes `pluginsChanged`, which invalidates every live plugin query. `operation(name, input)` (`operations.ts`) is the one routing owner for the hosted operations the app offers plugins: the `documents.*` operations (list, statuses, get, create, fromRepo, update, content get and put with `If-Match`, snapshots and restore, agentOpen, runtimeConflictResolve, moveToRepository). Any other name, or an input missing what the operation needs, is refused as `invalid` on either path. On the web and the unsigned desktop an operation is the connected server's `/documents` route; on a signed desktop (`config.account`) the same name and input go through `HostedAccount`, and main sends them to the account's control plane. Hosted operations the signed desktop sends to its account's control plane go through `HostedAccount`, never through `request`.
- Terminals (`terminals.ts`, `wire/terminals.ts`): the runtime's pty routes and socket. Text frames are output; a binary frame whose first byte is 0 carries `{cursor, checkpoint?}`; other binary frames are output decoded as one UTF-8 stream. A malformed meta frame closes the socket with 1002.

## State machines

- Connection (`stream.ts`): `connecting → connected`, and `connected → reconnecting(attempt)` on a drop. A stream reconnects while the app is open unless authorization or the session is refused (401, 403 or 404): a daemon restarted for an update or a laptop that slept keeps reconnecting, as today's app does. Backoff doubles from 250 ms to a 15 s ceiling (today's cap) with jitter in the top half. `retry` reconnects at once; the provider calls it on `online`, on window focus and when the page becomes visible. A stream with no frame for `EVENT_STREAM_STALL_TIMEOUT_MS` from `@claxedo/agent-runtime-contract` (40 s: two missed 10 s heartbeats and a beat of jitter) is dropped and reopened. A reconnect after the server lost the cursor gets `stream.replay-gap`, and every store re-reads on `streamGap`. `stream.test.ts` checks that attempts past any count still reconnect, and that a stream outlives two missed heartbeats and drops at the fourth.
- `server.connection` aggregates the open streams: reconnecting if any is reconnecting, else connecting, else connected. A bootstrap read that fails before any stream opens is offline with its reason; `retryConnection` reads it again.

## Invariants

- A frame that is not JSON, or has no type, is logged and dropped; the stream stays open.
- Frames are mapped in arrival order: at once while every frame's directory is placed, and behind the catalog re-read once one is not. The frames of one network chunk publish in one reactive batch. A frame naming a directory the catalog does not place re-reads the catalog once per directory until the next refresh; a failed re-read becomes a `streamGap`.
- The intake publishes each event as soon as it is mapped, in arrival order, and schedules no animation frames: rendering belongs to the views. A session's streamed deltas are held by that session's transcript store until its view commits them in a frame (`src/session/README.md`).
- Nothing outside `src/server/` imports `src/server/wire/`.
- `ServerProvider` owns the handle it is given: it provides the query client, retries the connection when the browser comes online or the page becomes visible, and disposes the handle on cleanup.

## Additive contract changes

- `ServerEvent` gained `sessionsChanged`, `placementsChanged`, `documentsChanged`, `usageChanged`, `cloudWorkspaceChanged`, the terminal events and `harnessHealthChanged` (the runtime's `harness.health` frame: a session's harness health and connection state).
- `AgentRequestReply`'s `dismiss` arm gained an optional `request` kind.
- `Server` gained `queries` and `cloud`; `PlacementsApi` gained `list`; `ServerQueries` gained `harnesses.options` and `harnesses.commands`; `HarnessInfo` gained `unavailableReason`; `PromptInput` gained `delivery`, and `prompt` answers the `PromptDelivery`; `Server` gained `request` and `livePlugins` (`bundle`, `remove`) and `ServerQueries` gained `livePlugins`; `SessionsApi` gained `subagents` and `ServerEvent` gained `subagentUpdated`; `Placement` gained `gitRemote`.

## Known limits

- The list costs one read per project at boot and none per placement; statuses ride on its rows.
- The relay path (remote placements off loopback) and the hosted control plane are not exercised by the probe.
- On loopback a remote cloud placement is reached through the daemon's `/workspaces/<id>` proxy, which ensures the sandbox; only the catalog's `reachable` keeps a read from waking a workspace that stopped after the catalog was read.
- The control plane stores no diff summary, todo, goal or full `lastTurn` for a session, so a stopped workspace's session shows none of them; its list row carries the last turn's status and time when the session's machine published them.

## Proof

`CLAXEDO_E2E_PORT_RANGE=46800-46899 bun e2e/probes/adapter-smoke.ts` runs the adapter against a real daemon started by the e2e harness, through a TCP proxy it can cut: projects, placements, files, git, terminals, harness options, create, session reads, a streamed turn, the project list and its row statuses, queue, stop, resume by `Last-Event-ID` and a forced replay gap.
