The workspace-runtime API is placement-agnostic: the **same route** serves a
workspace on your loopback and behind `@claxedo/workspace-relay` with signed
runtime-access tokens. The only thing that changes is the exposure option the
runtime is constructed with — and the relay-attached runtime proves its
boundary by rejecting direct calls.

## Run

```bash
bun run recipe:08-place-anywhere
```

<Note>
Needs **Bun** (the relay adapter requires `Bun.serve`) — nothing else. Both
runtimes, the relay, and the keys are created in-process on loopback ports;
the whole recipe completes in well under a second.
</Note>

## The core

```ts
// Placement 1 — LOCAL: loopback exposure.
const local = createWorkspaceRuntimeApp({
  target: { workspaceId: "cookbook-local", directory: localDir },
  storeRoot: path.join(localDir, ".claxedo-runtime-store"),
  exposure: loopbackWorkspaceRuntimeExposure(),
})

// Placement 2 — CLOUD-VM: the ONE option that changes.
const cloud = createWorkspaceRuntimeApp({
  target: { workspaceId, directory: cloudDir },
  storeRoot: path.join(cloudDir, ".claxedo-runtime-store"),
  exposure: relayWorkspaceRuntimeExposure({ key: hostKeys.publicKey, workspaceId, hostId }),
})

const relay = createWorkspaceRelayBun({
  runtimeAccessKey: accessKeys.publicKey,   // verifies client → relay tokens
  relayHostSigningKey: hostKeys.privateKey, // signs relay → runtime requests
  relayHostAlgorithm: "EdDSA",
  resolveTarget: (claims) => ({ workspaceId: claims.workspace_id, hostId: claims.host_id, baseUrl: cloudUrl, access: "cloud", backing: "cloud-vm" }),
})
```

Full source: [`src/recipes/08-place-anywhere.ts`](https://github.com/kyashrathore/Claxedo/blob/dev/claxedo-cookbook/src/recipes/08-place-anywhere.ts)

## Expected output

```text
placement: local
  GET http://127.0.0.1:56221/api/wr/health -> 200
placement: cloud-vm (via relay)
  GET http://127.0.0.1:56224/workspaces/cookbook-cloud/api/wr/health -> 200
  direct (bypassing relay) GET http://127.0.0.1:56223/api/wr/health -> 401 (refused)

--- same route, two placements ---
{
  "route": "/api/wr/health",
  "local":   { "status": 200, "routeAuthBoundary": "loopback-only",   "exposure": { "kind": "loopback" } },
  "cloudVm": { "status": 200, "routeAuthBoundary": "relay-host-auth", "exposure": { "kind": "relay" },
               "directBypassStatus": 401 }
}
--- end ---
```

Ports vary per run; the relay's `server-timing` phases (`rat-verify`,
`rht-mint`, `upstream-fetch`) are printed as evidence of the hop.

## Lift this into your app

The two-keypair split is the production shape: your control plane owns the
access keys and mints short-lived runtime-access tokens per request; the
relay owns the host signing key. In a real deployment those come from the
[relay-attached env contract](/framework/deploy/relay-attached), not in-process
`generateKeyPair` — the recipe's wiring shows the seams, not the key
management.
