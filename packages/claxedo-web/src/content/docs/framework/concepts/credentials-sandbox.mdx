When `@claxedo/workspace-runtime` runs inside a provider sandbox,
`@claxedo/sandbox-manager` places it and manages its lease. Getting credentials
into that sandbox comes down to one question: **is the code inside the sandbox
trusted with the raw value?**

<Note>
`@claxedo/sandbox-manager` is a kit — it owns generic placement/lease pieces and
provider drivers, not Claxedo auth, billing, or storage.
</Note>

## Two channels

<CardGroup cols={2}>
  <Card title="env — readable" icon="unlock">
    Ordinary environment variables, readable inside the sandbox via
    `process.env`. Reserve for credentials the agent is *meant* to hold — e.g.
    the user's own model API key, which the agent needs to call the model
    directly.
  </Card>
  <Card title="secrets — brokered" icon="lock">
    Credentials the sandbox must *use* on outbound requests but must never
    *read* or exfiltrate (connection tokens, deploy tokens). The raw value never
    enters the sandbox; the provider injects it on egress to an allowlist of
    hosts only.
  </Card>
</CardGroup>

### `env` — for trusted credentials

`SandboxManagerInput.env` (and the driver-level `env`) sets ordinary environment
variables readable via `process.env`.

### `secrets` — brokered, never readable

`SandboxManagerInput.secrets: SandboxBrokeredSecret[]` keeps the raw value out of
the sandbox. The provider substitutes/injects it on egress to allowlisted
`hosts` only:

```ts
// `manager` is a SandboxManager from createSandboxManager({ leaseStore, driver })
// — your app supplies the lease store and provider driver.
const workspaceId = "ws_1"
const notionToken = process.env.NOTION_TOKEN! // the credential to broker

await manager.ensure(workspaceId, {
  homeRegion: "us-east",
  secrets: [{
    name: "NOTION_TOKEN",
    value: notionToken,          // never enters the sandbox in plaintext
    hosts: ["api.notion.com"],   // substituted/injected only for these hosts
    header: "Authorization",     // required for Vercel and the Cloudflare proxy driver; optional for Daytona
  }],
})
```

## Per-provider brokering

Each driver either brokers secrets natively, via a proxy, or not at all:

| `secretBrokering` | Drivers | What it means |
| --- | --- | --- |
| `native` | Daytona, Vercel | The platform injects the credential on egress to allowlisted hosts; existing code reaches the real host unchanged. |
| `proxy` | Cloudflare | Brokered-host egress routes through a Worker proxy that injects the credential; the sandbox never holds the value. |
| `none` | Modal, Docker, fetch | Plaintext env only — cannot satisfy the never-readable contract. |

The full per-driver mechanism table lives in
[Sandbox drivers & secrets](/framework/deploy/sandbox-drivers-secrets#choosing-a-driver).

## Fail-closed contract

A brokered secret is **never silently downgraded to readable env**. `native`
(transparent egress) and `proxy` (Cloudflare Worker egress proxy) both keep the
value out of the sandbox and provision normally. Only a `none` driver makes the
manager refuse to provision:

```text
status: "unavailable", error: "secret_brokering_unsupported"
```

Brokered secret values are also never written to labels, never logged, and never
captured in a driver snapshot.

<Warning>
`native` brokering is transparent — existing code reaches the real host and the
platform injects the credential. Cloudflare `proxy` is **not** transparent: the
sandbox must route brokered-host requests through `CLAXEDO_EGRESS_PROXY_URL`
(with the `CLAXEDO_EGRESS_TOKEN` bearer and the `x-claxedo-egress-target`
header). Modal stays `none` — its secret store improves storage hygiene for
*readable* credentials but does not hide them from the sandbox.
</Warning>
