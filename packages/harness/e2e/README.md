# Harness flows

Run `bun run build:packages` from the repository root, then `bun run --cwd packages/harness flows` for every flow, or `bun run --cwd packages/harness flows H0 H3b` for the named ones. An id selects that flow and its variants; a file stem such as `H4-native-questions` selects that file alone. `bun run --cwd packages/harness typecheck` checks this folder with its own `tsconfig.json`, and `bun run --cwd packages/harness test` runs the pin tests in `harness/`. `CLAXEDO_E2E_KEEP_DATA=1` keeps the temporary stack directory for diagnosis. Give concurrent runs disjoint `CLAXEDO_E2E_PORT_RANGE` values, such as `46200-46299`. The daemon runs on the Node range `packages/claxedo-server/package.json` declares in `engines.node`; a `node` on PATH outside it is refused, so set `CLAXEDO_E2E_NODE` to a supported binary.

Each flow starts the real local daemon and workspace runtime. It creates sessions and sends prompts through HTTP, reads live SSE frames, reads stored messages through HTTP, and checks a server readback. The scripted ACP process speaks ACP over stdio, and the scripted model server answers real model requests. These are the only scripted turn boundaries. `harness/pinned-package.ts` installs each real harness program the flows run under `e2e/.artifacts/<program>/<version>` when missing, never from PATH: Pi at `PI_VERSION`, and Claude Code at one end of the transport's tested range (`CLAUDE_CODE_RANGE`), chosen by `CLAXEDO_E2E_CLAUDE=min|max` and `max` when unset. Each stack has its own temporary data directory, isolated home and XDG directories, and a rejecting egress proxy. H0 requires its egress record to be empty.

A Codex flow reaches an MCP tool the way a real model does: Codex defers MCP tools behind its `tool_search` tool, so the flow scripts a `tool_search` call (`format: "tool_search"`), the scripted model records the namespaces Codex returns in `tool_search_output`, and the flow then scripts a call to the loaded tool's `call` target.

A green flow shows the behavior in live frames, in stored messages, and in one independent server readback. A flow that proves a defect in the register is listed in `flows/expected-red.json` with its defect ids: it must fail, and the run fails when it passes, so its entry is removed in the change that proves the fix. Any other failing flow fails the run. A red run injects a fault at the boundary the flow claims to test, and must fail there. `CLAXEDO_E2E_RED=1` makes the scripted ACP agent and model endpoint reject every turn, which only proves H0 detects failed turns. A scripted endpoint can't prove live vendor behavior. Keep real harness programs pinned, and report unavailable programs or failing isolation as failures, never skips.

A program whose transport declares a version range is tested at both ends. `bun run --cwd packages/harness flows:versions` (or `flows:versions claude`) runs, for each end, that program's conformance suites and the flows that launch it, with the end's variable set, and prints one pass or fail line per end and suite; its table in `flows/version-matrix.ts` names the variable, the range and the flows. Raising `max` is a change to the range constant alone, proven by that command.

H19.default and H19.opencode boot the product sandbox entry (`host-entry.agent-plugins.ts`) with the driver's canonical boot environment. They check the default selection or lazy OpenCode composition, persisted session configuration/title and a live session update. H19.default's sandbox has no machine login, so a session is refused with `account_unavailable` until the owner's OpenAI account arrives in a signed config push, built by the control plane's delivery plan. The owner chose no default, so that push must keep the provisioned runner as the default. They do not send a provider turn; OpenCode provider credentials remain C-11. `CLAXEDO_E2E_CLOUD_FAULT=startup-key-withheld` removes the driver key before launch; `opencode-composition-refused` makes the lazy OpenCode store directory unwritable by placing a file there.

H33 uses the full cloud stack, whose sandbox driver boots that same product entry. It changes the default harness, saves a command and installs a scripted MCP plugin, then uses them in an ACP cloud session. It removes both and verifies the saved command and plugin contribution disappear without replacing the runtime. Its targeted config-push faults are `default-harness-withheld`, `commands-withheld`, `command-delete-withheld`, and `plugin-mcp-withheld`. The deletion fault withholds only the first post-delete snapshot, so the command assertion must run before plugin removal publishes another snapshot. A fault run is a negative check, not an `expected-red.json` entry: it must exit nonzero with the named boundary assertion, and a setup failure does not count.
