# Codex app-server transport

This transport uses Codex's JSON-RPC app-server over stdio. It carries native `turn/steer`, `thread/goal/*` goals and provider-started turns, thread recovery, usage, quota windows, and `model/list` discovery. ACP does not expose those native operations. A process belongs to one session and is started only through `services.spawn`; retirement uses the returned owned-process handle. The broker owns request persistence and grants before any answer goes back to Codex. An approval's grant key is the contract's `grantIdentity` digest of its method, workspace directory, permission mode and native parameters without the per-call IDs, so a persisted grant never carries a command or patch.

`turn/steer` sends the steered prompt's Claxedo id as `clientUserMessageId`. Codex opens a `userMessage` item carrying it as `clientId` where the input enters the turn, and the transport yields `input-incorporated` there; the reply acknowledges acceptance only. The id is recorded before the request is sent, because Codex can open the item before the reply arrives.

The app-server never asks this transport to refresh a ChatGPT token. `account/chatgptAuthTokens/refresh` belongs to Codex's external auth mode, which a client enters only by calling `account/login/start` with `chatgptAuthTokens` and then refreshing the tokens itself; this transport never calls `account/login/start`, so an owner's managed login refreshes inside Codex from its own auth file and a brokered account runs on the configured API-key placeholder. The request, like any other unexpected method, is refused with `-32601`; handler failures remain `-32603`.

Permission modes are today's four, `read-only`, `workspace-write` (the default), `untrusted` and `full-access`, each an approval policy and a sandbox applied to `thread/start`, `thread/resume` and every `turn/start`, so a change lands on the next turn. A completed `create_subagent` item from Claxedo's own MCP server binds the host-minted child to its call before the turn ends, as the spawn edge when the turn's own thread made the call and without an edge when a child thread did, because that call lives in the child's transcript, which the parent never draws. Titles come from an ephemeral read-only side thread archived afterwards, and a rename is written back with `thread/name/set`. Attachments are materialized into the workspace through the shared owner in `translate/attachments.ts`, named in the prompt by path, with images also sent as `localImage`; a file part that is not a `data:` URL is undeliverable and rejects the turn from `send`, as the contract requires of a prompt the transport cannot deliver. `thread/tokenUsage/updated` reports the turn stream does not carry, on the session thread after a turn or on a side thread are metered as growth to the session's last turn; a report for a thread this transport never started is a `codex.usage_unbilled` diagnostic.

Stop, pause, and cancel interrupt the turn, wait for its completion event within the deadline, and only then inventory and terminate the background terminals the turn's command events named, through `thread/backgroundTerminals/list` and `thread/backgroundTerminals/terminate`. Codex's `no active turn to interrupt` answer counts as a completed interrupt. The flows, conformance suites and every fault fixture run a pinned Codex from `e2e/.artifacts/codex/<version>`, never from `PATH`, at either end of `CODEX_RANGE`; 0.156.1 answers both terminal methods, and 0.133.0 refused them as unknown variants. A completed turn that observed no command execution reports `cleanup: "verified_clear"`: Codex reports every command it starts as an item, so nothing of the turn's is left to clean up. A turn that ran a command reports `verified_clear` once the inventory after termination is empty, and `unknown` with the refusal as its `error` when Codex refuses the inventory or the termination. A goal pause or stop sets the goal's state first and then stops the running turn; when the turn ran a command and its cleanup is not verified clear, a `harness-notice` (`codex.background_commands_unverified`) follows through the session broker, and a turn that cannot be confirmed stopped fails the operation with the state already applied.

A cancellation during `turn/start` waits for the native turn ID within the caller's deadline and interrupts that same captured turn. Old completions cannot settle a new turn.

A session's app-server is `ready`, `busy`, `lost` or `retiring` (`entry.ts`). A process that exits or fails under a session, or whose `turn/start` does not answer within 60 s (the transport retires it then, so no orphan turn runs), makes the entry `lost`: the connection reads `disconnected` and the runtime `degraded` (`harness_process_lost`) with the exit status and the last 2,000 characters of what Codex wrote to stderr. The next turn, goal operation, title, rename or model read resumes the thread on a new app-server in the same home (`thread/resume` with `excludeTurns`, because the transport never reads the returned history) and reads the thread's goal back. A credential or projection update that arrives while a user or goal turn runs is answered `deferred` (`after-active-turns`) and applied when the entry is next idle; it restarts the app-server only when the Codex launch itself changed (the Codex account projection, the owner, machine-login permission or the projection), never for another provider's account or a lease-only rotation. A failed `model/list` is not remembered.

The version comes from the `initialize` response's `userAgent` (`claxedo/<version> (...)`) and is checked against `CODEX_RANGE` in `version.ts` through the contract's `HarnessVersionGate`: 0.156.1 through 0.159.2. The protocol types are generated from the range's max, which the sandbox images also pin, so the translator knows every frame the newest tested Codex sends; an older Codex inside the range omits the newer optional fields. An older Codex fails the launch with a configuration error that names the update; an unreadable version is a protocol error; a newer one runs with one `codex.untested_version` diagnostic per transport. `CLAXEDO_E2E_CODEX=min|max` picks the end the e2e pin installs, and `flows:versions codex` runs the Codex conformance suites and native flows at both ends.

Requests Codex asks go to the running turn's broker: the user turn's, or a goal turn's once the host admits it, so an approval during a goal is never refused as a session ask. A `serverRequest/resolved` for a request still being asked aborts that ask, which closes its prompt, and no answer is sent. A `turn/started` on the session thread that is not the user turn's, with the goal active, is a goal continuation: it is recorded at once, buffers its events and requests, and asks `SessionBroker.admitProviderTurn` at once; the host hands it the session when the previous user or goal turn releases it. Stop and the host's abort of a goal turn interrupt it, and a steer lands in it. Setting the goal's state before stopping its turn keeps a continuation from starting in between. A goal snapshot the broker fails to publish is reported to the session's owner and does not fail the mutation. Every thread asks for reasoning summaries (`model_reasoning_summary = "auto"` in its config and `summary: "auto"` on every `turn/start`), because Codex's catalog defaults every current model to `none`.

A Codex thread spawns Codex children only through Codex's own multi-agent tools; Claxedo adds no spawn tool of its own to the thread. The transport registers no dynamic tool, so Codex never sends it an `item/tool/call`, and one would be refused with `-32601` like any unsupported request. Claxedo's spawn is its first-party MCP tool `create_subagent`, which exists for collaboration across harnesses and starts a child of any harness, Codex included, as its own session. Codex offers its multi-agent tools only to catalog models whose `multiAgentVersion` is `v1` or `v2`, and to models outside the catalog as `v1`; Codex 0.156.1 and 0.159.2 give `gpt-5.5` (`null` in the catalog) none, so a `gpt-5.5` session reaches a Codex child only through `create_subagent`, which a session gets wherever the runtime serves the first-party MCP server (a local session on the desktop or loopback runtime, and on a cloud root when its `subagents` tool group is consented). Codex fixes a thread's multi-agent version at its first turn: a thread started on `gpt-5.5` keeps no multi-agent tools after a switch to `gpt-6-astra`, and one started on `gpt-6-astra` keeps them after a switch to `gpt-5.5`, at both ends of `CODEX_RANGE`. Every child thread lives in the one `children` registry (`children.ts`), each with its own translator, turn state and ordered delivery. A v2 spawn is a `subAgentActivity` item of kind `started` whose id is the spawn call; a v1 spawn is a `spawnAgent` `collabAgentToolCall` whose child is named in `receiverThreadIds` on `item/completed`. Codex 0.156.1 and 0.159.2 send no `thread/started` for the child. A v1 spawn's `item/completed` can arrive after the child's first notifications, such as the model-metadata and under-development warnings Codex sends when the child thread starts, so frames of an unknown thread that arrive while the parent runs are held and delivered in order once a spawn names that thread; held frames no spawn claims are dropped when the parent's turn completes. The child's label is the last segment of the v2 `agentPath` (the model's task name), or `Codex subagent` for v1 with the prompt as description; the nickname Codex assigns is only readable with `thread/read`. The spawn is observed through `SessionBroker.observeSubagent` as a `background` child with the spawn call as `toolCallId` and the child thread as `providerId` and correlation key, and bound with `associateChild`, before the child's first frame is delivered: every child's steps run in arrival order on its own chain. A spawn from a child thread is admitted without a `toolCallId`, since that call lives in the child's transcript. The child's `item/*`, `turn/*` and `thread/tokenUsage/updated` frames arrive under the child thread id and are translated by the child's translator with a child route. While the session's user turn is open they join its stream, during a provider turn they join that turn, and otherwise they go through `SessionBroker.publishChild` once the last turn has released, so a child keeps its transcript moving after its parent's turn ended and the parent's own turn semantics do not change. The child's status comes from its own turns, which both protocol versions report: `turn/completed` settles it `completed`, `interrupted`, or `failed` (a failed turn, or an interrupted one that carries an error) once every frame before it has been delivered. The parent's `completed` and `interrupted` activity items carry no outcome and change nothing. A child whose previous turn ended starts a new child turn on the same child session with a `running` observation keyed by the call that asked it: the v2 `interacted` item or the v1 collab call (`sendInput`, `resumeAgent`, and the rest) naming it as a receiver, or the child's own turn id when no call was seen, because the host moves a finished subagent back to running only for a call it has not seen. A v1 call reporting the child `shutdown` observes it `killed`. The number of Codex-spawned children that are spawned or running reaches the session as `SessionBroker.publish({ type: "background-work", agents })` whenever it changes, and as zero when the app-server ends. Each child's usage reaches the ledger as owned, so it is metered once, on the child, through the child's `usage` events, and never to the session. `backgroundTasks.stop` maps the call that spawned a child, or one that started a later child turn, to that child's running turn and interrupts it with `turn/interrupt` on the child thread; the parent and other children keep running, and a child with no running turn answers `not_found`. A request from a child thread carries the contract's `child` route with the child thread id, its correlation key, so the broker files it on the child session; it is asked only after every step the child queued before it, so the child's spawn is bound first, because the child's first request can arrive while its spawn observation is still being admitted, and the broker files a request with an unbound key on the parent. It goes to the running turn's broker, or, with no turn running, to `SessionBroker.ask`, where the child's own open turn owns it; only a request from the session's own thread with no turn running is refused.

Translation constraints: cumulative usage replaces the previous observation in its native scope; overlapping native totals must not be counted twice. Child thread attribution uses the observed parent binding. Completed item snapshots contribute only content not already delivered by streaming deltas. A reasoning item that streamed contributes nothing at completion, and each later summary section (`summaryPartAdded`) opens after a blank line. A message or reasoning item that directly follows another item of the same kind opens after a blank line, so two items never run together; after a tool or the other kind it needs none, because the projection already starts a new part there, and after a user message (a steer taken into the turn) it needs none, because the reply after it opens its own message. MCP image results preserve the provider's supplied bytes. Every thread item type of the generated protocol has an explicit kind and tool name, so an item never falls through to an empty generic row: a file change is an `apply_patch` row whose metadata lists each file with its kind, move target and diff; a hook prompt shows the injected text; a sleep carries its duration; a native subagent's interaction or interruption names the agent path; a web search takes its query from the action when the item's own query is empty, and its results are the row's output; a generated image is an image attachment (inline when small, otherwise the file Codex saved), never base64 text. A declined or failed file change, a failed collab tool call and a refused image generation are errors, as a declined or failed command is. Codex emits a `dynamicToolCall` item only for a dynamic tool its client registered, and this transport registers none, so the item keeps only its kind and draws as a generic row. A completion whose input grew since the item started (a web search's query) updates the row's input.

Every projected MCP server, and Claxedo's own for a local session, reaches Codex in the thread's `mcp_servers`. Codex decides how the model sees their tools, and this transport doesn't override it: for a model whose catalog entry supports search, such as `gpt-5.5`, Codex 0.156.1 defers every MCP tool behind its client-executed `tool_search` tool, so the model first calls `tool_search`, receives the matching `mcp__<server>` namespaces in a `tool_search_output`, and then calls a tool in that namespace. A model without search support gets the tools directly.

Profile preparation first records the use of the owner's conversation store, which holds every home of that owner, through `services.recordHomeUse`, and the app-server is spawned holding that store, so the store and its homes stay out of collection for as long as the app-server lives, including after the runtime that launched it has gone. The app-server runs in the session's home with `-c sqlite_home=<store>`, and every `thread/start` and `thread/resume` names the home's model provider, so a session that moves to another home of its owner resumes its thread there (`profiles/codex/README.md`).

A failed turn's error class comes from Codex's own `codexErrorInfo`, one table over every value of the generated protocol: a usage limit for `usageLimitExceeded`; a temporary rate limit for `rateLimitExceeded` and an HTTP failure variant that answered 429; a credential failure for `unauthorized` and an HTTP 401 or 403; a model failure for `serverOverloaded` ("Selected model is at capacity") and `flexUnavailable`; a workspace failure for `sandboxError`; a session failure for `threadRollbackFailed`; and `unknown` for the rest, so the app never guesses a recovery from the message text. A failure that names only Codex's generic session error is explained by the last limited rate-limit window, and that window is a plan limit, so it is a usage limit too. The reset sentence of a limited window comes from the shared `translate/rate-limit-reset.ts`, as Claude's does. A turn Codex itself interrupted with an error (0.159's `tooManyDenials`) ends failed with that error; an interrupted turn without one is a stop. A `willRetry` error is a `session-retry` carrying Codex's own sentence ("Reconnecting... 2/5"); Codex reports no attempt number or delay as data, so the event carries neither.

Codex token counts include cached input within input and reasoning within output; metering separates those categories. Each native thread/turn is a usage scope, with separate model streams after a model change. The first report seeds from `last`; subsequent growth uses lifetime-total differences so a missed report does not lose spend. Repeated totals refresh context without adding usage. An observation outside a turn contributes only growth since the last observed lifetime total. Bounded thread state evicts the least recently reported thread.

A completed command can have null output fields after streaming stdout or after printing nothing. Preserve the streamed buffer or empty output, never the protocol envelope. `declined` means the command never ran; completed/failed command status agrees with zero/nonzero exit status. `systemError` precedes authoritative error/completion frames and cannot terminalize early, so it is a warning notice. A descendant error folded into an ancestor ends the descendant and remains a diagnostic on the ancestor. JSON-RPC `params` is the single boundary into generated protocol types. Realtime media, auto-approval reviews and global app surfaces have no classic chat projection. A hook run records nothing unless it did not complete or said something other than injected context; then it is a notice naming the hook's event, status and words. `thread/settings/updated` only records the served model, and goal notifications belong to the goal state in `notifications.ts`, so the translator reports neither. `turn/diff/updated` carries the turn's aggregated unified diff and becomes one file diff per `diff --git` section.
