# Codex app-server transport

`ConfigOperations.setModelSettings` validates model and effort against `model/list` before any control, then uses experimental `turn/settings/update` for the active native turn and `thread/settings/update` for future turns, including provider-started turns. Thread creation enables `step_model_switching`; the generated protocol includes experimental types. An in-flight model request retains its settings; subsequent requests within that turn use the published model and effort. Codex refuses destinations that change the admitted tool requirements or lack native model metadata. A refusal leaves the runtime selection unchanged and sends neither an interrupt nor a replacement turn. A completed target's `targetUnavailable` response, or a turn whose start failed, proceeds to the future thread setting; the failed start is that turn's own error. Effort reset uses the selected model's reported default because native `null` preserves the current effort. Model controls do not change speed, summary, permissions, processes, terminals or child threads.

This transport uses Codex's JSON-RPC app-server over stdio. It carries native `turn/steer`, `thread/goal/*` goals and provider-started turns, usage, quota windows, and `model/list` discovery. ACP does not expose those native operations. A process is started only through its workspace's `services.spawn`, and retirement uses the returned owned-process handle. The broker owns request persistence and grants before any answer goes back to Codex. An approval's grant key is the contract's `grantIdentity` digest of its method, workspace directory, permission mode and native parameters without the per-call IDs, so a persisted grant never carries a command or patch.

`turn/steer` sends the steered prompt's Claxedo id as `clientUserMessageId`. Codex opens a `userMessage` item carrying it as `clientId` where the input enters the turn, and the transport yields `input-incorporated` there; the reply acknowledges acceptance only. The id is recorded before the request is sent, because Codex can open the item before the reply arrives.

Sessions of one workspace share app-servers through `CodexProcessPool` (`pool.ts`), which each transport owns, so sessions of different workspaces never share a process and every app-server's launch record belongs to the workspace whose sessions use it. A pool entry is keyed by `launch-key.ts`: the composed home (the account owner, the broker binding or plan origin, and the plugin selection mode), the selected account's `credentialId` (`own-login` for the machine login; a binding without account metadata keys by its session, so two unidentified accounts never share), the plugin selection and the projection generation. The key never holds a secret, a placeholder, `auth.json` or the environment. An entry holds at most 8 sessions; a ninth opens a second app-server under the same key. When its last session leaves, the app-server stays for 30 s so a quick reattach skips spawn and `initialize`, and is then retired; an app-server that exits or breaks its channel leaves the pool at once, and the transport's `dispose` retires every app-server of its pool. Every app-server of one owner opens the owner's store as `sqlite_home`, so the first start for a store runs alone and the starts of that owner's other keys wait for it to initialize.

`CodexRouter` (`router.ts`) is the one reader of an app-server's frames. Each session joins as a `CodexMember` (`member.ts`), the connection its entry uses: a thread belongs to the member whose `thread/start` or `thread/resume` returned it, and a child thread to the member whose thread spawned it (a v2 `subAgentActivity` start or a v1 spawn `collabAgentToolCall` completion). A notification or request for a thread no member owns is held (`early-frames.ts`): a child's first frames can arrive before the spawn that names it. A held frame is delivered once its thread gets an owner; after 10 s, or past 256 held frames or 1 MiB, it is dropped with an `unrecognized-event` warning in the host log and a held request is answered with a `-32000` refusal. Frames of a thread whose session left are dropped silently. `account/rateLimits/updated` reaches every member, since they share the account; another notification without a thread belongs to no session. `account/chatgptAuthTokens/refresh`, the one request without a thread it answers, goes to the members in turn until one renews its ChatGPT plan; with none it is refused with `-32000`. Any other request without a thread is refused with `-32601`; handler failures remain `-32603`. Only an app-server exit or a broken channel fails every member.

The session's account reaches Codex through `account/login/start` (`CodexAccountLogin`, `account.ts`), sent before every `thread/start`, `thread/resume`, `turn/start` and `thread/goal/set` whenever it differs from the app-server's last login, and serialized per app-server. A brokered account logs in its placeholder as `apiKey`. A ChatGPT plan handed over directly (a `subscription` direct row on `codex-app-server`, which a cloud runtime receives because no edge can add the plan's account header) logs in as `chatgptAuthTokens` with the access token and the account id read from it. That is Codex's internal mode: the 0.159.2 schema marks it `[UNSTABLE] FOR OPENAI INTERNAL USE ONLY`, and it is verified only on 0.159.2 by `src/conformance/codex-plan.test.ts`. Codex refuses an access token that is not a JWT (`invalid ID token format`), so an opaque egress-swapped placeholder cannot stand in for it and the sandbox holds the real access token; the refresh token never leaves the control plane. Before each login the transport reads the token's own `exp` and, with less than ten minutes left, takes a fresh token through `services.refreshCredential`, which the host answers only while a turn is admitted, then logs in again. A `account/chatgptAuthTokens/refresh` Codex sends after a 401 is the backstop, answered the same way with the refused token's expiry so the host renews only when it holds nothing newer; on 0.159.2 the turn that met the 401 still fails with Codex's own `application network policy is unavailable` and the next turn carries the renewed token. If Codex renames or drops the mode, changes the refresh request or its response, or starts validating the token's signature, plan sessions stop signing in or renewing, and that conformance test fails. Every login is process-wide: every member of the entry spends the same account. The composed home stores it with `cli_auth_credentials_store = "ephemeral"`, so it never lands in a file, and a rotation keeps the app-server. The transport never logs in an own-login app-server, whose home links the owner's `auth.json`; Codex refreshes that login itself.

Permission modes are today's four, `read-only`, `workspace-write` (the default), `untrusted` and `full-access`, each an approval policy and a sandbox applied to `thread/start`, `thread/resume` and every `turn/start`, so a change lands on the next turn. A completed `create_subagent` item from Claxedo's own MCP server binds the host-minted child to its call before the turn ends, as the spawn edge when the turn's own thread made the call and without an edge when a child thread did, because that call lives in the child's transcript, which the parent never draws. Titles come from an ephemeral read-only side thread archived afterwards, and a rename is written back with `thread/name/set`. Attachments are materialized into the workspace through the shared owner in `translate/attachments.ts`, named in the prompt by path, with images also sent as `localImage`; a file part that is not a `data:` URL is undeliverable and rejects the turn from `send`, as the contract requires of a prompt the transport cannot deliver. `thread/tokenUsage/updated` reports the turn stream does not carry, on the session thread after a turn or on a side thread are metered as growth to the session's last turn; a report for a thread this transport never started is a `codex.usage_unbilled` diagnostic.

Stop, pause, and cancel interrupt the turn, wait for its completion event within the deadline, and only then inventory and terminate the background terminals the turn's command events named, through `thread/backgroundTerminals/list` and `thread/backgroundTerminals/terminate`. Codex's `no active turn to interrupt` answer counts as a completed interrupt. The flows, conformance suites and every fault fixture run a pinned Codex from `e2e/.artifacts/codex/<version>`, never from `PATH`, at either end of `CODEX_RANGE`; 0.156.1 answers both terminal methods, and 0.133.0 refused them as unknown variants. A completed turn that observed no command execution reports `cleanup: "verified_clear"`: Codex reports every command it starts as an item, so nothing of the turn's is left to clean up. A turn that ran a command reports `verified_clear` once the inventory after termination is empty, and `unknown` with the refusal as its `error` when Codex refuses the inventory or the termination. A goal pause or stop sets the goal's state first and then stops the running turn; when the turn ran a command and its cleanup is not verified clear, a `harness-notice` (`codex.background_commands_unverified`) follows through the session broker, and a turn that cannot be confirmed stopped fails the operation with the state already applied.

A cancellation during `turn/start` waits for the native turn ID within the caller's deadline and interrupts that same captured turn. Old completions cannot settle a new turn.

A session's entry is `ready`, `busy`, `lost` or `retiring` (`entry.ts`); its member is `joined`, `failed` or `left`. An app-server that exits or fails makes every entry on it `lost`: the connection reads `disconnected` and the runtime `degraded` (`harness_process_lost`) with the exit status and the last 2,000 characters of what Codex wrote to stderr. A `turn/start` that does not answer within 60 s fails only its own member, with the same health; when Codex answers it later, that turn is interrupted, so no orphan turn runs. The next turn, goal operation, title, rename or model read of a lost entry rejoins the pool for its key and resumes the thread (`thread/resume` with `excludeTurns`, because the transport never reads the returned history), then reads the thread's goal back. A missing-thread error is not retried: it fails the turn with Codex's own error, and recovery is cancelling that turn.

Codex lets one app-server write a thread at a time: a thread stays loaded, holding its writer, after `thread/unsubscribe`, and another app-server's `thread/resume` fails with `already has an active writer`. Only `thread/archive` unloads it. So a session that leaves an app-server (`thread-release.ts`) stops its running turn and its children's turns, terminates its thread's background terminals and archives its thread; a session whose own connection failed, after a `turn/start` timeout, skips the stops but still archives its thread while the app-server lives. A release that fails still leaves the entry `lost`, so the next use reopens it. Resuming a thread Codex reports archived first sends `thread/unarchive`. The thread's history and goal survive the round trip. A credential or projection update recomputes the launch key: when the key is unchanged, it only replaces the session's start input, so the next login carries a rotated placeholder; when it changed, the session leaves its entry and resumes its thread on the entry of the new key, while its siblings keep theirs. An update that arrives while a user or goal turn runs is answered `deferred` (`after-active-turns`) and applied when the entry is next idle; one that arrives while the entry is lost is kept for the resume. A failed `model/list` is not remembered.

The version comes from the `initialize` response's `userAgent` (`claxedo/<version> (...)`) and is checked against `CODEX_RANGE` in `version.ts` through the contract's `HarnessVersionGate`: 0.156.1 through 0.159.2. The protocol types are generated from the range's max, which the sandbox images also pin, so the translator knows every frame the newest tested Codex sends; an older Codex inside the range omits the newer optional fields. An older Codex fails the launch with a configuration error that names the update; an unreadable version is a protocol error; a newer one runs with one `codex.untested_version` diagnostic per transport. `CLAXEDO_E2E_CODEX=min|max` picks the end the e2e pin installs, and `flows:versions codex` runs the Codex conformance suites and native flows at both ends.

Requests Codex asks never reach the translator; `answerCodexRequest` asks the running turn's broker: the user turn's, or a goal turn's once the host admits it, so an approval during a goal is never refused as a session ask. A `serverRequest/resolved` for a request still being asked aborts that ask, which closes its prompt, and no answer is sent. A `turn/started` on the session thread that is not the user turn's, with the goal active, is a goal continuation: it is recorded at once, buffers its events and requests, and asks `SessionBroker.admitProviderTurn` at once; the host hands it the session when the previous user or goal turn releases it. Stop and the host's abort of a goal turn interrupt it, and a steer lands in it. Setting the goal's state before stopping its turn keeps a continuation from starting in between. A goal snapshot the broker fails to publish is reported to the session's owner and does not fail the mutation. Every thread asks for reasoning summaries (`model_reasoning_summary = "auto"` in its config and `summary: "auto"` on every `turn/start`), because Codex's catalog defaults every current model to `none`.

A Codex thread spawns Codex children only through Codex's own multi-agent tools; Claxedo adds no spawn tool of its own to the thread. The transport registers no dynamic tool, so Codex never sends it an `item/tool/call`, and one is refused by `answerCodexRequest` with `-32601` like any unsupported request. Claxedo's spawn is its first-party MCP tool `create_subagent`, which exists for collaboration across harnesses and starts a child of any harness, Codex included, as its own session. Codex offers its multi-agent tools only to catalog models whose `multiAgentVersion` is `v1` or `v2`, and to models outside the catalog as `v1`; Codex 0.156.1 and 0.159.2 give `gpt-5.5` (`null` in the catalog) none, so a `gpt-5.5` session reaches a Codex child only through `create_subagent`, which a session gets wherever the runtime serves the first-party MCP server (a local session on the desktop or loopback runtime, and on a cloud root when its `subagents` tool group is consented). Codex fixes a thread's multi-agent version at its first turn: a thread started on `gpt-5.5` keeps no multi-agent tools after a switch to `gpt-6-astra`, and one started on `gpt-6-astra` keeps them after a switch to `gpt-5.5`, at both ends of `CODEX_RANGE`. Every child thread lives in the one `children` registry (`children.ts`), each with its own translator, turn state and ordered delivery. A v2 spawn is a `subAgentActivity` item of kind `started` whose id is the spawn call; a v1 spawn is a `spawnAgent` `collabAgentToolCall` whose child is named in `receiverThreadIds` on `item/completed`. Codex 0.156.1 and 0.159.2 send no `thread/started` for the child. A v1 spawn's `item/completed` can arrive after the child's first notifications, such as the model-metadata and under-development warnings Codex sends when the child thread starts, so the router holds frames of an unknown thread and delivers them in order once a spawn names that thread. The child's label is the last segment of the v2 `agentPath` (the model's task name), or `Codex subagent` for v1 with the prompt as description; the nickname Codex assigns is only readable with `thread/read`. The spawn is observed through `SessionBroker.observeSubagent` as a `background` child with the spawn call as `toolCallId` and the child thread as `providerId` and correlation key, and bound with `associateChild`, before the child's first frame is delivered: every child's steps run in arrival order on its own chain. A spawn from a child thread is admitted without a `toolCallId`, since that call lives in the child's transcript. The child's `item/*`, `turn/*` and `thread/tokenUsage/updated` frames arrive under the child thread id and are translated by the child's translator with a child route. While the session's user turn is open they join its stream, during a provider turn they join that turn, and otherwise they go through `SessionBroker.publishChild` once the last turn has released, so a child keeps its transcript moving after its parent's turn ended and the parent's own turn semantics do not change. The child's status comes from its own turns, which both protocol versions report: `turn/completed` settles it `completed`, `interrupted`, or `failed` (a failed turn, or an interrupted one that carries an error) once every frame before it has been delivered. The parent's `completed` and `interrupted` activity items carry no outcome and change nothing. A child whose previous turn ended starts a new child turn on the same child session with a `running` observation keyed by the call that asked it: the v2 `interacted` item or the v1 collab call (`sendInput`, `resumeAgent`, and the rest) naming it as a receiver, or the child's own turn id when no call was seen, because the host moves a finished subagent back to running only for a call it has not seen. A v1 call reporting the child `shutdown` observes it `killed`. The number of Codex-spawned children that are spawned or running reaches the session as `SessionBroker.publish({ type: "background-work", agents })` whenever it changes, and as zero when the app-server ends. Each child's usage reaches the ledger as owned, so it is metered once, on the child, through the child's `usage` events, and never to the session. `backgroundTasks.stop` maps the call that spawned a child, or one that started a later child turn, to that child's running turn and interrupts it with `turn/interrupt` on the child thread; the parent and other children keep running, and a child with no running turn answers `not_found`. A request from a child thread carries the contract's `child` route with the child thread id, its correlation key, so the broker files it on the child session; it is asked only after every step the child queued before it, so the child's spawn is bound first, because the child's first request can arrive while its spawn observation is still being admitted, and the broker files a request with an unbound key on the parent. It goes to the running turn's broker, or, with no turn running, to `SessionBroker.ask`, where the child's own open turn owns it; only a request from the session's own thread with no turn running is refused.

Translation constraints: cumulative usage replaces the previous observation in its native scope; overlapping native totals must not be counted twice. Child thread attribution uses the observed parent binding. Completed item snapshots contribute only content not already delivered by streaming deltas. A reasoning item that streamed contributes nothing at completion, and each later summary section (`summaryPartAdded`) opens after a blank line. A message or reasoning item that directly follows another item of the same kind opens after a blank line, so two items never run together; after a tool or the other kind it needs none, because the projection already starts a new part there, and after a user message (a steer taken into the turn) it needs none, because the reply after it opens its own message. MCP image results preserve the provider's supplied bytes. Every thread item type of the generated protocol has an explicit kind and tool name, so an item never falls through to an empty generic row: a file change is an `apply_patch` row whose metadata lists each file with its kind, move target and diff; a hook prompt shows the injected text; a sleep carries its duration; a native subagent's interaction or interruption names the agent path; a web search takes its query from the action when the item's own query is empty, and its results are the row's output; a generated image is an image attachment (inline when small, otherwise the file Codex saved), never base64 text. A declined or failed file change, a failed collab tool call and a refused image generation are errors, as a declined or failed command is. Codex emits a `dynamicToolCall` item only for a dynamic tool its client registered, and this transport registers none, so the item keeps only its kind and draws as a generic row. A completion whose input grew since the item started (a web search's query) updates the row's input.

Every projected MCP server, and Claxedo's own for a local session, reaches Codex in the thread's `mcp_servers`. Codex decides how the model sees their tools, and this transport doesn't override it: for a model whose catalog entry supports search, such as `gpt-5.5`, Codex 0.156.1 defers every MCP tool behind its client-executed `tool_search` tool, so the model first calls `tool_search`, receives the matching `mcp__<server>` namespaces in a `tool_search_output`, and then calls a tool in that namespace. A model without search support gets the tools directly.

Profile preparation, at every session start, first records the use of the owner's conversation store, which holds every home of that owner, through `services.recordHomeUse`, and the app-server is spawned holding that store, so the store and its homes stay out of collection for as long as the app-server lives, including after the runtime that launched it has gone. The app-server runs with the home as its working directory and `CODEX_HOME`, and `-c sqlite_home=<store>`, and every `thread/start` and `thread/resume` names the home's model provider, so a session that moves to another home of its owner resumes its thread there (`profiles/codex/README.md`).

A failed turn's error class comes from Codex's own `codexErrorInfo`, one table over every value of the generated protocol: a usage limit for `usageLimitExceeded`; a temporary rate limit for `rateLimitExceeded` and an HTTP failure variant that answered 429; a credential failure for `unauthorized` and an HTTP 401 or 403; a model failure for `serverOverloaded` ("Selected model is at capacity") and `flexUnavailable`; a workspace failure for `sandboxError`; a session failure for `threadRollbackFailed`; and `unknown` for the rest, so the app never guesses a recovery from the message text. A failure that names only Codex's generic session error is explained by the last limited rate-limit window, and that window is a plan limit, so it is a usage limit too. The reset sentence of a limited window comes from the shared `translate/rate-limit-reset.ts`, as Claude's does. A turn Codex itself interrupted with an error (0.159's `tooManyDenials`) ends failed with that error; an interrupted turn without one is a stop. A `willRetry` error is a `session-retry` carrying Codex's own sentence ("Reconnecting... 2/5"); Codex reports no attempt number or delay as data, so the event carries neither.

Codex token counts include cached input within input and reasoning within output; metering separates those categories. Each native thread/turn is a usage scope, with separate model streams after a model change. The first report seeds from `last`; subsequent growth uses lifetime-total differences so a missed report does not lose spend. Repeated totals refresh context without adding usage. An observation outside a turn contributes only growth since the last observed lifetime total. Bounded thread state evicts the least recently reported thread.

A completed command can have null output fields after streaming stdout or after printing nothing. Preserve the streamed buffer or empty output, never the protocol envelope. `declined` means the command never ran; completed/failed command status agrees with zero/nonzero exit status. `systemError` precedes authoritative error/completion frames and cannot terminalize early, so it is a warning notice. JSON-RPC `params` is the single boundary into generated protocol types. Realtime media, auto-approval reviews and global app surfaces have no classic chat projection. A notification that names no thread (account, configuration, deprecation and Windows sandbox notices, `thread/started`) belongs to no session, so neither a turn nor the session listener routes it; only `account/rateLimits/updated` reaches the session, as its quota. A hook run records nothing unless it did not complete or said something other than injected context; then it is a notice naming the hook's event, status and words. `thread/settings/updated` only records the served model, and goal notifications belong to the goal state in `notifications.ts`, so the translator reports neither. `turn/diff/updated` carries the turn's aggregated unified diff and becomes one file diff per `diff --git` section.

A move to another launch key first checks the child registry and the native background-terminal inventory. If either has live work, it refuses the move and retains the pending configuration on the current app-server. Later sends retry that configuration before sending their prompt; after the jobs finish, the thread resumes with the new launch. Inventory failure also prevents the move. Explicit session close and user-requested task cancellation retain their separate lifecycle paths; close releases the thread as a move does, ending its running work.
