# Pi on pi-durable

`PiDurableTransport` drives Pi as an embedded library: one `@earendil-works/pi-durable` `Harness` per Claxedo session, in the process that hosts the transport. There is no Pi CLI, no child process for the agent loop and no IPC. The same class serves two placements through `PiPlacement` (`placement.ts`): the local daemon (`node.ts`, `createNodePiPlacement`) and a Durable Object host that implements the port itself. `index.ts` and `placement.ts` import no Node built-in, so a Worker bundle can import `@claxedo/harness/pi-durable`; pi-ai's provider APIs (the Anthropic SDK) still reference Node built-ins, so a Worker host needs `nodejs_compat`.

## What one session holds

- **Storage.** The local placement keeps each session in `<stateRoot>/sessions/<sessionId>.sqlite` through pi-durable's portable `SqliteStorage`: under Node over pi-durable's own `node:sqlite` adapter, under Bun over `bun:sqlite` (`storage.ts`), because Bun has no `node:sqlite` and the workspace runtime runs under both, as its own store does. Pi's transcript is the only copy; the binding's `upstreamSessionId` is the session id and its root conversation id, unique across sessions, and attach refuses a store whose root is another one.
- **Registry.** Pi stores extension names, not code, so the transport installs the same extensions before `resume()` on every open: Pi's `CodingTools` (read, write, edit, bash) and the `claxedo` extension (`extension.ts`) with the `question` tool, the session's MCP tools, the `available_skills` section and the approval hook.
- **Models.** `PiCredentials` (`credentials.ts`) gives the session its own pi-ai `Models` over a credential store built from `ResolvedCredentials.direct`. Only direct rows reach Pi; broker placeholders and the machine's own logins never do, and the auth context is empty, so pi-ai reads no environment variable and no file such as `~/.pi`. Each built-in provider's auth is replaced: an API key resolves from the row, a subscription is an OAuth credential whose `toAuth` sends the access token and whose `refresh` asks the placement's `refreshCredential` and otherwise fails with `credential_expired`, so Claxedo's authority stays the one refresher. A row's `baseUrl` and `apiPath` become the request's base URL (Anthropic's SDK appends `/v1` itself, so it gets the origin). A custom provider definition becomes an OpenAI-compatible provider spending the row its `credentialProviderId` names; a definition that reuses a built-in id is not registered, because the built-in provider plus the row's base URL already reach it. The model catalog (`piCatalog`, for a session and for a draft) lists every provider the owner has a usable row for, direct or a brokered account row, so a cloud workspace's machine, which receives account rows but no direct ones, answers a Pi draft without holding a secret. The launch catalog (`launch-catalog.ts`), which the control plane Worker serves for a Pi draft, reads each built-in provider's chat model table (`anthropic.models` and the rest), what that provider's `getModels()` answers before it fetches any model, rather than constructing the provider: a provider module carries its API client and the vendor SDK behind it, which would land in that Worker's bundle and startup. `launch-catalog.test.ts` holds the two equal. A turn still needs a direct row: a model whose provider has none is refused before the turn with `direct_credential_required`. `configure({ credentials })` swaps the rows in place and answers `applied`; nothing restarts.
- **Environment.** Tools run through `HarnessOptions.env`. Locally that is pi-durable's `NodeExecutionEnv` for files, with its `exec` replaced by `shell.ts`, which runs every command of a session in one long-lived shell host (`runner-child.ts`, the `@claxedo/harness/pi-runner` export, `pi-runner.mjs` beside a product bundle) started through `HarnessServices.spawn` on the session's first command, so the host is one owned launch with a launch record and a process group (on Windows, the launch gate's job). The composer passes the host's command (`PiNodeOptions.runner`); the transport never locates the file. Each command is a child of that host (`shell -c <command>`, in its own process group on POSIX), spoken over NDJSON on the host's stdin/stdout (`runner-protocol.ts`): output comes back in frames of at most 64 KiB, and the host pauses a command's streams while the pipe is full, so a command printing 50 MB neither buffers in the host nor holds up the commands beside it. The command returns when its shell exits; what it left running outlives it, as under pi-durable's own `NodeExecutionEnv`: a dev server started with `nohup … &` answers the session's later commands. A Stop or timeout ends that command's tree alone (`taskkill /T` on Windows, its process group elsewhere), and the session's close ends the host, which first ends every process group its commands started, after which the launch is retired (on Windows the job takes whatever is left). A host that dies mid-session fails the command it was running with one line, and the next command starts a new host and begins with `RUNNER_RESTARTED_NOTICE`; a command the dead host never acknowledged runs once on the new one. The host's resident memory under Node 26 on macOS is 40 MB idle, 41 MB after a command, 60 MB after streaming 50 MB; on Windows Server 2025 (t3.large) under Node 24 it is 36 MB idle, 36 MB after a command, 51 MB after streaming 50 MB, measured as the process working set. The bash is resolved as pi-durable's own `NodeExecutionEnv` resolves it (`piShell` mirrors its unexported `getShellConfig`): `/bin/bash` where there is one, and on Windows Git for Windows' `bash.exe` under ProgramFiles, beside the git on PATH (the installer puts only `Git\cmd` there) or a bash.exe on PATH other than WSL's launcher; a box without one fails every command with the one line naming the install. Output beyond the bash tool's limits is not spilled to a file; the retained tail is the result. Pi also builds the environment for every model request, to render prompt sections such as `available_skills`, so a placement whose machine may be asleep cannot tell a tool's use of it from a section's; the approval hook calls the placement's `toolCalling` once a tool call has passed approval, before Pi builds that call's environment.

## Turns

`send` refuses an attachment that is not an inline image before anything is submitted, applies the turn's model and thinking level with `conversation.configure`, claims the session stream with a `PiRun` and submits the prompt (`flattenTurnPrompt` with the system prefix) under a fresh request id. Pi deduplicates submissions by request id, and the shared conformance suite reuses turn ids, so the id is unique per send; Claxedo never resubmits a crashed turn, because Pi resumes the run itself.

`stream.ts` keeps one `watchEvents` stream per session and routes each commit's batch to its owner: nobody, the Claxedo turn in `send`, or a continuation provider turn. A run settles at the end of the batch that settles its submission, so the usage committed with the answer stays in the turn: `done` is `finish`, `unanswered` with reason `aborted` is `cancelled`, any other `unanswered` is the harness's own `error` with Pi's detail. A detail that is an HTML page is the vendor's edge refusing the host the session runs on (chatgpt.com answers some Cloudflare egress addresses with a block page whose "try again later" is no rate limit), so the error is the contract's `EDGE_REFUSED_MESSAGE` with class `egress` instead of the page; a retry Pi starts after such a page names the same message. A steer is submitted with `whenBusy: "steer"` under its own request id, and becomes `input-incorporated` for its Claxedo message when Pi places it.

| Pi event | Claxedo event |
|---|---|
| `message_start` / `message_update` / `message_end` of an assistant message | `text-delta`, `thinking-delta`; final content is reconciled against what streamed and a contradiction is refused |
| `message_end` with stop reason `length` | `harness-notice` `pi.output_limit` |
| `tool_execution_start` / `_update` / `_end` | `tool-start` + `tool-input`, `tool-content` for appended output, `tool-output` or `tool-error`; an end with no start first starts the call with the arguments its assistant message gave it |
| `usage_changed` | `usage`, the difference from the previous totals, reasoning taken out of output |
| `auto_retry_start` | `session-retry` |
| `compaction_start` / `compaction_end` | `session-compaction` |
| `task_failed` | `harness-notice` `pi.task_failed`; the turn ends with its submission |
| `snapshot` | baseline usage, and only the partial answer the stream had not shown |
| `run_*`, `turn_*`, `submission`, `inbox_update`, `agent_changed`, `entry_appended`, `auto_retry_end`, `deferred_poll` | nothing |
| anything else | one `debug` diagnostic per kind per session |

A tool result's diagnostics reach the model as a `<harness>` block Pi appends to the result's content, while the entry's `data.diagnostics` keeps them structured. The person sees the content without that block: a failed tool's error is its output followed by the diagnostics' messages, and a successful one's warnings (its output truncated) follow its output as plain notes, the diagnostics kept whole in its details.

A model error Pi retries is `session-retry` and its failed attempt shows nothing. A context overflow makes Pi compact and retry once, with Pi's own compaction and retry defaults.

`cancel` aborts the conversation: queued inputs are withdrawn, every task of the run is aborted, and a running bash command's group is retired. It answers `terminal` once Pi is idle, or `cancellation_timeout` at the deadline.

## Requests

The `beforeTool` hook asks before `write`, `edit`, `bash` and every `mcp__` tool when the session's mode is `ask` (`PI_PERMISSION_MODES`; `full`, the default, never asks). It asks the active run's broker, or the session broker during a continuation, with request id `pi-tool:<toolCallId>` and the tool name as grant key, so a re-ask of the same call after a crash replays the saved answer. Allow runs the tool; anything else blocks it with a reason the model reads. A blocked call, like one stopped while it waits for an answer, ends without ever starting: Pi's end names the tool but carries no arguments, so the translator keeps each tool call of an assistant message until it starts or ends, and the row shows that tool and its input, failed with Pi's reason (`Tool call blocked: The person denied this tool call`, `Tool bash was aborted`), never the call id. The `question` tool asks the person through the broker and returns their answer as text; it is not replay-safe, so a crash mid-question gives the model an interrupted result.

## MCP and skills

`mcp.ts` builds one pi-mcp `McpClient` per server of `sessionMcpServers`, with Claxedo's first-party server whenever the host's services offer one: the local runtime for a local session, the session host for its root from that turn's delivery. It lists each server's tools when the extension is installed (cached by projection generation and server names) and calls them over the same client; a dropped client reconnects on the next call. A call the server answers 404 for its session or 401 closes that client and is sent once more over a newly initialized one, which is the transport spec's recovery for a lost session and picks up a rotated bearer; the server never ran the refused call. Tool names are `mcp__<server>__<tool>`, reduced to `[A-Za-z0-9_]` within 64 characters with an FNV-1a suffix when they change. A server that fails to connect is reported as `mcp-server-status` `failed` and contributes no tools to that turn; the next turn lists it again, since a session host's workspace machine may have been asleep and is starting. Locally an HTTP server uses pi-mcp's `StreamableHttpTransport`, and a stdio server runs through `HarnessServices.spawn` (`mcp-stdio.ts`) with its own env over the standard MCP inherited set (`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`; the Windows equivalents), never the daemon's environment. SSE servers are refused (`harnessSupportsMcpServer`).

### MCP Apps

Every client advertises the MCP Apps extension at `initialize` (`capabilities.extensions["io.modelcontextprotocol/ui"]` with `text/html;profile=mcp-app`), because a server sends a UI only to a client that asked for one. The tool list keeps each tool's `_meta` and `annotations`; the cached list's key carries a shape marker, so a list cached before tools kept `_meta` is listed again instead of hiding every app in the session. A tool whose `_meta.ui.visibility` is declared without `"model"` is not offered to the agent.

A successful call returns its MCP facts in the result's `details` (`mcp`: server, tool, the result's `_meta` and `structuredContent`). When the tool declares a `ui://` resource (`mcpAppResourceUri`), the same client reads it once: the first content of type `text/html;profile=mcp-app` within `MCP_APP_MAX_BYTES`, measured before it is encoded, becomes `details.appDocument`, a base64 data URL, and the resource's `_meta.ui` becomes `mcp.app`. Pi stores `details` on the tool-result message, so a replayed transcript draws the same app after the server has changed or gone. A missing, oversized or wrong-type document leaves the ordinary result and logs the reason. The translator turns `details` into the `tool-output` event's `metadata.mcp` and one inline attachment, and drops `mcp.app` when the document is not there.

`PiDurableTransport.mcp` lists a server's tools, calls one and reads a resource over the session's own clients, outside any turn. A server the session does not project is `not_found`; a call to a tool declared without `"app"` visibility is `refused`; a server that cannot be reached is `unavailable`. The skills section lists each projected plugin skill's name, description and `SKILL.md` location, read through the section's environment, so it works wherever the tools run.

## Crash and resume

Pi commits a tool call's intent before executing it. When the process dies, reopening the store finds the live run: a `replay: "safe"` tool reruns and any other gets an `interrupted` error result, and the generation continues. The transport declares `durableRuns`; at boot the host attaches every session it interrupted, and the attach's stream sees the live run in its snapshot and admits it as a `continuation` provider turn, whose events and terminal are that turn's.

## Placement port

`PiPlacement.open` returns the session's `Harness`, root conversation and live registry, without resuming; the transport installs its extensions and resumes. `env` builds the execution environment, `mcpTransport` the transport for one server, `prepareTurn` (cloud) delivers the turn's credentials, projection and provider definitions before each turn, and `refreshCredential` renews an expiring subscription.

A cloud turn publishes its actual model and effort options through `config-update` after `prepareTurn` delivers credentials and the conversation accepts the model. A model read made before that delivery can be empty; the event replaces that earlier catalog without a reload or an invented model.
`launch-catalog.ts` owns the built-in provider table and the launch catalog: the models of a set of connected providers, as `piLaunchCatalog`, and the model and effort options built from a catalog, as `piCatalogOptions`. A draft with no model, or with one the catalog no longer lists, starts on `piDefaultModel`: the first connected provider (in `PI_LAUNCH_PROVIDERS` order) that has a reviewed default in `PI_DEFAULT_MODELS` (`@claxedo/agent-runtime-contract`), its vendor's newest general model; Pi's catalog has no release dates and sorts ids alphabetically, so its first row is no default. `launch-catalog.test.ts` checks every default is a model Pi's catalog offers. It is exported alone as `@claxedo/harness/pi-catalog`, without the Pi runtime, so the control plane answers a Pi draft on a cloud workspace from the account's connected providers with the same catalog the session host runs, and the Pi provider catalog lists those models whether or not a workspace is awake. A draft there that names no model asks for the model of the person's last finished Pi turn of the past 30 days (the usage ledger's `latestHarnessModel`), which `piDefaultModel` stands behind when its provider is no longer connected.
`model-catalog.ts` keeps the conversation's model choices (ids, names and effort levels, never credentials or endpoints) in a durable document, so a restarted session answers its model options before a turn delivers credentials again. A credential update replaces the document; a cloud open leaves it until `prepareTurn` delivers credentials. Every turn still needs freshly delivered credentials.
