# Pi RPC transport

Pi has no MCP protocol and no ACP wrapper. The native RPC transport carries Pi's session resume, `get_commands`, extension UI dialogs and notices, steering, its own session name, and Claxedo's first-party MCP tools. Source: pinned Pi 0.85.1 `packages/harness/e2e/.artifacts/pi/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md`.

`commands.list` returns every entry of `get_commands`. Pi lists only commands a `prompt` runs: extension commands, prompt templates and skills. Its interactive built-ins, such as `/model` and `/settings`, aren't listed (`docs/extensions.md`, `pi.getCommands()`). The conformance case proves an extension command from its fixture. Pi's bundled `/llama` downloads models, so it can't run in an offline suite.

Pi has no MCP intake, so a person's configured MCP servers stay refused (`profiles/pi`). Claxedo's own server reaches Pi through Claxedo's `claxedo-first-party-mcp.ts` extension, installed under the Claxedo state root beside the title extension and added with `-e` to a harness launch only when `services.firstPartyMcp` returns an entry for the session and its locality; it returns none for a remote session. After launch the transport writes the entry to an owner-only (0600) file under the Claxedo state root's `mcp-handoff` folder, confirms through `get_commands` that `/claxedo-mcp` is registered by exactly that extension file, and only then sends `/claxedo-mcp <file>` over RPC stdin, never argv or the environment, where Pi's bash tool would expose the bearer. An unregistered command would reach the model as the person's message, so the connection is refused instead. The extension reads the file and deletes it, the transport deletes it again whatever happened, and the extension connects over MCP streamable HTTP, registers each tool as `mcp__<server>__<tool>` through `pi.registerTool`, activates it, and closes on `session_shutdown`. The client runs inside Pi's own process, so it is extension source and cannot share the host's in-process client. A failed connection retires the launch and refuses the start. Source: pinned Pi `docs/extensions.md` (`registerTool`, `setActiveTools`, `session_shutdown`).

A draft's catalog probe is kept by `DraftProbeCache` while the files Pi read for it are unchanged: the owner profile's `settings.json`, `auth.json`, `models.json`, `trust.json` and `extensions/` entries (an extension can register providers), the `.pi` folder and `.pi/settings.json` of the workspace and of every folder above it, and the workspace's `.pi/extensions/` entries. An extension entry is a file in `extensions/`, or a subfolder's `index.ts`, `index.js` or `package.json` (pinned Pi `docs/extensions.md`); a file such an entry imports is not stamped. A brokered profile's files are written from the credentials the key already names.

A launch no session owns (a probe, or a start that failed before the session was remembered) whose retirement does not settle never fails the read it served and never touches health; it is retried when its process exits, in the background when a later launch starts (one attempt at a time, never delaying that launch), and at dispose, which waits for it. A session's own refused retirement keeps the session and reads `degraded`. A process lost under a session reads `harness_process_lost` through `ProcessLosses` until a replacement for that session starts or it closes; a deliberate retirement is not a loss.

The transport starts only through `HarnessServices.spawn`. A failed RPC exchange makes that launch unusable; it does not prove the operating system process exited. The owner of the process must retire it and report the result. RPC records split on LF, preserving Unicode line separators inside JSON strings, and a response must match both the pending id and command.

The runtime's old Pi adapter remains the only production path until the atomic P3 cutover. This folder is exercised through the contract conformance suite against pinned Pi and the scripted model server.
