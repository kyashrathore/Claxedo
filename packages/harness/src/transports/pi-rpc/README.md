# Pi RPC transport

Pi has no ACP wrapper. The native RPC transport carries Pi's session resume, `get_commands`, extension UI dialogs and notices, steering, its own session name, and MCP servers through Pi's own MCP support. Sources: pinned Pi `docs/rpc.md`, `docs/rpc-commands.md`, `docs/json.md` and `docs/mcp.md` under `packages/harness/e2e/.artifacts/pi/<version>/node_modules/@earendil-works/pi-coding-agent`.

Claxedo runs Pi inside `PI_RANGE` (`version.ts`, 0.99.0 to 0.99.1), read from `pi --version` before every launch through `services.spawn`. Pi reports its version nowhere in RPC mode. 0.99.0 is the first release with built-in MCP and with `prompt` and `steer` dispositions, which this transport needs. An older Pi refuses the launch with a typed update-Pi error before its RPC process starts; a newer one runs, with one `pi.untested_version` diagnostic per transport. The version matrix (`e2e/flows/version-matrix.ts pi`) runs Pi's conformance and flows at both ends.

Every record Pi 0.99 writes in RPC mode (`docs/json.md`, `docs/rpc-extension-ui.md`, `dist/core/agent-session.d.ts` `AgentSessionEvent`) is mapped or ignored by name in `translate/`. An extension's `notify` is a notice the person reads, in its own severity; its `setStatus`, `setWidget`, `setTitle` and `set_editor_text` pushes drive Pi's own terminal chrome, which Claxedo does not draw, so they are `debug` notices that stay diagnostics. An extension's `custom` message with `display: true` is an `info` notice. `auto_retry_start` and `summarization_retry_scheduled` are a `session-retry` with Pi's attempt, delay and error. A model error ends the turn only when Pi does not retry it: the assistant `message_end` with `stopReason: "error"` is held until `agent_end`, and `willRetry: true` drops it. `stopReason: "aborted"` settles the turn `cancelled`, and `"length"` adds a notice that the reply hit the output limit. Compaction start, completion and failure are `session-compaction` with Pi's reason. Pi's usage counts reasoning inside `output`, so the observation moves it to `reasoning`. `turn_start`, `turn_end`, `agent_end`, `queue_update`, `entry_appended`, `thinking_level_changed`, `auto_retry_end`, the other summarization retry records, `bash_execution_update` and the non-text `message_update` parts produce no event. A record, role, part, stop reason or extension UI method the transport does not know leaves one bounded `debug` diagnostic per kind per session, never the frame.

Every record of a launched Pi reaches one `PiSessionStream`, which owns the session's translator and knows who the records belong to: nobody, the Claxedo turn in `send`, or a run Pi started on its own. A prompt answered `disposition: "handled"` (an extension command or input handler took it) with no `agent_start` yet ends its turn with `finish`, since Pi starts no run for it (`docs/rpc.md`). An `agent_start` while no turn is open is Pi's own run, for example the `sendUserMessage` of an extension command that has already answered: it is admitted as a provider turn carrying the run's user message, its dialogs are asked through that turn, and stopping it sends `clear_queue` and `abort`; a refused admission stops the run. A notice or diagnostic outside any turn, such as the one Pi reports for an MCP server that failed to connect at startup, is published to the session, and an extension dialog outside any turn is still asked.

Pi's `steer` answer says whether Pi queued the input (`"queued"`) or an extension took it (`"handled"`). A handled steer is `declined`, since it never enters the conversation. Pi delivers queued steers in order as user messages, and the `message_start` of the user message whose text is the oldest pending steer's is where that steer entered the conversation: it becomes `input-incorporated` for its Claxedo message. The steer is pending from before the request is sent, so a withheld answer does not keep it from settling. A steer an input handler rewrote never matches and stays accepted in Claxedo's queue.

`commands.list` returns every entry of `get_commands`. Pi lists only commands a `prompt` runs: extension commands, prompt templates and skills. Its interactive built-ins, such as `/model` and `/settings`, aren't listed (`docs/extensions.md`, `pi.getCommands()`). The conformance case proves an extension command from its fixture. Pi's bundled `/llama` downloads models, so it can't run in an offline suite.

MCP reaches Pi through Pi's own MCP support (built in since 0.99.0, `docs/mcp.md`). A harness launch's servers are Claxedo's first-party server, for a local session only, and the session's projected servers; a remote session refuses a stdio server by name. Each becomes an `mcp.json`-shaped entry (`profiles/pi`) declared to the model with `exposure: "direct"`, so its tools keep the `mcp__<server>__<tool>` names the other harnesses use. Pi resolves `${NAME}` and a leading `!command` in header and env values, so every value is written literal. The transport writes the entries to an owner-only (0600) file under the Claxedo state root's `mcp-handoff` folder and passes only its path, in `CLAXEDO_PI_MCP_HANDOFF`, to the launch that adds Claxedo's `claxedo-mcp.ts` extension with `-e`. While Pi loads it, before any turn can run a tool, the extension removes the variable from Pi's environment, reads the file, deletes it and registers each entry with `pi.registerMcpServer`; registrations are never saved (`docs/extensions.md`). Once `get_state` answers, a file still present means the extension did not load, so the launch is retired and the start refused, and the transport deletes the file whatever happened. The bearer therefore never enters argv, Pi's environment, a file Pi's tools can find after launch, or Pi's session file. Pi's own client connects, retries transient failures, reconnects a dropped server on the next call and reports a server that failed to connect as an extension notice, which reaches the session outside any turn. Pi also reads `mcp.json` from its agent folder and, for a trusted project, `.pi/mcp.json`; an entry there with the same name replaces Claxedo's. Member sessions use a Claxedo profile folder, so they never read the machine owner's servers.

A draft's catalog probe is kept by `DraftProbeCache` while the files Pi read for it are unchanged: the owner profile's `settings.json`, `auth.json`, `models.json`, `trust.json` and `extensions/` entries (an extension can register providers), the `.pi` folder and `.pi/settings.json` of the workspace and of every folder above it, and the workspace's `.pi/extensions/` entries. An extension entry is a file in `extensions/`, or a subfolder's `index.ts`, `index.js` or `package.json` (pinned Pi `docs/extensions.md`); a file such an entry imports is not stamped. A brokered profile's files are written from the credentials the key already names.

A launch no session owns (a probe, or a start that failed before the session was remembered) whose retirement does not settle never fails the read it served and never touches health; it is retried when its process exits, in the background when a later launch starts (one attempt at a time, never delaying that launch), and at dispose, which waits for it. A session's own refused retirement keeps the session and reads `degraded`. A process lost under a session reads `harness_process_lost` through `ProcessLosses` until a replacement for that session starts or it closes; a deliberate retirement is not a loss.

The transport starts only through `HarnessServices.spawn`. A failed RPC exchange makes that launch unusable; it does not prove the operating system process exited. The owner of the process must retire it and report the result. RPC records split on LF, preserving Unicode line separators inside JSON strings, and a response must match both the pending id and command. Pi 0.99 exits when an extension throws while loading, so a Pi exit names its code with the last 2,000 characters of Pi's stderr, which say why. The runtime's spawn service passes a child no `CLAXEDO_` variable it does not allowlist; `CLAXEDO_PI_MCP_HANDOFF` is on that list (`process-ownership/src/spawn-env.ts`).

The workspace runtime drives Pi only through this transport (`compose.ts`). The contract conformance suite runs it against pinned Pi at both ends of `PI_RANGE` and the scripted model server.

A stop sends `clear_queue` and `abort` once per turn: the turn's own abort signal and the runtime's cancellation reach `cancel` together, and they share the one request pair in flight. Pi answers every `clear_queue` with a `queue_update` event, and a second pair's event would land before or after `agent_settled` depending on when Pi read it. Source: pinned Pi `dist/core/agent-session.js` (`clearQueue`, `abort`).
