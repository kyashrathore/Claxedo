# Claude Agent SDK transport

The native transport carries local plugin folders through the SDK `plugins` option, live `supportedModels()`, `supportedCommands()` and `supportedAgents()` discovery, per query effort, replay confirmed streaming steering, native `/goal` start and stop, and the SDK's per turn usage events. These surfaces are absent from standard ACP. Claude over ACP can receive plugin folders only through its wrapper's version specific `_meta.claudeCode.options` extension.

Claxedo launches the person's own `claude`, which the runtime resolves; the SDK's platform binary is never bundled. The transport supports the Claude Code versions in `CLAUDE_CODE_RANGE` (`cli-version.ts`), 2.1.280 through 2.1.285, and that range is exactly what `bun run --cwd packages/harness flows:versions claude` runs the Claude conformance suites and flows against. Every `system` `init` frame carries `claude_code_version`, the version the CLI reports about itself, so the check spawns nothing: the prompted and goal paths both pass each frame through `observeClaudeSessionMessage`, which hands the version to the transport's one `HarnessVersionGate` (see the contract README). An older CLI fails the turn and asks the person to update Claude Code; a newer one runs, with one `claude.untested_version` diagnostic per process. The model, command and agent probes are not checked: they read only the SDK `initialize` response, which carries no version, and the first turn on that CLI is checked at its `init`. The sandbox images install a Claude Code inside the range, which `cli-version.test.ts` holds them to.

A steer is written to the running query's input with a fresh uuid. Claude replays it as a user message at the point its conversation took it in; that replay acknowledges the steer and is yielded as `input-incorporated` with the id Claxedo submitted it under, which is where the runtime writes the steered prompt into the reply. A `command_lifecycle` frame naming that uuid as `cancelled`, `discarded` or `refused` means Claude will never take it in: the steer settles `declined` at once, and the turn no longer waits for its replay before ending at its result.

The SDK's `spawnClaudeCodeProcess` callback returns synchronously. `HarnessServices.spawn` returns a promise. `ClaudeProcess` gives the SDK streams immediately, forwards them to the process once `services.spawn` returns, and delegates retirement to that exact `OwnedProcess`. The callback never starts a process directly.

Brokered credentials are selected in `StartInput` by the session owner. `TurnInput.origin` is not used for credential choice. The Claude Code home for a brokered session is a Claxedo owned directory containing scrubbed copies of supported settings files and read only copies of named user configuration entries. It never mirrors account files. A machine owner session without brokered credentials uses their own Claude login.

Session config has one owner, the runtime: the transport implements no `harnessConfig`, as Codex, Cursor, Pi and OpenCode don't. Every launch reads the model, permission mode and permission state from `SessionBroker.config()`; the live query remembers only the settings the SDK has acknowledged, and `setPermissionMode` validates the mode and returns the state the runtime persists. `StartInput.config` is used only for the draft launch context and probe keys.

A model answer is kept while the files the CLI reads for it are unchanged: the owner's settings files and `.credentials.json` under the config folder, the project's `.claude/settings.json` and `.claude/settings.local.json`, and the `.claude.json` account (on macOS the login itself is in the Keychain, and `.claude.json` is what changes with it). The SDK reads `.claude.json` from `CLAUDE_CONFIG_DIR` when that is set and from the home directory otherwise, which is the folder above the default config folder (`sdk.mjs`, `CLAUDE_CONFIG_DIR ?? homedir()`).

Permission requests are answered by `TurnBroker`; the broker persists an answer before the callback releases the tool. "Always allow" keys the broker grant by the contract's `grantIdentity` digest of the request identity (tool, tool input, workspace directory, permission mode and permission context) together with the SDK `suggestions` rewritten to `destination: "session"`, and returns those suggestions as `updatedPermissions`, so Claude applies them for the rest of the query and never writes the person's settings. On the next launch the transport reads its own grants back from `permissionState.brokerGrants` through `connectionGrantKeys` and folds the saved rules and directories into `settings.permissions` and `additionalDirectories`, so Claude does not ask again. A saved `setMode` is not replayed at launch: the runtime owns the session's permission mode and its ceiling, and the transport has no config write. Within the answered query the SDK applies it, so the transport reports it through `StartInput.permissionModeKept`, and the runtime stores it and publishes the row; the next query starts in the stored mode. A prompt forced by the person's own ask rule (`matchedAskRule`) gets no grant. `decisionReason` is not a grant blocker: Claude Code 2.1.283 sets it to "This command requires approval" on ordinary Bash prompts. The grant identity leaves out only what cannot change the request: the callback's IDs and abort signal, the prompt's display labels (`title`, `displayName`, `description`), and Bash's `description` input, which the tool schema documents as a display summary of the command. Every other tool's input is kept whole, because an MCP or agent tool's `description` can be the content being approved. Blocked path, agent, decision reason and any permission-context field the SDK adds later are part of the identity. The key holds only the digest and the suggestions, because it is persisted in `permissionState.brokerGrants` and published with auto-answers: a Write grant must not carry the file it wrote. A Bash prompt without suggestions uses the same identity.

A permission request or `AskUserQuestion` from a subagent carries the contract's `child` route: the SDK's `agentID` is the subagent's task id, and the key is the first-level spawn call of the task `task_started` reported under that id, the key its frames route by, so the broker files it on the child session. A request whose `agentID` names no task `task_started` reported yet carries the `agentID` itself as the key: the host routes it once a result has named that agent, and otherwise files it with the unbound-child diagnostic. A subagent's request is not answered by its parent turn's signal, because the child's own turn owns it.

An MCP elicitation reaches the SDK's `onElicitation` and is asked through the same broker, the current turn's or, between turns, the session's; a form answer returns its values, a URL consent returns accept or decline, and Claude's `elicitation_complete` frame calls `completeElicitation` on the turn's broker. Without the callback the SDK declines every elicitation.

The command deny floor is a Claude setting the Claude profile ships in `settings.permissions.deny`; Claude Code enforces deny rules in every permission mode, including `bypassPermissions` and `dontAsk` (conformance proves each mode against the real CLI), so `canUseTool` and the broker never repeat it. A rule denial reaches the person as the SDK's `permission_denied` system message, translated to a `tool-error` event.

Every query passes `--thinking-display summarized`. In stream-json mode Claude Code 2.1.284 otherwise leaves the API's default display, which is `omitted` on current Opus and Sonnet models: thinking blocks arrive with empty text and nothing reaches the transcript. The flag leaves the thinking type to Claude Code, which picks adaptive or budgeted thinking per model; the SDK's `thinking` option would force `--thinking adaptive` on every model. Conformance reads the display from the request the real CLI sends to the scripted model server.

The SDK reports `session_id` after a query has begun. The transport immediately calls `SessionBroker.rebind`, which moves the live turn. The process's first reported identity is durable before that turn can finish or crash.

A Claude Code process lives while a turn runs or one of its background tasks does, and no longer. Claude Code reads user messages from stdin. Once stdin closes, Claude Code 2.1.285 stops a background shell about 5 s later but waits for a background agent to finish, up to `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, and exits nonzero when its last result was an error. `ClaudeLiveQuery` therefore reads the query's stream for the process's whole life and tracks the SDK's `background_tasks_changed` set, which replaces rather than accumulates. A turn claims the stream and ends at a `result`: Claude's own turn at its first `result`, a prompted turn at the first `result` after Claude has replayed every message the turn wrote (its prompt and its steers, each written with a fresh uuid), so a prompt that races a turn Claude began itself receives that turn and then its own answer, and a steer Claude queues past the turn's result still belongs to it. What the process does after that `result` never fails the turn. With no live background task stdin closes at the `result` and the process retires in the background; with one, stdin stays open and the process lingers. A message sent while it lingers reuses the process while its immutable launch inputs (effective credentials and projection, permission ceiling, system prompt and agent) are unchanged. Model, effort and permission mode changes use the SDK controls before the next prompt; unchanged values send no controls, and default effort explicitly clears the override. A refused control fails the new turn without closing the existing process. Preparing the prompt keeps stdin open if the last task finishes while the control is pending. A changed immutable launch is refused with a configuration error while background tasks remain; it never calls `stopTask` implicitly. Once there is no background work, the old process is closed and drained before a replacement starts. Session metadata and identical configuration snapshots do not invalidate the launch. When the last task settles, stdin closes at once between turns or at the running turn's `result`, and the turn Claude then runs to report it, which begins with `system init`, is admitted through `SessionBroker.admitProviderTurn` with reason `continuation`. Admission checks that the announced frames still belong to that continuation after taking the session lease, allocates a fresh assistant execution id, and parents it to the latest real prompt without creating a user row or writing another SDK input. A frame `claudeChildFrameKey` routes to a subagent is translated as it arrives, even between turns, and delivered with `SessionBroker.observeSubagent`, `associateChild` and `publishChild`, so a background agent's transcript keeps moving while its parent is idle; the next turn waits for those deliveries before it translates. Top-level peer deliveries and task completion notifications are published immediately with the transcript owner captured at ingress. Other parent frames between turns wait for the next turn; partial `stream_event` frames and `tool_progress` heartbeats among them are dropped because the complete message follows or they carry no event, a `task_progress` frame replaces the held one for its task, and past 1,000 held frames the oldest are dropped and the next turn reports how many. The session is told the process's background work through `SessionBroker.publish({ type: "background-work", agents, shells, other })` whenever those counts change: `task_type` ending in `_agent` counts as an agent, `local_bash` as a shell, any other type as other, and a task the SDK marks `ambient` (not activity, by its own definition) not at all. The counts go to zero when the set empties or the process ends, so they never outlive the process. One task ledger, one translator memory and one mirrored-usage relay span every turn on the process, so a background subagent's later frames settle the row its turn created, a child's running usage continues across the parent's turns, and usage the SDK mirrors before the first turn claims the stream is held for it. Permission requests go to the current turn's broker and, between turns, to `SessionBroker.ask`. A launch that fails ends its query, so the next turn launches again. A turn that throws before its `result` ends the process, because nothing would read what Claude does next. Cancel sends the SDK's `interrupt` control request and waits, until the cancel's deadline, for the turn's `result`; the turn then reports terminal execution and `unknown` cleanup, because background tasks outlive an interrupt. Every launch declares `perTaskStopAffordance`, so Claude Code spares background agents on an interrupt as it spares background shells; without it an interrupt stops them. The transport honors the declaration with `backgroundTasks.stop`: the call that started a live background task, as `task_started` reported it, maps to Claude's task id, and the SDK's `stopTask` stops that task alone. A call with no live task behind it, or a process whose stdin already closed, answers `not_found`. A refused interrupt, or one Claude does not answer by the deadline, ends the process and reports `unknown` execution. Session close ends the process and its background tasks.

Every launch passes `ScheduleWakeup`, `CronCreate`, `CronDelete` and `CronList` in `disallowedTools`. Claude Code 2.1.285 fires a session wakeup only inside the process that scheduled it, while that process is idle, and keeps a session-only job in memory; a durable job is read by the interactive scheduler. The process retires once no turn or background task needs it, so a wakeup offered to the model would never arrive.

A native goal is a provider turn admitted through `SessionBroker.admitProviderTurn` with reason `goal` that writes `/goal <objective>` to the session's Claude process like any prompt, with the session's model, effort, instructions and agent, so one process writes the session's transcript and a goal gets the same partial messages and replays a prompted turn gets. Its start answers with the first goal Claude reports. A goal that fails or is cancelled is cleared with `/goal clear`, written to the session's process outside any turn, because Claude Code keeps an uncleared goal in its transcript and pursues it again on the next turn after a resume; it is then blocked (failed) or paused (cancelled), and a clear Claude does not confirm as a successful zero turn command within 30 s blocks it with that reason. The cleared Goal Claude reports while that clear runs is its answer to our own command, so it is not published; the paused or blocked Goal that follows is. Stop cancels the goal's turn through the interrupt path and ends with that clear, so the stopped turn reports Claude's interrupted result, never a success. A goal turn that completes with its goal still active stays active while its process lingers for background work and is paused once that process ends with no newer one. A stream that ends without an SDK result fails with the one protocol error in `errors.ts` unless explicitly aborted. A stream that fails before its turn's `result` throws the transport's `process` error, retryable, with the last 4 KB of the CLI's stderr in `detail.stderr`; the runtime stores that detail on the turn's error record. Goal progress is read from SDK `active_goal` messages and `goal_status` transcript entries; the mirror answers `load` with null so resume uses Claude's own transcript. The transport reports `actions: []` because Claude has no native pause or resume command. Per turn usage is yielded from the existing Claude translator; a subagent request the stream never delivered is metered from the transcript mirror to the session owner through `SessionBroker.meter`. The SDK hands its transcript mirror over as soon as it reads it, ahead of the messages it has yet to deliver, so usage mirrored during a turn is held until the turn reaches its result and is then metered after the stream's own usage; usage mirrored after the result is metered at once.

Translation constraints: Bash reports a nonzero exit in result text rather than a numeric field. Tool images and documents require a base64 source with a media type. Claude Code 2.1.285 sends one `assistant` frame per content block, and several frames share one message id, so each frame is reconciled against what was streamed since the previous one. Structured `tool_use_result` has no call ID and can be attributed only when exactly one result block exists. Request answer metadata is present only for completed question calls. Claude reports a permission mode it moved to itself (plan mode, `setPermissionMode`) in a `status` frame, which the transport passes to `StartInput.permissionModeKept`.

Translation preserves these wire constraints:

- An assistant frame repeats the text and thinking of the block streamed before it. Each frame contributes only what the stream has not shown, or the portion beyond the common prefix; a divergent snapshot cannot duplicate the whole reply, and a turn without partial messages still shows its reasoning. Partial tool JSON can update display, but only a complete parse becomes the block's authoritative input. A server tool (`server_tool_use`, `mcp_tool_use`) settles its row once from its `*_tool_result` block, whichever of stream or snapshot carries it first; a result whose content type ends in `_error`, or an MCP result with `is_error`, is a tool error.
- A frame is a child frame when it carries `parent_tool_use_id` and is not `tool_progress`; `claudeChildFrameKey` is that one decision. Claude Code 2.1.285 also sets the field on tool heartbeats, sent every 30 s for any running tool: `tool_progress` with `heartbeat: true`, `tool_use_id` `<call>-heartbeat-<n>` and `parent_tool_use_id` naming the running tool itself, which is usually a plain Bash call. It sets the field on agent API retries too. `tool_progress` yields no event. A child frame routes under its first-level spawn call, and a subagent's own Agent calls fold into it through the task ledger. The runtime, not the translator, decides whether that key names a child: it reads the durable route binding. That matters because an agent resumed through SendMessage keeps sending its original Agent call id, and the ledger of a later process never saw that id. A frame that no binding names, or that names a child whose turn finished, is dropped with one diagnostic and never fails the parent's turn.
- Each observed child is bound under the observation's own call. A `create_subagent` a subagent makes therefore binds its host child under that call and leaves the subagent's route alone. `create_subagent` binds a child only when its result belongs to a call the ledger observed. Structured `tool_use_result` has no call ID and can stand in for block content only for a single-result message. A completed question carries answers in metadata; refusal is an error.
- `task_started` distinguishes Task subagents from ambient chores. Later task-ID-only frames use that recorded classification, and `spawn_depth` identifies nested work even when pinned SDK types omit it. A task's call is a spawn edge only when the parent's own assistant message made it as an Agent or `create_subagent` call. A Skill call's forked execution, or a call a subagent made, still routes its frames and joins its observations into one row, with no edge, because the parent's transcript has no part for it. Only a task's own terminal frames settle its row: `task_updated` with a status, then `task_notification`. A finished task leaves `background_tasks_changed` before those frames arrive, so leaving the set settles nothing. `task_progress` is not an observation: its description is the task's current activity ("Running …"), not its name, and it arrives many times per task. A notification's summary is the result, not a label. A `forked` result is final; only `async_launched` remains running. An agent resumed through SendMessage reports `task_started` under the resuming call, and the runtime runs it as a new turn of the same child session. Task notifications can precede the tool's actual stdout/error result and must not replace it with an empty summary.
- Usage reports for one request are monotonic across stream, assistant and transcript deliveries, and each request is metered once, by the first owner that reports it: a subagent request streamed to its child is not metered again from the mirror, and a mirrored request meters under its transcript's subpath. The model stream is fixed by the first report; requests accumulate separately by owner and model, the main thread's per turn and a child's for the process's life. Result usage repeats stream accounting and is not added again. Context occupancy comes from the last main-thread request, not a mirrored child's context; its size is the result's `modelUsage` entry for the main model (matched by key to the `init` model, or by `canonicalModel`), kept for the process, and `0` (unknown) before the first result.
- The turn's terminal is its `result`: `terminal_reason` `aborted_streaming` or `aborted_tools` is a cancellation (the CLI's own classification), `is_error` a failure, anything else a finish; reply text is never read. An assistant `error` frame (`max_output_tokens`, `rate_limit`, …) ends nothing while Claude recovers; it becomes the failure's message and class if the result then fails. An `auth_status` error is an `auth-status` event.
- Frames and subtypes are mapped or ignored by name. `api_retry` is a `session-retry` with Claude's attempt, delay and cause, so a retrying request reads as retrying rather than as a hang. `notification`, `memory_recall`, `informational` (hook blocks included), `model_fallback`, `model_consent_fallback`, `model_refusal_fallback`, `model_refusal_no_fallback` and `mirror_error` are `harness-notice`s, which the runtime writes into the reply as notices the person reads; `conversation_reset` (`/clear`, a plan-mode exit with a fresh context) is a `conversation-reset` carrying its trigger, drawn as a boundary in the same Claxedo session, and the `init` after it names the new conversation the session rebinds to; compaction start, completion and failure are `session-compaction`. Frames with nothing to show (`thinking_tokens`, `signature_delta`, `ping`, `task_summary`, `post_turn_summary`, `vcs_state_changed`, `session_title_changed`, `command_lifecycle`, `tombstone`, hook lifecycle, UI pushes and the other side channels the 2.1.285 schema declares) produce no event. A type or subtype the transport does not know leaves one bounded `debug` diagnostic per kind per process, never the frame; the CLI's schema says the set grows over time.
- Every model response starts with a `response-start` named by its API message id, from `message_start` or, when nothing streamed, from its first `assistant` frame; each frame's uuid is remembered against it. A refusal fallback retracts the refused response by identity: the replacement's `supersedes` and the end-of-turn `model_refusal_fallback` both list the refused frames' uuids, which resolve to their responses and become one `response-retracted` (idempotent downstream). When none of the uuids is known, the response whose stream stopped with `stop_reason: "refusal"` is withdrawn instead, with a `claude_sdk.retraction_unmapped` warning; with neither, nothing is withdrawn and the warning says so. `model_refusal_no_fallback` retracts nothing, because Claude keeps the partial answer.
- Native titles arrive through transcript `ai-title` or `custom-title` entries, not SDK messages. Rate-limit reset values arrive in seconds and are normalized to milliseconds; `utilization` is a fraction of the window (0.81 in real 2.1.285 frames) and becomes `usedPercent` 0–100, as the other harnesses report it.
- Bash errors carry the exit code in result text (`Exit code N`), even when the SDK error flag is absent. Tool images preserve supplied base64 bytes; a filename is only a display hint. URL-only image sources provide no MIME type for safe mapping.

Child reports use the SDK user frame’s structured `origin.kind: peer`, `origin.from`, `origin.body` and `uuid`. `ClaudeQueryInput.observe()` passes peer replays to the translator instead of treating them as echoed prompts. The adapter emits `agent-message` with the byte-exact body, sender and task/session correlation. A missing canonical sender, body or id produces a diagnostic rather than parsing the display envelope. `task_notification` is a separate `harness-notice` keyed by its SDK uuid; its summary is never joined into a generated prompt. Between-turn delivery is drained before the live query finishes. Persisted notice identity is scoped to the session and SDK uuid, so a replay after a continuation keeps the original owner. Native Claude delivers the report and decides whether to continue; Claxedo records and renders that behavior.
