# Embedded OpenCode engine

One `OpenCodeHost` owns the embedded SDK engine and its SQLite writer for all local workspaces in a runtime. The absolute database path is required because the SDK otherwise defaults to an in-memory database and loses sessions on restart. Concurrent first use shares one boot promise; closing waits for a boot already in progress so a late writer cannot remain after shutdown. A failed boot reports an unavailable reason and may be retried on the same engine path. A closed owner is terminal.

The SDK remains behind first use so shell hydration and generic runtime imports do not load its native module graph. The engine uses ripgrep for file search: its alternative indexer walked and hashed this monorepo in background workers, measured at 7 GB of reads and 200% CPU. The SDK's plugin registration settles asynchronously per location, so catalog and plugin-backed workspace reads await that location's activation. The desktop runs the same engine in Node/Electron; no Bun sidecar is involved.

Lifecycle and event health are separate. A host can serve sessions while its stream is reconnecting; collapsing them would hide a working session with a stale UI. The lifecycle progresses from cold through migration and ready to draining and closed. A failed pre-serving attempt is observable as unavailable, while a host already serving work drains instead of switching to unavailable.

The host retains one event pump. Browser subscribers receive its fan-out through the runtime hub, so a tab disconnect does not end another workspace's stream. The pump's `ready()` resolves once its first read is outstanding, allowing a mutation to subscribe before its own first event. A stop refuses further dispatch immediately, then waits for the outstanding SDK read and iterator cleanup. Runtime shutdown refuses events before closing the host, and awaits the drain even if host close fails. A listener that unsubscribes during dispatch cannot skip another listener because dispatch iterates a copy.

Event delivery is at least once. Events with both `durable.aggregateID` and `durable.seq` have an ordered per-aggregate position for checkpoints and downstream idempotency. Other events, including text deltas and usage updates, may be lost, duplicated or reordered during reconnect. They are invalidation hints: consumers re-read a snapshot rather than accumulate their payloads. In particular, turn usage closes by comparing the engine's session total before and after the turn, with a deadline, because step events can be missed. Recorded step usage keeps its durable identity. A failed total read yields a diagnostic without holding the turn. Consumers must be cheap and must not throw; a throwing consumer degrades health and is logged without killing the only pump. Stream loss degrades health and reconnects without synthesizing a terminal event.

The catalog port fails on an unavailable engine rather than fabricating an empty list that the UI would treat as a real empty workspace. Its model list describes what the running host can execute, including effort variants and pricing tiers; Claxedo's models.dev backed picker owns model identity. Location-scoped SDK lists return `{ location, data }`, so the port reads `data` explicitly.

`WorkspaceScope` is minted only after route authorization and resolves the real directory. The pinned SDK does not authorize `sessions.get({ sessionID })` by location; every session mutation and reply proves the session's location against the caller's scope. A scope is revalidated against the filesystem so symlink retargeting cannot widen access. Session listing passes a flat `directory`: a nested location filter is ignored by the SDK and can expose every workspace. Form answers remain structured values. Pending interaction reads before a serving host is ready return empty without booting the engine.

The session port uses the SDK's flat prompt shape, with model selection coming from agent/config. Its admitted message is read from the SDK response. Usage token categories are disjoint: input excludes cache reads and writes, output excludes reasoning, and an engine zero cannot distinguish unreported usage from reported zero. Session paging carries both previous and next cursors. File, agent and skill mentions use their SDK-specific keys; combining agent and skill keys in one computed property loses required-field typing. Assistant content remains opaque until transcript projection, while a session row is projected field by field so SDK shape drift cannot be silenced by a whole-row assertion.

Workspace launch policy projects Claxedo's MCP servers and skill directories into the SDK plugin registries, not project or global config files. Reload reruns transforms against the current document. Plugin storage is keyed by the engine's real directory. A failed write is reported to its caller and does not acknowledge a stale catalog. Skills come from `<directory>/<skill>/SKILL.md`; the schema mints its branded identifiers. A missing file is tolerated during a directory scan, while other filesystem failures propagate.

The provider policy persists each workspace's disabled provider IDs in plugin storage and applies activation in the engine catalog, not only in the picker. Invalid stored data is corruption and must fail instead of re-enabling providers. Activation is the SDK's availability switch and survives later provider declarations. Provider definitions declare integrations, endpoint, headers and models. Provider bindings carry broker placeholders, never vendor secrets in the SDK credential store. An absent binding leaves the engine's own auth; an unavailable selected account disables the provider so the engine cannot fall back to a machine login. Catalog transforms can be overwritten by config plugins, so bindings read back final rows, move their transform last when needed, and settle before acknowledging a change.

Engine reads annotate an SDK `ClientError` with operation and workspace because an undeclared non-2xx response otherwise carries little context. That error is matched structurally to keep the native SDK graph lazy. The launch document carries only the directory's shared MCP servers and skills. The transport lists the first-party MCP server with the calling session's credential and registers its tools through the SDK session tool port. Tool execution uses an in-process callback bound to that registration, so another engine session cannot borrow it. Conflicting tool definitions in a location fail rather than choosing one owner silently. Unregister reloads the location only after installation has settled.
