# ACP transport

ACP gives a client one standard way to hand an agent tools: the `mcpServers` list at `session/new`, `session/load` and `session/resume`. Nothing in the protocol carries skills, plugins, slash commands or instructions from the client, and nothing updates a running session's MCP servers. A server added later reaches the agent only when the session is loaded or resumed again with the full list, which may restart the agent's own process.

Claude plugins are the one exception this transport delivers. `@agentclientprotocol/claude-agent-acp` passes `_meta.claudeCode.options` straight to the Claude Agent SDK, and has done since 0.10.9, so its `plugins` option carries whole plugin roots. The handshake's `agentInfo` must report that package name and at least that version. Any other agent receives the MCP servers alone; the plugin roots are reported as not applied (`unsupported-by-harness`, "this ACP agent accepts MCP servers only") through a `harness-notice` on the session broker, because a custom ACP agent is a target for MCP servers and the session must still start. A remote agent never receives local plugin paths.

The chosen model, effort and permission mode reach the agent before each prompt through `session/set_config_option` (or `session/set_mode` for an agent that publishes only the `modes` channel), and the agent picker through `harnessConfig.update`, since the `mode` channel serves both the agent choice and the permission mode. A value the agent answers with a different current value is a refusal, never a turn run on something the picker never showed. Attachments follow the negotiated `promptCapabilities`: images inline, audio inline, other bytes as an embedded resource, and every file also written to the workspace (through the shared materializer) with a `resource_link` when the connection declares `sharedFilesystem`; a part the agent cannot take fails the turn before the prompt.

A session title is a throwaway `session/new` on the same agent whose chunks are collected off the main transcript; the side session's requests are answered `cancelled` and its updates never reach a turn.

A configure that arrives during a turn restarts the agent only after that turn has settled. The restart runs outside the turn: its failure goes to `SessionBroker.reportFailure`, the next turn or configure waits for it and is refused with the restart's reason once it has failed, and a later `start` or `attach` clears the record. A cancel is bounded by its caller's deadline, or by 5 seconds for an abort and the quiet timeout, so a hung write cannot keep a session busy; a cancel with no turn active writes nothing.



Every agent examined also reads its own global configuration over ACP (`~/.claude`, `~/.codex/config.toml`, Gemini's settings), so the servers a person configured locally reach it alongside the ones Claxedo passes.

`streams.ts` adapts the agent process's Node streams to the web streams `ndJsonStream` takes, with the global `ReadableStream` and `WritableStream` constructors. `Readable.toWeb` returns `node:stream/web` types, and a package that compiles this source with the DOM library (as `workspace-runtime` does) sees the SDK's parameters as the DOM's types, which that return type doesn't satisfy. The reader pulls one chunk per request, so a slow consumer applies backpressure to the agent's output.

Attach resumes the stored session (`session/resume`, else `session/load`). An agent that answers resource-not-found for that session refuses the attach with a typed `session` error; the transport never opens a replacement session or replays the transcript. A turn on a session whose agent has disconnected fails before its prompt with a typed `connection` error; nothing restarts the agent or retries the turn. Only an explicit attach or a configure restart starts the agent again, and both resume the same session.

Prompt-result `usage` is that prompt's own token usage. The schema's member comments say "across session", but `PromptResponse.usage` itself is documented as "Token usage for this turn", and `claude-agent-acp` (0.22.2) resets its tally at the start of every `prompt`. It is metered as the turn's cumulative observation with no baseline subtracted; subtracting the previous prompt's value would meter such an agent's second prompt as the difference between two prompts. An autonomous Goal turn has no usage carrier in ACP, so it ends with the same unavailable-usage diagnostic as a prompt that returned none. `usage_update` is the only source of context occupancy: the prompt-result usage event repeats the latest `size`/`used` the agent reported (0 before any), and occupancy is never derived from token spend. Result usage and its unavailable diagnostic precede terminal events. The presentation owner copies an unscoped cumulative observation into the assistant's token display; metering retains the original nullable categories.

Autonomous Goal updates enter the broker through `admitProviderTurn`. The negotiated Goal snapshot travels in `session/update`'s `_meta.goal` and is distinct from ordinary prompt completion. Updates are delivered one at a time, in the order the agent sent them, and a prompt's result is handled only after the updates that preceded it. The SDK dispatches each notification through its own awaited handler chain, so an update handled before the SDK would overtake a chunk the agent sent earlier; a subagent extension update, or an update kind the SDK does not know, is therefore handed to the SDK as a valid `session_info_update` carrying the original in the notification's `_meta` (`wire-updates.ts`), takes the same chain and reaches its handler in wire order. A subagent's end reaches the broker only after the running turn has taken the child output queued before it, because the broker ends the child at once. Each update is applied whole: an advance to another iteration ends the running provider turn before the update's content, which then opens the next iteration's turn; completion, pause or deletion ends the turn after the update's content is ingested, so the last output of a Goal lands in the turn it completes. Disconnection fails the turn. Updates from child sessions reach whichever turn is running, prompted or autonomous, under the child's correlation key.

Connection observations belong to the transport independently of optional peer extensions. A peer that disconnects while its session is being adopted is refused, and disconnected, failed and auth-required are final for that connection generation; readiness never replaces them. Closing a session drops its observation, so a deliberately closed session never reads as disconnected. A directory's connection state is its best live session (ready, then connecting, auth-required, failed, disconnected), and its runtime is healthy unless a live session is failed or needs authentication; a session whose agent acknowledged a cancel but kept its prompt open past the cancel deadline reads `degraded` (`harness_process_lost`) until that prompt settles. A fork's MCP values belong to the supplied child session, including its first-party bearer.

Beyond the protocol itself, this folder's line budget in `budget.json` carries four responsibilities no other owner can take: prompt-result metering (`usage.ts`), autonomous Goal turns admitted through the broker (`provider-turn.ts`), connection observations (`health.ts`), and fork MCP composed for the child session.

The client advertises `session.notices`, so an agent's `notice` update is a `harness-notice` (`acp.notice`) carrying its title and description, with `warning` read as `warn`; an agent told nothing may put the same words in a message instead. It does not advertise `session.compaction`: a compaction update patches a stored compaction by ID, which no event here can do, so an agent that sends one anyway reaches the unknown-update path.

Tool presentation metadata contains the derived ACP view, not raw input, raw output or the private `_meta` bag. Tool content is deduplicated by its JSON form, which every item decoded from the wire has. A parsed file-list command can refine a search tool into a list only when no search command is present. Standard `think` tools do not create tool rows; reasoning arrives through `agent_thought_chunk`. Config selections may be flat or grouped; malformed choices must not produce undefined IDs. Session-surface updates do not create tool rows, and message-step tracking follows assistant message chunks.
