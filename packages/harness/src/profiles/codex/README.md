# Codex profile

Codex reads skills from `CODEX_HOME/skills` and project `.agents/skills`, MCP configuration from `config.toml`, and plugins from marketplace entries plus `plugins/cache`. The format follows the Codex [skills](https://developers.openai.com/codex/skills.md), [configuration](https://developers.openai.com/codex/config-advanced.md) and [plugins](https://developers.openai.com/codex/plugins.md) documentation.

Claxedo never writes into a person's own `~/.codex`. Every session runs in a Claxedo-owned `CODEX_HOME` keyed by the session owner, the credential binding (own login, the broker's `baseUrl` and auth mode, or a directly handed ChatGPT plan's origin; the account is the owner's) and the plugin selection mode (default or selected, never the selected set or its artifact digests). The login and the plugin set differ per home; the conversations do not. Every home of one owner lives in that owner's store, `<homeRoot>/codex-owner-<digest>/homes/<key>`, and links `sessions/`, `archived_sessions/`, `thread-writer-locks/`, `memories/` and `session_index.jsonl` to the store, whose root is also Codex's `sqlite_home`. The app-server gets it as `-c sqlite_home=…`, which outranks any `sqlite_home` in the owner's or a project's config. Every home of the owner therefore reads one set of rollouts, thread rows, goals, names and memories, as Codex's single home does, and a session whose account or selection mode switches resumes its thread, history and goal in the new home. Codex 0.156.1 and 0.159.2 find a thread through the state database's `rollout_path`, which names the home that started the thread and is never rewritten on resume, and answer `no rollout found for thread id` once that path is gone, so a home is never collected on its own: the store is what `recordHomeUse` records and the app-server holds, and it is collected whole. The writer locks are shared because the rollouts they guard are. Two sessions composing one home at the same time both link the store; the link that loses the rename race is kept when it already names the store entry, because Windows cannot replace an existing directory link atomically.

A thread also records the model provider it ran on, and a home defines only its own: `broker` for a brokered account, `chatgpt-plan` for a directly handed ChatGPT plan, the owner's configured `model_provider` (Codex's default, `openai`, when none is set) for their own login. Resuming a thread elsewhere without naming a provider fails with `Model provider … not found`, or, for the built-in `openai`, would run unauthenticated, so the transport names the home's provider on every `thread/start` and `thread/resume`, reading an own-login home's with `config/read` for the session's directory.

The projected plugin set is not part of the key: every plugin a session projects is copied into the home's marketplace and cache in place, and the home keeps the plugins other sessions of the same key installed. Which plugins a thread loads is the thread's own config: `thread/start` and `thread/resume` carry `plugins.<name>@claxedo-agent-plugins.enabled` for exactly the session's projected set, which Codex merges over `config.toml`, so two sessions sharing a home each see only their own plugins and a changed set applies on the next resume. `prepareCodexProfile` runs at every session start, and every file it writes lands through a temporary name and a rename, so a concurrent session never reads a half-written file.

For an own-login session the home mirrors the owner's Codex home read-only: `config.toml` (with any Claxedo block from today's driver stripped and this profile's block appended), `AGENTS.md`, the legacy `instructions.md`, `hooks.json`, `skills/`, `prompts/`, `rules/` and `plugins/`. Links are resolved against the owner's real home and refused when they escape it, except a skill directory linked from `skills/` that carries a `SKILL.md`. Files Codex writes for itself are never mirrored or pruned: `skills/.system`, `plugins/cache/claxedo-agent-plugins`, `installation_id`, logs and `tmp/` stay in the composed home, and the conversations, sqlite databases and memories live in the owner's store, not the owner's own home. Secret files are excluded from the mirror: `auth.json`, `.env`, and any name carrying `credential`, `oauth`, `secret`, `token`, `password` or `keychain`. `auth.json` is instead a symlink to the owner's file, because Codex 0.133.0 writes that file in place through the link, so a login refresh the app-server performs lands in the owner's file; `account/logout` would remove the link in the composed home and leave the owner's file alone, and this transport never calls it. Selected executions exclude personal plugin config and caches; the canonical projection supplies their plugin set.

A brokered session's home carries only the broker provider fragment and the marketplace block; a plan session's carries the `chatgpt-plan` fragment instead, naming the plan's `chatgpt_base_url` (`<origin>/backend-api/`) and its model API (`<origin><apiPath>`) and never the token, which the transport logs in; with no mirror of anyone's config and no auth link. The fragment names the broker's `base_url` with `requires_openai_auth = true` and `cli_auth_credentials_store = "ephemeral"`, and never the placeholder: the transport logs the placeholder in through `account/login/start`, so a rotation changes neither the file nor the home. The marketplace lives at `<home>/marketplace` with a local `marketplace.json` listing every plugin installed there, and each projected plugin is copied there and into `plugins/cache/claxedo-agent-plugins/<name>/<version>`, replacing that plugin's other versions; a plugin no longer projected stays installed for the other sessions of the home and is simply not enabled.

Account selection reads `HARNESS_TABLE.codex.providerIds` in canonical order. A usable binding wins; otherwise a `subscription` direct row on `codex-app-server` selects the plan; otherwise an explicitly unavailable account refuses launch. With no binding, the composition's `MachineLoginPolicy` must permit the session owner to use the machine login before the profile reads or creates a home. A non-owner without a binding receives `CredentialSelectionError` with `account_unavailable` before any process starts.
