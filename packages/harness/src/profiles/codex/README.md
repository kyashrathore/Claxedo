# Codex profile

Codex reads skills from `CODEX_HOME/skills` and project `.agents/skills`, MCP configuration from `config.toml`, and plugins from marketplace entries plus `plugins/cache`. The format follows the Codex skills, configuration, and plugins documentation listed in `docs/harness-v2/profiles.md`.

Claxedo never writes into a person's own `~/.codex`. Every session runs in a Claxedo-owned `CODEX_HOME` under the transport's `homeRoot`, keyed by the session owner, the credential binding (own login, or the broker's `baseUrl` and auth mode; the account is the owner's) and the plugin selection mode (default or selected, never the selected set or its artifact digests). Codex resumes a thread only from the home it started in (a thread asked for in another home answers `no rollout found for thread id`), so the projected plugin set is not part of the key: every plugin a session projects is copied into the home's marketplace and cache in place, and the home keeps the plugins other sessions of the same key installed. Which plugins a thread loads is the thread's own config: `thread/start`, `thread/resume` and a `spawn_agent` child's `thread/start` carry `plugins.<name>@claxedo-agent-plugins.enabled` for exactly the session's projected set, which Codex merges over `config.toml`, so two sessions sharing a home each see only their own plugins and a changed set applies on the next resume. A selection mode change still moves the session to another home, where its thread cannot be resumed. `prepareCodexProfile` runs at every session start, and every file it writes lands through a temporary name and a rename, so a concurrent session never reads a half-written file.

For an own-login session the home mirrors the owner's Codex home read-only: `config.toml` (with any Claxedo block from today's driver stripped and this profile's block appended), `AGENTS.md`, the legacy `instructions.md`, `hooks.json`, `skills/`, `prompts/`, `rules/` and `plugins/`. Links are resolved against the owner's real home and refused when they escape it, except a skill directory linked from `skills/` that carries a `SKILL.md`. Files Codex writes for itself stay in the composed home and are never mirrored or pruned: `skills/.system`, `plugins/cache/claxedo-agent-plugins`, `sessions/`, `memories/`, the sqlite indexes, `installation_id`, logs and `tmp/`; a session's memories therefore accumulate in the Claxedo home, not the owner's. Secret files are excluded from the mirror: `auth.json`, `.env`, and any name carrying `credential`, `oauth`, `secret`, `token`, `password` or `keychain`. `auth.json` is instead a symlink to the owner's file, because Codex 0.133.0 writes that file in place through the link, so a login refresh the app-server performs lands in the owner's file; `account/logout` would remove the link in the composed home and leave the owner's file alone, and this transport never calls it. Selected executions exclude personal plugin config and caches; the canonical projection supplies their plugin set.

A brokered session's home carries only the broker provider fragment and the marketplace block, with no mirror of anyone's config and no auth link. The marketplace lives at `<home>/marketplace` with a local `marketplace.json` listing every plugin installed there, and each projected plugin is copied there and into `plugins/cache/claxedo-agent-plugins/<name>/<version>`, replacing that plugin's other versions; a plugin no longer projected stays installed for the other sessions of the home and is simply not enabled.

Account selection reads `HARNESS_TABLE.codex.providerIds` in canonical order. An explicitly unavailable account always refuses launch. With no binding, the composition's `MachineLoginPolicy` must permit the session owner to use the machine login before the profile reads or creates a home. A non-owner without a binding receives `CredentialSelectionError` with `account_unavailable` before any process starts.
